The C Language

The portable assembler that everything else is built on

Published

August 29, 2026

Overview


C is a small, procedural systems language designed to be a portable alternative to assembly. It has no objects, no generics, no exceptions, no garbage collector, and no string type, and this poverty is the entire point: every construct in C maps to a handful of machine instructions you can predict without reading the generated code. That predictability is why C became the substrate the rest of computing is built on. Operating system kernels, language runtimes (CPython and the original Rust compiler among them), device drivers, and embedded firmware are overwhelmingly C, and a great many languages define their foreign function interface as “whatever C does.”

C was written by Dennis Ritchie at Bell Labs between 1972 and 1973, for the purpose of rewriting Unix in something other than PDP-11 assembly. That origin explains most of the language. C is not a design that anticipated general-purpose programming; it is a tool that had one job, was good enough at it that Unix went with it, and inherited a universe by accident. Nearly every wart in the language, and nearly every strength, traces back to that: a small team solving an immediate problem on a machine with 64KB of memory, with no reason to believe the result would outlive the hardware.

NoteC is not C++

It is tempting to think of C as “C++ without the classes,” but the two are distinct languages with distinct philosophies. C is small, procedural, and deliberately close to the machine: what you write is roughly what the hardware does. C++ layers on classes, templates, RAII, exceptions, and a large standard library, trading C’s transparency for expressive power. Much valid C is also valid C++, but the reverse is far from true, and idiomatic code in each language looks nothing like the other. This chapter is strictly about C; C++ warrants its own treatment.

A Short History of the Standard

C is old, and it has evolved. Code you encounter in the wild may target any one of several standards, and knowing which is which explains why some features are present in one codebase and absent in another. Each revision was largely additive and backward-compatible, so newer compilers still happily compile decades-old code. This is a sharp contrast with C++, which had a genuine inflection at C++11 that split the language into “classic” and “modern” dialects. C never had such a break; C89 code is still idiomatic C today, for better and for worse.

Standard Year Common name What it introduced

ANSI C / ISO C90 1989 C89 / C90 The first standard. Function prototypes, the standard library, void, const, volatile. The lowest common denominator; still the baseline many embedded toolchains assume.
C99 1999 C99 // line comments, stdint.h fixed-width types, bool (stdbool.h), inline, designated initializers, variable-length arrays, mixed declarations and code, long long.
C11 2011 C11 _Static_assert, _Generic, atomics (stdatomic.h), threads (threads.h), anonymous structs/unions.
C17 / C18 2017 C17 A bug-fix release. No new features; clarifications only.

NoteYou are probably writing C99 already

Several conveniences this chapter uses are C99 features, not original C: the fixed-width types int16_t/uint8_t (from <stdint.h>), // comments, declaring a loop variable inside for, and declaring variables partway through a function rather than only at the top of a block. If a codebase forbids these, it is targeting C89, which is still common in conservative or safety-critical work. Compilers select a standard with a flag such as -std=c99 or -std=c11.

The C Philosophy

Trust the programmer

C’s design commitments were codified after the fact, in the rationale document accompanying the C89 standard. They read less like a language philosophy than a set of refusals:

Trust the programmer. Don’t prevent the programmer from doing what needs to be done. Keep the language small and simple. Provide only one way to do an operation. Make it fast, even if it is not guaranteed to be portable.

The first of these defines the language, and it is the one that has aged worst. C does not check array bounds, does not track object lifetimes, does not distinguish a pointer to one object from a pointer to an array of them, and will let you read uninitialized memory without comment. Every one of those omissions is a deliberate decision to skip a runtime check that would cost cycles. The result is a language with no runtime overhead and no safety net, which was a defensible trade in 1973 on a machine with 64KB of memory, and which is the direct cause of a large fraction of the memory-safety vulnerabilities of the last four decades. Microsoft and Google have each reported that roughly 70% of their severe security bugs are memory-safety issues in C and C++. This is not a knock on the language so much as the bill arriving for a choice made when the threat model was “the other person with an account on this PDP-11.”

“Keep the language small” C genuinely honored. There are 32 keywords in C89 and only a handful more since, against roughly 90 in C++. The grammar fits on a few pages; the standard library fits in an afternoon. What does not fit in an afternoon is undefined behavior, which is the price of the other commitments. Where a safer language would define a wrong answer, C declines to define anything at all, which frees the compiler to assume the situation never arises and optimize on that assumption. This is simultaneously the source of C’s speed and of its most surprising bugs, and it gets its own section below.

The last commitment, one way to do an operation, is why C feels sparse next to its descendants. There is no overloading, so abs, labs, and fabs are three separate functions. There are no generics, so a generic container is a void* and an element size. There are no namespaces, so library authors prefix every public symbol by hand, which is why you see pthread_mutex_lock and png_read_info. C++ and Rust each grew, in part, from a judgment that these particular economies cost more than they saved.

NoteThe virtue of a language you can hold in your head

It is easy to read the list above as a catalogue of deficiencies, and much of it is. But the same smallness is why C remains the lingua franca. A language with no runtime, no name mangling, and a trivial calling convention is one that every other language can call into and every platform can host. C is the interoperability layer of computing precisely because there is so little of it to disagree about.

The 32 Keywords

The original ANSI C standard defined 32 keywords. These are reserved words that cannot be used as identifiers. They form the skeleton of the language:

Data Types Control Flow Storage Classes Other
char if, else auto const
int switch, case, default extern volatile
short for, do, while register void
long break, continue static sizeof
float goto typedef enum
double return struct
signed union
unsigned

Later standards added a few more, nearly all spelled with a leading underscore and capital letter so they could not collide with existing identifiers: _Bool, inline, and restrict (C99); _Static_assert, _Generic, _Atomic, _Noreturn, _Alignas, and _Alignof (C11). C23 finally promoted several to ordinary spellings, making bool, true, false, static_assert, and constexpr keywords in their own right.

Two of the original 32 are effectively dead. auto meant “automatic storage duration,” which is the default for every local variable, so no one ever wrote it; C++11 recycled the keyword for type deduction, and C23 followed. register was a hint to keep a variable in a CPU register, and modern optimizers make far better allocation decisions than a human annotation can, so compilers now ignore it. Its one surviving effect is that you cannot take the address of a register variable.

Types and Declarations

C’s types are a thin veneer over what the hardware provides. There are no classes, no strings as a first-class type, and no built-in containers: just numbers, characters (which are small numbers), and aggregates you build yourself.

The Arithmetic Types

The integer types are defined by minimum width, not exact width. The standard guarantees a lower bound; the actual size is implementation-defined and depends on the target architecture.

Type Typical size Guaranteed minimum Notes
char 1 byte 1 byte Signedness is implementation-defined; may be signed or unsigned.
short 2 bytes 16 bits
int 2 or 4 bytes 16 bits The “natural” word size; 16-bit on some embedded targets, 32-bit on most desktops.
long 4 or 8 bytes 32 bits
long long 8 bytes 64 bits C99.
float 4 bytes (n/a) Single-precision floating point.
double 8 bytes (n/a) Double-precision.

Each integer type has a signed (default) and unsigned variant. This portability of minimums rather than exact sizes is exactly why C99 introduced fixed-width types.

Fixed-Width Types

<stdint.h>

When you need to know precisely how wide an integer is (essential when a value maps to a hardware register or a wire format), reach for the fixed-width types. These are the types this chapter uses throughout.

#include <stdint.h>

int8_t   a;   // exactly 8 bits, signed
uint8_t  b;   // exactly 8 bits, unsigned
int16_t  c;   // exactly 16 bits, signed
uint32_t d;   // exactly 32 bits, unsigned

// Also available:
//   int_least16_t  : smallest type with at least 16 bits
//   int_fast16_t   : fastest type with at least 16 bits
//   intptr_t       : an integer wide enough to hold a pointer

Prefer int16_t over short and uint8_t over unsigned char whenever the exact width matters. The intent is explicit and the code behaves identically across targets.

sizeof

sizeof yields the size of a type or object in bytes, evaluated at compile time. It is an operator, not a function, and its result has type size_t (an unsigned type wide enough to describe any object’s size).

sizeof(int)         // e.g. 4
sizeof(uint16_t)    // 2
int16_t buf[64];
sizeof(buf)         // 128 (64 elements at 2 bytes), NOT the pointer size
sizeof(buf) / sizeof(buf[0])   // 64: the idiom for array length

That last idiom is the canonical way to compute an array’s element count. Note it only works on a true array in scope, not on a pointer (a distinction developed in Arrays and Pointers).

bool

C had no Boolean type until C99, which added bool, true, and false via <stdbool.h>. Before that, and still in much older code, any integer serves: zero is false, any non-zero value is true.

#include <stdbool.h>

bool ready = true;
if (ready) { /* ... */ }

// Pre-C99 style, still valid and common:
int flag = 1;
if (flag) { /* ... */ }

C23 finally makes bool, true, and false proper keywords, so the <stdbool.h> include becomes unnecessary.

enum

An enum defines a set of named integer constants. By default they count up from zero, but any member may be assigned explicitly.

typedef enum {
    STATE_IDLE,        // 0
    STATE_RUNNING,     // 1
    STATE_ERROR = 10,  // 10 (explicit)
    STATE_HALTED       // 11 (continues from previous)
} State_t;

Unlike C++’s enum class, C enums are not type-safe: they are interchangeable with int, and nothing stops you assigning STATE_IDLE to an unrelated integer variable. They exist chiefly to give names to magic numbers and to make switch statements self-documenting.

typedef

typedef creates an alias for an existing type. It introduces no new type, only a new name, but that name can dramatically improve readability, particularly for structs and function pointers.

typedef unsigned char byte;      // 'byte' now means 'unsigned char'
typedef struct Point Point;      // avoid writing 'struct Point' everywhere
typedef int (*Comparator)(int, int);  // a name for a function-pointer type

The _t suffix (as in int16_t, size_t, State_t) is a widespread convention marking a type name. Strictly, POSIX reserves _t for future additions to its own headers, so a name you invent today could in principle collide with a standard one tomorrow. In practice the convention is near-universal and the risk is small; this chapter uses it throughout. Projects that care about strict portability sidestep it with a project prefix instead, such as dsp_state_t or AudioState.

Reading Declarations

C’s declaration syntax is famously puzzling, and the reason is a single design principle: “declaration mirrors use.” A declaration is written to look like the expression that retrieves a value of the base type. int *p declares p such that the expression *p is an int; int a[10] declares a such that a[0] is an int. Most languages instead name the type first and the identifier second (int[10] a), which reads more easily but does not compose the way C’s form does.

One consequence of that design bites immediately. The * binds to the name, not to the type. In a declaration of several names, each pointer needs its own *:

int* a, b;   // MISLEADING: a is a pointer, but b is a plain int
int *a, *b;  // both are pointers

This is why C programmers conventionally write the * against the name rather than against the type, even though int* a; and int *a; are identical to the compiler. The second spelling makes the binding visible and the trap above unlikely.

The principle scales to genuinely hairy declarations involving pointers, arrays, and functions in combination, which is a topic that needs pointers first. It resumes under Pointer Declarations and Qualifiers.

Type Qualifiers

A type qualifier constrains how a type may be used without changing its size or representation. C has three, and they answer three unrelated questions. It helps to keep them mentally distinct from the outset, because they are otherwise easy to lump together as “extra keywords near the type.”

Qualifier Question it answers Meaning Developed under
const May I change this? The object must not be modified through this name after initialization. here, and with pointers
volatile May the compiler assume this is stable? The object may change outside the program’s control; every access must actually happen. Optimization Levels
restrict Might two pointers touch the same memory? A promise that this pointer is the only route to the data it points at. Pointer Declarations and Qualifiers

Only const applies meaningfully to an ordinary value, so it is the only one this section develops. volatile is best understood as a barrier against specific optimizations, and restrict applies to pointers exclusively; both wait for the sections above.

const

const is a promise about a name, not a guarantee about storage. It tells the compiler that the object must not be modified through this particular identifier, which lets the compiler both diagnose violations and optimize on the assumption that no such violation occurs.

const int sample_rate = 48000;
sample_rate = 44100;              // error: assignment of read-only variable

The payoff is small on a lone value like this one and large on interfaces, where const documents the direction of data flow and the compiler enforces it. That use involves pointers, so it is developed with them.

Warningconst is not constexpr

A const object is read-only, not a compile-time constant. In C, const int n = 10; does not produce a constant expression, so int arr[n]; declares a variable-length array (C99) rather than a fixed-size one, and the same declaration is invalid outright at file scope. This differs from C++, where const int n = 10; is usable as a constant expression. For genuine compile-time constants, C offers #define, the enum trick (enum { Size = 10 };), or, as of C23, constexpr.

Casting away const and then writing through the result is undefined behavior if the underlying object was itself declared const. The cast compiles, the write may even appear to work, and the compiler remains free to have cached the old value or placed the object in genuinely read-only memory. If a function needs to write, do not lie about it in the signature.

Noteconst and read-only memory

const is what permits a toolchain to place data in read-only storage, not a guarantee that it will. On hosted systems, const file-scope data typically lands in a read-only segment (.rodata) that the OS marks non-writable. On embedded targets the placement rules are toolchain-specific and usually require explicit attributes or pragmas. The Applied DSP notes cover the specifics for that toolchain.

Expressions and Control Flow

C’s control flow is the ancestor of the C-family syntax found in C++, Java, JavaScript, and beyond. Little here will surprise a C++ reader; the notes below flag the C-specific edges.

Operators and Precedence

One symbol per operation, and the order they bind in

C has a large operator set for a small language, and the reason is the “one way to do an operation” commitment. With no overloading, every distinct operation needs its own symbol: three different absolute-value functions, and separate operators for logical and bitwise AND. What follows is not a tour of the obvious ones; addition and comparison work as you expect. It is the handful of places where C’s operators behave differently from the intuition a reader brings from elsewhere.

The families are conventional: arithmetic (+ - * / %), relational (< <= > >= == !=), logical (&& || !), bitwise (& | ^ ~ << >>), and assignment (= and its compound forms). Four operators sit outside those groups: sizeof, the cast (type), the ternary ?:, and the comma.

Logical vs. Bitwise

The most consequential distinction in the section, and the one that produces the quietest bugs. && and || are logical: they treat operands as true/false and produce 0 or 1. & and | are bitwise: they combine operands bit by bit and produce a full-width integer.

They frequently agree by accident. With operands that are already 0 or 1, a && b and a & b give the same answer, which lets a substitution survive testing. They diverge as soon as the operands are arbitrary integers: 2 && 1 is 1, while 2 & 1 is 0.

The deeper difference is not the result but the evaluation. && and || short-circuit: if the left operand settles the answer, the right operand is never evaluated at all. This is a guarantee in the standard, not an optimization, which is what makes the null-check idiom safe:

if (p != NULL && p->length > 0) { /* ... */ }

If p is null, p->length is never evaluated and the dereference never happens. Write & there instead and both sides are always evaluated, so a null p is dereferenced and the program has undefined behavior. The same guarantee underpins the guard-then-use pattern generally:

if (index < count && data[index] != 0) { /* ... */ }   // bounds check first
if (denominator == 0 || total / denominator > 1) { /* ... */ }  // no divide by zero

Because short-circuiting suppresses evaluation, an operand with side effects may simply not happen. if (ready() && start()) does not call start when ready returns false, which is usually the point, and occasionally a surprise when someone relied on the call.

Compound Assignment

x += 1 is shorthand for x = x + 1, and every binary arithmetic and bitwise operator has a compound form (-= *= /= %= &= |= ^= <<= >>=). The shorthand is not purely cosmetic: the standard guarantees the left operand is evaluated exactly once. That matters the moment the target is anything more complicated than a variable:

arr[next_index()] += 1;              // next_index() is called once
arr[next_index()] = arr[next_index()] + 1;   // called twice, on possibly different slots

The two lines are not equivalent, and the second is a bug waiting for next_index to acquire a side effect.

The Comma Operator

The comma evaluates its left operand, discards the result, then evaluates and yields its right. It is the lowest-precedence operator in C and is genuinely rare in practice, appearing mostly where the grammar allows one expression but you want two: the header of a for loop, or a macro that must do two things in a single expression.

for (int i = 0, j = n - 1; i < j; i++, j--) { /* ... */ }

Note that the int i = 0, j = n - 1 part is not the comma operator; that is the declaration syntax separating two declarators. Only i++, j-- is the operator. This ambiguity of the same punctuation meaning different things in different contexts is one more reason the comma operator stays uncommon.

Integer Division and Modulo

Integer division truncates toward zero, and % takes its sign from the dividend:

 7 / 2   //  3
-7 / 2   // -3   (truncated toward zero, not floored to -4)
 7 % 2   //  1
-7 % 2   // -1   (sign follows the left operand)

C99 pinned this down; before it, the rounding direction for negative operands was implementation-defined. Readers coming from Python should note the difference carefully: Python floors, so -7 // 2 is -4 and -7 % 2 is 1. Code that computes a wrapping index with % on a possibly-negative value therefore behaves differently in the two languages, and in C can produce a negative subscript.

Two rows in that table are worth committing to memory, because they are where the ordering violates intuition.

  1. The bitwise operators (8, 9, 10) bind more loosely than the comparisons (6, 7), so flags & MASK == ENABLED parses as flags & (MASK == ENABLED), which is almost never the intent.
  2. The shifts (5) bind more loosely than arithmetic (3, 4), so 1 << n + 1 is 1 << (n + 1).

Ritchie later acknowledged the bitwise precedence as a mistake, kept only because code already depended on it. Parenthesize both cases; see Operator Precedence Surprises for the practical fallout.

WarningPrecedence is not evaluation order

The table says how an expression groups, not the sequence in which its parts run. In f() + g(), precedence guarantees the addition happens last, and says nothing about whether f or g is called first; the compiler may choose either. This is why an expression that both reads and modifies the same object without an intervening sequence point is undefined behavior, not merely unpredictable:

i = i++ + 1;      // undefined behavior
f(i, i++);        // undefined behavior: unsequenced read and modification
arr[i] = i++;     // undefined behavior

&&, ||, ?:, and the comma operator do impose sequencing, which is exactly why the short-circuit idioms above are safe. Everything else, including function arguments, does not. See Undefined Behavior for why “it seems to work” is not evidence here.

What the bitwise operators actually compute, along with the set/clear/toggle idioms built from them, is covered under Bitwise Operations once pointers and memory layout are on the table.

Conditionals

if (x > 0) {
    positive();
} else if (x < 0) {
    negative();
} else {
    zero();
}

C has no dedicated Boolean context: the condition is simply an integer expression, and any non-zero value is “true.” This is why if (ptr) (is the pointer non-null?) and if (count) (is the count non-zero?) are idiomatic.

The ternary operator ?: is an expression, useful where a full if would be clumsy:

int max = (a > b) ? a : b;

Loops

The three loop forms:

for (int i = 0; i < n; i++) { /* ... */ }   // declaring i here is C99

while (condition) { /* ... */ }

do {
    /* runs at least once */
} while (condition);

break exits the enclosing loop; continue skips to the next iteration. Both act only on the innermost loop.

switch

switch selects among integer cases. Its defining and dangerous characteristic is fall-through: without a break, control flows into the next case.

switch (state) {
    case STATE_IDLE:
        start();
        break;              // without this, execution falls into STATE_RUNNING
    case STATE_RUNNING:
        process();
        break;
    default:
        handle_unknown();
        break;
}

Fall-through is occasionally useful (letting several cases share code), but far more often it is an accidental missing break. This footgun is revisited in Common Pitfalls.

goto

C retains goto, and although structured programming rightly discourages it, one use is genuinely idiomatic in C: unwinding on error in a function with several acquisition steps. Since C has no destructors or finally, goto provides a single, orderly cleanup path.

int setup(void) {
    if (acquire_a() != 0) goto fail_a;
    if (acquire_b() != 0) goto fail_b;
    if (acquire_c() != 0) goto fail_c;

    return 0;  // success

fail_c: release_b();
fail_b: release_a();
fail_a:
    return -1;
}

This “cleanup ladder” is common in systems code (the Linux kernel uses it heavily). Outside error handling, prefer structured control flow.

Functions

A function in C has a declaration (its prototype, announcing name, return type, and parameter types) and a definition (the body). Declarations typically live in header files; definitions live in .c files. Callers need only the declaration to generate a correct call.

// Declaration (prototype), usually in a .h file
int add(int a, int b);

// Definition, in a .c file
int add(int a, int b) {
    return a + b;
}
WarningAlways write prototypes

A function used before the compiler has seen a declaration is, in old C, assumed to return int with unchecked arguments. This “implicit declaration” is a rich source of bugs and is an error in C99 and later. Declare every function before use, and write void explicitly for an empty parameter list: int get_value(void). An empty () in C means “unspecified arguments,” not “no arguments”; another trap C++ does not share.

Parameter Passing

C is pass-by-value, always. A function receives copies of its arguments. Assigning to a parameter changes only the local copy; the caller’s variable is untouched.

void increment(int x) {
    x++;  // modifies the local copy only
}

int n = 5;
increment(n);   // n is still 5

To let a function modify a caller’s variable, you pass a pointer to it. This is C’s only mechanism for “pass by reference”, and it is explicit at both the call site (&n) and in the signature (int *):

void increment(int *x) {
    (*x)++;   // dereference, then modify what it points to
}

int n = 5;
increment(&n);  // pass the address of n
// n is now 6

Arrays are the one apparent exception, but only apparent: an array argument decays to a pointer to its first element, so the function receives an address, not a copy of the array. This is why a function cannot know an array’s length from the parameter alone, and why length is nearly always passed as a separate argument.

Storage Class and Linkage

Where data lives, and who can see it

Where a type qualifier constrains what may be done with an object, a storage-class specifier governs its lifetime (how long the object exists) and its linkage (which translation units can refer to it by name). These are independent axes, and conflating them is a common source of confusion, particularly the overloaded static.

Specifier Lifetime Linkage at file scope Notes
(none) Automatic (local) External (global) The default. Locals die at scope exit; globals are shared.
static Whole program Internal (this file) Two distinct meanings, depending on scope. See below.
extern Whole program External A declaration of something defined elsewhere.
auto Automatic (n/a) The default for locals; vestigial, never written.

The Three Faces of static

static is the most overloaded keyword in C, meaning materially different things depending on where it appears.

On a local variable, it changes lifetime. The variable is initialized once, before main runs, and retains its value between calls. Its scope is still the function; only its lifetime changes.

void count_calls(void) {
    static int count = 0;  // initialized once, at program start
    count++;
    printf("Called %d times\n", count);
}

On a file-scope variable, it changes linkage. The name becomes private to its translation unit, invisible to the linker and therefore to every other .c file.

// audio.c
static int16_t internal_buffer[256];   // not visible outside audio.c

On a function, it does the same. The function becomes private to the file, which also lets the compiler inline or specialize it more aggressively, since it can see every call site.

static void helper(void) { /* internal, not part of the public API */ }

The second and third uses are C’s only form of encapsulation. With just two levels of visibility, private-to-file and global-to-program, every library must defensively prefix its public names, which is why C APIs are full of identifiers like SDL_CreateWindow and pthread_mutex_lock. C++ namespaces exist to solve exactly this.

Warningstatic locals are not reentrant

A static local is shared by every invocation of the function, including recursive calls and calls from different threads or interrupt handlers. A function with static state is neither reentrant nor thread-safe, and the resulting bugs are timing-dependent and miserable to reproduce. This is the reason strtok has a strtok_r variant.

extern and the Definition/Declaration Split

extern declares that a name exists somewhere else, letting the compiler type-check uses of it without allocating storage. The canonical pattern puts the declaration in a header and the definition in exactly one .c file:

// config.h
extern int sample_rate;      // declaration: "this exists somewhere"

// config.c
int sample_rate = 48000;     // definition: allocates the storage

Putting the definition in the header instead means every file that includes it defines the same symbol, and the linker rejects the duplicates. This is C’s version of the One Definition Rule, enforced by the linker rather than the language.

Function Pointers

Callbacks and dispatch tables

Function pointers store the address of a function, enabling callbacks and runtime dispatch. They are C’s only mechanism for polymorphism, and they are how qsort accepts a comparison, how a driver registers a handler, and how a virtual method table works underneath C++.

// A name for the signature, which makes everything downstream readable
typedef void (*ProcessFunc_t)(int16_t *buffer, int length);

void echo_effect(int16_t *buf, int len)       { /* ... */ }
void reverb_effect(int16_t *buf, int len)     { /* ... */ }
void distortion_effect(int16_t *buf, int len) { /* ... */ }

ProcessFunc_t current_effect = echo_effect;

void process_block(int16_t *buffer, int length) {
    current_effect(buffer, length);   // call through the pointer
}

A dispatch table replaces a switch with an array lookup, which keeps the selection logic and the handler list in one place:

static const ProcessFunc_t effect_table[] = {
    echo_effect,
    reverb_effect,
    distortion_effect
};

#define EFFECT_COUNT (sizeof(effect_table) / sizeof(effect_table[0]))

void set_effect(size_t n) {
    if (n < EFFECT_COUNT) {
        current_effect = effect_table[n];
    }
}

Variadic Functions

Accepting an unknown number of arguments, and the price of doing so

A variadic function accepts a variable number of arguments, declared with ... after at least one named parameter. printf is the one everybody has used; this section explains how it works, which retroactively explains why its first argument is a format string rather than a convenience.

The Mechanism

The machinery lives in <stdarg.h> and consists of one type and four macros: va_list holds the traversal state, va_start initializes it, va_arg retrieves the next argument, and va_end releases it.

#include <stdarg.h>

int sum_ints(int count, ...) {
    va_list args;
    va_start(args, count);        // 'count' is the last *named* parameter

    int total = 0;
    for (int i = 0; i < count; i++) {
        total += va_arg(args, int);   // you must state the type
    }

    va_end(args);                 // required; may free resources on some ABIs
    return total;
}

sum_ints(3, 10, 20, 30);   // 60

Three obligations are visible in that code, and all three are on you rather than the compiler. va_start needs the last named parameter, which is why a variadic function cannot be entirely variadic. va_arg needs the type of each argument, because nothing in the call conveys it. And the loop needs to know when to stop, which is why count is passed explicitly.

That last point is the crux: nothing about the variable arguments is available at run time. Not their count, not their types. The values are placed in registers and on the stack according to the ABI, and the callee reads them back by asserting what it expects to find. Get the assertion wrong and you have not made a type error; you have misread raw memory.

A function needing to walk the list twice must copy it first, since a va_list may not be reusable after traversal:

va_list copy;
va_copy(copy, args);   // C99

Why printf Takes a Format String

Now printf’s design reads as a consequence rather than a convention. The function receives some bytes and no description of them, so the caller must supply that description out-of-band. The format string is the type information, transmitted as data:

printf("%s scored %d\n", name, score);
//      ^^        ^^ these tell printf to expect a char* then an int

Each conversion specifier tells printf which type to hand va_arg next. This is why a mismatch is dangerous rather than merely wrong. printf("%s", 42) instructs the function to interpret the integer 42 as a pointer and dereference it, which is a segfault at best and an information leak at worst. printf("%d") with no argument reads whatever happens to occupy the next argument slot. Neither is a diagnosable type error in the language; both are undefined behavior.

The specifiers themselves are catalogued with the rest of <stdio.h> under Input and Output.

Default Argument Promotions

Arguments passed through ... undergo the default argument promotions before the callee sees them:

  • float is promoted to double.
  • Integer types narrower than int (char, short, _Bool) are promoted to int.

The consequence is that certain va_arg requests are always wrong, no matter what the caller wrote:

va_arg(args, char)     // WRONG: a char argument arrived as an int
va_arg(args, float)    // WRONG: a float argument arrived as a double
va_arg(args, int)      // correct for char, short, and int alike
va_arg(args, double)   // correct for both float and double

This is also why printf has no separate specifier for float: %f handles both, because a float can never actually reach it. Conversely, types wider than int are not promoted, so long and int64_t need their own specifiers (%ld, and the macros in <inttypes.h> for fixed-width types).

Forwarding

the v Variants

Wrapping printf is a common need, and it cannot be done by passing ... along, because there is no syntax for expanding it. The standard library therefore provides a v-prefixed variant of each formatted-output function (vprintf, vfprintf, vsnprintf) that takes an already-started va_list instead of ...:

void log_error(const char *fmt, ...) {
    va_list args;
    va_start(args, fmt);

    fprintf(stderr, "[ERROR] ");
    vfprintf(stderr, fmt, args);   // hand the list to the real formatter
    fprintf(stderr, "\n");

    va_end(args);
}

This is the standard shape for any logging or diagnostic wrapper, and vsnprintf is the bounded version to reach for when writing into a fixed buffer.

WarningVariadic functions defeat the type system

A variadic call is one of the few places where C performs no argument checking whatsoever. The compiler cannot verify count or types, because the contract lives in a string it is not obliged to read. The practical mitigation is the format attribute described under Compiler Attributes, which asks GCC and Clang to parse the format string and check the arguments against it:

__attribute__((format(printf, 1, 2)))
void log_error(const char *fmt, ...);

With that in place, log_error("%s", 42) becomes a compile-time warning. Apply it to every printf-style wrapper you write; it costs one line and recovers most of the safety the mechanism gives up.

C++ and Rust solve this at the root rather than patching it. C++ variadic templates and Rust’s format! macro both know each argument’s static type at the call site, so formatting is checked by the compiler with no annotation and no run-time type assertions.

Pointers and Memory

Pointers are the feature that defines C. They are what let a 1972 language address hardware directly, and they are the reason so much of the language’s danger is concentrated in one place.

Pointers

A pointer is a variable that stores the memory address of another object. Two operators connect a value to its address: & (address-of operator) takes the address of an object, and * (dereference operator) dereferences an address to reach the object. Declaring a pointer also uses *, which is the “declaration mirrors use” principle at work: int *ptr declares ptr such that the expression *ptr is an int.

Dereference is using the asterisk * operator to access or modify the actual value stored at the memory address that the pointer holds. For a pointer to a pointer one uses ** to dereference the value.

int var = 5;
int *ptr = &var;
*ptr = 10;                      // writes value through the pointer
printf("%d, %d\n", var, *ptr);  // 10, 10

That last pair of lines is the whole idea. ptr is a separate object with its own address and its own storage, holding a number that happens to be where var lives. Dereferencing follows the number.

A pointer’s type is not decoration. Every pointer holds an address of the same width, but the type determines how many bytes a dereference reads, how those bytes are interpreted, and how arithmetic on the pointer scales. char * and double * on the same address see one byte and eight bytes respectively.

A pointer to a pointer stores the address of another pointer:

int **pptr = &ptr;   // pptr holds the address of ptr
**pptr = 30;         // two hops: to ptr, then to var

This is what a function needs when it must modify the caller’s pointer rather than the thing pointed at, which is exactly the case for an allocating function or an insertion at the head of a linked list. Passing int * lets you change the pointee; passing int ** lets you change the pointer itself.

void allocate_buffer(int **out, size_t count) {
    *out = malloc(count * sizeof **out);
}

int *buffer = NULL;
allocate_buffer(&buffer, 256);   // buffer now points at the allocation

Pointers underpin four things C could not otherwise do: dynamic memory allocation, efficient array traversal, letting a function modify its caller’s variables, and building linked data structures.

NoteNULL is a value, not a safety feature

NULL is C’s “points at nothing” sentinel, but nothing in the type system distinguishes a pointer that might be null from one that cannot be. Every dereference is an act of faith, and a null dereference is undefined behavior. Rust’s Option<T> and C++’s references exist to make that distinction visible to the compiler.

A pointer that is merely uninitialized is worse than one that is null, because it holds a plausible-looking garbage address that may not fault. Initialize pointers at declaration, to NULL if you have nothing better.

Pointer Arithmetic

Adding an integer to a pointer does not add bytes. It advances by that many elements, scaling automatically by the size of the pointed-to type:

int32_t values[4];
int32_t *p = values;

p + 1;   // advances 4 bytes (one int32_t), not 1
p + 3;   // advances 12 bytes

This is why the pointer’s type matters and why void * (below) cannot participate. The scaling is what makes p[i] and *(p + i) equivalent, and it is why array traversal by pointer reads so cleanly:

for (int32_t *cursor = values; cursor < values + 4; cursor++) {
    *cursor = 0;
}

Subtracting two pointers into the same array yields the number of elements between them, with type ptrdiff_t (from <stddef.h>):

ptrdiff_t distance = &values[3] - &values[0];   // 3, not 12

The operations C permits are deliberately few: add an integer, subtract an integer, subtract two pointers, and compare two pointers. There is no pointer multiplication, and adding two pointers is meaningless and illegal.

NoteThe arithmetic is exact, and that is a guarantee

Within these rules there is no hidden behavior. p + n is exactly p advanced by n * sizeof *p bytes, with no rounding, no alignment adjustment, and no bounds clamping. (p + 3) - 3 is p. If q - p is 5, then p + 5 is q. The compiler will not silently insert a check, and nothing at run time inspects whether the result is sensible.

That exactness cuts both ways, and it is the whole bargain. The arithmetic does precisely what you specify, including walking straight off the end of an array into unrelated memory, because there is nothing in a pointer that records where its object begins or ends. The rules above define what is legal; staying inside a real object is entirely your responsibility.

NoteOne past the end is legal to form, illegal to dereference

The standard specifically allows computing the address one element past the end of an array, which is what makes cursor < values + 4 well defined in the loop above. Dereferencing that address is undefined behavior, as is computing an address two past the end, or anywhere before the start. Arithmetic that wanders outside an array (plus that one boundary position) is undefined even if you never dereference the result, which is why the descending loop for (p = end - 1; p >= start; p--) is technically UB on its final decrement. Iterate forward, or compare with != against a valid boundary.

void *

A void * is a pointer to unspecified type: an address with the type information deliberately erased. It is C’s mechanism for generic code, and it is why malloc can serve every type in the language:

void *malloc(size_t size);
int  *numbers = malloc(10 * sizeof *numbers);   // converts implicitly

In C, void * converts to and from any object pointer type without a cast, which is what makes that line work. (C++ requires an explicit cast, one of the small but pervasive differences between the languages.)

Because the type is erased, two operations are unavailable: you cannot dereference a void *, and you cannot do arithmetic on it (see callout below for exceptions/extensions). Both need an element size, and void has none. Convert to a typed pointer first, which is an explicit statement of how you intend the bytes to be read:

void *raw = buffer;
/* raw + 4;  */                       // illegal in standard C: no element size
uint8_t *bytes = raw;
bytes + 4;                            // fine: advances 4 bytes
WarningGCC and Clang permit void * arithmetic as an extension

Both compilers treat sizeof(void) as 1 and allow arithmetic on void *, advancing it by bytes as though it were char *. This is a GNU extension, not standard C, and it compiles silently at default warning levels. Code relying on it will be rejected by a conforming compiler, and -pedantic will flag it. Cast to unsigned char * when you mean byte arithmetic; the intent is clearer and it is portable.

The other classic use is a generic callback interface. qsort sorts anything because it knows only addresses and an element size, deferring all type knowledge to a comparison function you supply:

int compare_ints(const void *a, const void *b) {
    int left  = *(const int *)a;    // cast back to the real type
    int right = *(const int *)b;
    return (left > right) - (left < right);   // avoids overflow of left - right
}

qsort(numbers, 10, sizeof numbers[0], compare_ints);

That round trip, erase the type to cross the interface and cast it back on the other side, is the closest thing C has to generics. It is also entirely unchecked: pass compare_ints to an array of double and the compiler is satisfied, while the program is not. Templates in C++ and generics in Rust exist to make the same abstraction type-safe.

Pointer Declarations and Qualifiers

Where the declaration syntax earns its reputation

Reading Declarations introduced C’s guiding principle, that a declaration mirrors the expression which uses the value. With pointers in hand, that principle can be applied to the declarations people actually find impenetrable, and the two qualifiers that only make sense alongside a * can finally be explained.

The Right-Left Rule

Any C declaration can be read aloud by following one procedure:

  1. Start at the identifier. Say its name.
  2. Look right. While the next token is […] or (…), consume it: say “array of N” or “function taking … returning”. Stop when you hit a ) that closes a group you are inside, or run out of tokens.
  3. Look left. Consume * as “pointer to”, and qualifiers as “const”/“volatile”. Stop when you hit a ( that opens the group you are inside.
  4. If you were inside parentheses, step outside them and repeat from step 2.
  5. When nothing is left, say the base type.

The right side binds tighter than the left, which is why step 2 comes before step 3: [] and () have higher precedence than *. Parentheses exist purely to override that, and they are the only reason you ever loop back to step 2.

The simplest case exercises the procedure in two steps, with the “look right” finding nothing:

int *pointer;

Start at pointer. Look right: nothing there, so move on immediately (an empty right side is not a blank to record; it just means there is nothing to say yet). Look left: *, “pointer to”. Nothing further left but the base type: int. Reading: pointer is a pointer to int.

Now the pair where the parentheses change everything:

int *arr[10];

Start at arr. Look right: [10], so “array of 10”. Look right again: nothing. Turn left: *, “pointer to”. Then int. Reading: arr is an array of 10 pointers to int.

int (*arr)[10];

Start at arr. Look right: ), which closes the group you are inside, so you must stop and turn left. Left: *, “pointer to”. Left again: (, which opens your group, so step outside it. Now resume looking right: [10], “array of 10”. Then left: int. Reading: arr is a pointer to an array of 10 int.

That bounce, right then left then right again, only ever happens because of the parentheses. Without them you read right once, then left once, and you are done.

A function pointer works the same way, with (int, int) consumed on the second pass right:

int (*fp)(int, int);

fp → ) blocks, turn left → * “pointer to” → ( closes the group, step out → right: (int, int) “function taking two ints returning” → int. Reading: fp is a pointer to a function taking two int and returning int.

NoteNot quite the “spiral rule”

You will find this widely described online as the “spiral rule,” which says to spiral outward from the identifier alternating right and left. That framing produces the right answer on the common cases but is not what the grammar actually does, and it misleads on two counts: it implies you always alternate (you do not; you exhaust the right side first, and only parentheses send you back), and it gives the wrong reading for some declarations mixing arrays with function parameters. The right-left rule above is the version that holds.

For anything genuinely gnarly, cdecl (the command-line tool, or cdecl.org) translates declarations to English and back. Reaching for it is not cheating. The better move, when you control the code, is a typedef so no one has to run the procedure at all.

Declaring a Pointer to a Function

That last example is worth contrasting with its unparenthesized twin, because function pointers are where the syntax defeats most people and where a typedef stops being a nicety:

int  *fp(int, int);    // a FUNCTION returning int*   (probably not what you meant)
int (*fp)(int, int);   // a POINTER to a function returning int

Without the parentheses, () binds tighter than * and you have declared a function. The parentheses around *fp force the pointer reading first. Everything else follows from that one grouping.

Assignment and calling are more forgiving than the declaration suggests, because a function name decays to a pointer much as an array name does:

int add(int a, int b) { return a + b; }

int (*operation)(int, int) = add;    // '&add' also works, and means the same
int result = operation(2, 3);        // '(*operation)(2, 3)' also works

Both spellings are legal for each step, and the short forms are conventional. The declaration is the only place the syntax is genuinely awkward, which is why a typedef earns its place the moment such a type appears more than once:

typedef int (*BinaryOp)(int, int);   // the alias reads left to right

BinaryOp operation = add;
void apply_all(BinaryOp op, const int *data, size_t count);   // now legible in signatures

The payoff compounds in return types. A function returning a function pointer is int (*get_handler(int kind))(int, int) written out, and BinaryOp get_handler(int kind) with the alias. Their use in dispatch tables and callbacks is covered under Function Pointers.

const Placement

Where const sits relative to the * changes what it qualifies:

const int *p;        // pointer to const int: *p is read-only, p can be reassigned
int const *p;        // identical to the above
int *const p;        // const pointer to int: p is fixed, *p is writable
const int *const p;  // const pointer to const int: neither can change

The rule: const applies to whatever is immediately to its left, unless nothing is there, in which case it applies to the right. The * is the boundary. In const int *p the qualifier has nothing to its left, so it grabs int; in int const *p it has int to its left, so it grabs int again. Same type, written two ways. Only when const crosses to the right of the * does it qualify the pointer itself, because now the thing on its left is the pointer.

const int *p is by far the most common form, and it is the foundation of const correctness: a function that promises not to modify the data behind a pointer parameter says so in its signature.

size_t count_zeros(const int16_t *data, size_t length);
//                 ^^^^^ promises not to write through data

This costs nothing at run time and buys three things: the compiler rejects accidental writes, callers holding const data can pass it without a cast, and a reader knows the direction of data flow from the prototype alone. Adopt it by default on pointer parameters you do not intend to write through.

WarningA typedef changes what const qualifies

Given typedef int *int_ptr;, the declaration const int_ptr p is not a pointer to const int. It is int *const p, a const pointer to a writable int. The qualifier applies to the aliased type as a whole, and that type is already “pointer to int,” so const has nowhere to go but the pointer. This surprises nearly everyone the first time, and it is a good reason to be wary of typedefs that hide a *.

restrict

Introduced in C99, restrict applies only to pointers. It is a promise from you to the compiler that, for the lifetime of the pointer, the data it points to will be accessed only through that pointer, or through pointers derived from it. No other pointer aliases the same memory.

Why does this matter? Consider scaling one buffer into another:

void scale(int16_t *out, const int16_t *in, int n, int16_t gain) {
    for (int i = 0; i < n; i++) {
        out[i] = in[i] * gain;
    }
}

The compiler cannot assume out and in are separate. If they overlapped, writing out[i] might change a later in[j], so the compiler must conservatively re-read in on every iteration and cannot vectorize or reorder freely. Adding restrict lifts that doubt:

void scale(int16_t *restrict out, const int16_t *restrict in, int n, int16_t gain) {
    for (int i = 0; i < n; i++) {
        out[i] = in[i] * gain;
    }
}

This is precisely the kind of tight loop where the optimization pays off, which is why restrict shows up in numerical code and in the prototypes of library functions like memcpy, whose whole contract is that source and destination must not overlap.

Warningrestrict is a promise you must keep

The compiler does not verify your claim. If you pass overlapping pointers to a restrict parameter, the behavior is undefined: the program may produce wrong results that appear only under optimization. Use restrict only when you are certain the regions are disjoint. When overlap is possible, use memmove rather than memcpy.

Arrays and Pointers

The duality

One of C’s most elegant and most confusing features is the relationship between arrays and pointers. Understanding it correctly resolves a large fraction of C’s apparent inconsistencies.

The Fundamental Truth

In most contexts, an array name decays to a pointer to its first element:

int buffer[256];
int *ptr = buffer;  // equivalent to: int *ptr = &buffer[0];

Array subscripting is defined as pointer arithmetic:

buffer[i]  ==  *(buffer + i)  ==  *(ptr + i)  ==  ptr[i]

All four expressions compile to identical machine code. A curious consequence of the commutativity of addition is that arr[3] and 3[arr] are both legal and identical, which is a fine piece of trivia and terrible style.

Where They Differ

Arrays and pointers are not the same type, and three contexts expose the difference:

int16_t arr[10];
int16_t *ptr = arr;

sizeof(arr);  // 20 on any target: 10 elements at 2 bytes each
sizeof(ptr);  // the size of a pointer: 8 on a 64-bit desktop

&arr;  // type: int16_t (*)[10]  (pointer to array of 10 int16_t)
&ptr;  // type: int16_t **       (pointer to pointer to int16_t)

Key distinction: an array is a fixed-size block of memory whose name is not an lvalue. A pointer is a separate variable holding an address, which you can reassign.

The decay rule is also why array bounds vanish at function boundaries. A parameter written int16_t data[10] is silently rewritten to int16_t *data, the 10 is discarded, and no bounds information survives. This is the root of a great deal of C’s memory unsafety, and the reason a length argument almost always accompanies an array argument.

Multidimensional Arrays

A 2D array in C is not an array of pointers. It is a single contiguous block, stored row-major, with the rightmost subscript varying fastest:

int grid[3][4];      // 3 rows of 4 ints: 12 ints, contiguous

grid[1][2] is computed as *(*(grid + 1) + 2), which reaches element 1 * 4 + 2 == 6. The row width is baked into the address arithmetic, which is why the compiler must know it.

Decay applies here too, but only to the outermost dimension. grid decays to a pointer to its first element, and its first element is a row, meaning int (*)[4], not int *:

int (*row)[4] = grid;      // pointer to an array of 4 ints
int *flat     = grid[0];   // pointer to the first int, if you want the flat view

This is the pointer-to-array type the right-left rule worked through earlier, and it is why a function taking a 2D array must name every dimension but the first:

void clear(int rows, int cols, int grid[rows][cols]);   // C99 variably-modified type
void clear_fixed(int grid[][4], int rows);              // all but the first dimension

Without the column count, the compiler cannot compute where row n begins.

Warningint ** is not a 2D array

A int ** is a pointer to a pointer, typically the head of an array of separately allocated row pointers. That layout is also common and equally valid, but it is a different thing: two dereferences through scattered allocations instead of one block with computed offsets. They are not interchangeable, and passing grid where int ** is expected does not compile. Choose the flat block for cache behavior and a single allocation; choose the pointer array when rows differ in length or must be reordered cheaply.

Strings

C has no string type. A C string is simply an array of char terminated by a null byte ('\0', the value zero). Every standard string function relies on that terminator to know where the string ends; forget it and you get buffer overruns and undefined behavior.

char greeting[] = "hello";   // 6 bytes: 'h','e','l','l','o','\0'

The implication is that finding a string’s length is an \(O(n)\) scan for the terminator, not a constant-time field lookup as in C++’s std::string or Python’s str.

String vs. Character Literals

Note the distinction, easy to conflate:

'A'    // a character: a single int-valued constant (0x41)
"A"    // a string: two bytes, 'A' and '\0'

The Standard String Functions

Declared in <string.h>, operating on null-terminated arrays:

Function Purpose
strlen(s) Length, not counting the terminator (scans for \0).
strcpy(dst, src) Copy src into dst. No bounds checking.
strncpy(dst, src, n) Copy at most n bytes. Safer, but may not null-terminate.
strcmp(a, b) Compare; returns 0 if equal.
strcat(dst, src) Append src to dst. No bounds checking.
strchr(s, c) Find first occurrence of character c.

The mem* family (memcpy, memset, memmove, memcmp) does the same for raw bytes without caring about a terminator, and is what you use for binary data and buffers.

WarningThe classic C vulnerability

strcpy and strcat write until they hit the source’s terminator, with no regard for the destination’s size. A source longer than the destination overruns the buffer, corrupting adjacent memory. This single design choice is behind a large fraction of security exploits in C’s history. The Common Pitfalls section shows the safe alternatives.

Building Strings Safely

For assembling a string into a fixed buffer, snprintf is the tool to reach for. It always terminates, it bounds the write, and its return value reports the length the result would have needed, which is how you detect truncation:

char path[64];
int needed = snprintf(path, sizeof path, "%s/%s.log", directory, name);
if (needed < 0 || (size_t)needed >= sizeof path) {
    /* truncated: handle it rather than proceeding with a half-built path */
}

Checking that return value is the step most code skips, and skipping it converts a loud overflow into a quiet wrong answer.

Copying and Splitting

strdup allocates a copy of a string and returns it, which saves the usual malloc(strlen(s) + 1) dance. It is POSIX rather than ISO C until C23, but is available essentially everywhere:

char *copy = strdup(original);   // caller must free()

The + 1 for the terminator is the classic off-by-one in hand-rolled versions, which is reason enough to prefer the library function.

strtok splits a string on delimiters, and it comes with two significant caveats: it modifies its input, writing terminators over the delimiters, and it keeps its position in a static variable, which makes it neither reentrant nor thread-safe.

char input[] = "alpha,beta,gamma";     // must be writable, not a literal
for (char *token = strtok(input, ","); token != NULL; token = strtok(NULL, ",")) {
    puts(token);
}

Passing NULL on subsequent calls is how it resumes. Because of the hidden state, two interleaved strtok loops will corrupt each other; use strtok_r (POSIX) or strtok_s (C11 Annex K) where that is a risk. This is the reentrancy hazard that static locals introduce, in its most widely encountered form.

char vs. int from Input

A subtle but important convention: functions like getchar return an int, not a char. This is because they must return every possible byte value and a distinct end-of-input marker, EOF (typically -1). A char cannot hold that extra value, so storing the result in a char before testing for EOF is a genuine bug.

int c;                          // int, not char!
while ((c = getchar()) != EOF) {
    putchar(c);
}

Structures

Organizing related data

A structure groups values of heterogeneous types into a single object. It is C’s only aggregation mechanism, and combined with function pointers it is enough to build essentially every data structure and object system C programmers have devised.

typedef struct {
    int16_t *buffer;      // pointer to the sample storage
    uint16_t size;        // capacity
    uint16_t head;        // write position
    uint16_t tail;        // read position
    uint8_t  overrun;     // error flag
} CircularBuffer_t;

// Designated initializers (C99) name the members explicitly
CircularBuffer_t audio_in = {
    .buffer = input_samples,
    .size = 512,
    .head = 0,
    .tail = 0,
    .overrun = 0
};

audio_in.buffer[audio_in.head++] = new_sample;

Designated initializers are worth adopting as a default. They are order-independent, they document each value at the point of assignment, and any member you omit is zero-initialized, so adding a field to the struct does not silently corrupt existing initializers the way positional initialization does.

Why typedef struct? In C, unlike C++, the struct tag lives in a separate namespace, so without a typedef you must write struct CircularBuffer at every use. The typedef collapses that to CircularBuffer_t.

Members are accessed with . on an object and -> on a pointer to one; p->size is shorthand for (*p).size.

Structs Are Values

Unlike arrays, structs do not decay. A struct is a value: it can be assigned, passed to a function, and returned from one, and each of those copies every byte.

CircularBuffer_t a = b;          // copies the whole struct
void configure(CircularBuffer_t cfg);      // receives a copy
CircularBuffer_t make_buffer(void);        // returns a copy

This asymmetry surprises people who expect arrays and structs to behave alike, and it has a practical consequence: a struct containing an array does copy that array, which is the standard trick for passing an array by value.

The copy is shallow. In the example above, a.buffer and b.buffer are two pointers holding the same address, so the two structs now share one sample buffer. Copying a struct duplicates its pointers, never what they point at. If each copy needs its own storage, you write that deep copy yourself; C has nothing like a C++ copy constructor to do it for you.

Large structs are usually passed by pointer instead, both to avoid the copy and because const Foo_t * documents that the callee will not modify the original.

Padding, Alignment, and offsetof

The compiler inserts padding between members so each satisfies its alignment requirement, which means sizeof a struct is generally more than the sum of its members, and member order affects the total:

struct Loose { char a; int b; char c; };   // often 12 bytes
struct Tight { int b; char a; char c; };   // often 8 bytes

Both hold the same data. Loose pads after each char to align the int; Tight groups the small members together. Ordering members from largest to smallest is a cheap habit that reduces padding on most targets.

When you need the actual offset of a member, offsetof from <stddef.h> reports it without guessing:

#include <stddef.h>
offsetof(struct Tight, c);   // byte offset of member c
WarningNever assume a struct’s layout

Because padding is implementation-defined, a struct is not a reliable description of a wire format, a file header, or a hardware register block. Read and write such formats field by field, or assert the layout with static assertions so a mismatch fails the build rather than corrupting data in the field. __attribute__((packed)) suppresses padding but slows member access, and on strict-alignment architectures it can produce unaligned accesses that fault outright.

Flexible Array Members

A struct may end with an array of unspecified length, which C99 calls a flexible array member. It lets a header and its variable-length payload live in a single allocation:

typedef struct {
    size_t  length;
    uint8_t data[];      // must be last, and cannot be the only member
} Packet_t;

Packet_t *packet = malloc(sizeof *packet + payload_size);
packet->length = payload_size;
memcpy(packet->data, payload, payload_size);

One malloc and one free instead of two, with the payload contiguous with its header. Note that sizeof *packet counts only the fixed part, which is exactly what makes the addition correct. The older workaround, declaring data[1] and over-allocating, is still visible in legacy headers and is technically undefined behavior; the flexible member is the sanctioned form.

Unions

Multiple views of the same memory

A union stores any one of several types in the same memory, sized to its largest member. Only one member is valid at a time, and nothing in the language tracks which one, so a union is almost always paired with a separate tag field indicating the active member.

typedef union {
    uint32_t word;
    struct {
        uint8_t byte0;
        uint8_t byte1;
        uint8_t byte2;
        uint8_t byte3;
    } bytes;
} Word32_t;

Word32_t data;
data.word = 0x12345678;
uint8_t high = data.bytes.byte3;   // byte order depends on endianness

The other common use is type punning, reinterpreting an object’s bits as a different type:

typedef union {
    float    f;
    uint32_t u;
} FloatBits_t;

FloatBits_t x = { .f = 3.14159f };
printf("Float bits: 0x%08X\n", x.u);
NoteUnion punning is legal in C, but not in C++

Reading from a union member other than the one last written is explicitly permitted in C99 and later, and is the standard-blessed way to reinterpret bits. The same code is undefined behavior in C++, where the sanctioned tool is std::bit_cast (C++20) or memcpy. Casting a pointer to a different type and dereferencing it is undefined in both languages; that is a strict-aliasing violation, and it is a different thing from union punning.

Bitwise Operations

Bitwise operators act on the binary representation of integers. They are how C manipulates hardware registers, packs flags, and implements the low-level half of nearly every protocol.

Operator Name Description Example (A=60, B=13) Result
& AND Sets bit to 1 if both bits are 1 A & B (0011 1100 & 0000 1101) 12 (0000 1100)
| OR Sets bit to 1 if one of bits is 1 A | B (0011 1100 | 0000 1101) 61 (0011 1101)
^ XOR Sets bit to 1 if only one is 1 A ^ B (0011 1100 ^ 0000 1101) 49 (0011 0001)
~ NOT Inverts all bits ~A (~0011 1100) -61 (1100 0011)
<< Left Shift Shifts bits left (multiply by \(2^n\)) A << 2 (0011 1100 << 2) 240 (1111 0000)
>> Right Shift Shifts bits right (divide by \(2^n\)) A >> 2 (0011 1100 >> 2) 15 (0000 1111)

The four idioms worth memorizing, where n is a bit position:

reg |=  (1u << n);   // set bit n
reg &= ~(1u << n);   // clear bit n
reg ^=  (1u << n);   // toggle bit n
if (reg & (1u << n))  { /* bit n is set */ }
WarningShifts have sharp edges

Shifting by a count greater than or equal to the width of the promoted operand is undefined, as is shifting a negative value left. Right-shifting a negative signed value is implementation-defined (in practice, arithmetic shift). Prefer unsigned types for bit manipulation, and note the 1u in the idioms above: 1 << 31 overflows a 32-bit signed int, while 1u << 31 is well defined.

Memory Management

C hands you the allocator and gets out of the way. There is no garbage collector, no ownership tracking, and no destructor; every allocation is a manual obligation to free exactly once, and both failures (never, or twice) are serious bugs.

Where Memory Lives

Region What lives there Lifetime Size known at
Stack Local variables, function arguments, return addresses Scope of the function Runtime (bounded by stack size)
Heap malloc/free allocations Until explicitly freed Runtime (unbounded)
Static / BSS Globals, static variables, const data Entire program lifetime Compile time

A frequent point of confusion: a fixed array at file scope, or one marked static, lives in the static region rather than the stack. It is allocated at compile time and exists for the whole run.

int16_t audio_buffer[512];          // static region: exists for the program's life
static int16_t filter_state[8];     // same region, but private to this file

void process(void) {
    int16_t local_buf[16];          // stack: gone when process() returns
}

Returning a pointer to a local is therefore a use-after-return bug: the storage is reclaimed the moment the function exits. Objects that must outlive their creating function belong on the heap or in static storage.

The Allocation Functions

<stdlib.h>

  • malloc(size): allocates uninitialized memory; contents are garbage.
  • calloc(n, size): allocates n * size bytes and zeroes them.
  • realloc(ptr, size): resizes an allocation, possibly moving it.
  • free(ptr): releases an allocation. free(NULL) is safe and does nothing.
int16_t *samples = malloc(count * sizeof *samples);
if (samples == NULL) {
    return -1;              // allocation can fail; check every time
}
/* ... use samples ... */
free(samples);
samples = NULL;             // avoids an accidental use-after-free

Two habits in that snippet are worth adopting. sizeof *samples rather than sizeof(int16_t) stays correct if the type ever changes. And the malloc result is not cast: in C the void* converts implicitly, and an explicit cast can mask a missing <stdlib.h> include. (This is one of the places C and C++ genuinely differ; C++ requires the cast, which is a hint that you should be using new or a container instead.)

Warningrealloc can leak if you are careless

realloc returns NULL on failure without freeing the original block. Writing p = realloc(p, n); therefore leaks the original allocation whenever it fails. Assign to a temporary, check it, and only then overwrite p.

The failure modes to know by name: use-after-free (dereferencing a freed pointer), double free (freeing twice), memory leak (never freeing), and buffer overrun (writing past the end). None are diagnosed by the language, all are undefined behavior, and all are what tools like AddressSanitizer and Valgrind exist to catch. Run them.

How the Allocator Works

What is actually happening behind malloc

malloc is not a system call and not a language feature. It is an ordinary library function managing a pool of memory it obtained from the operating system, and knowing roughly how it does that explains several things that otherwise look arbitrary.

Every allocation carries hidden bookkeeping. The allocator stores metadata, at minimum the block’s size, immediately before the address it hands you:

    [ header: size, flags ][ your bytes ................. ]
                           ^
                           the pointer malloc returns

This is how free(ptr) knows how many bytes to reclaim when you never told it: it steps backward from your pointer to read the header. Two consequences follow directly. A small allocation costs more than you asked for, typically 8 to 16 bytes of overhead plus rounding up for alignment, so a million 4-byte allocations may consume 24 MB rather than 4 MB. And writing before the start of your block, or freeing a pointer the allocator did not return, corrupts that header. This is why freeing a pointer you have advanced is undefined behavior rather than merely wasteful: the bytes preceding it are not a header, and the allocator reads them as one anyway.

Free blocks are tracked in free lists. When you free a block, the allocator does not return it to the operating system; it records it in a list (or several lists, binned by size) of blocks available for reuse. A subsequent malloc searches those lists for something suitable.

That search is where allocator design lives. Common strategies are first fit (take the first block large enough), best fit (take the smallest block that fits, minimizing waste but scanning more), and segregated fits (keep separate lists per size class, so common sizes are found in constant time). Real allocators such as glibc’s use size-binned lists plus a small cache of recently freed blocks, which makes the frequent case, allocate and free the same size repeatedly, very fast.

Splitting and coalescing keep the pool usable. If the block found is larger than requested, the allocator splits it, using the front and returning the remainder to the free list. When a block is freed, the allocator checks whether the blocks physically adjacent to it are also free, and if so coalesces them into one larger block. Without coalescing, a heap would degrade into a pile of unusably small fragments after enough churn.

Fragmentation

Coalescing helps, but it cannot fix everything, because it only merges blocks that happen to be neighbors.

External fragmentation is free memory that exists but is not contiguous. After allocating and freeing in a scattered pattern, the heap may hold 10 MB free across dozens of gaps and still fail a 1 MB request because no single gap is large enough:

[ used ][ free 400K ][ used ][ free 300K ][ used ][ free 350K ]
         a 1 MB request fails, despite 1,050K free

Internal fragmentation is the waste inside a block you were given: the header, the alignment padding, and the rounding up to a size class. Ask for 33 bytes and you may occupy 48.

WarningC cannot defragment

This is the important structural point, and it follows from the language rather than from any allocator’s cleverness. Defragmenting means moving live allocations to close the gaps, and an allocator cannot move a block it has handed you, because you hold its address and it has no way to find and update your copies of that pointer. Addresses in C are ordinary values; they can be stored in structs, copied into other variables, cast to integers, and written to files.

Garbage-collected runtimes with compacting collectors, and languages where the runtime tracks every reference, can and do relocate objects to defragment the heap. C trades that ability away for the guarantee that a pointer, once obtained, stays valid and stable until you free it. You cannot have both.

The practical mitigations are all about avoiding the situation: allocate long-lived objects up front so they are not interleaved with short-lived ones, use fixed-size pools when allocation patterns are regular, or use an arena that allocates cheaply and frees everything at once.

When malloc Fails

When the free lists cannot satisfy a request, the allocator asks the operating system for more memory (traditionally brk/sbrk to extend the heap; modern allocators typically use mmap, especially for large blocks, which is also why very large allocations are often returned to the OS on free while small ones are not). If the OS refuses, malloc returns NULL.

Handling that return is the entire contract, and it is one line:

int16_t *samples = malloc(count * sizeof *samples);
if (samples == NULL) {
    /* recover, or fail cleanly: do NOT proceed */
}

Skipping the check does not produce a crash at the point of failure. It produces a null dereference at some later, unrelated point, and on a system without memory protection it produces silent corruption instead.

NoteOn Linux, malloc succeeding does not mean the memory exists

Linux overcommits by default: it grants address space without reserving physical pages, on the reasonable bet that most programs do not touch everything they allocate. Pages are backed by real memory only when first written. The consequence is that malloc can return a perfectly valid non-NULL pointer for memory the system cannot actually provide, and the shortfall surfaces later as a fault when you write to it. If the system runs out at that moment, the kernel’s OOM killer selects a process and terminates it outright, so your program may die without malloc ever having returned NULL.

This surprises people who assume checking malloc is sufficient for robustness. On a desktop Linux system it largely is not; the check still matters (it catches size-overflow bugs and genuine refusals, and other platforms do not overcommit) but it is not a guarantee that the memory is yours. Overcommit behavior is tunable via /proc/sys/vm/overcommit_memory.

Two related failure modes are worth naming. A request whose size calculation overflows, such as malloc(count * sizeof *p) where count is attacker-controlled, may wrap to a small value and succeed, handing back a buffer far smaller than the code believes it has. Check the multiplication, or use calloc, which is required to detect overflow in n * size. And stack exhaustion is a separate matter entirely: deep recursion or a large local array overflows the stack, which malloc has nothing to do with and which typically faults immediately.

NoteDynamic allocation is often banned outright

In hard-real-time and safety-critical systems, malloc is frequently forbidden, and everything above is why: the search through free lists makes allocation time unbounded, fragmentation can cause a failure hours into a run that testing never reproduced, and the failure mode is difficult to recover from at the point it occurs. Such systems allocate everything statically up front, or use fixed-block pools with deterministic timing. The Applied DSP notes cover the pools-and-fixed-buffers approach in context.

The Preprocessor

Before the compiler proper sees your code, the preprocessor performs a purely textual transformation of it: pasting in headers, expanding macros, and selecting or discarding whole regions of source. It knows nothing of C’s types, scopes, or syntax; it manipulates tokens. That ignorance is the source of both its power and every one of its hazards.

Stages of Compilation

The build proceeds in four distinct stages:

  1. Preprocessing: directives beginning with # are executed. Headers are pasted in, macros expanded, conditional regions resolved. The output is a single expanded translation unit.
  2. Compilation: the translation unit is parsed, type-checked, optimized, and lowered to assembly for the target architecture.
  3. Assembly: assembly becomes machine code in an object file (.o), with a symbol table and unresolved references.
  4. Linking: object files and libraries are combined, symbols resolved, and a final executable produced.

Stages 2 and 3 are often collapsed and called “compilation,” which is why some references describe three stages rather than four.

#include

#include replaces the directive with the entire contents of the named file, then keeps going: whatever that file includes is pasted in too, recursively, until nothing is left to expand. There is no import, no module, no symbol table, no notion that a file has already been read. A forty-line .c file that includes <stdio.h> routinely hands the compiler tens of thousands of lines.

Two forms exist, differing only in where the search begins.

#include <stdio.h>      // the implementation's own directories
#include "audio.h"      // this file's directory first, then the above

The angle-bracket form searches an implementation-defined list of places: the standard library’s directories, plus anything added with -I. The quoted form is specified only as searching “in an implementation-defined manner,” and every real compiler implements that as the directory containing the file doing the including, then falls back to the angle-bracket search. The fallback is convention rather than a guarantee, but it is universal. The convention that follows is simple: angle brackets for headers you did not write, quotes for headers that ship with your project.

-I prepends a directory to the search path, and multiple -I flags are searched left to right:

cc -Iinclude -Ivendor/dsp/include -c audio.c

Note what the quoted form’s first rule really means. It resolves relative to the including file, not to the compiler’s working directory, so #include "../dsp/filter.h" inside src/audio/mixer.c looks in src/dsp/. This is why a header can be moved and break only the files that include it by relative path.

NoteComputed includes

The operand may itself be a macro, expanded before the file is looked up:

#define TARGET_HEADER "board/nucleo_f411.h"
#include TARGET_HEADER

This is how a build system selects a board or platform header without a chain of #ifdefs. It is rare, entirely legal, and worth recognizing when you meet it.

Because inclusion is literal and recursive, including the same header twice in one translation unit pastes its contents twice, which is an error for anything that cannot be declared twice. Every header therefore needs protection against it, which is what include guards are for.

NoteWhy C builds are slow

The compiler has no memory between translation units. If two hundred .c files each include the same eight-thousand-line header, that header is read, tokenized, and parsed two hundred times. Nothing is cached, because the preceding text can change the meaning of what follows: a macro defined before an #include alters the header’s expansion, so the same header genuinely may mean different things in different files. That is the price of textual inclusion, and it is the specific problem C++20 modules exist to solve.

Macros

#define introduces a macro, a name that the preprocessor replaces with a token sequence wherever it appears.

#define BUFFER_SIZE 256                     // object-like
#define SQUARE(x) ((x) * (x))               // function-like

The parentheses in SQUARE are not optional decoration. Because expansion is textual, #define SQUARE(x) x * x turns SQUARE(a + b) into a + b * a + b, which is not what anyone meant. Wrap every parameter, and wrap the whole body.

Other directives round out the set: #undef removes a definition, #error aborts the build with a message (useful for catching an unsupported configuration), and #pragma issues implementation-specific instructions to the compiler. Other Directives collects the full list.

NotePrefer the language to the preprocessor

Most historical uses of macros now have typed, scoped alternatives: enum or const for constants, static inline functions for small operations, and (as of C23) constexpr. A macro has no type, obeys no scope, ignores namespaces, and is invisible to the debugger, which sees only the expansion. Reach for a macro when you need something the language genuinely cannot express: conditional compilation, stringification, token pasting, or capturing __FILE__ and __LINE__ at the call site.

The Empty Macro

A third form is easy to miss because it looks unfinished:

#define USE_FIXED_POINT

There is no replacement list at all, and that is legal. The macro is defined, and its replacement is the empty token sequence. This is not the same as being undefined, and it is not the same as being zero: the name exists in the preprocessor’s table, it simply has nothing on the other side of it.

Before going further, one distinction has to be nailed down, because everything about empty macros depends on it. A macro name meets one of two fates, decided entirely by where it appears:

Fate Where What happens
Expanded Ordinary program text, and the controlling expression of a bare #if The name is replaced by its replacement list. For an empty macro, that means it is deleted.
Tested The operand of #ifdef, #ifndef, defined(), and #undef The name is looked up. The preprocessor asks only whether a definition exists; the replacement list is never consulted, and no expansion occurs.

An empty macro’s two uses line up exactly with those two fates.

The first, and by far the more common, is as a flag, which lives entirely in the “tested” column. The definition carries no value, only the fact of its own existence:

#define USE_FIXED_POINT

#ifdef USE_FIXED_POINT
    typedef int16_t Sample_t;
#else
    typedef float Sample_t;
#endif

Nothing here is expanded. #ifdef USE_FIXED_POINT is a lookup that answers yes, and the conditional then keeps exactly one of its two branches and discards the other, so the compiler is handed a single typedef and never sees the word USE_FIXED_POINT at all:

typedef int16_t Sample_t;

Comment out the #define and you get the float line instead. You cannot get both; a conditional always yields one branch or the other. The macro’s emptiness is irrelevant to any of this, which is the point: a flag exists to be tested, never to be expanded, so it needs no value.

The second use is annotation erasure, and it is the mirror image: it lives entirely in the “expanded” column, and the emptiness is the whole mechanism. Define a name to nothing and every use of it vanishes from the compiler’s view. This is how portable headers neutralize a keyword or attribute the target compiler does not have.

#if defined(__GNUC__)
    #define PACKED __attribute__((packed))
#else
    #define PACKED              // expands to nothing; the code still compiles
#endif

struct Header { uint8_t tag; uint32_t length; } PACKED;

On GCC the struct declaration comes out carrying the attribute. On a compiler that has never heard of __attribute__, PACKED is expanded to nothing and the declaration is handed over clean:

struct Header { uint8_t tag; uint32_t length; };

The single source line works on both, with no #ifdef at the point of use. That is the trick worth remembering: push the conditional up into the definition of a name, then use the name unconditionally.

The trap is what happens when you test an empty macro with #if instead of #ifdef, and the table above predicts it. A bare #if puts its operand in the expanded column, so the macro is replaced by nothing and the directive becomes #if followed by no expression at all. That is a syntax error, not a false condition:

#define USE_FIXED_POINT

#if USE_FIXED_POINT     // error: #if with no expression
#endif

An empty macro must be tested with #ifdef or defined(), never with a bare #if.

WarningTwo ways to be surprised by an empty macro

-D does not produce one. Defining a flag on the command line as -DUSE_FIXED_POINT defines it to 1, not to empty, because that is what the standard specifies for a -D with no =. So #if USE_FIXED_POINT compiles when the flag came from the build system and fails when someone moves the same flag into a header as #define USE_FIXED_POINT. Use #ifdef and both spellings work. To get a genuinely empty definition from the command line, write -DUSE_FIXED_POINT=.

Defined-as-zero is still defined. #define USE_FIXED_POINT 0 makes #ifdef USE_FIXED_POINT true, because #ifdef asks only whether the name has a definition and never looks at its value. If a macro is meant to be switched off, #undef it or do not define it; do not set it to 0 and expect #ifdef to notice. If a macro is meant to carry a value, test it with #if and be consistent about always defining it.

Macro Side Effects

Because a macro expands its arguments textually, an argument that appears twice in the body is evaluated twice:

#define MAX(a, b) ((a) > (b) ? (a) : (b))

int x = 5;
int result = MAX(x++, 10);   // x may be incremented twice

The comparison evaluates x++, then the selected branch evaluates it again. A function does not have this problem, because arguments are evaluated exactly once at the call:

static inline int max_int(int a, int b) {
    return (a > b) ? a : b;
}

static inline gives the same performance as the macro with none of the hazards. Use it whenever the operation is monomorphic; this is precisely the gap that C++ templates and Rust generics close properly.

_Generic

“Whenever the operation is monomorphic” is doing a lot of work in that last sentence, because the reason to write MAX as a macro in the first place is that it works on any type. C11 offers a partial escape. _Generic is a type-generic selection: an expression that chooses among several alternatives based on the type of a controlling expression, resolved entirely at compile time.

It is a language feature rather than a preprocessor one, but it appears here because it is essentially never used on its own. Its only practical form is inside a #define, wrapping the dispatch so callers see a single name.

#include <math.h>
#include <stdlib.h>

#define ABS(x) _Generic((x),    \
        long double: fabsl,     \
        double:      fabs,      \
        float:       fabsf,     \
        long:        labs,      \
        int:         abs        \
    )(x)

double d = ABS(-2.5);    // selects fabs,  calls fabs(-2.5)
int    n = ABS(-7);      // selects abs,   calls abs(-7)

The whole _Generic(...) expression is replaced by the selected alternative, here a function name, and the trailing (x) then calls it. Nothing is decided at run time and no branch is emitted; the compiler resolves the selection and generates a single direct call.

Returning a value rather than a function works the same way:

#define TYPE_NAME(x) _Generic((x),   \
        int:      "int",             \
        float:    "float",           \
        double:   "double",          \
        char *:   "char *",          \
        default:  "something else")

printf("%s\n", TYPE_NAME(3.0f));   // float

Four rules govern it, and each surprises somebody:

  • The controlling expression is not evaluated. Only its type is inspected. ABS(i++) increments i exactly once, in the call, not twice, which is a rare case of a macro not doubling its argument. It also means _Generic((int *)0, ...) is a legitimate way to select on a type you name directly rather than on a value you have.
  • Selection uses the type after lvalue conversion. Top-level qualifiers are dropped, so a const int matches the int association, and arrays and functions decay to pointers, so a char[16] matches char * rather than any array type. (C11 as published was ambiguous here; the committee resolved it this way afterward, so ancient compilers may disagree.)
  • Every branch must type-check, including the ones not selected. The unselected alternatives are discarded, but they are still parsed and checked first. This is the practical limit on _Generic: you cannot dispatch to operations that are merely invalid for the other types, only to ones that happen not to be chosen. It is not if constexpr.
  • The match must be unambiguous. Exactly one association may be compatible with the type. No match and no default is a compile error, which is often what you want: it turns an unsupported type into a build failure instead of a silent promotion.

This is how <tgmath.h> works, and _Generic exists largely so that header could be written in portable C rather than by compiler magic.

NoteDispatch, not polymorphism

Be clear about what this buys. _Generic selects from a list you wrote out by hand; it cannot generate code for a type you did not enumerate, cannot be extended by a caller, and produces error messages about the expansion rather than about your call. C++ templates and Rust generics instantiate new code per type and are open to types their author never saw. _Generic closes the narrow gap where a fixed, known set of types needs one name; it does not make C a generic language.

How Expansion Actually Works

Everything so far has treated expansion as obvious: the macro’s name is replaced by its body, arguments substituted in. That is true, but the order of operations has consequences that account for most of the genuinely baffling macro behavior, and the rules are short enough to learn once.

When the preprocessor decides to expand a function-like macro, it does three things in this order:

  1. Prescan. Each argument is completely macro-expanded on its own, before it is substituted into the body. The exception is an argument used as an operand of # or ##, which is substituted raw.
  2. Substitute. The expanded arguments are put into the replacement list.
  3. Rescan. The result is scanned again for macro names, and any found are expanded too.

Step 3 is what lets macros build on other macros. It is also what keeps the following from recursing forever:

// A debug build that logs every deallocation, still calling the real free().
#define free(p) do { log_free(__FILE__, __LINE__, (p)); free(p); } while (0)

During the rescan of a macro’s own expansion, that macro is marked and will not be expanded again. Compiler writers call this painting it blue: the name survives into the output, but it has been colored so that no further expansion touches it. So the free(p) in the body becomes a genuine call to the library function, not an infinite regress. Self-referential macros are safe by construction, which is what makes wrapping a function in a macro of the same name a workable technique rather than a trap.

The exception in step 1 is the one that bites. Because # and ## receive their operand unexpanded, stringifying a macro gives you its name:

#define VERSION 3
#define STRINGIFY(x)  #x
#define XSTRINGIFY(x) STRINGIFY(x)

STRINGIFY(VERSION)    // "VERSION"
XSTRINGIFY(VERSION)   // "3"

XSTRINGIFY works because its own argument is not an operand of #, so prescan expands VERSION to 3 before passing it along; the inner STRINGIFY then stringifies 3. This two-layer dance is standard practice and the same trick applies to ## when you need to paste an expanded macro rather than its name. If you find yourself writing a macro whose name begins with X or ends in _, this is almost always why.

WarningErrors point at the expansion, not the source

The compiler sees the post-expansion text, so a mistake inside a macro is reported at the line where the macro was used, described in terms of tokens the user never typed. GCC and Clang mitigate this by printing an expansion trace (“in expansion of macro …”), which is worth reading from the bottom up. When the trace is not enough, stop reasoning about the rules and read the actual output with -E.

Conditional Compilation

#if, #ifdef, #elif, #else, and #endif include or discard regions of source before compilation. Discarded regions need not even be valid C, which is what makes this the tool for portability.

#define DEBUG_LEVEL 2

#if DEBUG_LEVEL >= 2
    #define DEBUG_PRINT(fmt, ...) printf(fmt, ##__VA_ARGS__)
#elif DEBUG_LEVEL == 1
    #define DEBUG_PRINT(fmt, ...) printf(fmt "\n", ##__VA_ARGS__)
#else
    #define DEBUG_PRINT(fmt, ...) ((void)0)   // compiles to nothing
#endif

With DEBUG_LEVEL at 0, every call site vanishes: zero code size, zero run-time cost. This is the standard mechanism for debug instrumentation, feature flags, and platform variation.

defined

#ifdef X and #ifndef X are shorthand, and deliberately limited: each takes exactly one macro name and nothing else. The moment a condition involves two flags, or a flag combined with a value, you need the defined operator, which is available only inside #if and #elif and evaluates to 1 or 0:

#if defined(USE_FIXED_POINT) && !defined(HAVE_FPU)
    /* ... */
#elif defined(HAVE_FPU) && SAMPLE_RATE > 48000
    /* ... */
#endif

#ifdef X and #if defined(X) are exactly equivalent; the parentheses are optional (#if defined X) but conventionally written. Prefer defined for anything compound, and prefer it uniformly in a header that already needs it once, since mixing the two spellings for no reason makes a long conditional chain harder to read.

The arithmetic in #if deserves one caution of its own: it is performed in the widest integer type the implementation supports (intmax_t/uintmax_t), regardless of the types the program uses, and sizeof is not available because the preprocessor has no idea what a type is. #if sizeof(int) == 4 does not work. That is what static assertions are for.

WarningAn unknown name in #if is silently zero

After macro expansion, any identifier still remaining in an #if expression is replaced by 0. Not an error, not a warning by default: just false.

#if CONFG_DEBUG        // typo for CONFIG_DEBUG
    enable_tracing();  // silently never compiled
#endif

The block simply never appears, the build succeeds, and the feature quietly does not exist. This is one of the most durable bugs in C, because nothing anywhere reports it. -Wundef promotes the substitution to a warning and is worth turning on in any project that uses configuration macros at all. Note also that this is only how identifiers behave; defined(CONFG_DEBUG) on a misspelled name is legitimately 0 and no warning is possible, which is an argument for defining every configuration flag to an explicit 0 or 1 and testing it with #if.

Stringification and Token Pasting

Two operators exist only inside macro bodies. Stringification (#) converts an argument into a string literal:

#define STRINGIFY(x) #x
#define SHOW(expr) printf(#expr " = %d\n", expr)

SHOW(count * 2);   // printf("count * 2" " = %d\n", count * 2);

Both operators take their operand unexpanded, which is the rule from How Expansion Actually Works that costs people the most time. If the argument is itself a macro and you want its value rather than its name, route it through an extra layer, as XSTRINGIFY does above.

Token pasting (##) joins two tokens into one, which is how you generate families of related identifiers:

#define DEFINE_ACCESSORS(type, name)                  \
    static type get_##name(void)      { return name; } \
    static void set_##name(type v)    { name = v; }

DEFINE_ACCESSORS(int, sample_rate)   // defines get_sample_rate / set_sample_rate

Token pasting is the closest thing C has to code generation, and it is how many container and registration macros work. It is also nearly unreadable in bulk, and errors surface as messages about the expanded text.

X Macros

Sooner or later a C program acquires two lists that must agree. An enum of error codes and an array of strings to print them. A set of commands and the switch that dispatches them. A register map and the table that dumps it. They are edited at different times by different people, they drift, and the symptom is an off-by-one in a lookup table that nobody notices until a log line names the wrong error.

The X macro is C’s answer, and it has been in use since the 1960s. The trick is to write the data exactly once as a list of invocations of an undefined macro named X, then replay that list, redefining X each time to render the data a different way.

// commands.def: the single source of truth
X(CMD_START,  "start",  handle_start)
X(CMD_STOP,   "stop",   handle_stop)
X(CMD_STATUS, "status", handle_status)

Each replay defines X, includes the list, and undefines X again:

typedef enum {
    #define X(id, name, handler)   id,
    #include "commands.def"
    #undef X
    CMD_COUNT
} Command_t;

static const char *const command_names[] = {
    #define X(id, name, handler)   [id] = name,
    #include "commands.def"
    #undef X
};

int dispatch(Command_t cmd, const char *arg) {
    switch (cmd) {
        #define X(id, name, handler)   case id: return handler(arg);
        #include "commands.def"
        #undef X
        default: return -1;
    }
}

Adding a command is now a one-line edit to commands.def, and the enum, the name table, and the dispatch switch all update together. They cannot drift, because there is only one list. CMD_COUNT lands correctly for free, and the designated initializer [id] = name means the table stays right even if the list is reordered.

The list does not have to live in its own file. The same technique works with the list as a macro, which keeps everything in one place at the cost of a continuation on every line:

#define COMMAND_LIST            \
    X(CMD_START,  "start")      \
    X(CMD_STOP,   "stop")       \
    X(CMD_STATUS, "status")

typedef enum {
    #define X(id, name) id,
    COMMAND_LIST
    #undef X
} Command_t;
WarningPowerful, and genuinely hostile to read

Everything the earlier warnings said applies here at full strength. A newcomer meeting an X macro for the first time will not know what they are looking at, “go to definition” lands on a .def file full of a macro that has no definition, and the debugger has never heard of any of it. Errors are reported against the expansion, so a missing comma in the list produces a syntax error on the #include line.

It is still worth knowing, for two reasons. A great deal of long-lived C, including parts of the Linux kernel and most vendor peripheral headers, is built this way, so you will read it whether or not you write it. And the alternative it replaces, hand-maintained parallel lists, fails silently, whereas this fails loudly at build time. When you do use it, keep the list dead simple and leave one comment at the top of the file naming the technique, so the next reader has something to search for.

C23 does not retire the idiom. __VA_OPT__ and #embed solve adjacent problems, but nothing in standard C generates an enum and a matching table from one declaration. That capability arrives only with C++ templates and constexpr, or with Rust’s derive macros, both of which are the real reply to this entire section.

Variadic Macros

A macro can accept a variable number of arguments with ..., expanded via __VA_ARGS__ (C99):

#define LOG_ERROR(fmt, ...) \
    do { \
        fprintf(stderr, "[ERROR] %s:%d: " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__); \
    } while (0)

LOG_ERROR("Buffer overflow: size=%d, max=%d", size, max);
// [ERROR] audio.c:123: Buffer overflow: size=1024, max=512

This is the canonical example of a macro earning its place: a function cannot capture the caller’s file and line, because by the time it runs, that information is gone.

The ##__VA_ARGS__ needs explaining, because strict C99 requires at least one argument for the ..., and LOG_ERROR("failed") supplies none. Written plainly, the expansion would end in __FILE__, __LINE__, ), a dangling comma before the closing parenthesis. The ## prefix on __VA_ARGS__ is a GCC extension (adopted by Clang and most vendor compilers) that deletes the preceding comma when the variable arguments are empty.

C23 replaces the extension with __VA_OPT__(x), which expands to its own argument when __VA_ARGS__ is non-empty and to nothing when it is empty. The intent is now visible in the source rather than hidden in a punctuation trick:

#define LOG_ERROR(fmt, ...) \
    fprintf(stderr, "[ERROR] %s:%d: " fmt "\n", __FILE__, __LINE__ __VA_OPT__(,) __VA_ARGS__)

Read the tail as “a comma, but only if there is something after it.” Use __VA_OPT__ if you can rely on C23, and ##__VA_ARGS__ otherwise; the two are equivalent in this, the case that actually comes up.

NoteThe do { ... } while (0) wrapper

Wrapping a multi-statement macro body in do { ... } while (0) makes it a single statement that consumes a trailing semicolon correctly. Without it, an unbraced if (x) LOG_ERROR("...") ; else ... breaks, because the macro’s second statement terminates the if and orphans the else. The wrapper costs nothing (every compiler removes it) and is the standard idiom.

Include Guards vs. #pragma once

Because #include is literal text insertion, a header included twice in one translation unit defines everything twice, which is an error. Both solutions make the second inclusion a no-op.

// myheader.h  (traditional: guaranteed by the standard, portable everywhere)
#ifndef MYHEADER_H
#define MYHEADER_H

/* contents */

#endif  // MYHEADER_H

MYHEADER_H is an empty macro, and the guard is the purest illustration of what one is for. It has no value and is never expanded; it exists only so that the #ifndef on the line above has something to find. On the first inclusion the lookup fails, the guard is defined, and the contents are compiled. On every inclusion after that the lookup succeeds, the #ifndef is false, and the entire file between it and the #endif is discarded before the compiler ever sees it.

// myheader.h  (modern: non-standard, but supported by every major compiler)
#pragma once

/* contents */

#pragma once is shorter and immune to the guard-name collisions that bite in large projects, but it relies on the compiler correctly identifying “the same file,” which symlinks and network mounts can occasionally confuse. Include guards are guaranteed by the standard. Either is defensible; be consistent within a project.

Predefined Macros and Compile-Time Constants

What the implementation tells you about itself

Every conforming C implementation predefines a set of macros describing the file being compiled, the standard being followed, and the features available. Together with the limits headers, they are how portable C interrogates its own build environment. They fall into four groups.

Standard Predefined Macros

These are mandated by the standard and available everywhere:

__DATE__ Compilation date, "Mmm dd yyyy" Build stamps
__TIME__ Compilation time, "hh:mm:ss" Build stamps

__STDC_VERSION__ is the one you will actually branch on. Its values are 199901L for C99, 201112L for C11, 201710L for C17, and 202311L for C23:

#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 201112L
    #define ASSERT_STATIC(cond, msg) _Static_assert(cond, msg)
#else
    #define ASSERT_STATIC(cond, msg) /* unavailable before C11 */
#endif
Warning__func__ is not a macro

__func__ is a predefined identifier, declared as if by static const char __func__[] at the top of each function. It is not a preprocessor macro, so it will not participate in string-literal concatenation the way __FILE__ does. "in " __FILE__ compiles; "in " __func__ does not. Pass it as a %s argument instead.

Feature-Test Macros

C11 introduced a set of macros that a conforming implementation defines to say it lacks an otherwise-required feature. The inverted polarity is deliberate: absence is the exceptional case, so the macro is defined only when the feature is missing.

These matter most in freestanding environments, where a vendor legitimately omits large parts of the library:

    #include "portable_threads.h"   // fall back to a platform API
#else
    #include <threads.h>
#endif

Compiler and Target Identification

Not standardized, but universal in practice, and how real portable headers are written:

#if defined(__clang__)
    #define COMPILER_NAME "clang"
#elif defined(__GNUC__)                     // also defined by clang and icc
    #define COMPILER_NAME "gcc"
#elif defined(_MSC_VER)
    #define COMPILER_NAME "msvc"
#endif

#if __BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__
    /* little-endian path */
#endif

Order matters here: Clang defines __GNUC__ for compatibility, so a __GNUC__ test placed first will match Clang too. Check for the most specific compiler before the most general. Architecture and OS macros (__x86_64__, __aarch64__, __linux__, _WIN32) follow the same pattern, and the authoritative catalogue is the compiler’s own documentation.

Implementation Limits

Where the macros above describe the toolchain, the limits headers describe the types, as compile-time constant expressions usable in #if, array bounds, and static assertions.

Header Provides
<limits.h> CHAR_BIT, INT_MAX, INT_MIN, UINT_MAX, LONG_MAX, SIZE_MAX, …
<float.h> FLT_EPSILON, DBL_MAX, DBL_MIN, FLT_DIG, …
<stdint.h> INT16_MAX, UINT32_MAX, INTPTR_MAX, and the _C literal macros

CHAR_BIT is the one that surprises people: it is the number of bits in a byte, and the standard only guarantees it is at least 8. It is 8 on every platform you are likely to meet, but the constant exists because the standard declines to promise it.

Static Assertions

_Static_assert (C11; spelled static_assert in C23 and via <assert.h>) checks a constant expression at compile time and fails the build with your message if it does not hold. Paired with the macros above, it turns silent portability assumptions into loud build errors:

#include <assert.h>
#include <limits.h>
#include <stdint.h>

_Static_assert(CHAR_BIT == 8, "this code assumes 8-bit bytes");
_Static_assert(sizeof(int) >= 4, "16-bit int is not supported here");
_Static_assert(sizeof(Packet_t) == 32, "Packet_t must match the wire format");

That third assertion is the valuable one. Struct layout depends on padding rules you do not control, so a header describing a wire format or a hardware layout should assert its own size rather than trust that it came out right. The check costs nothing at run time and fails at the moment the mistake is introduced rather than in the field.

Note that _Static_assert succeeds precisely where #if cannot: it is a language construct, evaluated by the compiler, so it can see sizeof and real types. Its run-time counterpart, the assert() macro and the NDEBUG switch that disables it, is a library facility and is covered with the other headers.

Other Directives

The complete directive set is short. Most of it has now appeared:

Directive Purpose Covered in
#include Paste in another file, recursively #include
#define / #undef Create or remove a macro Macros
#if / #ifdef / #ifndef / #elif / #else / #endif Include or discard a region Conditional Compilation
#error Fail the build with a message below
#warning Warn without failing (universal extension; C23 standard) below
#pragma Implementation-specific instruction to the compiler below
#line Override __FILE__ and __LINE__ below

#error is the one you should reach for more than you do. A header that cannot work on a given configuration should say so at the top rather than emit forty lines of confusing type errors further down:

#if !defined(__STDC_VERSION__) || __STDC_VERSION__ < 201112L
    #error "this library requires C11 or later"
#endif

#pragma is a deliberate escape hatch: the standard reserves the directive and says nothing about what any particular pragma means, leaving each implementation free to define its own. #pragma once is the near-universal one; #pragma pack, #pragma GCC diagnostic, and vendor pragmas for placing objects in specific memory regions are the others you meet. An unrecognized pragma must be ignored, so a stray one is harmless (though -Wunknown-pragmas will point it out). C99 added _Pragma("..."), which does the same thing as an operator, so a pragma can be produced by a macro; a directive never can.

#line rewrites the values of __FILE__ and __LINE__ for the text that follows:

#line 42 "grammar.y"

Nobody writes this by hand. It exists for code generators, which is why the output of lex, yacc, and Bison is full of it: the generated .c file is what the compiler reads, but the error message should point at the .y file the human actually wrote.

#embed is C23’s newest addition and closes an old gap. Embedding a resource (a lookup table, a font, a firmware blob) previously meant running xxd -i in the build and committing or generating a large C array. Now the preprocessor does it:

static const unsigned char window_table[] = {
    #embed "hann_1024.bin"
};

The directive expands to a comma-separated list of byte values, so it works anywhere an initializer list does. The compiler can read the file directly rather than parsing a megabyte of decimal literals, which is dramatically faster than the tool it replaces. Support is arriving as C23 adoption proceeds; GCC 15 and Clang 19 have it.

Seeing What the Preprocessor Did

Every rule in this section is a rule about text, which means none of it has to be reasoned about in the abstract. When a macro does something unexpected, stop reading it and go look at what it produced.

Command Shows
cc -E audio.c The fully expanded translation unit on stdout
cc -E -P audio.c The same, without the line-marker noise
cc -dM -E - < /dev/null Every macro predefined for the current target
cc -dM -E audio.c Every macro defined at the end of that file, yours included
cc -save-temps -c audio.c A normal build that also leaves audio.i (preprocessed) behind
cc -H -c audio.c The include tree, one line per header, indented by depth

Three of these earn their keep regularly. -E -P piped through your pager answers “what did this macro actually become,” and it is the fastest way to settle any argument about expansion order. -dM -E - < /dev/null prints the several hundred macros your compiler defines before it reads a single line of your code, which is how you discover the right spelling of a target or feature macro instead of guessing. And -H answers “where on earth is this header coming from,” which after a -I ordering mistake is not a rhetorical question.

The output of -E is large and mostly headers. Search it rather than reading it, and remember that what you are looking at is exactly what the compiler was handed.

The Standard Library

The C standard library (libc) is not one library but a loose federation of headers, each covering a self-contained domain: string handling, memory, math, time, I/O, and more. A C program includes only the headers it needs, and a conforming compiler need not provide all of them. Two corners of it have already appeared in context: The Standard String Functions (<string.h>) and the allocation functions under Memory Management.

Unlike higher-level languages, C has no built-in I/O statements. Input and output are ordinary library functions, which is a direct expression of the “keep the language small” commitment.

NoteHosted vs. Freestanding

The C standard distinguishes two kinds of implementation. A hosted implementation assumes an operating system underneath it and provides the full standard library, including file I/O, wide characters, and (on POSIX systems) regular expressions. A freestanding implementation, the kind an embedded toolchain targeting a bare-metal device provides, is only required to supply a minimal subset: <stddef.h>, <stdint.h>, <stdbool.h>, <stdarg.h>, <float.h>, <limits.h>, and <iso646.h>. Everything else is present only if the vendor chose to implement or retarget it. You can detect which you have with __STDC_HOSTED__.

stdlib.h

General utilities

<stdlib.h> is the junk drawer of the standard library: allocation, conversion, sorting, randomness, and process control, related to each other only by having nowhere better to live. The allocation functions are covered under Memory Management; this section is everything else.

Converting Strings to Numbers

Text arrives as bytes and has to become numbers, and C offers two families for the job. Only one of them is usable.

The ato* family (atoi, atol, atof) is the obvious-looking choice and the wrong one. atoi("abc") returns 0. So does atoi("0"). The function has no way to report failure, because its return type is already fully occupied by legitimate values, so a parse error and a valid zero are indistinguishable. Worse, its behavior on a value too large for the target type is undefined, not merely wrong. For a string literal you wrote yourself this hardly matters; for anything read from a file, a socket, or a command line, it means the program cannot tell good input from bad.

The strto* family solves both problems, at the cost of a calling convention nobody enjoys:

long strtol(const char *restrict s, char **restrict endptr, int base);

The second parameter is the mechanism. strtol sets *endptr to the first character it did not consume, which tells you exactly how far the parse got. Combined with errno for range errors, that is enough to distinguish every outcome:

#include <errno.h>
#include <limits.h>
#include <stdlib.h>

bool parse_long(const char *text, long *out) {
    errno = 0;
    char *end;
    long value = strtol(text, &end, 10);

    if (end == text)            return false;   // no digits at all
    if (*end != '\0')           return false;   // trailing garbage: "12abc"
    if (errno == ERANGE)        return false;   // outside long's range
    *out = value;
    return true;
}

Four checks, and all four are load-bearing. end == text catches an empty or entirely non-numeric string. *end != '\0' catches a partial parse, which is the check most code omits and the reason "12abc" is so often silently accepted as 12. ERANGE catches overflow, and it is why errno must be zeroed first: the library only ever sets errno, it never clears it, so a stale value from an unrelated earlier failure would otherwise be read as this call’s result.

That this is the correct way to parse an integer, and that it takes ten lines, is a fair summary of C’s ergonomics. Essentially every C codebase of any size contains a wrapper very much like the one above, written independently, because the standard library provides the primitive and not the operation.

Function Returns Notes
strtol long The workhorse. base may be 0 to auto-detect 0x/0 prefixes.
strtoul unsigned long Accepts a leading - and silently negates. Check for it yourself.
strtoll long long C99.
strtoull unsigned long long C99.
strtod double Also parses inf and nan.
strtof float C99.

The base parameter deserves a note: passing 0 asks strtol to infer the base from the prefix, so "0x1f" reads as 31 and "017" reads as 15. That is occasionally what you want and frequently a surprise, particularly for zero-padded decimal input such as a timestamp field, where "08" becomes a parse error because 8 is not an octal digit. Pass 10 explicitly unless you mean otherwise.

Warningstrtoul and negative numbers

strtoul("-1", NULL, 10) does not fail. It parses the minus sign, converts, and negates the result under unsigned arithmetic, returning ULONG_MAX. If negative input is invalid in your context, scan for the - yourself before converting; the library will not do it for you.

Sorting and Searching

qsort and bsearch are the standard library’s two generic algorithms, and they are generic in the only way C knows how to be: through void * and an explicit element size, dispatching to a comparison function you supply. The mechanics of that were covered under void * and Function Pointers; what follows is the contract.

void qsort(void *base, size_t count, size_t size,
           int (*compare)(const void *, const void *));
void *bsearch(const void *key, void *base, size_t count, size_t size,
              int (*compare)(const void *, const void *));

The comparator returns a negative value if the first argument sorts before the second, zero if they are equivalent, and positive if it sorts after. Note that it is a sign that matters, not a magnitude, which invites the classic bug:

int compare_ints(const void *a, const void *b) {
    return *(const int *)a - *(const int *)b;      // WRONG
}

Subtraction produces the right sign only when it does not overflow. Comparing INT_MIN against a positive value overflows signed arithmetic, which is undefined behavior, and in practice yields a wrapped value whose sign is backwards. The array comes back subtly misordered, on inputs your tests probably do not contain. Compare instead:

int compare_ints(const void *a, const void *b) {
    int left = *(const int *)a, right = *(const int *)b;
    return (left > right) - (left < right);        // -1, 0, or 1
}

Two further properties are worth knowing. qsort is not required to be stable: equal elements may be reordered, and glibc’s implementation is a merge sort that usually is stable while musl’s smoothsort is not, so relying on it is a portability trap. And bsearch requires the array to be already sorted by the same comparator; give it a different ordering and it will not complain, it will simply fail to find elements that are present.

NoteThe cost of type erasure

qsort cannot inline your comparator. Every comparison is an indirect call through a function pointer, and every element swap is a byte-by-byte copy driven by a runtime size. C++’s std::sort takes the comparator as a template parameter, so it inlines, and typically runs two to three times faster on the same data for exactly that reason. This is the concrete price of C’s “generic means void *” answer, and it is the gap templates were invented to close.

Pseudo-Random Numbers

rand() returns a pseudo-random int between 0 and RAND_MAX inclusive, and srand(seed) sets the starting point. Without a call to srand, the sequence behaves as though seeded with 1, which is to say every run produces identical output. That is occasionally useful for reproducibility and usually a surprise.

srand((unsigned)time(NULL));    // conventional, and weak: predictable seed
int roll = rand() % 6 + 1;      // also biased; see below

Both lines of that snippet have problems, and they are worth naming because the idiom is everywhere.

rand() % n is biased. The range 0..RAND_MAX divides evenly into n buckets only when n divides RAND_MAX + 1. Otherwise the low-numbered outcomes get one extra representative each. With RAND_MAX at 32767 and n at 6 the skew is negligible, but as n approaches RAND_MAX it becomes severe: at n = 20000, values below 12768 are twice as likely as the rest. The fix is rejection sampling, discarding draws from the uneven tail rather than folding them in.

The low bits may be poor. Historic implementations used a linear congruential generator whose low-order bits have short periods; the notorious case is a version of rand() whose lowest bit simply alternated. rand() % 2 on such a system produces 0, 1, 0, 1. Modern libraries are better, but the standard guarantees nothing about quality, only about range.

The honest summary is that rand is adequate for a shuffled demo and nothing else. It is unsuitable for cryptography (use a platform CSPRNG: getrandom, arc4random, or BCryptGenRandom), and unsuitable for simulation work where the quality of the distribution is the whole point (use a Mersenne Twister or PCG implementation). C’s standard library simply does not offer a good generator, which is why serious numerical code always brings its own.

Returning from main is defined to be equivalent to calling exit with the returned value, so cleanup registered with atexit runs either way. Use EXIT_SUCCESS and EXIT_FAILURE rather than 0 and 1: they are the portable spellings, and on the handful of platforms where success is not 0 they are the only correct ones.

The distinction between exit and abort is about whether the program’s state is trustworthy. exit is an orderly shutdown, and it runs your handlers and flushes your buffers because it assumes those actions are safe. abort is for the case where an invariant has already been violated and the program cannot be trusted to clean up after itself; flushing a buffer that may be corrupt could write bad data over good. That is precisely why assert calls abort rather than exit, and why a crash dump from an aborted process is more useful than a tidy exit that hid the evidence.

Odds and Ends

abs, labs, and llabs compute integer absolute value; <math.h> supplies fabs for floating point. That there are four spellings of one operation is the “no overloading” commitment made visible, and <tgmath.h> is the later attempt to paper over it.

div and ldiv return a struct containing both quotient and remainder in one call. They exist for a historical reason worth knowing: before C99, the rounding direction of integer division with negative operands was implementation-defined, but div was always specified to truncate toward zero. C99 standardized / and % to truncate as well, which removed the original justification (see Integer Division and Modulo). What remains is the minor efficiency of getting both results from one division instruction, which compilers achieve on their own anyway.

getenv(name) returns a pointer to the value of an environment variable, or NULL if it is unset. The returned string belongs to the environment and must not be modified or freed, and a subsequent setenv or putenv may invalidate it, so copy it if you intend to keep it.

stdio.h

Input and Output

C has no I/O statements. Where Pascal has writeln and Python has print, C has a library function, and the entire mechanism is ordinary C that you could have written yourself. This is the “keep the language small” commitment paying off in an unexpected place: because I/O is not privileged, retargeting it for a platform the standard never imagined is a matter of supplying different functions, not a different compiler.

Streams and FILE

The abstraction is the stream: a sequence of bytes with a current position, which you read from or write to sequentially. A stream may be a file, a terminal, a pipe, or a socket, and the point of the abstraction is that the same functions work on all of them. That uniformity is the reason shell pipelines compose, and it is why the shell chapter can treat text as a universal interface.

A stream is represented by a FILE, and you never handle one directly. You hold a FILE *, obtained from fopen or one of the predefined streams, and pass it around; the structure behind it is opaque and its contents are the implementation’s business. Copying a FILE by value is meaningless and, on most implementations, actively harmful.

Three streams exist before main runs:

Stream Purpose Default destination Buffering
stdin Ordinary input Keyboard Line, if a terminal
stdout Ordinary output Screen Line if a terminal, otherwise full
stderr Diagnostics and errors Screen Unbuffered

The separation of stdout from stderr is a design decision, not an accident of history. Because they are distinct streams, a user can redirect one without the other: ./program > results.txt captures the data while error messages still reach the terminal. That only works if the program cooperates, which is the rule it implies. Diagnostics go to stderr, results go to stdout. A warning printed to stdout ends up interleaved into the data file, where it corrupts exactly the output someone was trying to collect.

Buffering

I/O is expensive, in the specific sense that reaching the operating system costs a system call and reaching a disk costs far more. So stdio accumulates bytes in a buffer and transfers them in batches. Three modes exist:

  • Fully buffered. Bytes accumulate until the buffer fills, then go out in one write. The default when a stream is not a terminal, which is to say whenever output is redirected to a file or a pipe.
  • Line buffered. The buffer is also flushed at each newline. The default for stdout when it is a terminal, because a human waiting for a prompt should not have to wait for 4096 bytes to accumulate.
  • Unbuffered. Every byte goes out immediately. The default for stderr, because an error message that is still sitting in a buffer when the program dies is an error message nobody reads.

Those defaults explain two symptoms that otherwise look like nonsense.

“My output vanished when the program crashed.” The printf calls succeeded; they wrote into a buffer. The crash bypassed the normal shutdown that would have flushed it, so the bytes died in memory. This is also why abort and _Exit lose pending output, and why a debugging printf placed just before a segfault so often fails to appear, sending you hunting in the wrong place. Adding fflush(stdout) after it, or using fprintf(stderr, ...) which is unbuffered anyway, restores your ability to trust what you see.

“My output is fine on screen but interleaved wrong in a file.” Run a program that writes to both streams and the terminal shows them in the order you expect. Redirect stdout to a file and its buffering silently switches from line to full, so its output now emerges in large batches while stderr continues to trickle out immediately. Nothing is ordered wrongly; the two streams simply have different latencies, and the relative order was never guaranteed.

fflush(stdout);                              // force this stream out now
fflush(NULL);                                // force out every output stream

setvbuf(stream, NULL, _IONBF, 0);            // unbuffered
setvbuf(stream, NULL, _IOLBF, BUFSIZ);       // line buffered
setvbuf(stream, buf,  _IOFBF, sizeof buf);   // fully buffered, your buffer

setvbuf must be called after opening the stream and before any other operation on it. Note that flushing an input stream is undefined behavior in ISO C, despite fflush(stdin) appearing in a great deal of tutorial code as a way to discard unread input; it happens to work on some implementations and does nothing or misbehaves on others.

It is ugly, and it is the only correct answer. This awkwardness is a direct consequence of formatting being a runtime protocol rather than a compile-time one; C++ variadic templates and Rust’s format! need no such macros because both know each argument’s type statically.

Formatted Input, and Why scanf Is a Trap

scanf is the mirror image of printf, and it is far more dangerous than its symmetry suggests. It appears in every introductory text and is nearly absent from production code, for reasons worth enumerating.

WarningFour ways scanf will hurt you

%s has no bound. scanf("%s", buf) reads until whitespace with no regard for the size of buf. It is gets wearing a disguise, and it is the same buffer overflow. A width is mandatory: scanf("%9s", buf) for a 10-byte buffer, with the off-by-one (the width excludes the terminator) left as an exercise you will get wrong at least once.

Failure leaves the input in place. On a conversion mismatch, scanf stops at the offending character and does not consume it. The classic consequence is an input-validation loop that spins forever: the read fails, nothing is consumed, the loop retries, and the same character fails again at full speed.

The return value is a count, not a status. It reports how many conversions succeeded, so a three-specifier format returning 2 means partial success with one variable left untouched, still holding whatever garbage it held before. Code that ignores the return value, which is most code, cannot distinguish this from success.

Whitespace handling is not what it looks like. Most specifiers skip leading whitespace; %c and %[ do not. A literal space in the format matches any amount of whitespace including none, and a \n in a format string does not mean “expect a newline,” it means the same as a space. Mixing scanf and getchar reliably leaves a stray newline behind to ambush the next read.

The robust alternative is to separate reading from parsing: pull a whole line with fgets, then convert it with strtol or sscanf, where a failure costs you nothing because the input is already safely in your buffer.

char line[128];
if (fgets(line, sizeof line, stdin) != NULL) {
    long value;
    if (parse_long_trimmed(line, &value)) {
        /* ... */
    }
}

sscanf on a string you already hold is genuinely useful and carries none of the stream-state hazards, since a failed parse leaves your buffer untouched and re-readable. It is scanf reading directly from a stream that causes the trouble.

fgets has an awkward contract worth stating plainly. It stops at a newline, at size - 1 characters, or at end of input, whichever comes first, and it keeps the newline when one was read. So the presence of a trailing \n is how you tell a complete line from a truncated one, and stripping it is a step every caller performs:

line[strcspn(line, "\n")] = '\0';   // truncate at the newline if present

gets deserves its own note, as an artifact. It read a line into a buffer with no size parameter at all, making overflow not a risk but a certainty for any input longer than the buffer. It was the vector for the 1988 Morris worm, was formally deprecated in C99, and was removed outright in C11. It is the only function ever deleted from the C standard library, and the reason is instructive: the interface could not be fixed, because there is no way to bound a write when the caller never says how much room exists. fgets is the replacement.

Both return the number of elements transferred, not bytes, so a short read is < count and the reason (end of input or a genuine error) has to be established separately. A complete read of a file, with every failure handled:

char *read_file(const char *path, size_t *out_size) {
    FILE *file = fopen(path, "rb");
    if (file == NULL) return NULL;

    if (fseek(file, 0, SEEK_END) != 0) { fclose(file); return NULL; }
    long length = ftell(file);
    if (length < 0)                    { fclose(file); return NULL; }
    rewind(file);

    char *buffer = malloc((size_t)length + 1);
    if (buffer == NULL)                { fclose(file); return NULL; }

    size_t got = fread(buffer, 1, (size_t)length, file);
    if (got != (size_t)length && ferror(file)) {
        free(buffer);
        fclose(file);
        return NULL;
    }
    buffer[got] = '\0';
    fclose(file);
    *out_size = got;
    return buffer;
}

The cleanup on every branch is what C error handling looks like without destructors or defer, and the repetition is why goto for cleanup is a genuinely idiomatic pattern once a function acquires more than one resource.

Note that fread returning less than requested is not treated as an error by itself: the seek-to-end technique gives a length that may not match what a text-mode read actually produces, so the check is ferror, not the count. Positioning within a file:

Errors, feof, and errno

Stream functions signal failure by return value, and the stream itself carries two sticky flags reporting what happened.

Function Reports

Warningwhile (!feof(file)) is always wrong

feof does not predict that the next read will hit the end; it reports that a previous read already did. The flag is set by the failing read, not before it.

So the loop runs one extra time. The final fgets or fread fails, sets the flag, and leaves the buffer untouched, but the body has already been entered and proceeds to process whatever the buffer held from the previous iteration. The symptom is a duplicated last line, which looks like an off-by-one somewhere else entirely.

Test the read instead, which reports success and end-of-input in one value:

while (fgets(line, sizeof line, file) != NULL) {
    /* ... */
}
if (ferror(file)) { /* a real error, not merely end of input */ }

feof and ferror earn their keep after the loop, distinguishing an orderly end from a failure, which is exactly the question the loop condition could not answer.

errno is a global (strictly, a thread-local int lvalue) set by library functions when they fail. Its contract has two halves that are easy to get wrong: functions may set it on failure but are never required to clear it on success, and a successful call is permitted to modify it as a side effect. So errno is meaningful only immediately after a call you have already determined failed. If you must test it without a failure indication, as with strtol above, set it to 0 first.

FILE *file = fopen(path, "r");
if (file == NULL) {
    perror(path);                                   // "config.txt: No such file or directory"
    fprintf(stderr, "detail: %s\n", strerror(errno));
}

On an embedded target there is no operating system to accept a write, so printf cannot work as shipped. Toolchains resolve this by leaving a small set of low-level hooks (commonly _write, _read, and friends) for you to implement, typically routing output to a UART. The printf machinery above it, format parsing and all, is ordinary C and works unchanged, which is often more code than a small microcontroller wants; hence the reduced-functionality variants (iprintf, tinyprintf) that omit floating-point support. string.h

<string.h> holds two families that look similar and mean different things. The str* functions operate on null-terminated strings and are catalogued under The Standard String Functions; the mem* functions operate on raw bytes, take an explicit length, and attach no meaning to a zero byte. Use str* for text and mem* for everything else, including text whose length you already know.

memcpy vs. memmove

Both copy n bytes from a source to a destination. The difference is a single qualifier in the prototype, and it is the entire story:

void *memcpy(void *restrict dest, const void *restrict src, size_t n);
void *memmove(void *dest, const void *src, size_t n);

memcpy’s parameters are restrict-qualified, which is a promise the caller makes: these regions do not overlap. Having been given that promise, the implementation is free to copy in whatever order and width the hardware prefers, backwards, in 32-byte vector chunks, or as several interleaved streams, because with disjoint regions no order is observable. That freedom is the whole reason memcpy is fast. memmove makes no such demand and behaves as if the source were first copied to a temporary buffer, which costs it either a direction check or a genuine intermediate copy.

Passing overlapping regions to memcpy is undefined behavior, not “probably fine.” It is worth being precise about why this matters in practice: overlapping copies frequently do work, for years, because a given implementation happened to copy forward and the overlap happened to run in the forgiving direction. Then a compiler upgrade selects a wider vector instruction, or the buffer’s alignment shifts by one, and the copy begins overwriting source bytes before reading them. The bug is in code that has not been touched in a decade. When regions may overlap, as when shifting elements within one array, memmove is not the cautious choice; it is the only correct one. See restrict for the general mechanism.

memset

memset(ptr, value, n) fills n bytes with value, and the operative word is bytes. value is an int for historical reasons, but it is converted to unsigned char, so only its low 8 bits survive.

This is the source of a persistent misunderstanding:

int values[10];
memset(values, 0, sizeof values);    // fine: all zeros
memset(values, 1, sizeof values);    // NOT ten 1s

The second call writes 0x01 into all 40 bytes, so each int becomes 0x01010101, or 16843009. Zero is the only value for which the byte-wise and element-wise interpretations agree, which is why memset(p, 0, n) is idiomatic and why memset with any other value should make you look twice. To fill an array with a repeated non-zero value, write a loop; the compiler will vectorize it.

NoteZeroing is not always erasing

Two further caveats. Zeroing a pointer with memset produces a null pointer on every real implementation, but the standard only guarantees that for assignment from NULL, not for all-bits-zero; the same applies to floating-point zero, which is all-bits-zero in IEEE 754 but not by language rule.

More practically, memset is a poor way to scrub a secret. If nothing reads the buffer afterward, the write is dead and the optimizer is entitled to delete it, which it does. memset_s (C11 Annex K, optional) and explicit_bzero (BSD, glibc) exist precisely because the obvious code does not survive optimization.

The Rest of the Family

memcmp(a, b, n) compares byte sequences and returns an ordering, negative, zero, or positive, like strcmp. Its one trap is comparing structs:

if (memcmp(&left, &right, sizeof left) == 0)   // unreliable

Structs contain padding, and padding bytes hold whatever they held. Two structs with identical members can differ in their padding and compare unequal; conversely, this is why memcmp on structs is undefined-ish in practice even when it appears to work. Compare member by member. memcmp is also unsuitable for comparing secrets, since it stops at the first difference and its timing therefore leaks how many bytes matched.

memchr(ptr, value, n) finds the first occurrence of a byte within a bounded region, returning a pointer to it or NULL. It is the tool for scanning a buffer that may not be null-terminated, where strchr would run off the end.

NoteThese are not ordinary functions

The str* and mem* families are the most heavily optimized code in any libc, typically hand-written in assembly per microarchitecture and selected at load time. Compilers go further and treat them as intrinsics: a memcpy of a known small size usually compiles to a couple of move instructions with no call at all, and a hand-written byte-copy loop is often recognized and turned back into a memcpy call. Writing your own to save the call overhead almost always makes things slower.

<ctype.h> and the Signed char Trap

The classification functions take an int, and the standard defines their behavior only for values representable as unsigned char and for EOF. Everything else is undefined.

That is a problem, because plain char may be signed, and on a signed-char platform any byte above 127 is negative:

char c = text[i];
if (isalpha(c)) { ... }               // undefined for bytes >= 0x80
if (isalpha((unsigned char)c)) { ... } // correct

Typical implementations index a lookup table with the argument, so a negative value reads memory before the start of the table. Usually it returns a plausible-looking wrong answer; occasionally it faults. The cast is mandatory whenever the argument came from a char, and it is unnecessary only when it came from getchar, which already returns a properly widened value or EOF.

These functions are also locale-dependent: isalpha may accept accented characters under one locale and reject them under the default "C" locale. For parsing anything with a fixed grammar, a wire format, a config file, an identifier, that variability is a hazard rather than a feature, which is why parsers often test ranges explicitly instead.

<assert.h> and NDEBUG

assert(expression) evaluates its argument and, if it is false, prints the expression, file, and line to stderr and calls abort. It is the runtime counterpart of _Static_assert, and the division of labor is clean: _Static_assert checks what the compiler can know and fails the build; assert checks what only the running program can know and fails the run.

The critical property is that assert is a macro that vanishes. If NDEBUG is defined when <assert.h> is included, assert(x) expands to nothing at all:

assert(buffer_size > 0);              // gone in release builds
assert(initialize_device() == 0);     // the call itself is gone too

The second line is the bug this invites, and it is common enough to be worth stating flatly: never put an expression with side effects inside an assert. Under NDEBUG the device is never initialized, and the failure appears only in release builds, which is the worst possible place for a behavioral difference to hide. Assign the result to a variable and assert on that.

NDEBUG is also the reason assertions are not a substitute for error handling. An assertion documents a condition you believe to be impossible, a violated internal invariant, a contract the caller broke. Conditions that can genuinely occur at runtime, a missing file, a malformed packet, a failed allocation, must be handled with real code, because in the build that ships the assertion is not there.

<math.h> and the Missing Library

On most Unix systems the math functions live in a separate library from the rest of libc, so using them requires an explicit link flag:

cc program.c -o program -lm      # without -lm: "undefined reference to `sqrt'"

The split is historical, dating to when floating-point support was optional and expensive to carry. It persists as a small trap for anyone who assumes that including a standard header is sufficient, and it is a useful illustration of the difference between the header (which declares) and the library (which defines); see The Translation Unit. Note that glibc 2.34 and later fold libm into libc, so the flag is increasingly a no-op on Linux while remaining necessary elsewhere.

<math.h> also displays C’s lack of overloading more starkly than any other header. Absolute value is abs, labs, llabs, fabs, fabsf, and fabsl depending on the argument type, and the same fan-out applies to sqrt/sqrtf/sqrtl and the rest. Calling the double version on a float silently promotes, computes at double precision, and narrows back, which is correct but can be needlessly slow on hardware with a single-precision unit. <tgmath.h> layers type-generic macros over the whole set so that sqrt(x) dispatches on the type of x; it is built on _Generic, and it is the closest thing C has to overloading.

Compilation and the Build

The build converts a project’s source files into an artifact you can run or load. For a hosted program that is an executable; for an embedded target it is typically a HEX or ELF image flashed into non-volatile memory, accompanied by a map file showing exactly where every function and object landed.

The Translation Unit

The unit of compilation in C is the translation unit: one .c file after the preprocessor has finished with it, headers and all. The compiler sees exactly one at a time and knows nothing of the others, which explains nearly everything about how C projects are organized.

Because of that isolation, a call to a function defined elsewhere is compiled as an unresolved reference, and it is the linker that eventually connects it. A declaration is how you promise the compiler that the definition exists somewhere; get the declaration wrong and the compiler cannot tell, because it has no access to the definition to compare against. This is precisely what headers exist to prevent: both the caller and the definition include the same declaration, so any mismatch becomes a compile error rather than a runtime mystery.

Declarations vs. Definitions Across Files

The mechanics of extern and the one-definition rule were covered under extern and the Definition/Declaration Split. What follows is the discipline that falls out of them, and the link errors that appear when it is violated.

What Goes Where

A header may be included by any number of translation units, so anything it contains will exist in all of them. That single fact determines the entire split:

Belongs in a header (.h) Belongs in exactly one source file (.c)
Function declarations (prototypes) Function definitions (bodies)
extern declarations of globals Global variable definitions
struct, union, and enum definitions static (file-local) variables and functions
typedefs Anything holding mutable state
Macros
static inline function definitions

The rule underneath the table: a header must not allocate storage or define an external function. Both would be duplicated in every including translation unit, and the linker would reject the copies.

static inline is the exception that proves it. Marking a small function static inline in a header gives each translation unit its own private copy, which is legal precisely because static means the copies never collide at link time. That is how a header can offer a real function body without violating the rule, and it is the C idiom for what C++ would express with an inline member function.

Tentative Definitions

C has a third category between declaration and definition, and it is the reason some questionable code has linked successfully for decades.

int counter;          // at file scope: a *tentative definition*
int counter = 0;      // a definition
extern int counter;   // a declaration

A file-scope declaration with no initializer and no extern is a tentative definition. If the translation unit never provides a real definition, the tentative one becomes a definition initialized to zero. That much is standard.

What was never standard, but was universal, is what happened across multiple translation units. Traditional Unix linkers placed such symbols in a common block and merged all the tentative definitions of a name into one object, in the manner of Fortran’s COMMON. So putting int counter; in a header, included by ten files, produced ten tentative definitions that the linker silently merged into a single variable. The code was ill-formed and worked anyway.

Warning-fno-common broke a lot of old code

GCC 10 (2020) changed the default from -fcommon to -fno-common, and Clang followed. Tentative definitions now go in the data section like ordinary definitions, so those ten copies collide and the link fails with multiple definition of 'counter'.

This is the single most common failure when building an older codebase with a modern compiler, and the error is misleading: it points at code that has not changed and that genuinely used to be fine. The fix is the discipline above, extern int counter; in the header and one real definition in a .c file, not -fcommon, which merely defers the problem.

Reading Link Errors

Linker errors read differently from compiler errors, and knowing which one you are looking at is half the diagnosis. A compiler error cites a source file and line, because the compiler has the source in front of it. A linker error cites object files and symbol names, because by then the source is gone and all that remains is a table of names that were promised and names that were provided.

There are essentially two failures, and they are opposites:

Error Means Usual causes
undefined reference to 'foo' Nobody defined it The .c was not compiled or not passed to the link; a library is missing (-lm, -lpthread); the name is misspelled; C++ calling C without extern "C".
multiple definition of 'foo' Too many things defined it A definition (not a declaration) in a header; a missing static on something meant to be file-local; tentative definitions under -fno-common.

The -lm case from <math.h> is the canonical undefined reference: the header supplied a declaration, so the compiler was satisfied, and no definition ever arrived because the library was not linked. That split is the whole point. The header promises; the library delivers. A missing header is a compile error, a missing library is a link error, and confusing the two sends you editing the wrong file.

NoteWhy a wrong declaration links fine and then corrupts

C symbols carry no type information. The linker matches sample_rate to sample_rate by name alone, with no record of whether either side thought it was an int or a double.

So if one file declares extern int sample_rate; while another defines double sample_rate = 48000.0;, everything compiles, everything links, and the program reads the first four bytes of a double as an integer. C++ avoids this by mangling type information into the symbol name, which turns the mismatch into a link error. In C the only defense is the discipline of putting the declaration in a header that the defining file also includes, so the compiler sees both and can object.

Compiler Attributes

__attribute__((...))

__attribute__ is not a preprocessor directive. It is a compiler extension, originating in GCC and supported by Clang and most vendor toolchains, that attaches metadata to a declaration for the compiler to act on. The preprocessor passes it through untouched.

Declaring Attributes of Functions:

…you can use function attributes to specify certain function properties that may help the compiler optimize calls or check code more carefully for correctness. For example, you can use attributes to specify that a function never returns (noreturn), returns a value depending only on the values of its arguments (const), or has printf-style arguments (format).

The doubled parentheses are part of the syntax, distinguishing an attribute from a function call:

__attribute__((attribute-list))

A few that earn their keep in ordinary hosted code:

Attribute Purpose
noreturn Function never returns; improves diagnostics and codegen.
format(printf, m, n) Type-check a wrapper’s format string against its arguments.
warn_unused_result Warn when a caller ignores the return value.
deprecated("msg") Warn at each use, with a migration note.
aligned(N) Force an object’s alignment.
packed Remove struct padding. Slows access; can fault on strict targets.

The format attribute is the underrated one: it makes a printf wrapper as type-safe as printf itself.

__attribute__((format(printf, 2, 3)))
void log_message(LogLevel_t level, const char *fmt, ...);

C23 finally standardizes an attribute syntax of its own, [[noreturn]] and [[deprecated]], borrowed from C++.

NoteMnemonic: no hash, not preprocessor

Preprocessor directives start with #. __attribute__ does not, so it is not a preprocessor feature; it is a note from you to the compiler saying “treat this declaration specially.” Attributes describing target-specific memory placement and interrupt handlers are covered in the Applied DSP notes.

Optimization Levels

Optimization lets the compiler restructure code for speed or size, at the cost of build time and debuggability.

  • -O0: no optimization. Code flow matches source lines exactly, which is what you want under a debugger.
  • -O1: modest optimization, still reasonably debuggable.
  • -O2: the usual release setting; aggressive but standard-conforming.
  • -O3: adds aggressive inlining and vectorization. Not always faster; measure.
  • -Os: optimize for size, which matters when program memory is the binding constraint.
  • -Og: optimize but preserve debuggability. The right default during development.
WarningOptimization exposes undefined behavior

A bug that hides at -O0 and appears at -O2 is almost always undefined behavior rather than a compiler bug. The optimizer assumes UB never happens and transforms code on that basis, so a latent violation becomes a visible failure only once optimization is enabled. Build with -Wall -Wextra, and run the sanitizers (-fsanitize=address,undefined) before blaming the compiler.

The volatile Keyword

Optimization is also the context in which the third type qualifier finally makes sense. Every transformation above rests on an assumption: that the compiler can see every way a value might change. When that assumption is false, the optimizer will happily produce a program that is faster and wrong.

volatile withdraws the assumption. It tells the compiler that an object may change outside the control of the program’s visible flow, so every read and write appearing in the source must actually occur in the object code, in the order written. The optimizer may no longer cache the value in a register, hoist a load out of a loop, or delete a store it believes no one observes.

// Without volatile, the compiler may load *status once, hoist it out of the
// loop, and generate an infinite loop that never re-reads the address.
volatile uint16_t *status = (volatile uint16_t *)0xFF00;
while (*status == 0) { /* wait for the hardware to set the flag */ }

The cast is required: assigning a bare integer to a pointer is a constraint violation that modern compilers reject outright. Note also the fixed-width uint16_t rather than int, since a hardware register has an exact width.

Three situations genuinely need volatile: memory-mapped hardware registers, variables shared between an interrupt handler and the main flow, and local variables that must survive a longjmp. Note also that const and volatile are not opposites and can coexist. const volatile describes a read-only hardware register: your code must not write it, yet the hardware may change it underneath you.

Warningvolatile is not an atomicity or threading primitive

volatile guarantees that accesses happen, and that they are not reordered with respect to other volatile accesses. It guarantees nothing about atomicity, and nothing about ordering relative to ordinary memory operations on other cores. A volatile increment is still a read-modify-write that an interrupt can tear in the middle. For concurrency, use C11’s <stdatomic.h> or the platform’s synchronization primitives. C++ makes the same point rather more loudly, having deprecated most compound volatile operations in C++20.

The Toolchain

The Pieces

gcc is not a compiler. It is a driver: a program that decides which real tools to run, in what order, with which arguments, based on the file extensions and flags you gave it. Understanding that removes most of the mystery from a build, because it explains how one command can preprocess, compile, assemble, and link, and why the same command does only some of those when you add -c.

Tool Does
cc, gcc, clang The driver. Runs the tools below and passes files between them.
cpp The preprocessor. Produces a translation unit.
cc1 The compiler proper. C to assembly. Rarely invoked by hand.
as The assembler. Assembly to an object file (.o).
ld The linker. Object files and libraries to an executable.
ar The archiver. Bundles .o files into a static library (.a).

The driver relationship has a practical consequence worth knowing: to pass an option to the linker rather than the compiler, you must route it through the driver with -Wl,. So -Wl,-rpath,/opt/lib hands -rpath /opt/lib to ld. The same applies to -Wa, for the assembler and -Wp, for the preprocessor. When a build fails with an unrecognized option, this is usually why: the flag was meant for a tool the driver never gave it to.

Flags Worth Knowing

Flag Purpose

-o <file> Name the output.
-I <dir> Add a directory to the header search path.
-L <dir> Add a directory to the library search path.
-l<name> Link lib<name>. -lm finds libm.so or libm.a.

-Wall is badly named: it does not enable all warnings, only an uncontroversial subset. -Wextra adds another useful tier, and even together they are not exhaustive. Treat -Wall -Wextra as the floor for any code you intend to keep, and read the output; in a language where so much is undefined rather than diagnosed, the warnings are a substantial fraction of the safety net that exists.

Note-Werror belongs in CI, not on your desk

-Werror turns every warning into an error. That is exactly right for a continuous integration job, where it prevents warnings from accumulating until nobody reads them.

It is usually wrong for local development, where it stops a build over an unused variable in code you are still writing, and where a compiler upgrade that adds a new warning can block work that has nothing to do with the change you were making. Keep it in CI, out of the default local build.

Inspecting the Output

A build produces binaries, and binaries are inspectable. These tools answer questions that guessing does not.

Tool Answers
nm What symbols does this object define, and which does it still need?
objdump -d What instructions did the compiler actually generate?
readelf -h What are this binary’s headers, sections, and dependencies?
size How large are the text, data, and BSS segments?
strings What literal text is embedded in this file?
ldd Which shared libraries will this need at launch, and are they found?

nm is the one that turns an undefined reference from a mystery into a two-minute diagnosis. Symbols are printed with a type letter: T for a definition in the text segment, D for initialized data, B for BSS, and U for undefined, meaning this object needs the symbol but does not provide it.

$ nm main.o | grep filter
                 U apply_filter          # main.o needs it
$ nm filter.o | grep filter
0000000000000000 T apply_filter          # filter.o provides it

If the second command comes back empty, the definition genuinely is not there and you have a source problem. If it shows T as above, the symbol exists and the link is simply not being told about filter.o, which is a build problem. Two commands, and you know which half of the system to go fix.

Static and Dynamic Linking

The last step has two modes, and the choice affects deployment more than it affects the code.

Static (.a) Dynamic (.so, .dll, .dylib)
Resolved at Link time Load time
Library code lives Inside your binary In a shared file on the system
Binary size Larger Smaller
Memory, many copies One copy per process One copy shared by all processes
Updating the library Requires relinking your program Takes effect on next launch
Missing at runtime Cannot happen Fails at launch, not at build

Static linking copies the object code you use into your executable, so the result is self-contained. Nothing can go missing, nothing can change underneath it, and it starts marginally faster because there is no symbol resolution at load. The costs are size and the fact that a security fix in a library requires rebuilding and redistributing every program that embedded it.

Dynamic linking resolves references when the program launches. One copy of libc serves every process on the machine, a patched library benefits everything immediately, and your binary stays small. The cost is that the dependency is now an environmental assumption: the notorious failure is a program that built cleanly and dies at launch with error while loading shared libraries, because the .so is absent, is the wrong version, or is somewhere the loader does not search. ldd ./program shows exactly what will be looked for and what resolves.

This tradeoff is why containers frequently ship statically linked binaries: the container is the deployment unit, and a self-contained executable removes an entire category of “works on my machine.” It is also why system tools are usually dynamically linked: a libc fix should not require rebuilding the operating system.

NoteCross-compilation

When the machine building the code is not the machine running it, the entire toolchain above is replaced by a target-prefixed version: arm-none-eabi-gcc, arm-none-eabi-ld, and so on, paired with a sysroot supplying the target’s headers and libraries. The concepts do not change, only the names. The C++ chapter’s treatment covers the bare-metal case in detail, and it applies to C unchanged.

Debugging and Diagnosis

Four tools, in the order you should reach for them

When a C program misbehaves, there are four tiers of tool available, and they are genuinely ordered: each catches things the previous one cannot, and costs more to use. Working down the list in order will find most bugs faster than starting at the bottom.

  1. Compiler warnings. Free, instant, and catch a surprising amount. -Wall -Wextra.
  2. Static analysis. Finds suspicious patterns without running the code.
  3. Sanitizers. Instrument the binary to catch memory and UB errors as they happen.
  4. The debugger. Inspect a running program, or a corpse.

Building for Debuggability

Two flags matter before any of this works.

-g emits debug information: the mapping from machine addresses back to source lines, variable names, and types. Without it a debugger can show you registers and addresses and essentially nothing else. It does not slow the program down; it only makes the binary larger, and it can be stripped later.

-Og is the optimization level designed to coexist with -g. This matters more than it sounds. At -O2 the optimizer inlines functions, reorders statements, and keeps variables in registers that it reuses for other purposes, so the debugger reports <optimized out> for a variable you are staring at in the source, and single-stepping jumps backwards through lines in an order that looks deranged. Neither is a malfunction; the machine code genuinely no longer corresponds to the source in the way you assumed. This is the most common reason people conclude the debugger is broken and go back to printf.

cc -g -Og -Wall -Wextra -o program main.c

The Dozen Commands That Matter

GDB and LLDB have hundreds of commands and you need roughly twelve. LLDB accepts most GDB spellings, so the differences below rarely bite.

Command Does
run (r) Start the program.
break f (b) Break at function f, or break file.c:42 at a line.
continue (c) Resume until the next breakpoint.
next (n) Execute one line, stepping over calls.
step (s) Execute one line, stepping into calls.
finish Run until the current function returns.
backtrace (bt) The call stack. The first thing to type after a crash.
frame N (f) Select a stack frame to inspect.

A Worked Session

A program crashes. Here is the whole loop, start to finish:

typedef struct Node { int value; struct Node *next; } Node;

int sum_list(Node *head) {
    int total = 0;
    for (Node *n = head; n->next != NULL; n = n->next) {   // bug is here
        total += n->value;
    }
    return total;
}
$ cc -g -Og -o list list.c && ./list
Segmentation fault (core dumped)

$ gdb ./list
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000555555555181 in sum_list (head=0x5555555592a0) at list.c:5
5           for (Node *n = head; n->next != NULL; n = n->next) {

(gdb) bt
#0  sum_list (head=0x5555555592a0) at list.c:5
#1  0x00005555555551d4 in main () at list.c:16

(gdb) print n
$1 = (Node *) 0x0

(gdb) print n->next
Cannot access memory at address 0x8

The diagnosis takes three commands. bt establishes that the crash is in sum_list, called from main, rather than somewhere unexpected. print n shows the loop variable is NULL. print n->next confirms it by failing at address 0x8, which is the offset of next within the struct, added to a null base.

The bug: the loop tests n->next != NULL but dereferences n, so on the final iteration it advances n to NULL and then tests NULL->next. The condition should be n != NULL. Note that the sum was also silently missing the last element before it crashed, which is the quieter half of the same mistake.

When Not to Reach for the Debugger

The debugger is superb at one thing: showing you the complete state of a program at a single instant. It follows that it is weak wherever the question is not about a single instant, and being honest about that is what makes it worth using when it does fit.

printf is better for patterns over time. If a value drifts wrong over a thousand iterations, or two events race in an order you cannot predict, or a bug appears once in fifty runs, stepping is hopeless; you need a log you can scan, diff, or graph. This is not a lesser technique, it is the right tool for a different question. Two cautions: buffered output can be lost when the program crashes, so flush or use stderr (see Buffering), and instrumentation changes timing, which can move or hide a race.

Sanitizers are better for memory bugs, and it is not close. A use-after-free under a debugger gives you a crash at the point of use, and finding who freed it is manual archaeology. AddressSanitizer prints both, with stack traces:

cc -g -fsanitize=address,undefined -o program main.c

It reports the access, the allocation that owns the memory, and the free that released it. UndefinedBehaviorSanitizer catches signed overflow, misaligned access, and shifts past the width of a type, which a debugger structurally cannot show you, because by then the optimizer has already reasoned on the assumption they never happen. The runtime cost is roughly 2x for ASan, which is fine for a test suite and the reason you would not ship it.

Valgrind answers a related question without recompiling, and finds leaks that ASan will not report unless asked. Reach for it when you cannot rebuild, or when you want a leak report from an existing binary.

Where the debugger genuinely wins. Inspecting a core dump from a crash you cannot reproduce (gdb ./program core). Answering “what is the state right now” when a program is wedged. Stepping through unfamiliar code to learn what it does, which is a reading tool rather than a debugging one and is arguably its most underrated use. And catching the moment a value changes, via watch.

The practical summary is that a memory bug should go to a sanitizer first, a timing or pattern bug to logging, and a “how did this get into this state” bug to the debugger. Not using the debugger much is a reasonable outcome of that ordering rather than a gap; it is worth knowing precisely so you recognize the third case when you hit it.

Static Analysis

Between compiler warnings and running the code sits static analysis: tools that examine source without executing it, applying checks too expensive or too opinionated for the compiler to run by default.

clang-tidy covers bug-prone patterns, portability, and style, and is configurable per project. cppcheck is standalone, easy to run, and finds buffer overruns, null dereferences, and resource leaks by whole-program reasoning. Both produce false positives, which is the nature of the technique: they must be conservative where the compiler must be certain. Run them in CI, tune the check set once, and treat the output as a prompt to look rather than an accusation.

Build orchestration itself belongs to a separate tool. Make tracks which outputs depend on which inputs and rebuilds only what changed, and it gets full treatment in the Makefile chapter.

Undefined Behavior and Common Pitfalls

C gives you enormous power and freedom, and with it the responsibility to avoid a catalogue of subtle bugs. Most of what follows traces back to one root cause, so it is worth naming that first.

Undefined Behavior

The worst kind of bug

Some operations have undefined behavior: the standard places no requirements whatsoever on what happens. The program might work, crash, corrupt data silently, or behave differently under a different optimization level. Crucially, UB is not “the machine does whatever is natural.” The compiler is entitled to assume undefined behavior never occurs and to optimize on that assumption, which means a single UB violation can delete a bounds check hundreds of lines away.

Common sources:

  • Signed integer overflow. INT_MAX + 1 is undefined. Unsigned overflow, by contrast, is well defined and wraps.
  • Null pointer dereference. *ptr where ptr == NULL.
  • Use after free, and dereferencing any dangling pointer.
  • Out-of-bounds access. arr[100] where arr has 50 elements.
  • Reading an uninitialized variable.
  • Strict aliasing violations. Accessing an object through a pointer to an incompatible type.
  • Modifying a string literal.
  • Shifting by more than the operand’s width, or shifting a negative value left.
WarningThe optimizer is not being stupid

When a program works at -O0 and breaks at -O2, the instinct is to blame the compiler. It is nearly always UB. The optimizer reasoned from an assumption your code violated, and the result is a transformation that looks insane and is entirely legal. Build with -Wall -Wextra and run -fsanitize=undefined; UBSan catches most of the list above at run time and prints exactly what was violated.

Integer Promotion and Implicit Conversions

Before arithmetic, any integer type narrower than int is promoted to int (the integer promotions). The arithmetic therefore happens at int width, not at the operands’ declared width, and whether that saves you or burns you depends entirely on how wide int is on the target.

int16_t a = 30000;
int16_t b = 30000;

int32_t result = a + b;
// 32-bit int: a and b promote to int, sum is 60000, correct.
// 16-bit int: promotion buys no headroom, so the sum overflows before assignment.

Casting one operand to a type at least as wide as the result forces the arithmetic to happen at that width:

int32_t result = (int32_t)a + b;   // b converts too; the addition is 32-bit everywhere

The related trap is signed/unsigned comparison. When one operand is signed and the other unsigned of the same rank, the signed value converts to unsigned, so -1 < 1u is false. This is why for (size_t i = n - 1; i >= 0; i--) never terminates: an unsigned value is always >= 0. Enable -Wsign-compare (included in -Wextra).

Operator Precedence Surprises

if (flags & MASK == ENABLED)     // parsed as: flags & (MASK == ENABLED)
if ((flags & MASK) == ENABLED)   // what you meant

Bitwise operators bind more loosely than comparison operators, a decision Ritchie later called a mistake, retained because code already depended on it. The same ordering catches shifts: 1 << n + 1 shifts by n + 1.

Neither case produces a warning by default, because both are perfectly legal expressions that simply mean something other than what you wrote. Parenthesize any expression mixing bitwise operators with comparison or arithmetic, and consult the precedence table when in doubt.

Assignment vs. Comparison

if (x = 5)   // assignment, not comparison; always true
if (x == 5)  // comparison

Modern compilers warn about this when the assignment is not parenthesized, so -Wall catches most instances. Where an assignment in a condition is genuinely intended, wrap it in extra parentheses to say so: while ((c = getchar()) != EOF).

Buffer Overruns

The classic C vulnerability:

char buffer[10];
strcpy(buffer, "This string is way too long");   // overruns the buffer

// Bounded, but silently truncates, and may not terminate
strncpy(buffer, "This string is way too long", sizeof(buffer) - 1);
buffer[sizeof(buffer) - 1] = '\0';

snprintf is usually the better tool:

int n = snprintf(buffer, sizeof(buffer), "Value: %d", x);
if (n < 0 || (size_t)n >= sizeof(buffer)) {
    /* output was truncated */
}
WarningTruncation is a bug too

strncpy stops the overflow but replaces it with a quieter failure: the string is cut short and nothing tells you. If the value mattered (a path, a device identifier, a command), you now carry corrupted data forward instead of crashing. snprintf at least reports it: it returns the length the output would have needed, so comparing that against the buffer size detects truncation. Treat a bound as something to check, not merely something to impose.

Off-by-One Errors

int array[10];
for (int i = 0; i <= 10; i++) {   // writes array[10]: out of bounds
    array[i] = 0;
}

A loop over n elements runs while the index is < n, never <= n. Counting down, start at n - 1 and run while the index is >= 0, and keep the index signed so the termination test can actually fail.

Pointer Arithmetic and free

int16_t *p = malloc(10 * sizeof *p);
p++;              // now points at the second element
free(p);          // undefined behavior: not the pointer malloc returned

free must receive exactly the pointer the allocator returned. Keep the original and iterate with a separate cursor.

Modifying String Literals

char *str = "Hello";   // points into read-only storage
str[0] = 'h';          // undefined behavior; typically a segfault

char arr[] = "Hello";  // a modifiable copy on the stack
arr[0] = 'h';          // fine

Declare pointers to literals as const char * and let the compiler catch the write.

Forgetting break in switch

switch (state) {
    case STATE_IDLE:
        init_processing();
        // falls through to STATE_ACTIVE, almost certainly by accident
    case STATE_ACTIVE:
        process_data();
        break;
}

Deliberate fall-through should be announced, both for readers and for -Wimplicit-fallthrough:

case STATE_WARNING:
    flash_led();
    /* fallthrough */
case STATE_ERROR:
    halt_system();
    break;

Uninitialized Variables

Objects with static storage duration are zero-initialized before main. Locals are not; they hold whatever was on the stack, and reading one is undefined behavior. Initialize at the point of declaration, which C99’s mixed declarations make easy.

Key Differences from C++

What C leaves to you

The two languages share a syntax, a type system foundation, a pointer model, and a compilation model, which is exactly what makes the differences easy to underestimate. Nearly everything C++ adds is an answer to a problem C solves by convention, and the convention is the part that has to live in your head.

The table reads in the direction you are travelling: here is what you do in C, and here is what C++ offers instead.

Concern C C++
Cleanup Manual free/fclose, often a goto ladder RAII: destructors run on every exit path
Heap ownership Raw pointers; who frees is documented, not enforced unique_ptr, shared_ptr
Generic code void * plus an element size, or macros Templates, type-checked per instantiation
Dynamic dispatch A struct of function pointers, filled in by hand virtual functions and the vtable
Failure reporting Return code, sentinel value, or errno Exceptions or optional/expected
Out-parameters T * the callee writes through; may be null T&: cannot be null, cannot be reseated
Name collisions Prefix every public symbol: png_read_info Namespaces
Encapsulation static in a .c file, plus convention private, enforced by the compiler
Data structures Write your own, once per project STL containers and algorithms
Strings char *, a terminator, and <string.h> std::string, std::string_view
Compile-time values #define, or the enum hack constexpr: typed, scoped
One name, many types abs, labs, fabs Overloading, and <tgmath.h> becomes unnecessary
Symbols One per name, untyped Mangled, so mismatches fail to link

The first row carries the rest. In C, a resource’s lifetime lives in the programmer’s memory and in comments; in C++ it lives in the type system, and the compiler emits the cleanup. Once destructors exist, smart pointers are just RAII pointed at the heap and containers are RAII pointed at collections. The goto cleanup ladder from the file-reading example is the C answer to the same problem, and it works, but it is re-derived by hand in every function that acquires more than one thing.

WarningValid C is not automatically valid C++

The overlap is large enough to be misleading. Several things compile in both and mean different things, and several ordinary C constructs are simply rejected by a C++ compiler:

  • void * does not convert implicitly. The idiomatic int *p = malloc(n); is an error in C++, which is why C++ code casts, and why it should be using new or a container instead.
  • sizeof('a') differs. A character constant is an int in C and a char in C++, so the answer is 4 in one language and 1 in the other.
  • Union type punning is legal in C (C99 onward) and undefined in C++, where the sanctioned tools are std::bit_cast or memcpy. See Unions.
  • const has internal linkage in C++ and external linkage in C, so a const at file scope in a header behaves differently in each.
  • Designated initializers and VLAs are C99 features that C++ never adopted wholesale; designated initializers arrived in a restricted form in C++20, and variable-length arrays never did.
  • struct tags share the ordinary namespace in C++, so the typedef struct Foo Foo; dance C requires is unnecessary.

Compile C as C and C++ as C++, and mark the boundary with extern "C" so the C++ side does not mangle names the C side expects unmangled.

The honest summary is that C++ is not “C with more features,” it is a different set of habits built on the same machine model. A C++ program written in C’s idioms, raw new, manual cleanup, hand-rolled containers, is worse than the C program it replaced: it pays C++’s compile times and complexity and collects none of the safety. If you move, move the idioms too.

Key Differences from Rust

The same job, fifty years apart

Rust targets C’s territory directly: systems work, no garbage collector, no runtime to speak of, performance in the same class. The difference is what each language does with the knowledge that programmers make mistakes. C’s answer, stated plainly in its design principles, is to trust the programmer. Rust’s is to require proof.

Concern C Rust
Memory lifetime malloc/free, correctness by discipline Ownership; freed automatically at scope end

Unsafety The whole language unsafe blocks, and they are greppable

Every row is the same trade in a different costume. C moves a decision to run time or to the programmer; Rust moves it to compile time and refuses to build until it is settled. The pointer-and-length convention is the clearest small example: C passes (buffer, count) and every function trusts that the caller got them consistent, while a Rust slice makes them a single value that cannot disagree with itself. Nothing about the generated code differs much. What differs is who is responsible for the invariant.

unsafe is the row most often misread. It does not turn off the borrow checker or make Rust into C. It permits five specific operations, chiefly dereferencing a raw pointer and calling another unsafe function, and everything else stays checked. The practical difference from C is not that unsafety is absent but that it is delimited: the audit surface for a memory bug is what appears in unsafe blocks rather than the entire program.

What C keeps is not sentimental. It is the substrate: every operating system’s syscall interface, every language’s FFI, every architecture that has ever had a compiler, and fifty years of libraries that are not going to be rewritten. Rust interoperates with C precisely because C is the boundary everything agrees on, and that role does not transfer. C is also genuinely smaller. You can hold the whole language in your head, which is a real virtue when the alternative is a borrow checker you are still arguing with in month two.

The framing worth keeping: C assumes you are careful; Rust verifies that you were. Reading Rust makes C’s implicit contracts visible, and going back to C afterward is a different experience, because you can see exactly which invariants you have quietly agreed to maintain by hand.

Where to Go Next

cppreference’s C section is the reference to keep open. It marks which standard introduced each feature, which is what you need when a project is pinned to C99 and half the internet’s examples assume C11.

Documentation and Standards

  • cppreference: C is the practical daily reference, indexed by both header and by language feature.
  • The standard itself is worth reading once, for the sections on undefined behavior. Final drafts are freely available (N1570 for C11, N3096 for C23) and are nearly identical to the published versions.
  • Compiler Explorer shows the assembly your code becomes, across compilers and optimization levels. It settles arguments about what the optimizer does in about ten seconds, and it makes the optimization and volatile material concrete in a way prose cannot.
  • The SEI CERT C Coding Standard catalogues the rules that matter in security-sensitive code, each with non-compliant and compliant examples.

Tooling Worth Adopting Early

The full treatment is in Debugging and Diagnosis; this is the short list, in order of value per unit of effort.

  • Sanitizers. -fsanitize=address,undefined on every test run. This is the highest-value habit available to a C programmer, full stop: it converts the silent memory corruption that defines C’s reputation into an immediate, located error message.
  • -Wall -Wextra. Free, and a meaningful fraction of the safety net a stricter language would give you.
  • valgrind for leak hunting and for binaries you cannot rebuild.
  • clang-tidy and cppcheck for the bugs that are visible without running anything.
  • clang-format. Commit the config and stop discussing braces.

Books

  • The C Programming Language (Kernighan and Ritchie, 2nd ed.) remains the best short book on the language, and it is short. It predates C99, so treat its examples as period-correct rather than current, but its explanations have not been improved on in forty years.
  • Expert C Programming: Deep C Secrets (van der Linden) is the book for the declaration syntax, the array/pointer confusion, and the war stories behind the language’s odder corners. Funny, and unusually honest about C’s mistakes.
  • C Interfaces and Implementations (Hanson) is the answer to “how do I structure a large C program,” which K&R does not address. It builds real libraries with real APIs, and it is the best available argument that C can be written cleanly.
  • Modern C (Gustedt), freely available, teaches C as it exists now rather than as it existed in 1988. The right corrective if your C is self-taught from older material.

Practice

Read something real. C’s great advantage as a language to learn from is that its most important programs are readable: SQLite is famously well-commented, redis is approachable, and the Linux kernel is the largest working demonstration of C’s conventions at scale.

Then write something that forces the issues this chapter raised. A dynamic array or hash table teaches ownership and realloc semantics. A line-oriented file parser teaches the string handling and the error paths. Anything with a struct of function pointers teaches why C++ has virtual. Build all of it with sanitizers on from the first commit, and the feedback loop will teach you more about undefined behavior than any amount of reading.
