The C Language

Published

July 31, 2026

Overview


C is a general-purpose, procedural computer programming language supporting structured programming, lexical variable scope, and recursion. It provides constructs that map efficiently to typical machine instructions, making it the “lingua franca” of embedded systems and Digital Signal Processing (DSP). It sits at the intersection of high-level readability and low-level hardware control.

NoteC is not C++

It is tempting to think of C as “C++ without the classes,” but the two are distinct languages with distinct philosophies. C is small, procedural, and deliberately close to the machine: what you write is roughly what the hardware does. C++ layers on classes, templates, RAII, exceptions, and a large standard library, trading C’s transparency for expressive power. Much valid C is also valid C++, but the reverse is far from true, and idiomatic code in each language looks nothing like the other. This chapter is strictly about C; C++ warrants its own treatment.

The 32 Keywords

The original ANSI C standard defined 32 keywords. These are reserved words that cannot be used as variable names. They form the skeleton of the language:

Data Types Control Flow Storage Classes Other
char if, else auto const
int switch, case, default extern volatile
short for, do, while register void
long break, continue static sizeof
float goto typedef enum
double return struct
signed union
unsigned

The Standard Library and I/O

C provides a rich Standard Library (often referred to as libc). Unlike higher-level languages, C does not have built-in statements for Input/Output (I/O). Instead, I/O is handled by functions in the standard library, primarily defined in <stdio.h>.

  • printf / scanf: The workhorses for formatted output and input.
  • fprintf / fscanf: Versions that work with file streams.
NoteWhat is stdout on Embedded Systems?

In an embedded context (like the dsPIC): There is no “screen” or “keyboard” by default. The standard library functions must be “retargeted.” This usually means the low-level functions that printf calls (often named write or _mon_putc) are implemented by the developer to send characters byte-by-byte over a peripheral like UART (Universal Asynchronous Receiver-Transmitter). Thus, printf("Hello") effectively sends 5 bytes out of the serial port to your computer’s terminal.

The Compiler

A compiler is a program that translates computer code written in one programming language (the source language, like C) into another language (the target language, usually machine code or assembly). For the dsPIC, we typically use the XC16 compiler.

The Linker

A linker is a utility program that takes one or more object files generated by a compiler and combines them into a single executable file, library file, or another ‘object’ file. It resolves references between different modules (e.g., if main.c calls a function defined in dsp.c).

A Short History of the Standard

C is old, and it has evolved. Code you encounter in the wild may target any one of several standards, and knowing which is which explains why some features are present in one codebase and absent in another. Each revision was largely additive and backward-compatible, so newer compilers still happily compile decades-old code.

Standard Year Common name What it introduced
K&R C 1978 “K&R” The original language from Kernighan & Ritchie’s book. No function prototypes; loose typing.
ANSI C / ISO C90 1989 C89 / C90 The first standard. Function prototypes, the standard library, void, const, volatile. The lowest common denominator; still the baseline many embedded toolchains assume.
C99 1999 C99 // line comments, stdint.h fixed-width types, bool (stdbool.h), inline, designated initializers, variable-length arrays, mixed declarations and code, long long.
C11 2011 C11 _Static_assert, _Generic, atomics (stdatomic.h), threads (threads.h), anonymous structs/unions.
C17 / C18 2017 C17 A bug-fix release. No new features; clarifications only.
C23 2023 C23 true/false/bool as keywords, nullptr, constexpr, binary literals (0b1010), #embed, typeof.
NoteYou are probably writing C99 already

Several conveniences this chapter uses are C99 features, not original C: the fixed-width types int16_t/uint8_t (from <stdint.h>), // comments, declaring a loop variable inside for, and declaring variables partway through a function rather than only at the top of a block. If a codebase forbids these, it is targeting C89, which is still common in conservative or safety-critical embedded work. Compilers select a standard with a flag such as -std=c99 or -std=c11.

The Basics

Before the features that make C distinctive (pointers, manual memory, bit manipulation), it is worth grounding the fundamentals: the type system, how declarations read, functions, control flow, and strings. Readers from C++ will find much of this familiar in syntax but should note where C is deliberately more spartan.

Types

C’s types are a thin veneer over what the hardware provides. There are no classes, no strings as a first-class type, and no built-in containers: just numbers, characters (which are small numbers), and aggregates you build yourself.

The Arithmetic Types

The integer types are defined by minimum width, not exact width. The standard guarantees a lower bound; the actual size is implementation-defined and depends on the target architecture.

Type Typical size Guaranteed minimum Notes
char 1 byte 1 byte Signedness is implementation-defined; may be signed or unsigned.
short 2 bytes 16 bits
int 2 or 4 bytes 16 bits The “natural” word size; 16-bit on dsPIC, 32-bit on most desktops.
long 4 or 8 bytes 32 bits
long long 8 bytes 64 bits C99.
float 4 bytes — Single-precision floating point.
double 8 bytes — Double-precision.

Each integer type has a signed (default) and unsigned variant. This portability of minimums rather than exact sizes is exactly why C99 introduced fixed-width types.

Fixed-Width Types

<stdint.h>

When you need to know precisely how wide an integer is (essential when a value maps to a hardware register or a wire format), reach for the fixed-width types. These are the types this chapter uses throughout.

#include <stdint.h>

int8_t   a;   // exactly 8 bits, signed
uint8_t  b;   // exactly 8 bits, unsigned
int16_t  c;   // exactly 16 bits, signed
uint32_t d;   // exactly 32 bits, unsigned

// Also available:
//   int_least16_t  — smallest type with at least 16 bits
//   int_fast16_t   — fastest type with at least 16 bits
//   intptr_t       — an integer wide enough to hold a pointer

Prefer int16_t over short and uint8_t over unsigned char whenever the exact width matters. The intent is explicit and the code behaves identically across targets.

sizeof

sizeof yields the size of a type or object in bytes, evaluated at compile time. It is an operator, not a function, and its result has type size_t (an unsigned type wide enough to describe any object’s size).

sizeof(int)         // e.g. 4
sizeof(uint16_t)    // 2
int16_t buf[64];
sizeof(buf)         // 128 (64 elements × 2 bytes), NOT the pointer size
sizeof(buf) / sizeof(buf[0])   // 64: the idiom for array length

That last idiom is the canonical way to compute an array’s element count. Note it only works on a true array in scope, not on a pointer (a distinction developed in Arrays and Pointers).

bool

C had no Boolean type until C99, which added bool, true, and false via <stdbool.h>. Before that, and still in much embedded code, any integer serves: zero is false, any non-zero value is true.

#include <stdbool.h>

bool ready = true;
if (ready) { /* ... */ }

// Pre-C99 style, still valid and common:
int flag = 1;
if (flag) { /* ... */ }

enum

An enum defines a set of named integer constants. By default they count up from zero, but any member may be assigned explicitly.

typedef enum {
    STATE_IDLE,        // 0
    STATE_RUNNING,     // 1
    STATE_ERROR = 10,  // 10 (explicit)
    STATE_HALTED       // 11 (continues from previous)
} State_t;

Unlike C++’s enum class, C enums are not type-safe: they are interchangeable with int, and nothing stops you assigning STATE_IDLE to an unrelated integer variable. They exist chiefly to give names to magic numbers and to make switch statements self-documenting.

typedef

typedef creates an alias for an existing type. It introduces no new type, only a new name, but that name can dramatically improve readability, particularly for structs and function pointers.

typedef unsigned char byte;      // 'byte' now means 'unsigned char'
typedef struct Point Point;      // avoid writing 'struct Point' everywhere
typedef int (*Comparator)(int, int);  // a name for a function-pointer type

The _t suffix (as in int16_t, size_t, State_t) is a widespread convention marking a type name. Strictly, POSIX reserves _t for future additions to its own headers, so a name you invent today could in principle collide with a standard one tomorrow. In practice the convention is near-universal and the risk is small; this chapter uses it throughout (State_t, CircularBuffer_t). Projects that care about strict portability sidestep it with a project prefix instead, such as dsp_state_t or AudioState.

Reading Declarations

C’s declaration syntax is famously puzzling. The guiding principle is “declaration mirrors use”: a declaration reads the way the variable is used in an expression. int *p declares p such that *p is an int.

Two traps snare newcomers immediately.

The * binds to the name, not the type. In a multiple declaration, each pointer needs its own *:

int* a, b;   // MISLEADING: a is int*, but b is a plain int!
int *a, *b;  // Both pointers. This is why C programmers write the * by the name.

Reading complex declarations: the spiral rule. Start at the identifier and spiral outward, reading right then left, until you run out of tokens:

int *ptr;              // ptr is a pointer to int
int arr[10];           // arr is an array of 10 ints
int *arr[10];          // arr is an array of 10 pointers to int
int (*arr)[10];        // arr is a pointer to an array of 10 ints
int (*fp)(int, int);   // fp is a pointer to a function taking two ints, returning int

The parentheses matter: int *arr[10] and int (*arr)[10] are entirely different types. When declarations get this hairy, the kindness is a typedef.

const Placement

Where const sits relative to * changes its meaning. Read right-to-left from the *:

const int *p;        // pointer to const int: *p is read-only, p can be reassigned
int const *p;        // identical to the above (const binds to what's left of it)
int *const p;        // const pointer to int: p is fixed, *p is writable
const int *const p;  // const pointer to const int: neither can change

The rule: const applies to whatever is immediately to its left, unless nothing is there, in which case it applies to the right. const int *p is by far the most common form: a function that promises not to modify the data behind a pointer parameter. This is the foundation of const correctness, developed further under const and static.

Type Qualifiers

C has three type qualifiers, keywords that constrain how a type may be used without changing its size or representation. They answer three separate questions about a variable, and it helps to keep them mentally distinct.

Qualifier Question it answers Meaning
const May I change this? The object must not be modified through this name after initialization.
volatile May the compiler assume this is stable? The object may change outside the program’s control; every access must actually happen.
restrict Might two pointers touch the same memory? A promise that this pointer is the only route to the data it points at.

const and volatile are not opposites and can even coexist (const volatile describes a read-only hardware register: your code must not write it, yet the hardware may change it). Both get fuller, embedded-flavored treatment later: const under The const and static Keywords, and volatile, the single most important qualifier in embedded C, under The volatile Keyword. The third, restrict, appears nowhere else and is worth introducing here.

restrict

Introduced in C99, restrict applies only to pointers. It is a promise from you to the compiler that, for the lifetime of the pointer, the data it points to will be accessed only through that pointer (or pointers derived from it). No other pointer aliases the same memory.

Why does this matter? Consider copying between two buffers:

void scale(int16_t *out, const int16_t *in, int n, int16_t gain) {
    for (int i = 0; i < n; i++) {
        out[i] = in[i] * gain;
    }
}

The compiler cannot assume out and in are separate. If they overlapped, writing out[i] might change a later in[j], so the compiler must conservatively re-read in on every iteration and cannot vectorize or reorder freely. Adding restrict lifts that doubt:

void scale(int16_t *restrict out, const int16_t *restrict in, int n, int16_t gain) {
    // Compiler now KNOWS out and in never overlap, and can optimize aggressively.
    for (int i = 0; i < n; i++) {
        out[i] = in[i] * gain;
    }
}

This is precisely the kind of tight signal-processing loop where the optimization pays off, which is why restrict shows up in DSP code and in the prototypes of library functions like memcpy (whose whole contract is that source and destination must not overlap).

Warningrestrict is a promise you must keep

The compiler does not verify your claim. If you pass overlapping pointers to a restrict parameter, the behavior is undefined: the program may produce wrong results that appear only under optimization. Use restrict only when you are certain the regions are disjoint. When overlap is possible, use memmove rather than memcpy.

Functions

A function in C has a declaration (its prototype, announcing name, return type, and parameter types) and a definition (the body). Declarations typically live in header files; definitions live in .c files. Callers need only the declaration to generate a correct call.

// Declaration (prototype) — usually in a .h file
int add(int a, int b);

// Definition — in a .c file
int add(int a, int b) {
    return a + b;
}
WarningAlways write prototypes

A function used before the compiler has seen a declaration is, in old C, assumed to return int with unchecked arguments. This “implicit declaration” is a rich source of bugs and is an error in C99 and later. Declare every function before use, and write void explicitly for an empty parameter list: int get_value(void). An empty () in C means “unspecified arguments,” not “no arguments”; another trap C++ does not share.

C is pass-by-value, always. A function receives copies of its arguments. Assigning to a parameter changes only the local copy; the caller’s variable is untouched.

void increment(int x) {
    x++;  // modifies the local copy only
}

int n = 5;
increment(n);   // n is still 5

To let a function modify a caller’s variable, you pass a pointer to it. This is C’s only mechanism for “pass by reference”, and it is explicit at both the call site (&n) and in the signature (int *):

void increment(int *x) {
    (*x)++;   // dereference, then modify what it points to
}

int n = 5;
increment(&n);  // pass the address of n
// n is now 6

Arrays are the one apparent exception, but only apparent: an array argument decays to a pointer to its first element, so the function receives an address, not a copy of the array. This is why a function cannot know an array’s length from the parameter alone, and why length is nearly always passed as a separate argument.

Control Flow

C’s control flow is the ancestor of the C-family syntax found in C++, Java, JavaScript, and beyond. Little here will surprise a C++ reader; the notes below flag the C-specific edges.

Conditionals

if (x > 0) {
    positive();
} else if (x < 0) {
    negative();
} else {
    zero();
}

C has no dedicated Boolean context: the condition is simply an integer expression, and any non-zero value is “true.” This is why if (ptr) (is the pointer non-null?) and if (count) (is the count non-zero?) are idiomatic.

The ternary operator ?: is an expression, useful where a full if would be clumsy:

int max = (a > b) ? a : b;

Loops

The three loop forms:

for (int i = 0; i < n; i++) { /* ... */ }   // declaring i here is C99

while (condition) { /* ... */ }

do {
    /* runs at least once */
} while (condition);

break exits the enclosing loop; continue skips to the next iteration. Both act only on the innermost loop.

switch

switch selects among integer cases. Its defining and dangerous characteristic is fall-through: without a break, control flows into the next case.

switch (state) {
    case STATE_IDLE:
        start();
        break;              // without this, execution falls into STATE_RUNNING
    case STATE_RUNNING:
        process();
        break;
    default:
        handle_unknown();
        break;
}

Fall-through is occasionally useful (letting several cases share code), but far more often it is an accidental missing break. This footgun is revisited in Common Pitfalls.

goto

C retains goto, and although structured programming rightly discourages it, one use is genuinely idiomatic in C: unwinding on error in a function with several acquisition steps. Since C has no destructors or finally, goto provides a single, orderly cleanup path.

int setup(void) {
    if (acquire_a() != 0) goto fail_a;
    if (acquire_b() != 0) goto fail_b;
    if (acquire_c() != 0) goto fail_c;

    return 0;  // success

fail_c: release_b();
fail_b: release_a();
fail_a:
    return -1;
}

This “cleanup ladder” is common in systems code (the Linux kernel uses it heavily). Outside error handling, prefer structured control flow.

Strings

C has no string type. A C string is simply an array of char terminated by a null byte ('\0', the value zero). Every standard string function relies on that terminator to know where the string ends; forget it and you get buffer overruns and undefined behavior.

char greeting[] = "hello";   // 6 bytes: 'h','e','l','l','o','\0'

The implication is that finding a string’s length is an \(O(n)\) scan for the terminator, not a constant-time field lookup as in C++’s std::string or Python’s str.

String vs. Character Literals

Note the distinction, easy to conflate:

'A'    // a character: a single int-valued constant (0x41)
"A"    // a string: two bytes, 'A' and '\0'

The Standard String Functions

Declared in <string.h>, operating on null-terminated arrays:

Function Purpose
strlen(s) Length, not counting the terminator (scans for \0).
strcpy(dst, src) Copy src into dst. No bounds checking.
strncpy(dst, src, n) Copy at most n bytes. Safer, but may not null-terminate.
strcmp(a, b) Compare; returns 0 if equal.
strcat(dst, src) Append src to dst. No bounds checking.
strchr(s, c) Find first occurrence of character c.

The mem* family (memcpy, memset, memmove, memcmp) does the same for raw bytes without caring about a terminator, and is what you use for binary data and buffers.

WarningThe classic C vulnerability

strcpy and strcat write until they hit the source’s terminator, with no regard for the destination’s size. A source longer than the destination overruns the buffer, corrupting adjacent memory. This single design choice is behind a large fraction of security exploits in C’s history. The Buffer Overruns pitfall shows the safe alternatives.

char vs. int from Input

A subtle but important convention: functions like getchar return an int, not a char. This is because they must return every possible byte value and a distinct end-of-input marker, EOF (typically -1). A char cannot hold that extra value, so storing the result in a char before testing for EOF is a genuine bug.

int c;                          // int, not char!
while ((c = getchar()) != EOF) {
    putchar(c);
}

This is the reason the upper.c example later in this chapter declares int c;.

The C Language

C is characterized by its simplicity and efficiency. It uses a static type system to prevent unintended operations and manage memory usage. Key concepts include:

  • Pointers: Variables that store memory addresses, allowing direct memory manipulation.
  • Memory Management: Manual control over allocation (stack vs. heap), though in embedded DSP, static allocation is preferred to avoid non-deterministic behavior.
  • Bitwise Operations: Crucial for setting hardware registers (AND, OR, XOR, SHIFT).

Pointers

A pointer is a variable that stores the memory address of another variable. They are fundamental to C, allowing for:

  • Dynamic Memory Allocation: Allocating memory at runtime.
  • Array Manipulation: Accessing and iterating through array elements efficiently.
  • Pass-by-Reference: Modifying variable values inside functions.
  • Complex Data Structures: creating linked lists, trees, etc.

A pointer to a pointer is simply a pointer that stores the address of another pointer. This allows for multiple levels of indirection.

To declare a pointer, use the * operator: int *ptr; declares a pointer to an integer. To declare a pointer to a pointer, use two * operators: int **pptr;. To dereference a pointer (access the value it points to), use the * operator again.

#include <stdio.h>

int main() {
    int var = 10;
    int *ptr = &var;    // ptr holds the address of var
    int **pptr = &ptr;  // pptr holds the address of ptr

    printf("Value of var: %d\n", var);
    printf("Value via ptr: %d\n", *ptr);
    printf("Value via pptr: %d\n", **pptr);

    return 0;
}

Arrays and Pointers

The Duality

One of C’s most elegant (and confusing) features is the relationship between arrays and pointers. Understanding this is essential for writing efficient DSP code.

The Fundamental Truth

In most contexts, an array name decays to a pointer to its first element:

int buffer[256];
int *ptr = buffer;  // Equivalent to: int *ptr = &buffer[0];

Array subscripting is actually pointer arithmetic:

buffer[i]  ≡  *(buffer + i)  ≡  *(ptr + i)  ≡  ptr[i]

All four expressions compile to identical machine code.

Where They Differ

Arrays and pointers are not the same:

int16_t arr[10];
int16_t *ptr = arr;

sizeof(arr);  // 20 on any target: 10 elements × 2 bytes each
sizeof(ptr);  // the size of a pointer: 2 on dsPIC, 8 on a 64-bit desktop

&arr;  // Type: int16_t (*)[10]  (pointer to array of 10 int16_t)
&ptr;  // Type: int16_t **       (pointer to pointer to int16_t)

Key distinction: An array is a fixed-size block of memory. A pointer is a variable holding an address.

Pointer Arithmetic for DSP

This equivalence makes DSP code elegant:

void process_samples(int16_t *input, int16_t *output, int length) {
    for(int i = 0; i < length; i++) {
        *output++ = (*input++) >> 1;  // Halve amplitude
    }
}

This is often faster than array indexing because:

  • No index register needed
  • Increment happens in parallel with memory access

Structures

Organizing Complex Data

Embedded DSP often requires managing related data. Structures group heterogeneous data types.

typedef struct {
    int16_t *buffer;      // Pointer to sample buffer
    uint16_t size;        // Buffer size
    uint16_t head;        // Write position
    uint16_t tail;        // Read position
    uint8_t  overrun;     // Error flag
} CircularBuffer_t;

// Initialize
CircularBuffer_t audio_in = {
    .buffer = input_samples,
    .size = 512,
    .head = 0,
    .tail = 0,
    .overrun = 0
};

// Use
audio_in.buffer[audio_in.head++] = new_sample;
if(audio_in.head >= audio_in.size) audio_in.head = 0;  // Wrap

Why use typedef struct? In C (unlike C++), without typedef you’d need to write struct CircularBuffer everywhere. With typedef, just CircularBuffer_t suffices.

Unions

Multiple Views of the Same Memory

A union allows storing different types in the same memory location. Only one member is valid at a time.

Example: Treating 32-bit data as bytes:

typedef union {
    uint32_t word;
    struct {
        uint8_t byte0;
        uint8_t byte1;
        uint8_t byte2;
        uint8_t byte3;
    } bytes;
} Word32_t;

Word32_t data;
data.word = 0x12345678;

// Access individual bytes without bit shifting
uint8_t high_byte = data.bytes.byte3;  // 0x12

DSP Use Case: Fast type punning (reinterpreting bits without conversion):

typedef union {
    float    f;
    int32_t  i;
    uint32_t u;
} FloatBits_t;

// Inspect binary representation of a float
FloatBits_t x = {.f = 3.14159f};
printf("Float bits: 0x%08X\n", x.u);
WarningAlignment Matters

Structures and unions must be properly aligned for efficient access. The dsPIC requires 16-bit values to be at even addresses. Use __attribute__((packed)) cautiously: it disables alignment, slowing access.

The const and static Keywords

Despite often appearing together in embedded code, const and static address entirely different concerns. const is a type qualifier: it constrains mutability, telling the compiler that a value must not be changed after initialization. static is a storage-class specifier: it governs lifetime and linkage, either extending a local variable’s lifetime to the duration of the program or restricting a global variable or function’s visibility to its translation unit. In short, const is about what can be done with data, while static is about where data lives and who can see it.

const

Putting Data in Flash

NoteConst Correctness

Const correctness is a programming principle of using the const keyword to explicitly enforce the immutability of data that is not intended to be modified. This practice helps prevent accidental data modifications, enhances code readability, and allows the compiler to catch potential errors at compile time, leading to more robust and maintainable code.

In embedded systems, RAM is precious, ROM/Flash is abundant. Use const to store read-only data in program memory:

// Without const: lives in RAM (scarce!)
int16_t filter_coeffs[128] = {123, 456, 789, ...};

// With const: lives in Flash (abundant!)
const int16_t filter_coeffs[128] = {123, 456, 789, ...};

On the dsPIC, accessing const data requires enabling PSV (Program Space Visibility). The compiler handles this automatically in most cases.

Const correctness also prevents accidental modification:

//                ^^^^^^                                  ^^^^^^
//                Promises not to modify input or coefficients

static

Three Distinct Meanings

The static keyword is overloaded in C, with different meanings depending on context:

1. Static Local Variables

Function Scope

Retains value between function calls:

void count_calls(void) {
    static int count = 0;  // Initialized ONCE at program start
    count++;
    printf("Called %d times\n", count);
}

Use case: Persistent state without global pollution.

2. Static Global Variables

File Scope

Limits visibility to the current file:

// In audio.c
static int16_t internal_buffer[256];  // Only visible in audio.c

void process_audio(void) {
    // Can use internal_buffer here
}

// In main.c
// internal_buffer is NOT accessible here

Use case: Encapsulation, preventing name collisions across files.

3. Static Functions

File Scope

Function only visible within the file:

static void helper_function(void) {
    // Internal helper, not part of public API
}

The compiler can inline or optimize these more aggressively since it knows they’re never called externally.

Function Pointers

Callbacks and Dispatch Tables

Function pointers store the address of a function, enabling callbacks and runtime dispatch.

// Define a function pointer type
typedef void (*ProcessFunc_t)(int16_t *buffer, int length);

// Functions matching the signature
void echo_effect(int16_t *buf, int len) { /* ... */ }
void reverb_effect(int16_t *buf, int len) { /* ... */ }
void distortion_effect(int16_t *buf, int len) { /* ... */ }

// Use a function pointer
ProcessFunc_t current_effect = echo_effect;

void process_audio_block(int16_t *buffer, int length) {
    // Call through function pointer
    current_effect(buffer, length);
}

// Switch effects at runtime
void set_effect(int effect_number) {
    switch(effect_number) {
        case 0: current_effect = echo_effect; break;
        case 1: current_effect = reverb_effect; break;
        case 2: current_effect = distortion_effect; break;
    }
}

Dispatch table for efficient switching:

ProcessFunc_t effect_table[] = {
    echo_effect,
    reverb_effect,
    distortion_effect
};

#define NUM_EFFECTS (sizeof(effect_table) / sizeof(effect_table[0]))

void set_effect(int n) {
    if(n >= 0 && n < NUM_EFFECTS) {
        current_effect = effect_table[n];
    }
}

Memory Management

Memory management refers to the process of controlling and coordinating computer memory, assigning blocks to various running programs to optimize overall system performance.

Standard Functions

defined in <stdlib.h>

  • malloc(size_t size): Allocates a block of uninitialized memory.
  • calloc(size_t n, size_t size): Allocates memory for an array and initializes it to zero.
  • realloc(void *ptr, size_t size): Resizes a previously allocated memory block.
  • free(void *ptr): Deallocates memory, making it available for future use.
Where Does Memory Actually Live?

C has three distinct memory regions. Understanding the difference is essential for embedded work:

Region What Lives There Lifetime Size Known At
Stack Local variables, function arguments, return addresses Scope of the function Runtime (bounded by stack size)
Heap malloc/free allocations Until explicitly freed Runtime (unbounded)
Static / BSS Global variables, static variables, const data Entire program lifetime Compile time
NoteFixed Arrays: Stack or Static?

This is a common point of confusion. Fixed arrays declared at file/global scope or with the static keyword live in the BSS/data segment (static memory), not the stack. They’re allocated at compile time and exist for the entire duration of the program.

// --- STATIC MEMORY (BSS segment) ---
int16_t audio_buffer[512];          // Global: compile-time, lives forever
static int16_t filter_state[8];     // Static local: same region, but file-scoped

void process(void) {
    // --- STACK ---
    int16_t local_sample;           // Stack: only exists inside process()
    int16_t local_buf[16];          // Stack: gone when function returns!
}

When embedded programmers say “everything is in fixed arrays,” they mean global or static arrays — all occupying statically-allocated memory, known at compile time.

Strategies
  • Static Allocation: Memory is allocated at compile time and persists for the life of the program. This is the dominant strategy in safety-critical embedded systems: zero runtime overhead, completely deterministic, no fragmentation possible.
  • Dynamic Allocation: Memory is requested from the heap at runtime via malloc/free. Flexible, but carries risks of fragmentation, non-deterministic timing, and leaks.
  • Pool Allocation: A hybrid. A large static block is pre-allocated, then subdivided and managed at runtime as fixed-size chunks. You get dynamic-like flexibility with the determinism of static allocation.
  • No Allocation (Static-Only): Many embedded coding standards (MISRA-C, DO-178C for aviation, IEC 61508 for industrial safety) ban malloc/free entirely. All memory is declared at compile time. The tradeoff: you must know your worst-case memory needs up front.
Examples
Static Allocation
// Buffer lives in BSS segment for the entire program
static int16_t audio_buffer[512];
static int16_t filter_coeffs[64];

void process_audio(void) {
    for(int i = 0; i < 512; i++) {
        audio_buffer[i] = apply_filter(audio_buffer[i], filter_coeffs);
    }
}

Pros: Zero runtime cost, completely predictable, no fragmentation, no failure mode. Cons: Memory is always reserved even when not in use. Total memory usage must be known at design time.

Dynamic Allocation
void process_variable_length(int length) {
    int16_t *buffer = malloc(length * sizeof(int16_t));
    if(buffer == NULL) { handle_error(); return; }

    // Use buffer...

    free(buffer);   // Must not forget this, or memory leaks
}

Pros: Flexible sizes, only uses memory when needed. Cons: malloc can fail unpredictably, timing is non-deterministic, heap fragments over time.

Pool Allocation
#define POOL_BLOCK_SIZE  64   // Each block holds 64 samples
#define POOL_NUM_BLOCKS   8   // Pool has exactly 8 blocks

typedef struct {
    int16_t data[POOL_BLOCK_SIZE];
    uint8_t in_use;
} PoolBlock_t;

// The entire pool is statically allocated — this is the key
static PoolBlock_t memory_pool[POOL_NUM_BLOCKS];

PoolBlock_t *pool_alloc(void) {
    for(int i = 0; i < POOL_NUM_BLOCKS; i++) {
        if(!memory_pool[i].in_use) {
            memory_pool[i].in_use = 1;
            return &memory_pool[i];
        }
    }
    return NULL;  // Pool exhausted — deterministic failure, not a random crash
}

void pool_free(PoolBlock_t *block) {
    block->in_use = 0;
}

// Usage
PoolBlock_t *buf = pool_alloc();
if(buf) {
    fill_samples(buf->data);
    process(buf->data, POOL_BLOCK_SIZE);
    pool_free(buf);
}
  • Pros: No fragmentation (all blocks are the same size), bounded and deterministic (you know exactly how many allocations are possible at any time), fast, no heap required, failure mode is explicit (NULL return) rather than silent.
  • Cons: Wastes memory when block sizes don’t match your needs. Cannot handle variable-size requests without maintaining multiple pools of different sizes.

The Standard Library

The C standard library (libc) is not one library but a loose federation of headers, each covering a self-contained domain: string handling, memory, math, time, I/O, and more. A C program includes only the headers it needs, and a conforming compiler need not provide all of them. This chapter has already covered two corners of it in context: The Standard String Functions (<string.h>) and the allocation functions under Memory Management (<stdlib.h>’s malloc/calloc/realloc/free). This section rounds out the tour with the rest of <stdlib.h>, then <stdio.h>, <wchar.h>, and <regex.h>.

NoteHosted vs. Freestanding

The C standard distinguishes two kinds of implementation. A hosted implementation assumes an operating system underneath it and provides the full standard library, including file I/O, wide characters, and (on POSIX systems) regular expressions. A freestanding implementation, the kind you get from an embedded toolchain like XC16 targeting a dsPIC with no OS, is only required to provide a minimal subset: <stddef.h>, <stdint.h>, <stdbool.h>, <stdarg.h>, <float.h>, <limits.h>, and <iso646.h>. Everything else, including most of what follows in this section, is present only if the vendor chose to implement or retarget it. <stdlib.h>’s conversion and sorting functions are pure computation and port easily to freestanding environments; fopen, wide-character I/O, and POSIX regex assume a filesystem or a POSIX environment that a bare-metal target simply does not have.

stdlib.h

defined in <stdlib.h>

Beyond the allocation functions already covered under Memory Management, <stdlib.h> is a grab-bag of utility functions: converting strings to numbers, sorting and searching generic arrays, controlling program termination, and generating pseudo-random numbers.

Numeric Conversion
Function Purpose
atoi(s) / atof(s) Convert a string to int / double. No error reporting: invalid input silently returns 0.
strtol(s, endptr, base) Convert a string to long, in any base from 2 to 36 (or 0 to auto-detect 0x/0 prefixes).
strtod(s, endptr) Convert a string to double, with the same error-detection mechanism.

strtol and strtod are strictly better than atoi/atof because they report failure. The endptr parameter is set to point at the first character that didn’t parse; if it still points at the start of the string, nothing was converted.

const char *input = "42abc";
char *end;

long value = strtol(input, &end, 10);
if (end == input) {
    // nothing parsed: not a number at all
}
printf("parsed %ld, stopped at \"%s\"\n", value, end);   // parsed 42, stopped at "abc"

Compare end against the variable holding the string, never against a literal: end == "42abc" compares addresses, and identical literals are not guaranteed to share one.

Sorting and Searching

qsort and bsearch work on any array, of any element type, because they take a comparator function pointer rather than assuming a type, the same pattern covered in Function Pointers.

int compare_ints(const void *a, const void *b) {
    int arg1 = *(const int *)a;
    int arg2 = *(const int *)b;
    return (arg1 > arg2) - (arg1 < arg2);   // -1, 0, or 1
}

int samples[5] = {30, 10, 40, 20, 50};
qsort(samples, 5, sizeof(int), compare_ints);
// samples is now {10, 20, 30, 40, 50}

int target = 40;
int *found = bsearch(&target, samples, 5, sizeof(int), compare_ints);

Both functions operate through void *, so the comparator must cast back to the real element type before dereferencing. bsearch requires the array to already be sorted (ascending, by the same comparator) or its binary search will silently return wrong results.

On a bare-metal target there is no OS to return a status code to, and often no meaningful way to “exit” a program that’s supposed to run forever. Embedded codebases frequently either omit exit/abort entirely or retarget them to something like an infinite loop plus a watchdog reset.

Pseudo-Random Numbers

rand()’s quality varies by implementation; older C libraries produce visibly patterned low-order bits (which is why rand() % 100 is a better bet than masking), and none are suitable for anything security-related. <stdlib.h> has no cryptographically secure generator; that requires a platform-specific API or a dedicated library.

stdio.h: Input and Output

defined in <stdio.h>

C has no built-in I/O statements; all of it goes through functions in <stdio.h>, operating on a FILE * stream. Three streams are open automatically: stdin, stdout, and stderr.

Two independent questions shape every I/O call. First, what the call does with the bytes: interpret them against a format string (formatted) or move them verbatim (unformatted). Second, how the stream schedules them: accumulate in a buffer (buffered) or hand them to the OS immediately (unbuffered). The two axes are orthogonal; fprintf is formatted whether the stream buffers or not.

Buffered vs. Unbuffered I/O

Every stream buffers by one of three strategies:

Mode Behavior Typical Use
Fully buffered Data accumulates until the buffer fills, then is flushed in one system call. Files: fopen’d streams default to this.
Line buffered Data flushes whenever a newline is written. Interactive terminals: stdout defaults to this when connected to a terminal.
Unbuffered Every write happens immediately. stderr, by convention, so error messages appear even if the program crashes before a buffer would otherwise flush.

setvbuf(stream, buf, mode, size) overrides the default, and fflush(stream) forces a flush of a fully- or line-buffered stream on demand:

setvbuf(stdout, NULL, _IOFBF, 8192);   // force full buffering, 8 KB buffer
printf("this may sit in the buffer...");
fflush(stdout);                        // ...until this forces it out

Buffering matters because it trades latency for throughput: fewer, larger writes are far cheaper than many small ones, but data can be lost if the program crashes before a buffer is flushed, which is exactly why stderr opts out.

NoteBuffering on Embedded Systems

The dsPIC has no filesystem and no OS-level buffered writes. When printf is retargeted to a UART (see What is stdout on Embedded Systems?), “buffering” is whatever the developer implements: often a small ring buffer (see Ring Buffers) that the UART’s transmit interrupt drains one byte at a time. The standard library’s notion of buffering modes is a hosted-environment concept; embedded code usually manages its own buffer explicitly instead of relying on setvbuf.

Buffered

Formatted I/O

The printf/scanf family, already introduced in the Overview: printf/fprintf/sprintf for output, scanf/fscanf/sscanf for input, each parsing or producing text according to a format string. sprintf/sscanf work against an in-memory buffer instead of a stream, which is how C formats or parses strings without a <sstream>-style abstraction.

char name[32];
int age;
FILE *fp = fopen("people.txt", "a");

fprintf(fp, "%s is %d years old\n", "Ada", 36);   // formatted write, buffered

FILE *in = fopen("people.txt", "r");
fscanf(in, "%31s is %d years old", name, &age);   // formatted read, buffered

char line[64];
sprintf(line, "%s: %d", name, age);   // format into memory, no stream involved

fp and in are both file streams, so each defaults to fully buffered with its own private buffer: the fprintf and fscanf calls above go through the C library rather than triggering a system call apiece.

Unformatted (Binary) I/O
Function Purpose
fgetc(stream) / fputc(c, stream) Read or write a single byte.
fgets(buf, n, stream) Read a line (or up to n - 1 bytes), null-terminated.
fread(ptr, size, count, stream) Read count objects of size bytes each into ptr.
fwrite(ptr, size, count, stream) Write count objects of size bytes each from ptr.

fread/fwrite move raw bytes without interpreting them, the natural choice for binary formats (structs, sample buffers) where printf’s text formatting would be both slower and lossy for floating-point precision.

Warningputc vs. fputc: the macro trap

Several stdio functions come in pairs that look redundant: putc/fputc, getc/fgetc. The f prefix does not mean “buffered”; both members of each pair are buffered identically, according to the stream’s mode. The difference is that fputc and fgetc are guaranteed to be real functions, while putc and getc are permitted to be macros that evaluate their stream argument more than once.

putc('x', streams[i++]);    // UNDEFINED: i may be incremented twice
fputc('x', streams[i++]);   // safe: stream evaluated exactly once

The payoff for putc/getc is avoiding function-call overhead in tight loops; the cost is that any argument with side effects is a latent bug. putchar(c) and getchar() are simply putc/getc hardwired to stdout/stdin. Prefer the f versions unless you have measured a reason not to, and never pass them an expression that does more than name a stream.

int16_t samples[256] = { /* ... */ };
FILE *fp = fopen("samples.bin", "wb");

fwrite(samples, sizeof(int16_t), 256, fp);   // one buffered bulk write
fclose(fp);                                   // buffer flushes here if not already full

FILE *in = fopen("samples.bin", "rb");
int16_t loaded[256];
size_t count = fread(loaded, sizeof(int16_t), 256, in);   // one buffered bulk read
fclose(in);

A single fwrite call of 512 bytes still goes through the stream’s internal buffer; the library only issues an actual write() system call when that buffer fills or the stream is flushed/closed, which is the whole point of buffering: many small logical writes collapse into few physical ones.

Unbuffered

There are two ways to get unbuffered behavior, and they sit at different levels.

Turning Off a Stream’s Buffer

stderr is unbuffered by default, and any stream can be forced unbuffered with setvbuf(stream, NULL, _IONBF, 0). Every write then goes straight through instead of accumulating:

fprintf(stderr, "fatal: config file missing\n");   // appears immediately, no flush needed

FILE *fp = fopen("audit.log", "w");
setvbuf(fp, NULL, _IONBF, 0);   // force unbuffered, even though it's a file stream
fprintf(fp, "user logged in\n");   // handed to the OS now, not at fclose

This is still stdio; you are just telling it to hold nothing back.

Below stdio: File Descriptors

declared in <unistd.h> and <fcntl.h>, POSIX only, not part of ISO C

The genuinely unbuffered layer is the one stdio is built on. POSIX exposes the raw system calls directly, operating on an int file descriptor rather than a FILE *:

Buffered (ISO C stdio) Unbuffered (POSIX) Purpose
fopen open Open a file.
fread read Read bytes.
fwrite write Write bytes.
fclose close Close a file.
fseek lseek Reposition the offset. 
#include <fcntl.h>
#include <unistd.h>

int fd = open("samples.bin", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fd < 0) {
    perror("open");
    return 1;
}

int16_t samples[256] = { /* ... */ };
ssize_t written = write(fd, samples, sizeof(samples));   // one syscall, no userspace buffer
if (written != (ssize_t)sizeof(samples)) {
    // a short write is not an error: write() may transfer fewer bytes than requested
}
close(fd);

There is no userspace buffer anywhere in that sequence: write is a thin wrapper over the system call itself. fwrite is this plus a buffer, which is precisely what “buffered I/O” means.

Two habits carry over from stdio and two do not. Error reporting still goes through errno/perror, but these functions signal failure with a negative return rather than NULL or EOF. And write is permitted to perform a short write, transferring fewer bytes than asked; robust code loops until the full count is written, a detail fwrite handles for you.

NoteUnbuffered is not the same as durable

Turning off buffering means stdio (or your code) hands bytes to the kernel immediately. It does not mean those bytes are on the disk. The kernel’s own page cache still holds them, so an unbuffered write survives a process crash but not a power loss. Getting data onto physical media requires fsync(fd) (or fflush followed by fsync when going through stdio). Audit logs and databases that must survive hardware failure use fsync; unbuffered alone is not enough.

The tradeoff is throughput. A system call costs on the order of a microsecond, against tens of nanoseconds for a memcpy into a buffer, so writing a file one byte at a time through write is dramatically slower than through fwrite. Reach for the unbuffered layer when you need immediacy, exact control over syscall boundaries, or access to things stdio cannot express (sockets, O_APPEND semantics, non-blocking I/O), not as a default.

File Management

fopen’s mode string controls direction, truncation, and translation:

Mode Behavior
"r" Read only. Fails if the file does not exist.
"w" Write only. Creates the file, or truncates it to zero length if it exists.
"a" Append. Creates the file if needed; every write goes to the end.
"r+" Read and write. Fails if the file does not exist; does not truncate.
"w+" Read and write, truncating as "w" does.
"a+" Read anywhere, but all writes still go to the end.
…"b" Appended to any of the above ("rb", "w+b") for binary mode. 
FILE *fp = fopen("config.txt", "r+");   // read and write, must already exist
if (fp == NULL) {
    perror("fopen failed");
    return 1;
}

fseek(fp, 0, SEEK_END);        // reposition: end of file
long size = ftell(fp);         // current offset, so: the file's size in bytes
rewind(fp);                    // back to the start, equivalent to fseek(fp, 0, SEEK_SET)

fclose(fp);

Two traps are worth internalizing. "w" silently destroys an existing file’s contents the moment you open it, so reaching for it when you meant "a" or "r+" is unrecoverable. And the "b" suffix is a no-op on POSIX systems but essential for portability to Windows, where text mode silently rewrites \n to \r\n on the way out and back on the way in, corrupting any binary payload that happens to contain those byte values.

Error Handling

FILE *fp = fopen("data.txt", "r");
if (fp == NULL) {
    perror("fopen");        // prints a message based on errno
    return 1;
}

int c;
while ((c = fgetc(fp)) != EOF) {
    putchar(c);
}

if (ferror(fp)) {
    fprintf(stderr, "read error\n");
} else if (feof(fp)) {
    printf("reached end of file normally\n");
}
fclose(fp);

feof/ferror distinguish why a read loop stopped, since a function like fgetc returns the same EOF sentinel for both “end of file” and “an error occurred.” This is the same char-vs-int subtlety already covered under char vs. int from Input: EOF must be distinguishable from every valid byte value.

wchar.h

defined in <wchar.h>

C’s char is one byte, which is fine for ASCII but cannot hold most non-Latin characters directly. <wchar.h> introduces wchar_t, a wider integer type (commonly 16 or 32 bits, platform-dependent), along with wide analogues of familiar functions: wprintf/wscanf for formatted I/O, wcslen/wcscpy/wcscmp mirroring the <string.h> functions from The Standard String Functions.

#include <wchar.h>
#include <locale.h>

wchar_t greeting[] = L"café";   // L prefix marks a wide string literal
setlocale(LC_ALL, "");              // required before wide I/O behaves sensibly
wprintf(L"%ls has %zu characters\n", greeting, wcslen(greeting));
NoteC’s Thin Unicode Story

<wchar.h> predates Unicode’s dominance and reflects an era when “wide character” meant “big enough for one locale’s character set,” not “a full Unicode code point.” Compared to Rust’s UTF-8-guaranteed String or Python’s Unicode-native str, C’s wide-character support is inconsistent across platforms (wchar_t is 16 bits on Windows, 32 on Linux) and rarely used in new code. In practice, most modern C code sidesteps <wchar.h> entirely and treats UTF-8 text as a plain char byte sequence, since UTF-8 is deliberately designed to be transparent to byte-oriented code (no embedded nulls, no ambiguity with ASCII). <wchar.h> is also irrelevant on the dsPIC-class embedded targets this book otherwise focuses on, where text handling, if it exists at all, is almost always raw ASCII bytes over a UART.

regex.h

defined in <regex.h>, POSIX only, not part of ISO C

Unlike everything else in this section, <regex.h> is a POSIX extension, not part of the ISO C standard. It provides POSIX-flavored regular expression matching in four functions:

Function Purpose
regcomp(preg, pattern, flags) Compile a pattern string into a regex_t.
regexec(preg, string, nmatch, matches, flags) Match a compiled pattern against a string.
regfree(preg) Release resources held by a compiled pattern.
regerror(code, preg, buf, size) Translate an error code into a human-readable message. 
#include <regex.h>
#include <stdio.h>

regex_t pattern;
if (regcomp(&pattern, "^[0-9]+\\.[0-9]+\\.[0-9]+\\.[0-9]+$", REG_EXTENDED) != 0) {
    fprintf(stderr, "failed to compile pattern\n");
    return 1;
}

const char *input = "192.168.1.1";
int result = regexec(&pattern, input, 0, NULL, 0);
if (result == 0) {
    printf("%s has the shape of an IPv4 address\n", input);
} else if (result == REG_NOMATCH) {
    printf("%s does not match\n", input);
}

regfree(&pattern);
WarningShape is not validity

That pattern checks structure, not meaning: [0-9]+ accepts any run of digits, so 999.999.999.999 matches happily despite being no address at all. Constraining each octet to 0-255 in pure regex is possible but grotesque ((25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)), which is the general lesson: regex is good at recognizing shape and poor at enforcing range. Match the shape, then validate the captured numbers in C.

regcomp must be paired with regfree (compiling allocates internal state), the same discipline as malloc/free under Memory Management. REG_EXTENDED selects POSIX Extended Regular Expressions (the more familiar +/?/| syntax); omitting it falls back to POSIX Basic Regular Expressions, an older and more awkward dialect.

NoteAvailability

Because <regex.h> is POSIX rather than ISO C, it is absent on Windows without a compatibility layer (MinGW, Cygwin, WSL) and virtually never available on embedded toolchains. C++ programmers reaching for pattern matching generally use <regex> instead, which is part of the C++ standard library proper and portable wherever a conforming C++ compiler runs.

The Build

The “build” is the process of converting your entire project (source files, headers, configuration bits) into a machine-readable format. In an embedded context, this output is often a HEX file. This file is not run by an OS like an .exe on Windows; instead, it is “flashed” directly into the microcontroller’s non-volatile program memory. The build process also generates a Map File, which is critical for debugging. It shows exactly where every function and variable is placed in the device’s memory.

Stages of Compilation

The build process involves four distinct stages:

  1. Preprocessing: The preprocessor obeys commands that begin with # (like #include and #define). It expands macros and includes header files into the source.
  2. Compilation: The compiler translates the preprocessed source code into assembly language specific to the target architecture (e.g., dsPIC assembly).
  3. Assembly: The assembler translates the assembly code into machine code (binary instructions), producing an object file (.o).
  4. Linking: The linker combines the object files and necessary libraries to produce the final executable (e.g., .elf or .hex file) suitable for loading onto the hardware.

Sometimes stages 2 and 3 are combined and just called “compilation”, which is why you’ll see “three stages” in some references:

  1. Preprocessing
  2. Compilation (includes assembly)
  3. Linking

Preprocessing

The preprocessor provides directives that instruct the compiler to perform specific actions before the actual compilation begins.

  • #include: Inserts the contents of a specified file into the source code at the point where the directive appears. This is commonly used to include header files.
  • #define: Creates a macro, which is a fragment of code which has been given a name. Whenever the name is used, it is replaced by the contents of the macro.
  • #undef: Removes a macro definition.
  • #pragma: Provides the compiler with special instructions (e.g., configuring optimization levels or hardware-specific settings like configuration bits on the dsPIC). For example:
    • #pragma config FOSC = INTOSC sets the oscillator configuration.
    • #pragma GCC optimize ("O2") sets the optimization level.
  • #error: Aborts the compilation process and displays a specified error message. This is often used to ensure correct configuration options are selected.
  • __FILE__: A predefined macro that expands to the name of the current input file as a string literal. It is useful for logging and debugging.

Conditional Compilation

Select code paths at compile time based on configuration:

#define DEBUG_LEVEL 2

#if DEBUG_LEVEL >= 2
    #define DEBUG_PRINT(fmt, ...) printf(fmt, ##__VA_ARGS__)
#elif DEBUG_LEVEL == 1
    #define DEBUG_PRINT(fmt, ...) printf(fmt "\n", ##__VA_ARGS__)
#else
    #define DEBUG_PRINT(fmt, ...) ((void)0)  // Compiles to nothing
#endif

// Usage
DEBUG_PRINT("Sensor value: %d", adc_result);

In production builds, change DEBUG_LEVEL to 0, and all debug prints vanish: zero code size, zero performance impact.

Stringification

Stringification (#) converts a macro argument to a string:

#define STRINGIFY(x) #x
#define REGISTER_NAME(reg) printf("Register " #reg " = 0x%04X\n", reg)

REGISTER_NAME(AD1CON1);
// Expands to: printf("Register " "AD1CON1" " = 0x%04X\n", AD1CON1);

Token Pasting

Token pasting (##) concatenates tokens:

#define GPIO_SET(port, pin) LAT##port##bits.LAT##port##pin = 1

// Expands to: LATBbits.LATB10 = 1

Practical use: Creating similar macros for all GPIO pins without copy-paste:

#define DEFINE_LED(name, port, pin) \
    static inline void name##_ON(void)  { LAT##port##bits.LAT##port##pin = 1; } \
    static inline void name##_OFF(void) { LAT##port##bits.LAT##port##pin = 0; } \
    static inline void name##_TOGGLE(void) { LAT##port##bits.LAT##port##pin ^= 1; }

// Define all three LED functions at once
DEFINE_LED(LED1, B, 10)
DEFINE_LED(LED2, B, 11)
DEFINE_LED(LED3, B, 12)

// Use

LED2_TOGGLE();

Variadic Macros

Macros that accept variable arguments using ... and __VA_ARGS__:

#define LOG_ERROR(fmt, ...) \
    do { \
        fprintf(stderr, "[ERROR] %s:%d: " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__); \
    } while(0)

// Usage
LOG_ERROR("Buffer overflow: size=%d, max=%d", buffer_size, MAX_SIZE);
// Expands to: fprintf(stderr, "[ERROR] audio.c:123: Buffer overflow: size=1024, max=512\n");

The do { ... } while(0) wrapper ensures the macro behaves like a single statement even with semicolon:

if(error_condition)
    LOG_ERROR("Something failed");  // Semicolon after macro
else
    continue_processing();

Without the wrapper, the else would attach incorrectly after macro expansion.

Key Difference

Why this Matters for DSP

  • space(dma): DMA controller can only access specific RAM regions. Without this attribute, your buffer might be placed where DMA cannot reach, causing silent failures.

  • aligned(N): Many DSP operations and DMA transfers require data aligned to specific boundaries. Misaligned data causes performance penalties or hardware faults.

  • interrupt: Generates optimized entry/exit code for ISRs, saving precious cycles; critical for real-time signal processing.

The volatile Keyword

In embedded C, volatile is perhaps the most important qualifier. It tells the compiler: “The value of this variable may change at any time, without any action being taken by the code the compiler finds nearby.”

This prevents the compiler from optimizing away reads/writes to:

  • Hardware Registers: A status flag might change due to an interrupt, not software flow.
  • Global Variables: Shared between an Interrupt Service Routine (ISR) and the main loop.
// Without volatile, the compiler might replace this loop with a generic 'while(true)'
// or remove the read entirely if it thinks the value never changes.
volatile uint16_t *status_reg = (volatile uint16_t *)0xFF00;
while (*status_reg == 0); // Wait for hardware flag

The cast is required: assigning a bare integer to a pointer is a constraint violation, and modern compilers reject it outright. Note also the fixed-width uint16_t rather than int, since a hardware register has an exact width.

Features and Libraries for DSP

Digital Signal Processing requires specific features to handle continuous signals efficiently.

Fixed-Point Arithmetic

While floating-point is easy to use, many DSCs (Digital Signal Controllers) are optimized for fixed-point arithmetic. This represents fractional numbers using integers, trading dynamic range for speed and determinism.

Fractional Representation

1.15 Format

NoteQ15

Q15 (or 1.15) is a fixed-point number format where:

  • 1 bit is used for the sign.
  • 15 bits are used for the fractional part. This allows representing numbers in the range \([-1, 0.999969]\). It is widely used in 16-bit DSPs because it maps perfectly to the 16-bit integer registers.

In 16-bit DSPs, we often use the Q15 (or 1.15) format.

  • The 16 bits are treated as a signed integer range \([-32768, +32767]\).
  • Conceptually, we divide this integer by \(2^{15}\) (32768).
  • Range: \(-1.0\) to \(\approx 0.999969\).
  • 0x8000 (-32768) represents exactly \(-1.0\).
  • 0x7FFF (32767) represents \(32767/32768 \approx 0.999969\), just short of \(+1.0\).

The range is deliberately asymmetric: \(-1.0\) is exactly representable but \(+1.0\) is not. This is why multiplying two Q15 values is safe (the only product that could reach \(+1.0\) is \(-1.0 \times -1.0\), the single case that saturates) and why DSP hardware provides saturation to handle it.

Arithmetic: When you multiply two Q15 numbers, the result is conceptually Q30 (since \(2^{-15} \times 2^{-15} = 2^{-30}\)). To store this back into a 16-bit Q15 variable, you must shift the result to the right by 15 bits.

\[ Result_{Q15} = (A_{Q15} \times B_{Q15}) >> 15 \]

DSP hardware often does this shift (and handles saturation so overflows don’t wrap around to negative numbers) automatically in a single cycle.

DSP Extensions and Intrinsics

Standard C does not natively support specialized DSP hardware instructions like MAC (Multiply-and-Accumulate) with saturation. To bridge this, compilers provide intrinsics: function-like commands that map directly to assembly instructions.

// Example of a built-in intrinsic for dsPIC (XC16)
// Performs a 16x16 multiply and accumulates to an accumulator
__builtin_mac(a, b, &accumulator, ...);

Circular Buffers

DSP algorithms (like FIR filters) often require sliding windows over data. Circular buffers allow the pointer to wrap around automatically when it reaches the end of the buffer, often supported by hardware modulo addressing.

The DSP Library

Microchip provides a DSP library (often included with the compiler) containing optimized functions for:

  • Vector operations (add, subtract, dot product)
  • Filters (FIR, IIR)
  • Transforms (FFT)

Using these pre-validated libraries is often more efficient than writing raw C implementations.

Common Pitfalls and Best Practices

C gives you enormous power and freedom, but with that comes the responsibility to avoid subtle bugs. Here are the most common traps that snare even experienced programmers.

1. Integer Promotion and Implicit Conversions

C’s type promotion rules are surprising. Before arithmetic, any integer type narrower than int is promoted to int (the integer promotions). The arithmetic therefore happens at int width, not at the operands’ declared width, and whether that saves you or burns you depends entirely on how wide int is on your target.

int16_t a = 30000;
int16_t b = 30000;

int32_t result = a + b;
// Desktop (32-bit int): a and b promote to int, sum is 60000, correct.
// dsPIC   (16-bit int): a and b promote to int, which is only 16 bits,
//                       so the sum overflows to -5536 before assignment.

The bug is not that the compiler used the declared 16-bit type; it is that int itself is 16 bits on the dsPIC, so promotion buys no extra headroom. Signed overflow is undefined behavior, so the -5536 is what typically happens, not what is guaranteed.

Casting one operand to a type at least as wide as the result forces the arithmetic to happen at that width:

int32_t result = (int32_t)a + b;   // b converts to int32_t; addition is 32-bit everywhere

Rule of thumb: When arithmetic on narrow types might overflow, cast one operand to the desired result type. Do not assume promotion to int gives you room to spare; on a 16-bit target it does not.

3. Assignment vs. Comparison

            // Always true (5 is non-zero)

Defensive programming: Some teams write constants first (Yoda conditions):

4. Uninitialized Variables

int16_t sample;  // Garbage value!
process_sample(sample);  // Undefined behavior

int16_t sample = 0;  // Always initialize

Global and static variables are automatically zero-initialized. Local variables are not.

5. Buffer Overruns

The classic C vulnerability:

char buffer[10];
strcpy(buffer, "This string is way too long");  // Buffer overflow!

// No overflow, but silently truncates to "This stri"
strncpy(buffer, "This string is way too long", sizeof(buffer) - 1);
buffer[sizeof(buffer) - 1] = '\0';  // strncpy may not terminate: do it yourself

Or better yet, use snprintf:

snprintf(buffer, sizeof(buffer), "Value: %d", x);
WarningTruncation is a bug too

strncpy stops the overflow but replaces it with a quieter failure: the string is cut short and nothing tells you. If the value mattered (a path, a device identifier, a command), you now carry corrupted data forward instead of crashing. snprintf at least reports it: it returns the length the output would have needed, so storing that return in an int n and checking if (n >= (int)sizeof(buffer)) detects truncation. Treat a bound as something to check, not merely something to impose.

6. Off-by-One Errors

int array[10];
for(int i = 0; i <= 10; i++) {  // Wrong! Accesses array[10] which doesn't exist
    array[i] = 0;
}

// Correct
for(int i = 0; i < 10; i++) {
    array[i] = 0;
}

Rule: A loop over n elements runs while the index is < n, never <= n. Counting down, start at n - 1 and run while the index is >= 0:

for (int i = n - 1; i >= 0; i--) { /* ... */ }

Beware the unsigned version of that descending loop: if i is unsigned, i >= 0 is always true and the loop never ends.

7. Pointer Arithmetic Gone Wrong

int16_t *ptr = malloc(10 * sizeof(int16_t));
ptr++;  // Now points to second element

free(ptr);  // WRONG! Must free the original pointer

Rule: Never free() a pointer that has been modified. Keep the original pointer.

8. Modifying String Literals

char *str = "Hello";  // String literal in read-only memory
str[0] = 'h';         // Undefined behavior! Might crash

// Correct: Array on stack (modifiable)
char str[] = "Hello";
str[0] = 'h';  // OK

9. Forgetting break in switch Statements

switch(state) {
    case STATE_IDLE:
        init_processing();
        // Oops! Falls through to STATE_ACTIVE
    case STATE_ACTIVE:
        process_data();
        break;
}

Fallthrough is rarely intentional. Always use break unless you explicitly want fallthrough (and comment it!):

case STATE_WARNING:
    flash_led();
    // FALLTHROUGH  (intentional)
case STATE_ERROR:
    halt_system();
    break;

10. Macro Side Effects

#define MAX(a,b) ((a) > (b) ? (a) : (b))

int x = 5;
int result = MAX(x++, 10);  // x incremented TWICE if x > 10!

Macros expand textually. If the argument has side effects, they happen multiple times.

Solution: Use inline functions:

static inline int max(int a, int b) {
    return (a > b) ? a : b;
}

11. Undefined Behavior

The Worst Kind of Bug

Some operations have undefined behavior: the C standard places no requirements on what happens. The program might work, crash, or corrupt data silently.

Common sources
  • Signed integer overflow: INT_MAX + 1 is undefined (use unsigned for modulo arithmetic)
  • Null pointer dereference: *ptr where ptr == NULL
  • Accessing freed memory: “use after free”
  • Array out of bounds: arr[100] when arr has size 50
  • Uninitialized variables: Reading before writing
  • Violating strict aliasing: Casting pointer types incorrectly
WarningStupid Optimizer

The optimizer assumes undefined behavior never happens and optimizes accordingly, potentially causing bizarre bugs in release builds that don’t appear in debug builds.

Interrupts

Interrupts are the mechanism by which hardware events can pause the normal flow of your program, execute a short handler function, and then resume where it left off. In embedded DSP systems, interrupts are essential, they allow your processor to respond to time-critical events (ADC samples ready, timer ticks, button presses) without constantly polling hardware.

What Are Interrupts?

Think of interrupts as hardware-triggered function calls. When an event occurs (e.g., a timer expires), the processor:

  1. Pauses the currently executing code (saves context)
  2. Jumps to a special function called an Interrupt Service Routine (ISR)
  3. Executes the ISR
  4. Returns to where it left off (restores context)

All of this happens automatically in hardware, you just write the ISR.

Why use interrupts instead of polling?
// Polling (wasteful)
while(1) {
    if(TIMER_FLAG) {
        do_something();
        TIMER_FLAG = 0;
    }
    // CPU sits here burning power, checking constantly
}

// Interrupt-driven (efficient)
void __attribute__((interrupt)) _T1Interrupt(void) {
    do_something();
    IFS0bits.T1IF = 0;  // Clear flag
}

// Main can do other work or sleep
while(1) {
    do_other_work();  // ISR interrupts this when needed
}

Anatomy of an ISR

dsPIC

Here’s a complete timer interrupt example for the dsPIC33F:

// Global counter incremented by ISR
volatile unsigned int timer1Count = 0;

// Timer 1 ISR - called every time Timer1 expires
void __attribute__((interrupt, auto_psv)) _T1Interrupt(void)
{
    timer1Count++;           // Increment counter
    IFS0bits.T1IF = 0;       // Clear interrupt flag (REQUIRED!)

    // Keep ISRs SHORT! No printf, no delays, no heavy math.
}
Key elements
  1. __attribute__((interrupt, auto_psv)): Tells compiler this is an ISR
    • Automatically saves/restores registers
    • auto_psv handles program space visibility for dsPIC
  2. ISR name: Must match the vector name (e.g., _T1Interrupt for Timer 1)
    • See device datasheet for all vector names
    • Common ones: _T1Interrupt, _T2Interrupt, _ADC1Interrupt, _INT0Interrupt
  3. Clear the interrupt flag: IFS0bits.T1IF = 0;
    • If you forget this, the ISR will immediately trigger again!
    • Each interrupt source has a flag bit
  4. Returns void, takes no parameters: ISRs are invoked by hardware, not by your code, so there is no caller to pass arguments or receive a result

Communicating Between ISR and Main

ISRs and main code run asynchronously, the ISR can fire at any moment. To share data safely:

1. Use Global Variables

// In timer.c
volatile unsigned int timer1Count = 0;  // Modified by ISR

void __attribute__((interrupt, auto_psv)) _T1Interrupt(void) {
    timer1Count++;
    IFS0bits.T1IF = 0;
}
// In main.c
extern volatile unsigned int timer1Count;  // Access the same variable

int main(void) {
    timer1Init(15625);  // Start timer interrupts

    while(1) {
        if(timer1Count >= 10) {  // Check flag set by ISR
            timer1Count = 0;
            toggle_led();
        }
    }
}
Why volatile?

The volatile keyword tells the compiler: “This variable can change at any time (by an ISR), so always read it from memory, never cache it in a register.”

Without volatile, the compiler might optimize:

while(timer1Count < 10);  // Compiler sees: "timer1Count never changes in this loop"
                          // Optimizes to: while(1);  (infinite loop!)

With volatile:

volatile unsigned int timer1Count;
while(timer1Count < 10);  // Compiler: "Must check memory every time"

Rule of thumb: Any variable accessed by both ISR and main must be volatile.

2. Flag-Based Pattern

A cleaner pattern for event-driven code:

volatile uint8_t button_pressed = 0;  // Flag set by ISR

// Button press ISR
void __attribute__((interrupt, auto_psv)) _INT0Interrupt(void) {
    button_pressed = 1;  // Set flag
    IFS0bits.INT0IF = 0;
}

// Main loop
int main(void) {
    init_button_interrupt();

    while(1) {
        if(button_pressed) {
            button_pressed = 0;     // Clear flag
            handle_button_event();  // Do heavy processing here
        }

        // Do other work...
    }
}

Philosophy: ISR does minimal work (set a flag), main loop does the heavy lifting.

3. Atomic Operations

If you need to read/write multi-byte variables that have a larger bit width than the CPU’s word size (16 bits for dsPIC), you need protection for atomic access. One way is to disable interrupts temporarily:

volatile uint32_t sample_count = 0;  // Modified by ISR

// Reading in main (without protection)
uint32_t count = sample_count;  // DANGER! Could be interrupted mid-read
                                // (16-bit CPU reads 32-bit value in 2 operations)

// Safe version
uint32_t get_sample_count(void) {
   uint32_t count;
   uint16_t saved_ipl = SRbits.IPL;  // Save current interrupt priority
   SRbits.IPL = 7;                   // Disable all interrupts (priority 7)
   count = sample_count;             // Now atomic
   SRbits.IPL = saved_ipl;           // Restore interrupts
   return count;
}

Note: For single-byte or single-word (16-bit on dsPIC) variables, reads/writes are inherently atomic: no protection needed.

Common Interrupt Patterns

Timer-Based Real-Time Clock

// Create a millisecond timebase
volatile uint32_t millis = 0;

void __attribute__((interrupt, auto_psv)) _T1Interrupt(void) {
    millis++;  // Increments every 1ms
    IFS0bits.T1IF = 0;
}

// Use in main
void delay_ms(uint32_t ms) {
    uint32_t start = millis;
    while((millis - start) < ms);  // Wait
}

int main(void) {
    timer1_init_1ms();  // Configure for 1ms ticks

    while(1) {
        LED = 1;
        delay_ms(500);
        LED = 0;
        delay_ms(500);
    }
}

ADC Data Acquisition

#define BUFFER_SIZE 512
volatile int16_t adc_buffer[BUFFER_SIZE];
volatile uint16_t buffer_index = 0;
volatile uint8_t buffer_ready = 0;

void __attribute__((interrupt, auto_psv)) _ADC1Interrupt(void) {
    adc_buffer[buffer_index++] = ADC1BUF0;  // Read sample

    if(buffer_index >= BUFFER_SIZE) {
        buffer_index = 0;
        buffer_ready = 1;  // Signal main: buffer full
    }

    IFS0bits.AD1IF = 0;
}

int main(void) {
    adc_init();

    while(1) {
        if(buffer_ready) {
            buffer_ready = 0;
            process_buffer(adc_buffer, BUFFER_SIZE);  // FFT, filter, etc.
        }
    }
}

Common Pitfalls

1. Forgetting volatile

uint16_t flag = 0;  // WRONG! Compiler may optimize away

void ISR(void) { flag = 1; }

while(!flag);  // May loop forever if compiler caches flag in register

Fix: volatile uint16_t flag = 0;

2. ISRs That Are Too Long

void __attribute__((interrupt)) _T1Interrupt(void) {
    printf("Timer fired\n");  // VERY BAD! printf is slow
    delay_ms(100);            // TERRIBLE! Blocks other interrupts
    compute_fft();            // NO! Do this in main
    IFS0bits.T1IF = 0;
}

ISR golden rule: Get in, do minimal work, get out. Typically < 10-20 µs.

Good ISR: Set flags, read/write hardware registers, increment counters.

Bad ISR: Heavy computation, floating-point math, I/O operations, long delays.

3. Not Clearing Interrupt Flags

void __attribute__((interrupt)) _T1Interrupt(void) {
    do_something();
    // Forgot: IFS0bits.T1IF = 0;
}
// ISR will re-trigger immediately, hanging your system!

4. Re-entrancy Issues

An ISR can interrupt itself if you nest interrupts. Generally, keep default behavior (ISRs don’t interrupt each other) unless you have a good reason.

5. Stack Overflow

Each interrupt uses stack space. Too many nested interrupts or large local variables in ISRs can overflow the stack.

Best practice: Use global or static variables in ISRs, not large local arrays.

Setting Up Interrupts

dsPIC Example

void timer1_init(uint16_t period) {
    // Configure Timer1
    T1CON = 0x0000;              // Stop timer, clear settings
    TMR1 = 0;                    // Clear counter
    PR1 = period;                // Set period

    // Configure interrupt
    IPC0bits.T1IP = 4;           // Set priority (1-7, 0=disabled)
    IFS0bits.T1IF = 0;           // Clear flag
    IEC0bits.T1IE = 1;           // Enable interrupt

    // Start timer
    T1CONbits.TON = 1;
}
Key steps
  1. Configure the peripheral (timer, ADC, etc.)
  2. Set interrupt priority (IPCx registers)
  3. Clear interrupt flag (IFSx registers)
  4. Enable interrupt (IECx registers)

Real-World Example

LED Blink with Timer

Putting it all together, the example from your code:

// timer.c
volatile unsigned int timer1Count = 0;

void __attribute__((interrupt, auto_psv)) _T1Interrupt(void) {
    timer1Count++;
    IFS0bits.T1IF = 0;
}

void timer1Init(uint16_t period) {
    T1CON = 0x0030;      // Prescaler 1:256
    TMR1 = 0;
    PR1 = period;
    IPC0bits.T1IP = 4;
    IFS0bits.T1IF = 0;
    IEC0bits.T1IE = 1;
    T1CONbits.TON = 1;
}
// main.c
#include "timer.h"

extern volatile unsigned int timer1Count;

int main(void) {
    init_hardware();

    // Timer interrupts every 100ms
    timer1Init(15625);  // (40MHz / 4) / 256 / 15625 = 10Hz

    while(1) {
        RED_LED = 1;
        while(timer1Count < 10);  // Wait 1 second (10 × 100ms)
        timer1Count = 0;

        RED_LED = 0;
        while(timer1Count < 10);
        timer1Count = 0;
    }
}
How it works
  • Timer 1 fires every 100ms, incrementing timer1Count in the ISR
  • Main loop waits for counter to reach 10 (1 second), then resets it
  • LED blinks on/off with 1 second periods

This is exactly the pattern you encountered; now you know what’s happening behind the scenes!

Embedded C Idioms

State Machines

Many embedded systems are best modeled as finite state machines:

typedef enum {
    STATE_IDLE,
    STATE_ACQUIRING,
    STATE_PROCESSING,
    STATE_ERROR
} State_t;

static State_t current_state = STATE_IDLE;

void state_machine_update(void) {
    switch(current_state) {
        case STATE_IDLE:
            if(start_button_pressed()) {
                current_state = STATE_ACQUIRING;
                init_acquisition();
            }
            break;

        case STATE_ACQUIRING:
            if(buffer_full()) {
                current_state = STATE_PROCESSING;
            } else if(timeout_occurred()) {
                current_state = STATE_ERROR;
            }
            break;

        case STATE_PROCESSING:
            process_buffer();
            current_state = STATE_IDLE;
            break;

        case STATE_ERROR:
            handle_error();
            current_state = STATE_IDLE;
            break;
    }
}
Benefits
  • Clear, maintainable code
  • Easy to visualize as a diagram
  • Deterministic behavior

Ring Buffers

Circular Buffers

Essential for continuous data streams (audio, serial data):

#define BUFFER_SIZE 256  // Must be power of 2 for fast modulo

typedef struct {
    int16_t buffer[BUFFER_SIZE];
    volatile uint16_t head;  // Write position (ISR writes)
    volatile uint16_t tail;  // Read position (main reads)
} RingBuffer_t;

// ISR writes
void buffer_write(RingBuffer_t *rb, int16_t value) {
    rb->buffer[rb->head] = value;
    rb->head = (rb->head + 1) & (BUFFER_SIZE - 1);  // Fast modulo
}

// Main loop reads
int16_t buffer_read(RingBuffer_t *rb) {
    int16_t value = rb->buffer[rb->tail];
    rb->tail = (rb->tail + 1) & (BUFFER_SIZE - 1);
    return value;
}

// Check if data available
int buffer_available(RingBuffer_t *rb) {
    return (rb->head - rb->tail) & (BUFFER_SIZE - 1);
}

Why power of 2? Modulo becomes a simple AND: x % 256 ≡ x & 255 (much faster).

Why volatile? The ISR and main loop access these independently; the compiler must not optimize away reads.

Bit Fields for Hardware Registers

typedef struct {
    unsigned pin0  : 1;
    unsigned pin1  : 1;
    unsigned pin2  : 1;
    unsigned       : 5;  // Reserved bits
    unsigned mode  : 2;
    unsigned       : 6;  // Reserved
} ControlRegister_t;

volatile ControlRegister_t *ctrl_reg = (ControlRegister_t*)0x0040;

// Access individual bits
ctrl_reg->pin0 = 1;
ctrl_reg->mode = 2;

Caveat: Bit field layout is compiler-dependent. For portable code, use bitwise operations instead.

TRISCBITS is a bit field and is used to control the direction of pins on Port C: whether each pin is an input or output. This struct overlays the 16-bit TRISC hardware register, giving you named access to individual bits instead of having to manually mask and shift.

It’s in p33FJ256GP506.h which is included via xc.h (which is the chip selector). We use it in BlinkBlocking.

#define TRISC TRISC
extern volatile uint16_t TRISC __attribute__((__sfr__));
typedef struct tagTRISCBITS {
  uint16_t :1;
  uint16_t TRISC1:1;
  uint16_t TRISC2:1;
  uint16_t :9;
  uint16_t TRISC12:1;
  uint16_t TRISC13:1;
  uint16_t TRISC14:1;
  uint16_t TRISC15:1;
} TRISCBITS;
extern volatile TRISCBITS TRISCbits __attribute__((__sfr__));

Breaking down TRISCBITS:

  • uint16_t :1; - Anonymous 1-bit field (bit 0) - reserved/unused pin
  • uint16_t TRISC1:1; - Named 1-bit field for pin C1 (bit 1)
  • uint16_t TRISC2:1; - Pin C2 (bit 2)
  • uint16_t :9; - Anonymous 9-bit field (bits 3-11) - pins that don’t exist on Port C
  • uint16_t TRISC12:1; - Pins C12 (bit 12)
  • uint16_t TRISC13:1; - Pins C13 (bit 13)
  • uint16_t TRISC14:1; - Pins C14 (bit 14)
  • uint16_t TRISC15:1; - Pins C15 (bit 15)

The TRISC register controls pin direction on Port C:

  • TRISCbits.TRISC1 = 0; → Pin C1 is an output
  • TRISCbits.TRISC1 = 1; → Pin C1 is an input
