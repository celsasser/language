Makefile Language

The dependency graph that build systems keep reinventing

Published

August 14, 2026

Overview


Make is a build automation tool, and more interestingly, a small declarative language for describing dependency graphs. You tell it which files are built from which other files and how, and it works out what is stale and what needs to run. That is the whole idea. Everything else in this chapter is detail layered on top of it.

Make has survived since 1976, outliving nearly all of its contemporaries, and the reason is worth stating plainly: the problem it solves does not go away. Any project with more than a handful of source files needs to know what to rebuild after a change, and rebuilding everything is too slow. Modern tools (CMake, Ninja, Bazel, Cargo) have not replaced that idea; they have reimplemented it with better ergonomics, and several of them still emit makefiles as their final output. Learning Make means learning the model that all of them share.

It also has a reputation for being cryptic, and the reputation is earned. Make is not one language but three sharing a single file, with an evaluation order that is not obvious from reading top to bottom. Once you can see which of the three you are looking at, the syntax stops being arbitrary and starts being merely terse.

A Short History

Make was written by Stuart Feldman at Bell Labs in 1976, reportedly after a colleague lost a morning of debugging to a program that was not being rebuilt from the source he was editing. The tool that came out of that afternoon is still recognizable in the one you run today, which is either a testament to the design or an indictment of the industry, depending on your mood.

Era What happened
1976 Feldman writes Make at Bell Labs for Unix v7. The core model (targets, prerequisites, recipes, timestamp comparison) arrives essentially complete.
1980s Make ships with every Unix, and every vendor extends it incompatibly. Writing a portable makefile becomes genuinely hard.
1988 POSIX standardizes a common core, deliberately small: suffix rules, basic macros, no conditionals, no functions.
1988 onward GNU Make adds what the standard left out: pattern rules, a real function library, conditionals, include, and parallel builds. It becomes the de facto dialect.
1990s Autotools builds a code-generation layer on top of Make to paper over portability. ./configure && make && make install enters the culture.
2000s onward CMake, Ninja, Bazel and language-native tools (Cargo, Go’s toolchain) take over new projects, most of them generating or reimplementing Make’s graph.
NoteWhich make is on your machine?

On Linux, make is almost always GNU Make. On macOS, /usr/bin/make is GNU Make 3.81 from 2006, kept at that version for licensing reasons, and it is missing newer features. BSD systems ship a genuinely different make with incompatible syntax. When portability matters, gmake is the conventional name for GNU Make where it is not the default. This chapter assumes GNU Make and flags the places where that assumption shows.

The Make Philosophy

Three decisions that explain everything else

Make rests on three design decisions. Each one buys something significant, and each one costs something you will eventually trip over. Knowing both halves is most of what it takes to use Make well.

You Describe Relationships, Not Order

A shell script is imperative: it runs top to bottom and does the same work every time. A makefile is declarative. You state which files depend on which other files, and Make derives the build order itself by walking the resulting graph.

The difference shows up the moment a project grows. A build script has to be written in a correct order, and that order has to be maintained by hand as the project changes. A makefile has no order to maintain. Rules can appear in any sequence, because the dependencies, not the layout of the file, determine what runs when.

That declarative structure is also what makes make -j8 (--jobs=8: compile in parallel by running up to 8 concurrent jobs (processes) simultaneously) possible. Once Make knows the graph, it knows which targets are independent, and independent targets can compile simultaneously. You get parallelism for free from a description you wrote for a different reason. A shell script cannot offer this, because it has no idea which of its lines are related.

The cost is that the graph has to be true. Make trusts what you declare. A dependency you failed to mention is a dependency Make will happily ignore, producing a build that is subtly stale and, under -j, unpredictably broken.

Timestamps, Not Content

Make decides a target is out of date by comparing modification times: if any prerequisite is newer than the target, the target is rebuilt. It does not read your files or hash them.

This is cheap. A stat call per file is close to free, needs no database, no cache directory, and no state carried between runs. Make can be dropped into any directory and work immediately, which is a large part of why it spread and stayed.

It is also the root of a whole family of failures, because a timestamp is a proxy for “has this changed” rather than an answer to it. The proxy fails in both directions. touch a file and Make rebuilds work that did not need doing. Restore a file with an old timestamp and Make skips work that did. Clock skew between machines on a network filesystem produces both at once. These are gathered in When Timestamps Lie.

The newer generation of build tools made the opposite trade. Ninja, Bazel, and Cargo hash file contents, paying to read every input in exchange for knowing precisely what changed. That is the right call for large builds, and Make’s approach is the right call for being able to type make in an unfamiliar directory and have it work.

The Shell Is the Recipe Language

Make knows nothing about compiling. It has no notion of C, no concept of an object file, no model of a linker. What it knows is how to decide whether a command should run. The command itself is handed to /bin/sh.

This separation is why Make outlived the toolchains it was written for. Anything you can express as “these outputs come from those inputs, via this command” fits the model. Compiling C is one instance. So is rendering LaTeX to PDF, converting images, generating code from a schema, building a container, or rendering this notebook from .qmd to HTML. Make does not need to be taught any of these; it only needs to be told what depends on what.

NoteThis is why Make is still here

It is tempting to read Make’s longevity as inertia. It is closer to the opposite. By refusing to know anything about the work it schedules, Make stayed useful across fifty years of tooling churn that obsoleted its more knowledgeable contemporaries. A tool that understood 1976’s compilers deeply would have died with them.

The cost arrives in the next section: because recipes are shell and everything above them is not, a makefile is not written in one language. It is written in three.

The Three Languages in One File

The chapter’s organizing idea

Make has a reputation for being cryptic that its size does not justify. The syntax is genuinely small. What makes makefiles hard to read is that a single file interleaves three different languages, with different rules, evaluated at different times, and the file gives you almost no visual cue about which one you are looking at.

Once you can identify the three on sight, the syntax stops being arbitrary. Nearly every baffling Make error is a boundary error: code written in one of the three languages that got evaluated as another.

Language What it does How to spot it
1 Rules Declares the dependency graph: what is built from what target: prerequisites, at the left margin
2 Macros Text substitution: variables and functions NAME = value, and $(...) anywhere
3 Shell Does the actual work Any line starting with a tab

Here is the same makefile with every line labeled by which language it belongs to:

CC      := gcc                    # `macro`: a variable definition
CFLAGS  := -Wall -O2              # `macro`
OBJS    := main.o util.o          # `macro`

app: $(OBJS)                      # `rule`, with `macro` expansions in it
    $(CC) $(CFLAGS) -o $@ $^      # `shell`, after `macros` are expanded

%.o: %.c                          # `rule` (a pattern rule)
    $(CC) $(CFLAGS) -c $< -o $@   # `shell`, after `macros` are expanded

Note what the tab-indented lines are and are not. They are shell, but Make gets to them first: it expands every $(...) and then hands the resulting text to /bin/sh. Two languages occupy the same line, one after the other. That single fact generates a surprising number of bugs.

Why This Framing Pays Off

Three of the most common Make confusions are all the same confusion wearing different clothes. Each is treated fully later; the point here is that they share a cause.

Tabs are a language marker. The rule that recipe lines must start with a tab looks like a pointless historical wart, and its origin genuinely was an accident. But it is doing real work: the tab is how the parser knows a line is shell rather than macro or rule. Indent with spaces and Make tries to parse your compiler invocation as a makefile construct, which is why the error reads missing separator. See Tabs, and Why.

$ means different things on either side of the boundary. Make consumes $ for its own expansions, so a $ that should survive into the shell has to be written $$. This is why a shell loop inside a recipe uses $$i and not $i: $i would be expanded by Make, find nothing, and hand the shell an empty string. See Common Pitfalls.

Macros and rules run at different times. The macro language is fully evaluated before any recipe executes. So $(shell date) reports the moment Make parsed the file, not the moment your command ran, and a $(wildcard build/*.o) cannot see object files that a recipe is about to create. See Two-Phase Evaluation.

TipA diagnostic habit

When a makefile does something inexplicable, the first question worth asking is not “what does this syntax mean” but “which language is this line, and when does it get evaluated?” That question resolves the majority of real-world Make problems, and it is the thread this chapter follows throughout.

There is a fourth thing worth naming, though it is not a language: Make’s macro layer has no types. Everything is text, and lists are just strings with spaces in them. There are no numbers, no arrays, no structures, and no local scope. Once you stop expecting a programming language and start reading it as a text preprocessor closer in spirit to cpp than to C, the function library in Functions becomes much easier to predict.

Anatomy of a Rule

The one construct everything else decorates

The rule is Make’s only real idea. Variables, functions, pattern matching, and conditionals are all machinery for writing rules more compactly. Read this section carefully and the rest of the chapter is elaboration.

Targets, Prerequisites, Recipes

A rule has three parts:

target: prerequisites
    recipe
  • Target: what this rule produces. Usually a file, occasionally just a name (see Phony Targets).
  • Prerequisites: what the target is built from. Also called dependencies. May be empty.
  • Recipe: the shell commands that turn prerequisites into the target. Every line must begin with a tab.

Read a rule as a sentence with two clauses: “target is built from prerequisites, and here is how.” The first clause is a fact Make uses to build its graph. The second is a command it runs only when it concludes the target is out of date.

app: main.o util.o
    gcc -o app main.o util.o

This says app depends on the two object files, and if either is newer than app, run gcc. Nothing more is implied. Make does not know that gcc produces app, or that these are C programs at all. It compares timestamps and runs the command you gave it.

Multiple Prerequisites

Prerequisites are a whitespace-separated list, and long lists are conventionally continued with a backslash:

app: main.o util.o parser.o network.o \
     config.o logging.o
    gcc -o app $^

Order within the list does not matter for correctness. Make may build them in any order, and under -j it will build them simultaneously. If two prerequisites genuinely must be built in sequence, that ordering has to come from a dependency between them, not from their position in this list. Assuming left-to-right order is one of the most common ways a makefile works serially and then fails under make -j8.

Multiple Targets

A rule may name several targets. The meaning is probably not what you would guess:

a.o b.o: shared.h
    @echo "rebuilding for $@"

This is shorthand for writing the same rule once per target, and the recipe runs once for each out-of-date target, not once in total. For the common case of one command producing several files at once, this is the wrong construct; GNU Make 4.3 added &: (grouped targets) for that, and older makefiles fake it with a stamp file.

Multi-Line Recipes

Each line of a recipe is passed to the shell, and every line gets its own shell process:

report.txt:
    echo "building"
    date > report.txt

Two lines, two separate sh invocations. This is the source of a classic frustration:

# BROKEN: the cd does not persist to the second line
install:
    cd build
    cp app /usr/local/bin/

The cd affects only the shell that ran it, which exits immediately. The cp runs in the original directory. The fix is to make it one shell command:

install:
    cd build && cp app /usr/local/bin/

GNU Make’s .ONESHELL special target changes this globally so that an entire recipe runs in a single shell. It is convenient and it is also a portability tradeoff, discussed in Special Targets.

Recipe Line Prefixes

Two characters at the start of a recipe line modify how Make treats it:

Prefix Effect Typical use
@ Do not echo the command before running it @echo messages, keeping output readable
- Ignore a non-zero exit status -rm -f in a clean target, cleanup that may find nothing 
clean:
    @echo "Cleaning..."
    -rm -f app *.o

By default Make prints each command as it runs it, which is genuinely useful and worth keeping for real build steps. Reserve @ for messages, not for hiding compiler invocations that you will want to see when a build breaks.

Warning- hides real failures

Ignoring exit status means Make continues even when a step failed. That is correct for rm -f on a file that may not exist, and dangerous almost everywhere else, because a failed build step will not stop the build. Use it deliberately and narrowly.

Rules Without Recipes

A rule may declare prerequisites and no recipe at all:

main.o: config.h defs.h

This adds config.h and defs.h to whatever main.o already depends on, leaving the recipe to be supplied elsewhere, typically by a pattern rule. It is pure graph information: “also rebuild main.o when these headers change.”

This form matters more than it first appears. It is exactly what compiler-generated dependency files contain, which is the mechanism behind Auto-Generated Dependencies, the idiom that makes a C build genuinely correct.

When Two Rules Match

Nothing stops you from writing two rules for the same target, and Make’s response depends entirely on how many of them carry a recipe. The distinction is not cosmetic: one case is the mechanism behind auto-generated dependencies, and the other silently discards work.

One recipe between them: the prerequisites combine. This is the useful case, and the reason the recipe-less form above exists.

main.o: main.c
    $(CC) $(CFLAGS) -c $< -o $@

main.o: config.h util.h

main.o ends up depending on all three files, built by the only recipe available. No warning, because nothing is in conflict: each rule contributed what it had. A .d file generated by -MMD is exactly the second rule, which is why including one strengthens the graph rather than replacing anything.

A .d file is a dependency file generated by compilers like GCC or Clang. It contains Makefile rules that list the header files a specific source file depends on, ensuring that your program recompiles correctly whenever a dependency header changes.

An excerpt from the pico-tracker project (pico-tracker/build/desktop/CMakeFiles/picotracker_desktop.dir/system/desktopSystem.cpp.o.d):

CMakeFiles/picotracker_core.dir/Users/curtis/pico-tracker/sources/System/io/Status.cpp.o: \
  /Users/curtis/pico-tracker/sources/System/io/Status.cpp \
  /Users/curtis/pico-tracker/sources/System/io/Status.h \
  /Users/curtis/pico-tracker/sources/Adapters/desktop/../../Foundation/T_Factory.h \
  /Users/curtis/pico-tracker/sources/Adapters/desktop/../../Foundation/T_Factory.cpp \
  /Users/curtis/pico-tracker/sources/Adapters/desktop/../../System/Console/nanoprintf.h \
  /Library/Developer/CommandLineTools/usr/lib/clang/14.0.3/include/stdarg.h \
  /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/c++/v1/stddef.h \
  /Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/c++/v1/__config \
  ...

Two recipes: the last one wins, with a warning.

app: main.o
    $(CC) -o $@ $^

app: main.o util.o
    $(CC) -O2 -o $@ $^
Makefile:4: warning: overriding recipe for target 'app'
Makefile:1: warning: ignoring old recipe for target 'app'

Make uses the second recipe and discards the first. The prerequisites still combine, so the target is correct in the graph, but only one recipe survives. Two things make this worse than the warning suggests: it is easy to lose in a wall of compiler output, and last means last-read, which with include may be a file you are not looking at. A fragment included at the bottom of a makefile can quietly override a rule defined at the top.

An explicit rule beats any pattern rule. If a target has an explicit rule with a recipe, Make never consults its pattern rules for that target:

%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

legacy.o: legacy.c
    $(CC) -w -O0 -c $< -o $@      # this one, always

No warning here, because there is no ambiguity to warn about. This is the ordinary way to carve out a special case, and it composes with the pattern-rule layering shown in How Make Chooses Among Candidates.

Two pattern rules match: specificity decides. That is a separate resolution procedure, described in full in How Make Chooses Among Candidates. Briefly: a rule whose prerequisites can actually be satisfied wins first, then the shortest stem, then file order.

Situation Outcome Warns
Two rules, one recipe Prerequisites combine, that recipe runs No
Two rules, two recipes Prerequisites combine, last recipe wins Yes
Explicit rule vs. pattern rule Explicit wins outright No
Two pattern rules Viable first, then shortest stem, then file order No
WarningThe dangerous asymmetry is silence

A duplicated explicit recipe warns. A pattern rule that fails to apply does not: it is simply passed over, and the failure surfaces later as a confusing error from some other rule, or as a target that mysteriously was not built. That silence is the strongest argument for static pattern rules, where a target that does not match its pattern is a parse-time error naming the offending file.

A Complete Small Makefile

Putting it together, here is a working build for a two-file program:

app: main.o util.o
    gcc -o app main.o util.o

main.o: main.c util.h
    gcc -Wall -c main.c

util.o: util.c util.h
    gcc -Wall -c util.c

clean:
    -rm -f app *.o

Everything in this chapter after this point is about writing that same build with less repetition and more correctness. The variables in Variables remove the duplicated gcc -Wall. The pattern rules in Pattern Rules collapse the two nearly identical .o rules into one. The automatic dependency generation in Auto-Generated Dependencies replaces the hand-written util.h prerequisites, which are already a maintenance liability at this size and hopeless at a hundred files.

Tabs, and Why

Recipe lines must begin with a literal tab character. Not spaces. Not a mix. A tab.

This is Make’s most notorious wart, and it is worth understanding rather than merely suffering, because it follows directly from the three-languages structure. Make needs to know whether a line is shell to be executed or a makefile construct to be parsed. It uses leading whitespace as the signal, and specifically the tab.

Indent with spaces and you get the error that has confused programmers for five decades:

Makefile:5: *** missing separator.  Stop.

The message is unhelpful because Make is not reporting “you used spaces.” It tried to parse your gcc command as a variable assignment or a rule, found neither a = nor a :, and reported the absence of the separator it was looking for. The error names the symptom of a failed parse, not the cause.

ImportantTabs do not survive this web page

Code blocks in this chapter are rendered to HTML, and the tabs in them become spaces along the way. Makefiles copied from the rendered page will fail with missing separator until you convert the recipe indentation back to tabs. This is a limitation of the rendering, not of the examples.

The origin is an accident that its author has been apologizing for ever since. Stuart Feldman added the tab rule early in Make’s development, before the tool spread, and by the time the problem was obvious it was too late:

Why the tab in column 1? Yacc was new, Lex was brand new. I hadn’t tried either, so I figured this would be a good excuse to learn. After getting frustrated with the mking of Lex, I just did something simple with the pattern newline-tab. It worked, it stayed. And then a few weeks later I had a user population of about a dozen, most of them friends, and I didn’t want to screw up my embedded base. The rest, sadly, is history.

— Stuart Feldman

GNU Make offers an escape hatch. .RECIPEPREFIX changes the character that introduces a recipe line:

.RECIPEPREFIX = >
app: main.o
> gcc -o app main.o

It works, and it is rarely used. A makefile written this way surprises every reader and every tool that expects the convention, which is usually a worse problem than the one it solves. The practical answer is to configure your editor: tell it not to expand tabs in makefiles. Most editors already know to do this for files named Makefile, and an .editorconfig entry makes it explicit:

[{Makefile,*.mk}]
indent_style = tab

The Default Goal

Running make with no arguments builds the default goal: the first target in the file that is not a special target and does not begin with a period. Nothing else about being first matters, and nothing about the name all is magic.

all: app docs        # this is the default goal, because it comes first

app: main.o
    gcc -o app main.o

docs:
    quarto render

Convention puts a target named all at the top, listing everything the project normally builds as its prerequisites. It is a convention worth following: it means make alone does the obvious thing, and it survives someone later adding a rule above it only if they know the rule. Which is why GNU Make lets you state it explicitly instead of relying on file position:

.DEFAULT_GOAL := all

With that line, all is the default no matter where it sits in the file or what gets added above it. In a makefile of any size this is worth writing.

You can also name goals on the command line, and Make builds them in the order given:

make clean app        # clean first, then build app
make -j8 app docs     # build both, in parallel where the graph allows
Notemake with no target is not make all

It is easy to assume make means “build everything.” It means “build the first target,” which is only the same thing because of a convention you are free to break by accident. If someone adds a debugging rule at the top of a makefile, plain make silently starts building that instead. .DEFAULT_GOAL prevents it.

Phony Targets

Most targets name a file. Some name an action: clean, test, install, all. These are phony targets, and they need to be declared as such:

.PHONY: all clean test install

Without that declaration, they are a bug waiting for the right filename. Consider:

clean:
    -rm -f app *.o

This works until the day a file or directory named clean exists in the project. Then:

$ make clean
make: 'clean' is up to date.

Make did exactly what it was told. It found a target named clean, found a file named clean, saw the rule had no prerequisites newer than that file, and concluded there was nothing to do. The build system stops working, and the reason is invisible unless you know to look for it. A docs/ directory silently breaking make docs is the same failure and is considerably more likely.

Declaring the target phony tells Make that the name does not refer to a file, so it should never be compared against one:

.PHONY: clean
clean:
    -rm -f app *.o

Now make clean runs its recipe unconditionally, whatever happens to exist on disk.

.PHONY has a second, smaller benefit. For a normal target, Make searches its built-in rules for a way to build the file, which is wasted work for a target that is not a file. Marking it phony skips the search.

Two conventions for where to write it. Declaring them together at the top is compact and easy to audit:

.PHONY: all clean test install docs

Declaring each next to its rule keeps the pair visible and never drifts, at the cost of repetition:

.PHONY: clean
clean:
    -rm -f app *.o

.PHONY: test
test: app
    ./run-tests.sh

Either is fine. The failure mode to avoid is a .PHONY list at the top that someone forgets to update when adding a target, which is exactly the case where the bug lies dormant until a filename collides. Phony targets carry most of the weight in Make as a Task Runner, where essentially every target is one.

The Dependency Graph

What Make actually computes

A makefile looks like a list of rules. It is better understood as a graph: each target is a node, each prerequisite is an edge, and running Make means walking that graph to decide which nodes are stale. Every capability in this chapter, parallelism, incremental rebuilds, the freedom to write rules in any order, falls out of that one structure.

How Make Decides What to Rebuild

The rule is short enough to state exactly. A target is out of date if it does not exist, or if any of its prerequisites has a more recent modification time than the target. When a target is out of date, Make runs its recipe.

The subtlety is that this test is applied recursively, bottom-up. Before Make can compare app against main.o, it must know whether main.o is itself current, which means checking main.o against main.c and util.h first. So Make walks depth-first to the leaves of the graph, then evaluates staleness on the way back up. A rebuild deep in the tree updates a timestamp, which propagates staleness upward to everything that depends on it.

Take the makefile from A Complete Small Makefile. Its graph looks like this, with an edit to util.h marked:

Touching util.h makes both object files stale, because both list it as a prerequisite. Rebuilding them updates their timestamps, which in turn makes app stale. Three recipes run. Had you edited util.c instead, main.o would have been left alone and only two would have run.

Now notice what this depends on. main.o is rebuilt only because someone wrote util.h in its prerequisite list. Make cannot read main.c, does not know what #include means, and has no way to discover that relationship on its own. The graph is not derived from your source code; it is asserted by you, and Make trusts the assertion completely. Omit util.h from that line and the rebuild silently does not happen, leaving an object file compiled against a header that no longer exists in that form. This is the single most common source of stale builds, and it is common enough that the fix, generating those prerequisites automatically from the compiler itself, gets its own section in Auto-Generated Dependencies.

NoteNewer, not different

The comparison is strictly newer than, not not equal to. A prerequisite older than its target is considered fine no matter how much its contents changed. This sounds like pedantry until you restore a file from a backup or check out an old branch, at which point it is the whole problem. See When Timestamps Lie.

Graph Traversal and Ordering

Make derives execution order from the graph alone. The order rules appear in the file is irrelevant, with exactly one exception: the first target in the file is the default goal. Beyond that, you can shuffle the rules in a makefile arbitrarily and the build will run identically.

This is worth dwelling on, because it is the concrete payoff of the declarative design described in You Describe Relationships, Not Order. In a build script, the order of the lines is the build order, and keeping it correct as the project grows is manual work. In a makefile there is no order to maintain. Adding a source file means adding a node and its edges; where you type it does not matter.

Two consequences follow directly.

A target is built at most once per run. If both main.o and util.o depend on a generated config.h, Make does not generate it twice. The graph is walked, not the file, and a node already visited and brought up to date is not revisited. This is why a diamond-shaped dependency is unremarkable in Make and a genuine hazard in a shell script.

Independent subtrees can run concurrently. Nothing connects main.o to util.o, so nothing requires one to precede the other. make -j exploits exactly this, and it needs no additional annotation from you because the information was already in the graph. The catch is that parallelism turns an incomplete graph from a latent bug into an intermittent one: a missing edge that happened to work serially, because the file order accidentally matched the true order, will fail unpredictably under -j. Parallelism treats this properly.

WarningCycles

Because the structure is a graph rather than a tree, it is possible to write a cycle: a depends on b, which depends on a. GNU Make detects this, prints Circular a <- b dependency dropped, and continues by ignoring one of the edges. It is a warning rather than an error, which means a cyclic makefile builds something, just not reliably the right thing. Treat that message as a bug to fix, not noise to tolerate.

Order-Only Prerequisites

Sometimes a target requires that something exist without caring when it was last modified. The canonical case is an output directory.

Consider building objects into build/. The directory must be there before the compiler writes into it, so the instinct is to make it a prerequisite:

# BROKEN: rebuilds everything, constantly
build/%.o: %.c build
    $(CC) -c $< -o $@

build:
    mkdir -p build

This builds correctly and then rebuilds far more than it should. The reason is that a directory’s modification time changes every time a file is created inside it, so build is a prerequisite whose timestamp moves on its own, without anyone editing a source file.

Whether that bites on the very next run is a matter of timing. If every object lands within the same timestamp tick as the directory update, the comparison is equal rather than newer and nothing rebuilds, which is why this makefile can look fine in a quick test. The failure surfaces as soon as anything is added to build/ afterward: a newly added source file, a generated artifact, a later build step writing its output there. Any of these advances the directory’s mtime past every object already in it, and the next run recompiles all of them despite nothing having changed. In a real project that is a rebuild-everything, at unpredictable intervals, for no visible reason.

The | separator solves it. Prerequisites listed after the pipe are order-only: Make guarantees they are brought up to date before the target’s recipe runs, but their timestamps are excluded from the staleness comparison.

build/%.o: %.c | build
    $(CC) -c $< -o $@

build:
    mkdir -p build

Now build is created if missing and otherwise ignored. The ordering guarantee is kept; the false staleness is gone.

target: normal-prereqs | order-only-prereqs

Directories are the overwhelmingly common use, to the point that the | $(BUILD_DIR) idiom is worth recognizing on sight. The general principle is broader: reach for order-only whenever a prerequisite is a precondition rather than an input. A tool that must be built before it can be run on your sources, or a code generator whose mere presence matters but whose timestamp does not, both fit.

Tipmkdir -p and the missing recipe

An alternative you will see is skipping the rule entirely and creating the directory inside the recipe: @mkdir -p $(@D). Here $(@D) is the directory part of the target (see Automatic Variables), and -p makes it succeed when the directory already exists. This is less elegant, since it runs on every compile rather than once, but it is robust and needs no order-only prerequisite at all. Both idioms are in wide use.

When Timestamps Lie

Make’s use of modification times is the cheap approximation described in Timestamps, Not Content, and the ways it fails are worth cataloguing, because each has a recognizable symptom and a known fix.

Clock skew. A file whose mtime is in the future is newer than every target that depends on it, permanently, so its dependents rebuild on every invocation. Make usually notices and warns:

make: Warning: File 'util.c' has modification time 47 s in the future

The cause is almost always a mismatched clock across a boundary: a network filesystem where the server and client disagree, a VM or container whose clock drifted from the host, or a dual-boot machine where one OS keeps local time and the other UTC. The fix is to correct the clock, not the files, though find . -newer . -exec touch {} + will paper over an already-damaged tree.

Version control does not preserve mtimes. Git records content, not timestamps, and sets a file’s mtime to the moment it was written into your working tree. So git checkout of an older branch produces files with newer timestamps, and a fresh clone stamps the entire tree with the current time. The usual consequence is a full rebuild after switching branches, which is merely slow. The dangerous inverse happens when a build artifact survives a checkout that rewound its sources: the artifact is newer than the sources it no longer matches, and Make sees nothing to do. When a build is inexplicably wrong right after a branch switch, this is the first thing to suspect, and make clean is the answer.

touch cuts both ways. It is the intended tool for forcing a rebuild without editing anything (touch config.h; make) and for the opposite, marking a target as current without running its recipe (make -t, --touch). Both are legitimate. Both also make the timestamps stop reflecting reality, and a make -t run performed to silence a rebuild loop will hide genuine staleness afterward.

Sub-second resolution. Modern filesystems record nanoseconds and GNU Make compares them, so a generated file and its output landing in the same second are ordered correctly. Older combinations are not so lucky: filesystems with one-second granularity (or Make 3.81, still shipping as /usr/bin/make on macOS) can see a prerequisite and its target as having identical timestamps, and identical is not newer, so the rebuild is skipped. Very fast generate-then-compile steps are where this shows up, and it is maddening precisely because it is timing-dependent and vanishes under a debugger or a slower machine.

Regenerated files that did not change. A code generator rerun on unchanged input typically rewrites its output byte-for-byte, updating the mtime. Everything downstream rebuilds despite nothing having actually changed. The standard remedy is to write to a temporary file and move it into place only if it differs:

generated.h: schema.json
    ./generate $< > $@.tmp
    @if cmp -s $@.tmp $@; then rm $@.tmp; else mv $@.tmp $@; fi

This restores content-sensitivity by hand, for the one file where it matters most.

Taken together, this is the bill for the design decision in Timestamps, Not Content. The newer generation of build systems pays a different price: Ninja, Bazel, and Cargo hash file contents, so none of the failures above can occur, at the cost of reading every input on every build and maintaining a state database to compare against. Make trades correctness in the corner cases for needing nothing but stat and no state at all. For a chapter’s worth of source files that is a fine trade; for a monorepo it stopped being one some time ago.

Variables

The macro language, and the one distinction that matters most

Variables are the second of the three languages: pure text substitution, closer to the C preprocessor than to a programming language. There are no types. A variable holds a string, and a list is only a string with spaces in it. Keeping that in mind explains most of what follows, including several behaviors that look like bugs.

Conventionally they are written in uppercase, referenced as $(NAME) or ${NAME}, and a single-character name can drop the parentheses entirely, which is why $@ works and why $(CC) cannot be written $CC. That last spelling means “expand the variable C, then append a literal C”, and since C is almost certainly undefined, you get the bare string C. Empty expansion of an undefined variable, with no error, is Make’s default and the root of a great many silent failures.

The Two Flavors

The highest-value thing to understand in Make

Make has two assignment operators that look interchangeable and are not.

= creates a recursively expanded variable. The right-hand side is stored as text, unevaluated, and re-expanded every single time the variable is used.

:= creates a simply expanded variable. The right-hand side is evaluated once, at the moment of definition, and the result is stored.

A := hello
B  = $(A) world      # stored as the literal text "$(A) world"
C := $(A) world      # stored as "hello world"

A := goodbye         # redefine A

$(info B is $(B))    # B is goodbye world   <- re-expanded, sees the new A
$(info C is $(C))    # C is hello world     <- frozen at definition time

B changed because it was never really “hello world”; it was a recipe for computing a string, re-run on each reference. C was computed once and is now inert.

This is Make’s deferred-evaluation mechanism, and it is genuinely useful. It lets a variable refer to another that is defined later in the file, which is how makefiles offer overridable configuration blocks:

CFLAGS = $(OPTIMIZATION) $(WARNINGS)     # OPTIMIZATION not defined yet

OPTIMIZATION := -O2
WARNINGS     := -Wall -Wextra

With := on the first line, CFLAGS would expand to a single space, permanently, because both operands were empty when it was evaluated. With = it resolves correctly whenever it is eventually used.

The cost is that a recursively expanded variable is re-evaluated on every reference, which matters when the right-hand side does real work:

VERSION = $(shell git describe --tags)    # runs git EVERY time $(VERSION) appears
VERSION := $(shell git describe --tags)   # runs git exactly once

In a makefile referencing $(VERSION) in a dozen recipes, the first spelling forks a dozen git processes. This is a common and easily missed cause of sluggish builds.

The two flavors also differ on self-reference. Appending to a recursively expanded variable is a genuine infinite loop, and Make refuses it outright:

A = $(A) more        # *** Recursive variable 'A' references itself (eventually). Stop.
A := $(A) more       # fine: expands the old value once, then reassigns
TipPrefer :=

Use := unless you specifically need deferred expansion. It evaluates once, cannot loop, does not re-run $(shell) calls, and behaves the way a reader coming from any other language expects. Reach for = deliberately, when you want a variable whose value depends on something defined later or on a target-specific value resolved per-target. POSIX blesses ::= as a synonym for :=; GNU Make accepts both, and := is what you will see in practice.

Note!= and shell assignment

GNU Make 4.0 added VAR != command as shorthand for VAR := $(shell command). It is concise and increasingly common, but it is a GNU extension and absent from the Make 3.81 that macOS ships, so a makefile that must run there should use $(shell ...) explicitly.

?= and +=

Two further operators cover the common cases.

?= assigns only if the variable is not already set. This is how you write a default that a user can override:

CC      ?= gcc
PREFIX  ?= /usr/local

Run make and CC is gcc. Run make CC=clang, or export CC in the environment, and your assignment is skipped entirely. Note that “already set” includes being set to the empty string, and that the built-in default for CC is already cc, so CC ?= gcc in a makefile using the built-in rules never takes effect. Where that matters, assign unconditionally or use override.

+= appends, with a space separator. Its subtlety is that the flavor is inherited from how the variable was first defined, and the two behave differently:

SIMPLE := -Wall
SIMPLE += $(EXTRA)      # $(EXTRA) expanded NOW, while it is still empty

RECUR   = -Wall
RECUR  += $(EXTRA)      # $(EXTRA) left as text, expanded later

EXTRA := -Wextra

$(info SIMPLE = $(SIMPLE))   # SIMPLE = -Wall
$(info RECUR  = $(RECUR))    # RECUR  = -Wall -Wextra

Same operator, same order, different results, decided entirely by an assignment several lines earlier. When appending something that may not be defined yet, either define the base with = or move the append below the definition it depends on.

Appending to an undefined variable is well defined: it behaves like =, creating a recursively expanded variable.

Where Values Come From

The same variable can be set in five places, and Make resolves the conflict by a fixed precedence. Highest wins:

Rank Source Example Notes
1 override in the makefile override CFLAGS += -Wall Beats even the command line
2 Command line make CC=clang The user’s intent; beats the file
3 Makefile assignment CC := gcc The ordinary case
4 Environment CC=clang make Loses to the makefile, unless -e is passed
5 Built-in defaults CC is cc, CFLAGS is empty Make’s own table, visible via make -p

The pairing of rows 2 and 4 is the useful part. A makefile assignment beats the environment, which means a stray CFLAGS exported in someone’s shell profile cannot silently change your build. A command-line assignment beats the makefile, which means a user can still override deliberately when they mean to. That default is almost always what you want; make -e inverts it and is best avoided.

override exists for the case where the makefile must win regardless, most often to append a flag the build genuinely requires:

override CFLAGS += -fno-strict-aliasing    # survives `make CFLAGS=-O2`

Without override, make CFLAGS=-O2 would discard that flag entirely, since the command line wins and the assignment is skipped.

Recipes and the Environment

A point that catches people: recipes do not automatically see makefile variables as shell variables. Consider:

GREETING := hello

show:
    echo $(GREETING)      # Make expands this to: echo hello
    echo $$GREETING       # the shell sees $GREETING, which is unset -> empty

The first line works because Make substitutes the text before the shell ever runs, exactly as described in The Three Languages in One File. The second asks the shell for an environment variable that was never exported. export bridges the gap:

export GREETING := hello

show:
    echo $$GREETING       # now the shell has it too

A bare export with no arguments exports everything, which is occasionally convenient and mostly a way to leak makefile internals into every subprocess. Export deliberately, and prefer plain $(VAR) expansion unless a recipe genuinely needs the value in its environment, as when it invokes a script that reads it.

Target-Specific and Pattern-Specific Variables

A variable can be given a different value for one target and everything beneath it in the graph. The syntax hangs an assignment off a target:

target: VARIABLE = value

This is how build variants are done without duplicating rules. The classic is a debug build:

CFLAGS := -Wall -O2

app: main.o util.o
    $(CC) $(CFLAGS) -o $@ $^

debug: CFLAGS += -g -O0 -DDEBUG
debug: app

Running make app compiles with -Wall -O2. Running make debug compiles the same rules with -Wall -O2 -g -O0 -DDEBUG. One set of rules, two configurations.

The critical detail is the scope: the value applies to the named target and to every prerequisite reached through it. That is what makes the example work at all, since the flags need to reach main.o and util.o, which are built by rules that never mention debug. This inheritance is a genuine exception to Make’s otherwise flat, global variable model, and it is the only scoping mechanism the language has.

WarningVariant builds and stale objects

make debug after make reuses whatever .o files already exist, because the object files are up to date by timestamp and Make has no idea the flags changed. You get a mix of optimized and unoptimized objects and a confusing debugging session. The simple fix is make clean between variants; the better one is to put each variant’s objects in its own directory (build/debug/, build/release/) so they cannot collide. Content-hashing build systems track flag changes as inputs and rebuild correctly; Make does not.

Pattern-specific variables generalize the same idea to a pattern rather than a named target, which is useful for treating one class of file differently:

%.o: CFLAGS += -fPIC          # every object file gets -fPIC
generated/%.o: CFLAGS += -w   # but generated sources compile without warnings

Automatic Variables

Inside a recipe, Make defines a set of variables describing the rule currently being executed. They are what make pattern rules possible: a single rule cannot name its target and prerequisites literally, so it refers to them positionally.

Variable Expands to
$@ The target
$< The first prerequisite
$^ All prerequisites, duplicates removed
$+ All prerequisites, duplicates kept, in order
$? Only the prerequisites newer than the target
$* The stem: the part matched by % in a pattern rule
$| The order-only prerequisites

Each also has directory and file variants, formed by adding D or F: $(@D) is the target’s directory, $(@F) its filename. $(<D) and $(<F) do the same for the first prerequisite. These are why the @mkdir -p $(@D) idiom from Order-Only Prerequisites works.

Here they are at work in a realistic pattern rule:

build/%.o: src/%.c include/config.h | build
    @echo "compiling $* ..."
    $(CC) $(CFLAGS) -c $< -o $@

Building build/parser.o from this rule gives:

Variable Value
$@ build/parser.o
$< src/parser.c
$^ src/parser.c include/config.h
$* parser
$| build
$(@D) build

Note why $< rather than $^ is passed to the compiler. $^ would include include/config.h, and handing a header to gcc -c as a second input is an error. The pattern is nearly universal: $< for compilation, where exactly one input is the source, and $^ for linking, where all the inputs genuinely are inputs:

app: $(OBJS)
    $(CC) $(LDFLAGS) -o $@ $^      # every object goes on the link line

$? is the specialist of the group, expanding to only those prerequisites newer than the target. Its natural use is a target that can be updated incrementally rather than rebuilt, such as an archive:

libutil.a: $(OBJS)
    ar rcs $@ $?            # replace only the members that changed
ImportantAutomatic variables exist only inside recipes

They describe the rule being executed, so they have no meaning anywhere else. Using $@ in a plain variable assignment at the top of a file yields an empty string, silently. The exception is the right-hand side of a target-specific variable, which is evaluated in the context of its target and can therefore see them.

Two-Phase Evaluation

Why makefiles do not read top to bottom

Make does not execute a makefile the way a shell executes a script. It runs the file twice, in two distinct passes over different parts of it. Nearly every remaining Make mystery, $(shell date) reporting the wrong time, $(wildcard) not seeing generated files, $$ in shell loops, is a consequence of this split.

The two phases:

Phase 1, read. Make reads every makefile (and everything they include), expands the macro language, evaluates conditionals and $(shell) calls, and assembles the dependency graph. Nothing is compiled. Nothing on disk changes. At the end of this phase Make has a complete, fully-expanded picture of what depends on what, and a set of recipes still stored as unexpanded text.

Phase 2, run. Make walks the graph from the requested goal, decides which targets are stale, and for each one it must rebuild, expands that recipe’s text and hands the result to the shell.

The dividing line is the tab. Everything at the left margin is phase 1; everything tab-indented is phase 2. That is the same boundary as the three languages, viewed on a timeline instead of a page: the rule and macro languages are read first and completely, and only then does the shell language start running.

TipA diagnostic question

When something in a makefile behaves impossibly, ask “which phase is this in?” A value that is empty when you expected content is usually phase 1 looking for something phase 2 has not created yet. A $ that vanished is phase 1 consuming something phase 2 needed. Almost nothing else produces those two symptoms.

What Runs When

The consequences are specific enough to enumerate.

$(shell) in a variable runs at parse time. A timestamp captured this way records when Make read the file, not when the recipe ran:

BUILD_TIME := $(shell date +%T)

app: main.o
    @echo "starting link at $$(date +%T)"
    @echo "BUILD_TIME says $(BUILD_TIME)"
    $(CC) -o $@ $^

On a build where compilation takes a minute, those two lines print times a minute apart. $(BUILD_TIME) was frozen before the first object file was compiled. That is usually what you want for stamping a version into a binary, and it is emphatically not a way to time a build step.

$(wildcard) cannot see files a recipe will create. This is the same fact with a sharper edge:

# BROKEN: OBJS is empty on a clean tree
OBJS := $(wildcard build/*.o)

app: $(OBJS)
    $(CC) -o $@ $^

On the first run, build/ is empty or missing, $(wildcard) returns nothing, and app links against no objects. Run make a second time and it works, because now the files exist at parse time. A makefile that only builds correctly on the second invocation is nearly always this bug. The fix is to derive the object list from the sources, which do exist when the file is read:

SRCS := $(wildcard src/*.c)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))

Conditionals are decided in phase 1. An ifeq cannot test anything a recipe produced, because no recipe has run yet:

# BROKEN: the test happens before the compiler ever runs
ifeq ($(wildcard build/app),)
    $(info app does not exist yet)
endif

Conditionals are for configuration (platform, toolchain, build variant), all of which is knowable at parse time. Anything that must be decided from the state of the build belongs in the recipe, where it is written as a shell if.

Recipes are expanded in phase 2, which is why $$ exists. Make expands a recipe’s $(...) and $ references immediately before handing the text to the shell. A $ intended for the shell must be escaped as $$ so it survives that pass:

list:
    for f in *.c; do echo "found $$f"; done

Written as $f, Make would expand it first, find no variable named f, substitute the empty string, and the shell would receive echo "found ". Silently, with no error, on every iteration. The rule is mechanical: inside a recipe, $(...) is Make’s, $$ is the shell’s.

Immediate and Deferred

The GNU Make manual describes the same split in terms of when a given expansion happens, and the vocabulary is worth having because the manual uses it everywhere.

Construct Expanded
VAR := value Immediately (phase 1)
VAR = value Deferred, on each reference
Target and prerequisite lists Immediately (phase 1)
Recipe lines Deferred (phase 2)
Right-hand side of a target-specific variable Deferred, when the target is considered

The row that surprises people is the third: prerequisite lists are expanded during the read phase, along with the targets. This is why a variable used in a prerequisite list must have its final value by the time Make reaches that line, and why a $(wildcard) there is frozen at parse time.

$(eval)

Writing Makefile text at parse time

Because phase 1 is a text-processing pass, Make provides a way to feed generated text back into it. $(eval ...) takes a string and parses it as makefile source, right there during the read phase:

PROGRAMS := server client monitor

define program_rule
$(1): $(1).o common.o
    $$(CC) $$(LDFLAGS) -o $$@ $$^
endef

$(foreach p,$(PROGRAMS),$(eval $(call program_rule,$(p))))

This generates three complete rules from one template. Note the doubled $$ in the template body: the first expansion (of $(call ...)) must leave $(CC), $@, and $^ intact so that $(eval) sees them as makefile text, and phase 2 expands them later. Getting the number of $ right is the entire difficulty of eval, and it is why heavily generated makefiles become unreadable.

Warningeval is a last resort

It is the one construct that lets a makefile write itself, which makes it powerful and makes debugging miserable: the file you are reading is not the file Make built its graph from. Before reaching for it, check whether a static pattern rule or a plain pattern rule does the job. When you do use it, make -p will show you the rules that were actually generated.

Pattern Rules and Implicit Rules

One rule for a whole class of files

The makefile in A Complete Small Makefile has two nearly identical rules, differing only in a filename. At two files that is mild redundancy. At two hundred it is unmaintainable, and every added source file is an opportunity to forget a line.

An implicit rule solves this by describing a class of transformation rather than a single instance: “any .o file can be built from the .c file of the same name, like this.” Make then applies it wherever it needs a target that no explicit rule covers. This is the machinery that turns a hundred-file build back into a makefile you can read in one screen.

There are two spellings, one obsolete and one current, plus a controlled variant worth preferring over both.

Suffix Rules

The original form, standardized by POSIX and still lurking in old makefiles, keys off filename suffixes. The target is the concatenation of the source suffix and the target suffix:

.SUFFIXES: .c .o

.c.o:
    $(CC) $(CFLAGS) -c $< -o $@

.c.o: reads backwards from what you would guess: it means “to make a .o from a .c”, source first. Only suffixes listed in .SUFFIXES participate, which is why the declaration is there.

The form is genuinely limited. It can only match on suffixes, so it cannot express build/%.o: src/%.c, cannot match a whole filename, and cannot handle a name with no suffix at all. Directory-separated builds are impossible to write with it, which is most of why it was superseded.

Know it well enough to read it, and write pattern rules instead. If you inherit a makefile with suffix rules, they still work; GNU Make supports both.

Pattern Rules

The modern form uses % as a wildcard matching one or more characters:

%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

The text matched by % is the stem, and it must be the same on both sides. Building parser.o matches this rule with a stem of parser, which makes the prerequisite parser.c. The automatic variables then carry the specifics into the recipe: $< is parser.c, $@ is parser.o, and $* is the stem itself.

That one rule replaces every hand-written compile rule in the project. Here is the small makefile rewritten with it:

CC     := gcc
CFLAGS := -Wall

OBJS := main.o util.o

app: $(OBJS)
    $(CC) -o $@ $^

%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

main.o util.o: util.h

.PHONY: clean
clean:
    -rm -f app *.o

Adding a source file now means adding one word to OBJS. The pattern rule does not change.

Note the recipe-less rule near the bottom, the form introduced in Rules Without Recipes. It contributes the header dependency to targets whose recipe comes from the pattern rule. Prerequisites from an explicit rule and a pattern rule are combined, not overridden, which is exactly the mechanism Auto-Generated Dependencies relies on.

Paths and the Stem

Because % matches directory separators too, pattern rules handle out-of-tree builds directly:

build/%.o: src/%.c | build
    $(CC) $(CFLAGS) -c $< -o $@

Building build/net/socket.o gives a stem of net/socket and a prerequisite of src/net/socket.c. The % spans the subdirectory without any special handling. This is the shape most real makefiles use, and it is worth noting that the target’s directory must exist before the compiler writes into it, hence the order-only | build. For nested output directories, @mkdir -p $(@D) in the recipe is the more robust choice.

How Make Chooses Among Candidates

When Make needs a target with no explicit recipe, it searches its pattern rules for one whose target pattern matches. Several may. The resolution rules, in order:

  1. A rule whose prerequisites already exist or can be built wins over one whose cannot. A rule that would require a nonexistent foo.y is discarded in favor of one needing an existing foo.c.
  2. Among viable rules, the one with the shortest stem wins. This makes the most specific pattern win: matching build/net/socket.o against build/%.o (stem net/socket) and build/net/%.o (stem socket) selects the latter.
  3. Among equal stems, the first rule in the file wins. Order matters only after specificity fails to decide.

The practical consequence is that you can layer a special case over a general one:

%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

generated/%.o: generated/%.c
    $(CC) $(CFLAGS) -w -c $< -o $@       # generated code compiles warning-free

NotePattern rules never fail for lack of a match

An explicit rule for a missing prerequisite is an error: No rule to make target 'foo.c'. A pattern rule that does not match is simply not used, silently, and Make moves on to try another. A typo in a pattern rule therefore does not announce itself; it just quietly stops applying, and you get a mystifying error from a different rule further along. Static pattern rules exist partly to close this gap.

Built-in Rules and Why to Disable Them

GNU Make ships with a substantial catalog of built-in pattern rules and variables, ready before it reads a single line of your file. This is why the following builds:

$ ls
hello.c
$ make hello
cc     hello.c   -o hello

There is no makefile at all. Make’s built-in rules know how to link an executable from a C source, and its built-in variables supply CC = cc and an empty CFLAGS. You can see the whole table:

make -p -f /dev/null        # print the built-in database with no makefile

The output runs to several hundred lines and covers C, C++, Fortran, Pascal, Modula-2, Ratfor, assembly, Lex, Yacc, RCS, and SCCS. Some of those languages have been dead for thirty years, and the rules for them are still consulted on every target lookup.

That catalog causes two real problems in a serious makefile.

Surprising builds. A target you did not write a rule for may nonetheless build, using flags you never chose, from a source you did not intend. A stray .c file in a directory can be compiled by a rule you have never seen, producing an object that quietly joins your link line via a wildcard. Worse, a built-in rule can shadow the behavior you expected: the built-in %.o: %.c uses $(CC) $(CPPFLAGS) $(CFLAGS), so a makefile that sets only CFLAGS inherits a compile line it never wrote.

Wasted work. For every target it cannot resolve explicitly, Make tries the built-in patterns in order, stating candidate prerequisites for each. On a large project this is thousands of pointless filesystem calls, and it is measurable: disabling built-ins commonly cuts a no-op build’s time by a third or more.

Turn them off. The command-line flag is -r (--no-builtin-rules), and its companion -R (--no-builtin-variables), but a makefile should not depend on the user remembering to pass them. Set it in the file:

MAKEFLAGS += --no-builtin-rules --no-builtin-variables

MAKEFLAGS is read by Make itself and applies to the current invocation and to any recursive sub-makes. The older, POSIX-portable equivalent clears the suffix list, which disables suffix rules but not pattern rules:

.SUFFIXES:            # empty list: no suffix rules apply

Both are worth having in a makefile of any size. Once built-ins are off, every rule that fires is one you wrote, and an unbuildable target says so instead of silently finding an ancient Ratfor rule that half-applies.

WarningDisabling built-in variables means defining your own

--no-builtin-variables removes CC, CFLAGS, AR, and the rest of the default table. If your makefile relied on CC defaulting to cc, it will now invoke the empty string. Define what you use explicitly, which is better practice regardless: an explicit CC := gcc documents the toolchain, and CC ?= gcc lets the user override it.

Static Pattern Rules

A pattern rule applies to anything that matches, which is more freedom than you usually want. A static pattern rule applies the same pattern to an explicit list of targets, and nothing else:

targets: target-pattern: prereq-pattern
    recipe

Three colon-separated parts instead of two. The first is the list of targets the rule governs; the second is the pattern each of them is matched against to extract a stem; the third builds the prerequisite from that stem.

OBJS := main.o util.o parser.o

$(OBJS): %.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

This behaves like %.o: %.c restricted to exactly those three objects. A stray.o in the directory will not be built by it.

The advantage is diagnostics. With an ordinary pattern rule, a target that fails to match is silently skipped and the error surfaces somewhere else. With a static pattern rule, a target in the list that does not match its pattern is an error at parse time, naming the file:

*** target 'README' doesn't match the target pattern.  Stop.

That difference matters more than it sounds. A build system that fails loudly at the point of the mistake is worth real ergonomic cost, and here the cost is one extra field.

Static pattern rules also let one target list drive several transformations, which is awkward otherwise:

SRCS := $(wildcard src/*.c)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))
DEPS := $(patsubst src/%.c,build/%.d,$(SRCS))

$(OBJS): build/%.o: src/%.c | build
    $(CC) $(CFLAGS) -MMD -MP -c $< -o $@
TipPrefer static pattern rules when you know the list

Which is most of the time: the object list is nearly always computed from a source list you already have. Reserve bare pattern rules for genuinely open-ended cases, like a rule that any target might reach through chaining. The failure modes of the two are what separates them, not the expressiveness.

VPATH and vpath

By default Make looks for prerequisites relative to the directory it was invoked from. VPATH adds a search path for files it cannot find there:

VPATH = src:src/net:src/util

%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

Now socket.o can be built even though socket.c is in src/net/. Make searches the VPATH directories in order, finds it, and $< expands to the found path, src/net/socket.c, so the recipe works unchanged. The directive form vpath (lowercase) restricts the search to a pattern, which is a little less blunt:

vpath %.c src:src/net
vpath %.h include

This is real functionality solving a real problem, and it is also the feature in this chapter most likely to cost you an afternoon. The trouble is asymmetry: VPATH affects where prerequisites are found, and has no effect at all on where targets are written. $@ is whatever the rule named, unaffected by the search. So the rule above finds src/net/socket.c and writes socket.o into the current directory, flattening a structured source tree into a pile of objects in one place. Two files named socket.c in different subdirectories then collide, silently, with the second overwriting the first’s object.

The other failure is subtler. If a stale copy of a file exists in an earlier VPATH directory, Make finds that one instead of the one you are editing, and the build compiles a file you are not looking at. Debugging that requires knowing VPATH is involved at all, which is not visible from the rule.

The alternative is to construct paths explicitly, which is what most modern makefiles do:

SRCS := $(wildcard src/*.c src/net/*.c src/util/*.c)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))

$(OBJS): build/%.o: src/%.c
    @mkdir -p $(@D)
    $(CC) $(CFLAGS) -c $< -o $@

More text, and every path is stated rather than searched for. Object files mirror the source layout, so nothing collides, and reading a rule tells you exactly which file it compiles. VPATH earns its place mainly in one situation: an out-of-tree build where you run Make from a build directory and point it back at the source tree, which is how Autotools builds work. That is a legitimate use. For a build you write yourself, prefer explicit paths.

Functions

Text transformations over space-separated words

Make’s function library looks intimidating in the manual and is small in practice, because every function does a variant of the same thing: take a string, treat it as a list of words separated by whitespace, and produce another string. There are no numbers, no arrays, no dictionaries, no local scope, and no return values other than text. A “list” in Make is a string that happens to contain spaces, and the only structure it has is where those spaces fall.

Accepting that up front makes the library predictable. $(words ...) returns the count as the text of a number. $(sort ...) sorts words alphabetically and removes duplicates because that is what sorting a word list means to Make. There is no other layer underneath.

The call syntax is a function name, whitespace, then comma-separated arguments:

$(function arg1,arg2,arg3)

The separator between the name and the first argument is whitespace; every separator after that is a comma. Leading whitespace in an argument is stripped, trailing whitespace is not, and a literal comma inside an argument has to be smuggled in through a variable holding one. These are the sharp edges, and they account for most function-related confusion.

Text Manipulation

Function Result
$(subst from,to,text) Replace every occurrence of from; plain text, no wildcards
$(patsubst pat,repl,text) Replace each word matching pat, where % is the wildcard
$(strip text) Collapse internal whitespace, remove leading and trailing
$(findstring find,in) find if present, empty otherwise
$(filter pat...,text) Words matching any pattern
$(filter-out pat...,text) Words matching none of the patterns
$(sort list) Sorted, duplicates removed
$(word n,text) The nth word, 1-indexed
$(wordlist s,e,text) Words s through e inclusive
$(words text) How many words
$(firstword text) The first word; $(lastword text) for the last

Worked, with the result in a comment:

SRCS := main.c util.c parser.c

$(info $(patsubst %.c,%.o,$(SRCS)))          # main.o util.o parser.o
$(info $(subst .c,.o,$(SRCS)))               # main.o util.o parser.o  (see below)
$(info $(filter %.c,$(SRCS) README.md))      # main.c util.c parser.c
$(info $(filter-out main.c,$(SRCS)))         # util.c parser.c
$(info $(words $(SRCS)))                     # 3
$(info $(sort b a c a))                      # a b c

subst and patsubst produce the same answer above and are not interchangeable. subst is a blind substring replacement with no notion of words, so $(subst .c,.o,src.check/main.c) mangles the directory name into src.oheck/main.o. patsubst anchors its pattern to whole words, which is almost always what you meant. Use patsubst.

patsubst has a shorthand that appears constantly in real makefiles:

OBJS := $(SRCS:.c=.o)                # identical to $(patsubst %.c,%.o,$(SRCS))
OBJS := $(SRCS:%.c=build/%.o)        # the general form, with %

Two idioms are worth recognizing on sight. $(sort ...) is frequently used purely to deduplicate, the ordering being incidental, which is how a list of include directories gets cleaned up. And $(filter ...) is the standard way to test membership, since Make has no boolean type:

ifeq ($(filter debug,$(MAKECMDGOALS)),debug)
    CFLAGS += -g -O0
endif

$(strip ...) matters more than it looks. Trailing whitespace in a Make variable is real, invisible, and load-bearing: ifeq ($(MODE),debug) fails against MODE := debug with a trailing space, and nothing in the error tells you why. Strip anything that came from a $(shell) call or a hand-edited configuration block before comparing it.

Filenames

These treat each word as a path and decompose it.

Function On src/net/socket.c Notes
$(dir ...) src/net/ Keeps the trailing slash
$(notdir ...) socket.c The filename alone
$(basename ...) src/net/socket Strips the suffix, keeps the path
$(suffix ...) .c Includes the dot
$(addprefix p,...) $(addprefix build/,$(notdir ...)) Prepends to every word
$(addsuffix s,...) $(addsuffix .o,names) Appends to every word
$(join a,b) pairwise concatenation Rarely what you want
$(realpath ...) absolute, symlinks resolved Empty if the file does not exist
$(abspath ...) absolute, symlinks kept Works on nonexistent paths

All of them map over the whole list, so $(notdir src/a.c src/b.c) yields a.c b.c.

$(wildcard pattern) is the one that touches the filesystem, expanding a glob into the matching filenames:

SRCS := $(wildcard src/*.c)

It is also the function most likely to produce a build that only works the second time. $(wildcard) runs during phase 1, so it sees the tree as it was when Make read the file, not as a recipe will leave it. Globbing an output directory is therefore always wrong:

OBJS := $(wildcard build/*.o)         # empty on a clean tree, forever wrong

Derive outputs from inputs instead. Glob the sources, which exist at parse time, and transform them:

SRCS := $(wildcard src/*.c)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))
Note$(wildcard) and the missing file

A glob matching nothing expands to nothing, silently. A typo in a directory name gives you an empty SRCS, an empty OBJS, and a link command with no inputs, whose error message is about the linker rather than about the path you got wrong. When a build fails inexplicably early, $(info SRCS = $(SRCS)) is the first thing to add.

Control and Iteration

Make has no loops in the ordinary sense. $(foreach ...) is a text-generating construct: it binds a variable to each word in turn, expands a body, and concatenates the results with spaces.

DIRS := src lib tools
$(info $(foreach d,$(DIRS),-I$(d)/include))
# -Isrc/include -Ilib/include -Itools/include

The variable d exists only inside the expansion. This is Make’s only local binding, and it is why foreach shows up wherever a per-item transformation is too irregular for addprefix.

$(if condition,then,else) tests whether its first argument expands to a non-empty string. There is no boolean type, so non-empty is true and that is the whole semantics:

CFLAGS += $(if $(DEBUG),-g -O0,-O2)

$(or ...) and $(and ...) follow the same convention, returning the first non-empty argument and the last argument respectively, with short-circuiting.

$(call ...) invokes a user-defined function, which is just a variable whose body refers to $(1), $(2), and so on:

# $(call check_tool,name)
check_tool = $(if $(shell command -v $(1)),,$(error $(1) not found in PATH))

$(call check_tool,arm-none-eabi-gcc)
$(call check_tool,openocd)

Define these with =, never :=. A simply expanded variable evaluates its $(1) at definition time, when no arguments exist, and freezes the empty result. This is the single most common call bug.

Multi-line bodies use define:

define compile_and_size
    $(CC) $(CFLAGS) -c $< -o $@
    @$(SIZE) $@
endef

$(eval ...) parses generated text as makefile source. It belongs to phase 1 and is covered in Two-Phase Evaluation, along with the reason its $ counting is so error-prone. The short version: use it to generate a family of near-identical rules from a list, and reach for static pattern rules first.

shell, and When It Runs

$(shell command) runs a command through /bin/sh, captures its standard output, strips the trailing newline, and converts every remaining newline to a space. That last conversion is deliberate: it turns command output into a Make word list.

VERSION  := $(shell git describe --tags --always)
NPROC    := $(shell nproc)
SOURCES  := $(shell find src -name '*.c')

Two things about it deserve care.

It runs during phase 1, before anything is built. This is the trap described in What Runs When, and it is worth restating with a case that looks reasonable:

# BROKEN: the objects do not exist when this line is read
TOTAL_SIZE := $(shell cat build/*.o | wc -c)

app: $(OBJS)
    $(CC) -o $@ $^
    @echo "objects totalled $(TOTAL_SIZE) bytes"

The cat runs before the first compile, fails, and TOTAL_SIZE is empty. Anything that must observe the state of the build after work has happened belongs in a recipe, where it is written as ordinary shell:

app: $(OBJS)
    $(CC) -o $@ $^
    @echo "objects totalled $$(cat $^ | wc -c) bytes"

Note the $$(...): that is shell command substitution, escaped so it survives Make’s expansion.

The assignment flavor decides how many times it runs. With =, the command re-runs on every single reference:

VERSION  = $(shell git describe --tags)      # forks git on every use
VERSION := $(shell git describe --tags)      # forks git exactly once

In a makefile that stamps $(VERSION) into a dozen compile lines, the first spelling is a dozen git invocations, each one a process spawn and a repository read. Combined with the built-in rule search, this is the usual explanation for a makefile that takes a noticeable pause before doing anything. Use := for $(shell) unless you have a specific reason not to.

$(shell) also sets .SHELLSTATUS to the command’s exit code, which is how you check whether it actually succeeded:

GIT_TAG := $(shell git describe --tags 2>/dev/null)
ifneq ($(.SHELLSTATUS),0)
    GIT_TAG := unknown
endif

Without that check, a failed command yields an empty string that is indistinguishable from a command that succeeded and printed nothing.

error, warning, info

These are Make’s entire diagnostic vocabulary, and they are the tools you debug the macro language with.

Function Output goes to Prefixed with file:line Stops the build
$(info text) stdout No No
$(warning text) stderr Yes No
$(error text) stderr Yes Yes, immediately

$(info) is printf debugging for phase 1. Because everything in Make is text and expansion order is the usual culprit, dumping a variable at a specific point in the file answers most questions faster than any other technique:

$(info CFLAGS  = $(CFLAGS))
$(info OBJS    = $(OBJS))
$(info nothing = "$(MAYBE_UNSET)")     # quotes make an empty value visible

Wrapping the value in quotes is the trick for distinguishing empty from whitespace, which a bare $(info) cannot show you.

$(warning) differs mainly in carrying its location, which makes it the better choice inside a variable definition or a function body where you need to know which expansion you are watching. Since it expands to nothing, it can be embedded in a value without disturbing it:

CFLAGS := $(warning computing CFLAGS)-Wall -O2

$(error) aborts. Its purpose is failing fast, at configure time, with a message a human can act on, rather than letting the build proceed to a confusing failure fifty lines of compiler output later. The guard-clause idiom is the canonical use:

ifndef TOOLCHAIN
    $(error TOOLCHAIN is not set. Try: make TOOLCHAIN=arm-none-eabi-)
endif

ifeq ($(wildcard $(LINKER_SCRIPT)),)
    $(error linker script not found: $(LINKER_SCRIPT))
endif

Both checks run during phase 1, so they fire before a single compiler is invoked. Compare that with the alternative: no guard, a cross-compiler that does not exist, and a hundred lines of command not found before anything says what is wrong.

Warning$(error) fires when it is expanded, not where it is written

Inside a recursively expanded variable, the error triggers on first use, which may be far from the definition and may not happen at all. Put guard clauses at the top level of the file where they expand immediately, or inside a conditional as above. An $(error) hidden in a = variable that is never referenced is a check that silently does not exist.

Conditionals

Configuration decided at read time

Conditionals let a makefile take different shapes on different platforms, toolchains, or build variants. They look like C preprocessor directives and behave differently in two ways that matter.

ifeq ($(CC),gcc)
    CFLAGS += -Wno-unused-result
endif

The four openers, with else and endif closing them:

Directive True when
ifeq (a,b) The two expand to the same text
ifneq (a,b) They do not
ifdef VAR VAR expands to something non-empty
ifndef VAR VAR is undefined or empty

ifeq accepts three interchangeable spellings, and the quoted forms are worth knowing because they survive values containing spaces or commas:

ifeq ($(MODE),debug)
ifeq "$(MODE)" "debug"
ifeq '$(MODE)' 'debug'

else if chains are written as else ifeq, with a single endif closing the whole chain:

ifeq ($(ARCH),x86_64)
    CFLAGS += -march=x86-64-v2
else ifeq ($(ARCH),aarch64)
    CFLAGS += -mcpu=generic
else
    $(error unsupported ARCH: $(ARCH))
endif

They Are Not the Preprocessor

Two differences separate these from #ifdef, and both bite.

They are evaluated in phase 1. A conditional is resolved while Make reads the file, before any recipe has run, which is the constraint described in What Runs When. It can test a variable, the environment, or the output of a $(shell) call, because all of those are knowable at read time. It cannot test anything the build produced, because nothing has been built yet. Logic that depends on the state of the build belongs in a recipe, written as a shell if.

Indentation is dangerous. A conditional indented with a tab becomes a recipe line, handed to the shell rather than interpreted by Make:

app: main.o
    ifeq ($(DEBUG),1)          # TAB: this is now a shell command
    ...

The shell has no ifeq, so you get ifeq: command not found, an error that says nothing about makefiles. Indent conditional bodies with spaces if you indent them at all. This is the one place in a makefile where spaces are correct and a tab is a bug, which is the exact inverse of the rule for recipes and catches people accordingly.

WarningConditionals inside a recipe are shell, not Make

Once you are inside a tab-indented recipe, ifeq is unavailable and shell syntax is what you have:

app: main.o
    if [ "$(DEBUG)" = "1" ]; then echo "debug build"; fi

Note this is a shell conditional testing text that Make already substituted. Because each recipe line is its own shell, a multi-line shell if needs &&/\ continuation or .ONESHELL.

ifdef and the Empty-String Trap

ifdef does not test whether a variable is defined. It tests whether it expands to something non-empty, and a variable set to the empty string is defined but reads as false:

EMPTY :=

ifdef EMPTY
    $(info this does not print)
endif

That is usually the behavior you want, since an empty flag variable is normally as good as unset. When you genuinely need to distinguish “never set” from “set to nothing,” $(origin) answers precisely:

ifeq ($(origin CFLAGS),undefined)
    $(info CFLAGS was never set anywhere)
endif

$(origin VAR) returns undefined, default, environment, file, command line, override, or automatic, which maps directly onto the precedence table in Where Values Come From. It is the tool for answering “where did this value come from,” and it pairs with $(flavor VAR) (simple, recursive, or undefined) when the question is how a variable was assigned.

There is one more subtlety: ifdef expands the variable’s name, not its value, so it does not trigger a recursive expansion. For a variable defined with = whose body calls $(shell), ifdef will still run that shell command to determine emptiness, which is an easy way to fork a process from a line that looks like a pure test.

NotePOSIX has no conditionals

ifeq and friends are GNU extensions. POSIX make has no conditional syntax at all, which is why portable makefiles from the Autotools era push configuration into a generated config.mk that is included, rather than branching in the makefile itself. If a makefile must run under BSD make, that generated-include approach is the portable path. Everything in this section assumes GNU Make.

Practical Uses

Three patterns cover most real conditionals.

Platform detection, via uname:

UNAME_S := $(shell uname -s)

ifeq ($(UNAME_S),Darwin)
    LDFLAGS += -framework CoreAudio
    SO_EXT  := dylib
else ifeq ($(UNAME_S),Linux)
    LDFLAGS += -lasound
    SO_EXT  := so
endif

:= matters here: with =, every reference to UNAME_S forks another uname.

Build variants, driven from the command line:

BUILD ?= release

ifeq ($(BUILD),debug)
    CFLAGS += -g -O0 -DDEBUG -fsanitize=address
    LDFLAGS += -fsanitize=address
else
    CFLAGS += -O2 -DNDEBUG
endif

BUILD_DIR := build/$(BUILD)

Invoked as make BUILD=debug. Note the last line: deriving the output directory from the variant is what keeps debug and release objects from colliding, the hazard flagged in Target-Specific and Pattern-Specific Variables. This is why a conditional is often the better tool for a variant than a target-specific variable, since a conditional can also relocate the outputs.

Toolchain guards, failing fast on a missing prerequisite:

ifeq ($(shell command -v $(CC) 2>/dev/null),)
    $(error compiler not found: $(CC))
endif

One further construct: $(MAKECMDGOALS) holds the goals named on the command line, which lets a makefile skip expensive setup for targets that do not need it. The common case is not generating dependency files during make clean:

ifeq ($(filter clean distclean,$(MAKECMDGOALS)),)
    -include $(DEPS)
endif

Without that guard, make clean reads every .d file, and worse, regenerates any that are missing before deleting them all. The $(filter ...) idiom is doing membership testing here, exactly as described in Text Manipulation.

Multiple Files

Splitting a build, and the idiom that makes it correct

include and -include

include splices another file into the current one at that point, as though its text had been typed there:

include config.mk

Multiple files and globs both work, and the included file is ordinary makefile source: variables, rules, conditionals, anything. The usual reason to reach for it is a shared configuration block that several makefiles need:

# config.mk
CC       ?= gcc
CFLAGS   := -Wall -Wextra -std=c17
PREFIX   ?= /usr/local

A missing file is a fatal error. Prefix the directive with a dash and Make carries on silently instead:

-include $(DEPS)          # fine if none of these exist yet

That distinction looks minor and is the hinge of the next section. A build’s generated dependency files do not exist before the first compile, so requiring them would make a clean tree unbuildable.

The Restart Mechanism

There is a subtlety here that is easy to miss and genuinely clever. When Make cannot find an included file, it does not simply give up. It first checks whether it knows a rule to build that file. If so, it builds it, and then restarts itself from the beginning, re-reading every makefile with the now-existing include in place.

config.mk: config.mk.in
    ./configure-script $< > $@

include config.mk

Running make on a tree with no config.mk generates it, then re-executes with the generated values in scope. You can watch it happen with make --debug=b, which prints Re-executing.

This is how a makefile bootstraps its own configuration, and it is the mechanism behind CMake re-running itself when you edit a CMakeLists.txt, noted in Reading a CMake Project. It is also why an infinite restart loop is possible: a rule whose recipe always updates its target’s timestamp will rebuild, restart, rebuild, forever. If make hangs producing no output, a self-regenerating include is the first suspect.

Auto-Generated Dependencies

The idiom that makes a C build actually correct

This is the most practically important section in the chapter. Nearly every makefile that “works but needs make clean sometimes” is missing exactly this.

The Problem: Your Prerequisites Are a Lie

Consider the honest-looking rule:

main.o: main.c
    $(CC) $(CFLAGS) -c $< -o $@

It is wrong, and it is wrong in the way How Make Decides What to Rebuild warned about. main.c does not depend only on itself. It includes headers:

#include "config.h"
#include "util.h"

Editing config.h changes what main.o should contain. Make has no idea. It cannot read C, does not know #include exists, and sees only the prerequisite you declared. So main.o is left alone, the object file continues to reflect the old header, and you get a binary built half from one version of a struct and half from another.

That last failure is worth dwelling on because of how it presents. Change a field in a struct, rebuild, and the objects that were recompiled use the new layout while the ones that were skipped use the old. The program links without complaint and then corrupts memory at runtime, with a stack trace pointing nowhere near the header you edited. Every C programmer has lost hours to this, and the reflex it teaches (make clean whenever anything is odd) is a workaround for a broken dependency graph.

The obvious fix is to write the headers down:

main.o: main.c config.h util.h

This is correct today. It drifts tomorrow. Headers include other headers, so the true list is the transitive closure of the include graph, and it changes every time anyone adds an #include anywhere. Maintaining it by hand across a hundred files is not merely tedious, it is a task nobody actually performs, which is why the lists in old makefiles are always subtly wrong.

The Solution: Ask the Compiler

The compiler resolves every #include as part of its normal work, so it already knows the exact transitive list. GCC and Clang will write it out in makefile syntax.

-MMD compiles as usual and additionally emits a .d file beside the object:

$ gcc -MMD -c main.c -o build/main.o
$ cat build/main.d
build/main.o: main.c config.h util.h /usr/include/stdio.h ...

That is a rule without a recipe, precisely the form that contributes prerequisites to a target whose recipe comes from elsewhere. Include it and Make’s graph becomes true.

The complete idiom is four lines:

SRCS := $(wildcard src/*.c)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))
DEPS := $(OBJS:.o=.d)

$(OBJS): build/%.o: src/%.c | build
    $(CC) $(CFLAGS) -MMD -MP -c $< -o $@

-include $(DEPS)

Reading it in order: derive objects from sources, derive dependency filenames from objects, compile with the flags that emit them, and include them if they exist. On the first build the .d files are absent, -include shrugs, and everything compiles because nothing exists yet anyway. Each compile writes its .d. Every subsequent build reads them, and header edits now propagate correctly.

What the Flags Mean

Flag Effect
-M Emit dependencies to stdout instead of compiling
-MM Same, but omit system headers
-MD Compile and write a .d file, including system headers
-MMD Compile and write a .d file, omitting system headers
-MP Add a phony target for each header listed
-MF Name the dependency file explicitly
-MT Override the target name written into the rule

-MMD is the standard choice. -MD includes /usr/include/stdio.h and friends, which is technically more correct and practically noise: system headers change when you upgrade libc, at which point you were going to rebuild everything anyway. Omitting them keeps the .d files small and the graph focused on your code.

When objects go in a separate directory, the target written into the .d file must match the target Make is building. -MMD handles this correctly on modern GCC and Clang because it derives the name from -o, but older toolchains write a bare main.o rather than build/main.o, producing a rule for a target that does not exist. -MT fixes it explicitly:

    $(CC) $(CFLAGS) -MMD -MP -MT $@ -MF $(@:.o=.d) -c $< -o $@

Worth knowing when a dependency setup silently fails to trigger rebuilds.

Why -MP Matters

-MP looks like a curiosity and prevents a specific, infuriating failure. It adds an empty phony target for every header:

build/main.o: main.c config.h util.h

config.h:
util.h:

Now delete util.h, because you refactored and nothing needs it anymore. Without -MP, the stale .d file still lists it as a prerequisite of build/main.o, and Make refuses to proceed:

make: *** No rule to make target 'util.h', needed by 'build/main.o'.  Stop.

The build is wedged. The file that references the deleted header is a generated artifact you did not know existed, in a directory you never look at, and the only recovery most people find is make clean. With -MP, the header has its own rule producing nothing, so Make treats it as buildable-and-up-to-date, rebuilds main.o, and the fresh .d no longer mentions the deleted file. The problem resolves itself in one build.

Always pass both. -MMD -MP is effectively one flag with a space in it.

Importantclean must remove the .d files

Dependency files are build artifacts. Leaving them behind after make clean means the next build reads dependency data describing a tree that no longer exists. Removing the whole build directory is the simplest correct answer:

.PHONY: clean
clean:
    -rm -rf build

This is another argument for putting objects and .d files in a build directory rather than beside the sources, where cleaning them means globbing for artifacts and hoping the pattern is right.

Recursive Make

The traditional way to structure a multi-directory project is for each directory to have its own makefile, with the top level invoking them in turn:

SUBDIRS := lib src tools

.PHONY: all $(SUBDIRS)
all: $(SUBDIRS)

$(SUBDIRS):
    $(MAKE) -C $@

$(MAKE) -C dir changes into a directory and runs Make there. Use $(MAKE) rather than a literal make: it carries the correct executable name and, critically, the jobserver file descriptors that let a single -j8 budget be shared across the whole recursion. Write make instead and each sub-make starts its own unlimited job pool, which is how a build ends up spawning hundreds of compilers and thrashing the machine.

This structure dominated for decades, and its appeal is real. Each directory’s build is self-contained and comprehensible. A subdirectory can be built alone during development. The top-level makefile stays short.

Recursive Make Considered Harmful

In 1997 Peter Miller published a paper with that title, and the argument has held up well enough that every build system designed since has taken it seriously.

The core claim is that each sub-make sees only a fragment of the dependency graph, and a fragment is not enough to be correct. When src/Makefile runs, it knows its own sources and nothing about lib/. If src/main.c includes lib/util.h, that edge exists in reality and in no makefile. The top level imposes an order, building lib before src, and order is a weaker guarantee than dependency: it means lib is built first, not that src rebuilds when lib changes.

The failures follow directly:

Incomplete rebuilds. Change a header in lib/, and src rebuilds only if src/Makefile happens to name it. Usually it does not. You get exactly the stale-object corruption described above, now spanning directories where it is even harder to see.

Order masquerading as dependency. SUBDIRS := lib src tools looks like it encodes structure. It encodes sequence. Reorder the list and the build may still succeed, having simply produced different wrong output.

Limited parallelism. The $(SUBDIRS) rule above serializes at directory boundaries unless carefully written, so tools waits on all of src even if it needs only one library. The jobserver keeps the total job count sane; it cannot recover parallelism the structure threw away.

Repeated work. Every sub-make re-reads its makefiles, re-expands variables, re-runs $(shell) calls. On a deep tree, no-op builds spend real time doing nothing.

Miller’s uncomfortable observation is that these bugs hide behind clean builds. A nightly make clean && make always produces a correct binary, so the recursive structure looks fine while incremental builds quietly produce wrong ones. The symptom is a team culture of “just clean it and try again.”

This is precisely why CMake and Ninja construct a single flat graph for the entire project, and why the directory layout of a CMake project looks recursive while behaving as its opposite.

NoteIt is a real tradeoff, not a settled question

Recursive make survives in large projects (the Linux kernel most visibly) because at sufficient scale a single graph has costs of its own: parse time, memory, and a build description no individual can hold in their head. The kernel’s Kbuild is recursive by design and manages correctness with considerable machinery around it. The honest summary is that recursion buys comprehensibility and costs correctness, and that the correctness cost is usually the more expensive one.

Non-Recursive Make

The alternative keeps per-directory files while building one graph. Each directory contributes a fragment that is included into a single Make invocation rather than executed by a separate one:

# top-level Makefile
include lib/module.mk
include src/module.mk
include tools/module.mk

all: $(ALL_TARGETS)

%.o: %.c
    @mkdir -p $(@D)
    $(CC) $(CFLAGS) -MMD -MP -c $< -o $@

-include $(ALL_DEPS)
# lib/module.mk
LIB_SRCS := $(wildcard lib/*.c)
LIB_OBJS := $(LIB_SRCS:.c=.o)

lib/libutil.a: $(LIB_OBJS)
    $(AR) rcs $@ $^

ALL_TARGETS += lib/libutil.a
ALL_DEPS    += $(LIB_OBJS:.o=.d)
# src/module.mk
SRC_SRCS := $(wildcard src/*.c)
SRC_OBJS := $(SRC_SRCS:.c=.o)

src/app: $(SRC_OBJS) lib/libutil.a
    $(CC) $(LDFLAGS) -o $@ $^

ALL_TARGETS += src/app
ALL_DEPS    += $(SRC_OBJS:.o=.d)

One Make process now holds every node. src/app depends on lib/libutil.a as a genuine graph edge, so changing a library source rebuilds the application. -j8 parallelizes across the entire project rather than within one directory at a time. The .d files supply header dependencies across directory boundaries, which recursion could not express at all.

The ergonomic cost is real and worth stating plainly.

Paths are project-relative, always. There is one working directory (the top level) no matter which fragment a rule came from. Every path in lib/module.mk must be written lib/..., which is easy to get wrong and produces confusing errors when you do.

Variables are global, so names need namespacing. SRCS in two fragments is one variable, silently merged. The convention above (LIB_SRCS, SRC_SRCS) is not decoration, it is required, and it is on you to maintain since Make has no module scope. Accumulator variables like ALL_TARGETS must use += and must be defined before the first include.

Building one directory alone takes work. make -C lib no longer exists as a concept. You get it back by naming targets (make lib/libutil.a) or defining phony aliases per module, which is more setup than recursion needed.

Order of includes matters more than you would like. Fragments are read top to bottom, so a variable a fragment depends on must be set before its include. := and += interact with this in the way described in ?= and +=.

This is the structure Miller advocated, and it is the right choice for a project that wants correct incremental builds from Make itself. It is also, at a certain size, the point where the discipline required starts to look like reimplementing CMake by hand. That is a reasonable moment to consider using CMake.

Real Makefiles

Three complete builds, every line accounted for

Everything to this point has been machinery introduced in isolation. This section assembles it. Each example is complete and runnable, and together they cover the three situations Make is actually used for today: building a hosted program, cross-compiling for a microcontroller, and running project tasks.

A Hosted C/C++ Project

Start with the smallest thing that works. upper.c reads standard input, uppercases it, and writes standard output:

#include <stdio.h>
#include <ctype.h>

int main(void) {
    int c;
    while ((c = getchar()) != EOF) {
        putchar(toupper(c));
    }
    return 0;
}

The int c rather than char c is deliberate, and the reason is explained in the C chapter: getchar returns an int so that EOF is distinguishable from every valid character value.

A makefile for one source file:

CC     := gcc
CFLAGS := -Wall -Wextra -std=c17 -O2

.PHONY: all clean
all: processor

processor: upper.o
    $(CC) -o $@ $^

upper.o: upper.c
    $(CC) $(CFLAGS) -c $< -o $@

clean:
    -rm -f processor upper.o

Ten lines, and every construct has appeared already: variables for the toolchain, all as the default goal, $@ and $^ and $< from Automatic Variables, and a phony clean. Run make and you get processor. Run it again and Make says there is nothing to do.

It is also wrong in the way Auto-Generated Dependencies described. Add a header, edit it, and nothing rebuilds. At one file you might get away with it. At twenty you will not.

The Real Thing

Here is the same build grown up: multiple directories, out-of-tree output, correct header dependencies, and debug/release variants.

# ---- toolchain -------------------------------------------------------------
CC       ?= gcc
BUILD    ?= release

# ---- behavior --------------------------------------------------------------
MAKEFLAGS += --no-builtin-rules --no-builtin-variables --warn-undefined-variables
.DELETE_ON_ERROR:
.SUFFIXES:
.DEFAULT_GOAL := all

# ---- flags -----------------------------------------------------------------
WARNINGS := -Wall -Wextra -Wpedantic -Wshadow
CPPFLAGS := -Iinclude
CFLAGS   := $(WARNINGS) -std=c17
LDFLAGS  :=
LDLIBS   := -lm

ifeq ($(BUILD),debug)
    CFLAGS += -g -O0 -DDEBUG -fsanitize=address,undefined
    LDFLAGS += -fsanitize=address,undefined
else ifeq ($(BUILD),release)
    CFLAGS += -O2 -DNDEBUG
else
    $(error BUILD must be debug or release, got '$(BUILD)')
endif

# ---- layout ----------------------------------------------------------------
SRC_DIR   := src
BUILD_DIR := build/$(BUILD)
TARGET    := $(BUILD_DIR)/app

SRCS := $(shell find $(SRC_DIR) -name '*.c')
OBJS := $(patsubst $(SRC_DIR)/%.c,$(BUILD_DIR)/%.o,$(SRCS))
DEPS := $(OBJS:.o=.d)

# ---- rules -----------------------------------------------------------------
.PHONY: all clean test
all: $(TARGET)

$(TARGET): $(OBJS)
    @mkdir -p $(@D)
    $(CC) $(LDFLAGS) -o $@ $^ $(LDLIBS)

$(OBJS): $(BUILD_DIR)/%.o: $(SRC_DIR)/%.c
    @mkdir -p $(@D)
    $(CC) $(CPPFLAGS) $(CFLAGS) -MMD -MP -c $< -o $@

test: $(TARGET)
    ./tests/run.sh $(TARGET)

clean:
    -rm -rf build

-include $(DEPS)

Forty lines, and the parts worth pointing at:

BUILD_DIR := build/$(BUILD) is the line that makes variants safe. Debug and release objects live in separate trees, so switching between them cannot mix incompatible objects, the hazard flagged in Target-Specific and Pattern-Specific Variables. make BUILD=debug and make coexist without a clean between them.

$(shell find ...) rather than $(wildcard ...) because wildcard does not recurse into subdirectories. Both run at parse time, so a source file added while Make is running is not seen, which is fine.

The static pattern rule ($(OBJS): $(BUILD_DIR)/%.o: ...) restricts compilation to objects derived from the source list. A stray .c elsewhere in the tree cannot wander into the build, and a target that fails to match is an error rather than a silent skip.

@mkdir -p $(@D) creates the output directory per target, which handles nested source layouts that an order-only prerequisite on a single directory would not.

CPPFLAGS separate from CFLAGS follows the convention the built-in rules use: preprocessor concerns (-I, -D) in one, code generation in the other. It costs nothing and matches what other tools expect.

LDLIBS after $^ on the link line, not in LDFLAGS. Static library resolution is order-sensitive: libraries must follow the objects that reference them. Putting -lm in LDFLAGS places it before the objects and produces undefined-reference errors that look like the library is missing.

-include $(DEPS) at the bottom so header edits propagate. This single line is the difference between a build you trust and one you clean out of superstition.

A Cross-Compiled Embedded Target

Cross-compilation changes less than you might expect. The graph is the same; what changes is that the toolchain is prefixed, the link step needs a linker script, and the output must be converted into something a programmer can flash.

This targets ARM Cortex-M, matching the embedded focus of the C chapter and the assembly chapter.

# ---- toolchain -------------------------------------------------------------
CROSS_COMPILE ?= arm-none-eabi-
CC      := $(CROSS_COMPILE)gcc
OBJCOPY := $(CROSS_COMPILE)objcopy
SIZE    := $(CROSS_COMPILE)size

MAKEFLAGS += --no-builtin-rules --no-builtin-variables
.DELETE_ON_ERROR:
.DEFAULT_GOAL := all

ifeq ($(shell command -v $(CC) 2>/dev/null),)
    $(error cross compiler not found: $(CC))
endif

# ---- target hardware -------------------------------------------------------
MCU_FLAGS := -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
LINKER_SCRIPT := ld/stm32f4.ld

# ---- flags -----------------------------------------------------------------
CPPFLAGS := -Iinclude -DSTM32F407xx
CFLAGS   := $(MCU_FLAGS) -Wall -Wextra -std=c17 -Og -g3 \
            -ffunction-sections -fdata-sections
LDFLAGS  := $(MCU_FLAGS) -T$(LINKER_SCRIPT) -nostartfiles \
            -Wl,--gc-sections -Wl,-Map=$(BUILD_DIR)/firmware.map

# ---- layout ----------------------------------------------------------------
BUILD_DIR := build
ELF := $(BUILD_DIR)/firmware.elf
HEX := $(BUILD_DIR)/firmware.hex
BIN := $(BUILD_DIR)/firmware.bin

SRCS := $(shell find src -name '*.c') $(wildcard src/*.S)
OBJS := $(patsubst src/%,$(BUILD_DIR)/%.o,$(SRCS))
DEPS := $(OBJS:.o=.d)

# ---- rules -----------------------------------------------------------------
.PHONY: all size flash clean
all: $(HEX) $(BIN) size

$(ELF): $(OBJS)
    @mkdir -p $(@D)
    $(CC) $(LDFLAGS) -o $@ $^

$(BUILD_DIR)/%.c.o: src/%.c
    @mkdir -p $(@D)
    $(CC) $(CPPFLAGS) $(CFLAGS) -MMD -MP -c $< -o $@

$(BUILD_DIR)/%.S.o: src/%.S
    @mkdir -p $(@D)
    $(CC) $(CPPFLAGS) $(CFLAGS) -MMD -MP -c $< -o $@

%.hex: %.elf
    $(OBJCOPY) -O ihex $< $@

%.bin: %.elf
    $(OBJCOPY) -O binary $< $@

size: $(ELF)
    @$(SIZE) --format=berkeley $<

flash: $(HEX)
    openocd -f interface/stlink.cfg -f target/stm32f4x.cfg \
            -c "program $< verify reset exit"

clean:
    -rm -rf $(BUILD_DIR)

What is different from the hosted build, and why:

CROSS_COMPILE ?= as a prefix. Every tool name is derived from one variable, so retargeting to a different chip family is a single override: make CROSS_COMPILE=riscv64-unknown-elf-. The ?= lets the environment or command line supply it, which is how CI systems inject a pinned toolchain path.

The toolchain guard. A missing cross-compiler otherwise produces dozens of command not found lines before anything explains the problem. The $(error) guard fails in phase 1 with an actionable message.

MCU flags appear in both CFLAGS and LDFLAGS. The linker needs to know the architecture and float ABI to select the right multilib variants of libc and libgcc. Omitting them from LDFLAGS is a classic error whose symptom is a link failure about incompatible float ABIs.

-T$(LINKER_SCRIPT). A hosted link uses the system’s default script; bare metal has no operating system to provide one. The script maps sections onto the chip’s flash and RAM, and it is a genuine input to the link. Adding it as a prerequisite of $(ELF) would be an improvement to this makefile, since editing the memory layout should force a relink.

-ffunction-sections -fdata-sections with -Wl,--gc-sections. Together these place each function and object in its own section and let the linker discard unreferenced ones. On a part with 512 KB of flash this routinely saves tens of kilobytes.

-Og rather than -O2. Optimized enough to fit and run at speed, structured enough that a debugger can still follow the source. On embedded targets, where the debugger is often the only visibility you have, this is usually the right default.

objcopy to .hex and .bin. The ELF contains symbols, debug information, and section metadata that a flash programmer has no use for. Intel HEX carries addresses and is what most programmers expect; raw binary is a flat image for a known load address. Both come from the same ELF via pattern rules, so neither is written twice.

A size target in all. Printing the flash and RAM budget on every build makes creeping growth visible while there is still room to react. This is a habit worth forming; discovering you are over budget at integration time is considerably worse.

flash as a phony target. It produces no file, so it must be phony, and it depends on $(HEX) so that flashing always programs a current image rather than whatever was built last week.

Warningflash and parallelism

A hardware programmer is a single physical resource. Two flash invocations at once will fail or, worse, brick a device mid-write. This is the narrow legitimate case for .NOTPARALLEL, or for keeping flash targets out of any rule that could run concurrently.

Make as a Task Runner

The third use has nothing to do with compilation. Here the makefile is a project’s command menu: every target is phony, there is barely a dependency graph, and the value is that make test works in every project regardless of what language it is written in.

.DEFAULT_GOAL := help
.PHONY: help install fmt lint test build docs clean

VENV := .venv
PY   := $(VENV)/bin/python

help:  ## Show this help
    @grep -E '^[a-zA-Z_-]+:.*?## .*$$' $(MAKEFILE_LIST) \
      | awk 'BEGIN {FS = ":.*?## "}; {printf "  \033[36m%-12s\033[0m %s\n", $$1, $$2}'

$(VENV):  ## Create the virtual environment
    python3 -m venv $(VENV)
    $(PY) -m pip install --upgrade pip

install: $(VENV)  ## Install dependencies
    $(PY) -m pip install -e '.[dev]'

fmt:  ## Format the source tree
    $(PY) -m ruff format src tests

lint:  ## Run the linter and type checker
    $(PY) -m ruff check src tests
    $(PY) -m mypy src

test:  ## Run the test suite
    $(PY) -m pytest -q

docs:  ## Render the notebooks
    quarto render

clean:  ## Remove build artifacts
    -rm -rf dist .pytest_cache .ruff_cache .mypy_cache
    find . -name __pycache__ -type d -exec rm -rf {} +

Running make prints a formatted list of targets:

  help         Show this help
  install      Install dependencies
  fmt          Format the source tree
  lint         Run the linter and type checker
  test         Run the test suite
  docs         Render the notebooks
  clean        Remove build artifacts

The self-documenting help target is the idiom worth stealing. It greps the makefile for targets followed by a ## comment and formats them with awk. $(MAKEFILE_LIST) is a built-in variable holding every makefile read so far, so the help stays correct when the build is split across files. The $$ are escaped for the shell, since awk needs its own $1 and $2. Setting .DEFAULT_GOAL := help means a bare make documents itself instead of doing something unexpected.

Note that $(VENV) is a real file target, not phony: the directory either exists or it does not, so install depends on it and the environment is created exactly once. Even in a task runner, a genuine dependency is worth expressing as one.

Why People Reach for Make Here

It is already installed. There is no new tool to add to a README, no version to pin, no configuration file format to learn. Shell tab-completion knows makefile targets, so make te<Tab> completes. And a newcomer to the project can read the entire set of available commands in one screen, which is more than can be said for a scripts/ directory of loose shell files.

Every language ecosystem has grown its own task runner (npm scripts, cargo make, just, invoke), and they are all better at this job than Make. What none of them have is being present on every Unix machine already, which is why a polyglot repository so often ends up with a makefile at its root delegating to whatever each subproject uses.

Where It Strains

Arguments are awkward. Make has no notion of passing arguments to a target. make test -k pattern parses -k as a Make flag. The workarounds are variables (make test ARGS="-k pattern", then $(PY) -m pytest $(ARGS)) or the $(MAKECMDGOALS) trick of consuming extra goals, which is fragile enough that most people accept the variable.

Every target must be declared phony. Forget one and it breaks the day someone adds a matching file or directory. A docs/ directory silently disabling make docs is the common one, exactly as described in Phony Targets.

Names with dashes work; names with other punctuation may not. make db-migrate is fine. Colons, spaces, and % in a target name are not, since all three are Make syntax.

There is no error handling worth the name. A recipe is a sequence of shell commands, each checked only for exit status. Anything conditional or recoverable has to be written in shell inside the recipe, and at that point the makefile is a shell script with extra parsing rules between you and it. When a task grows past a few lines, move it into scripts/ and have the makefile call it.

Parallelism

Free speedup, if the graph is true

make -j8 runs up to eight recipes at once:

make -j8              # up to 8 concurrent jobs
make -j               # unlimited: as many as the graph allows
make -j$(nproc)       # one per core, the usual choice

On a multi-core machine this is close to a linear speedup for the compile phase, and it costs nothing to ask for. That is the payoff promised back in You Describe Relationships, Not Order: you described dependencies for a different reason, and parallelism fell out of the description. Make already knows which nodes are unrelated, so it already knows what can run simultaneously. No annotation, no thread pool, no change to a single rule.

Bare -j with no number is worth avoiding. It imposes no limit at all, so a large project spawns hundreds of compilers, exhausts memory, and runs slower than -j8 would have. Give it a number.

Parallelism Is a Correctness Test

Here is the part that matters. -j does not introduce bugs; it reveals them. A missing prerequisite is a lie in the graph whether or not you build in parallel. Serially, Make happens to visit targets in an order that often masks the lie, because file order accidentally matches the true order. In parallel, that accident stops holding.

The symptom is unmistakable once you know it:

$ make -j8
... build fails somewhere odd ...
$ make -j8
... succeeds ...

A build that fails intermittently under -j and passes on retry is almost never a Make bug. It is a missing edge. Two targets that must be ordered are not connected in the graph, so Make, correctly reasoning from what you told it, runs them together.

The classic instance is a generated header:

# BROKEN under -j: nothing says main.o needs version.h
main.o: main.c
    $(CC) -c $< -o $@

version.h:
    ./gen-version > $@

Serially, if version.h is built first, everything works and you never notice. Under -j8, the compile of main.c starts while gen-version is still writing, and you get a missing header, or worse, a half-written one. The fix is to state the truth:

main.o: main.c version.h
    $(CC) -c $< -o $@

A related failure is two recipes writing the same file. Nothing in Make prevents it, and under -j they interleave. If two rules both >> into a log, or both produce an intermediate with the same name, the output is nondeterministic garbage. Every output file should be produced by exactly one rule.

TipTest with -j even if you build serially

Running make -j8 in CI on a clean tree is a cheap and effective audit of the dependency graph. It converts latent missing-prerequisite bugs into loud failures, at the point where they are still easy to fix. A makefile that survives repeated clean parallel builds has a graph you can trust; one that has only ever been built serially has a graph nobody has checked.

Warning-j and recursive make

This is where recursive make hurts most. Each sub-make sees only its fragment, so cross-directory ordering rests on the SUBDIRS sequence rather than on real edges, and that sequence is exactly the guarantee -j is entitled to ignore within a level. Always invoke sub-makes as $(MAKE), never a literal make, so the jobserver is inherited.

Interleaved Output

Parallel jobs write to the same terminal at the same time, so a failing compiler’s error message arrives shredded between two other jobs’ output. -O (--output-sync) buffers each job’s output and prints it in one piece:

make -j8 -O            # or: -Otarget, the default granularity
make -j8 -Oline        # per line
make -j8 -Orecurse     # group a whole sub-make together

-Otarget groups all output from one target, which is what you want almost always: an error message stays attached to the compile that produced it. -Orecurse is the right choice with recursive make, keeping each subdirectory’s output contiguous.

This is a genuinely large quality-of-life improvement and it is not the default, so it is worth putting in MAKEFLAGS:

MAKEFLAGS += -Otarget

The tradeoff is latency: a job’s output appears when the job finishes rather than as it runs. For a long-running step you lose the ability to watch progress live.

Constraining Parallelism

Sometimes concurrency genuinely must be limited, and Make offers three tools of decreasing bluntness.

.NOTPARALLEL forces the entire makefile to run serially even when -j is given. As noted in Suppressing Output and Parallelism, this is usually the wrong fix, because it hides a graph bug while surrendering the speedup. It is legitimate only when recipes contend for a resource the graph cannot express: a single hardware programmer, a test database, a physical serial port.

.WAIT (GNU Make 4.4, 2022) is the precise version. Placed between prerequisites, it forces everything before it to complete before anything after it starts:

all: generate .WAIT compile

This expresses a barrier without inventing fake dependencies, which is what people previously resorted to. Being new, it is not available on macOS’s Make 3.81 or on many distributions’ defaults, so treat it as a tool for controlled environments.

Order-only prerequisites remain the right answer when the constraint is genuinely “this must exist first,” which is the directory case. They impose ordering without falsely marking the target stale.

The Jobserver

One detail explains how -j8 stays -j8 across a recursive build. If each sub-make independently honored -j8, a tree with six subdirectories could run 48 compilers.

Make solves this with the jobserver: the top-level process creates a pipe holding one token per available job slot. A sub-make wanting to start a job reads a token from the pipe, and returns it when the job finishes. No token, no job. Because the pipe is inherited through the process tree, every make in the recursion draws from one shared pool, and the total stays at eight.

This is also the mechanism you break by writing make -C subdir instead of $(MAKE) -C subdir. $(MAKE) is special-cased: Make recognizes it and passes the jobserver file descriptors through. A literal make gets no tokens, so it either warns and runs serially, or starts its own unlimited pool. GNU Make 4.4 moved to a named-pipe implementation that is more robust across shells and tools, and Ninja and Cargo can participate in the same protocol, which is how a Rust build invoked from a makefile stays inside your job budget.

Special Targets

Names Make reserves for configuring itself

A handful of target names starting with a period are not targets at all. Make reserves them as directives, written in rule syntax because rule syntax was already there. .PHONY is the one everybody knows; the rest configure behavior that is otherwise unreachable, and at least one of them fixes a correctness bug present in most makefiles.

Two forms appear. Most take prerequisites, listing the targets they apply to:

.PHONY: clean test

A few take none and simply switch a global behavior on:

.DELETE_ON_ERROR:

The empty prerequisite list is not a mistake; the presence of the line is the whole declaration.

Target Effect
.PHONY Its prerequisites are actions, not files; never compared against disk
.DELETE_ON_ERROR Delete a target whose recipe failed. Use this
.DEFAULT_GOAL A variable, not a rule: sets what plain make builds
.ONESHELL Run each recipe in a single shell instead of one shell per line
.SILENT Suppress echoing, for the named targets or globally if empty
.SUFFIXES The suffix-rule list; empty it to disable them
.PRECIOUS Do not delete these targets on interrupt or failure
.INTERMEDIATE Treat these as intermediate: delete them when the build completes
.SECONDARY Intermediate, but do not delete. Empty means “all”
.NOTPARALLEL Run this makefile serially regardless of -j
.EXPORT_ALL_VARIABLES Export every makefile variable into recipe environments
.LOW_RESOLUTION_TIME Compare these targets’ timestamps at one-second granularity

.DELETE_ON_ERROR

The one to add to every makefile you own

Consider what happens when a recipe fails partway through:

report.txt: data.csv
    ./analyze data.csv > report.txt

The shell creates report.txt and opens it for writing before analyze runs. If analyze writes half its output and then crashes, the file exists, contains truncated garbage, and carries a modification time newer than data.csv. Make reports the failure and stops. So far so good.

Now run make again:

$ make
make: 'report.txt' is up to date.

The build is broken and Make sees nothing to do. Whatever consumes report.txt downstream now consumes corrupt input, and the only symptom is wrong results much further along. Nothing in the output points back at the failed step, which happened in a previous invocation and scrolled away.

One line prevents all of it:

.DELETE_ON_ERROR:

With that declaration, a recipe that exits non-zero after modifying its target causes Make to delete the target before stopping. The next run sees a missing file and rebuilds properly. The failure stays a failure instead of decaying into a stale artifact.

ImportantWhy is this not the default?

Backward compatibility, entirely. Make’s original behavior predates the realization that it was a bug, and changing a default that has stood since 1976 would break makefiles that depend on partial output surviving, however few of those are deliberate. The GNU Make manual recommends .DELETE_ON_ERROR without reservation, and the practical advice is unambiguous: put it near the top of every makefile you write. The cost is one line; the bug it prevents is silent and produces wrong output rather than a visible error.

The exemption is .PRECIOUS, which protects specific targets from this deletion (and from deletion on Ctrl-C). Reach for it when a target is genuinely expensive to regenerate and safe to have in a partial state, which is rare enough that needing it is a signal worth double-checking.

.ONESHELL

By default each recipe line gets its own shell, which is the source of the cd problem in Multi-Line Recipes. .ONESHELL changes it globally:

.ONESHELL:

install:
    cd build
    cp app /usr/local/bin/
    echo "installed"

Now all three lines run in one shell, cd persists, and shell variables set on one line are visible on the next. Recipes stop needing && chains and trailing backslashes, which makes anything with real shell logic in it far more readable.

The tradeoffs are real, though. It is a GNU extension, absent from BSD make and from POSIX. Error handling changes: only the shell’s final exit status is checked, so an early failure no longer stops the recipe unless you add set -e (.SHELLFLAGS := -ec is the usual way). And the @ and - prefixes now apply to the whole recipe rather than a line, since there is only one command.

Use it when a makefile has recipes with multi-step shell logic, and know you have traded portability for it. For a makefile whose recipes are single compiler invocations, it buys nothing.

Intermediate Files

.SECONDARY and .INTERMEDIATE

Chained inference invents files nobody asked for, and by default Make deletes them once the build completes. That is usually tidy and occasionally infuriating, because a deleted intermediate must be regenerated next time, so a build you expected to be a no-op does work.

The concrete case: a rule chain from .proto to .c to .o deletes the generated .c files after every build. You cannot read them to debug the generator, and every subsequent build regenerates and recompiles them.

.SECONDARY marks a file as intermediate but exempt from deletion. With no prerequisites, it applies to everything:

.SECONDARY:

This is a common blanket setting in makefiles that use chaining heavily, and the cost is disk space for files you might have wanted anyway.

.INTERMEDIATE is the opposite direction: it marks a file you wrote an explicit rule for as intermediate, so it gets cleaned up like an inferred one. It is much rarer, and usually a sign that a temporary file should have been handled inside a single recipe instead.

Suppressing Output and Parallelism

.SILENT suppresses command echoing. With prerequisites it applies to those targets; empty, it applies globally:

.SILENT: docs           # just these
.SILENT:                # everything

Global .SILENT is best avoided. Echoed commands are how you find out what a failing build actually ran, and hiding them project-wide trades debuggability for tidy output. Prefer per-line @ on the messages you want quiet, or make -s when a specific invocation should be quiet. The same reasoning applies to .EXPORT_ALL_VARIABLES, which exports every makefile variable into every subprocess environment: convenient, and a good way to have a makefile variable collide with something a tool reads from the environment.

.NOTPARALLEL forces serial execution of the current makefile even under -j:

.NOTPARALLEL:

This is almost always the wrong fix. A makefile that fails under -j8 and passes serially has a missing prerequisite, and .NOTPARALLEL hides the bug while giving up the speedup. It is legitimate in a narrow case: when recipes genuinely contend for a shared external resource, such as a single hardware programmer or a database, that the dependency graph cannot express. See Parallelism.

TipA reasonable preamble

Most of these decisions are the same in every serious makefile, which makes a standard opening block worth copying:

MAKEFLAGS += --no-builtin-rules --no-builtin-variables --warn-undefined-variables
.DELETE_ON_ERROR:
.SUFFIXES:
.DEFAULT_GOAL := all
SHELL := /bin/bash

That is: no surprise rules, no stale targets after a failure, no suffix rules, an explicit default goal, and a known shell rather than whatever /bin/sh is on this machine. --warn-undefined-variables catches the typo’d $(CFLGAS) that would otherwise expand to nothing in silence.

Debugging Makefiles

Asking Make what it thinks it is doing

Make’s error messages are famously unhelpful, but its introspection tools are good and underused. Nearly every question you will have is one of two kinds: what would you run (phase 2) or what is this variable (phase 1). Different tools answer each.

The Toolkit

Command Answers
make -n What would you run, without running it
make --trace Which recipe is running, and why
make --debug=b The decisions: what is out of date and what caused it
make -p Every rule and variable Make knows, including built-ins
make -p -f /dev/null The built-in database alone, with none of your makefile
$(info ...) Printf debugging during phase 1
$(origin VAR) Where a value came from
$(flavor VAR) Whether it was = or :=

-n (--just-print) is the first thing to reach for. It prints commands without executing them, so you can confirm what a build would do before letting it. It is also the safe way to inspect a clean or install target you did not write.

make -n install

Note one limitation: -n still expands everything, so any $(shell) call runs. A makefile that does real work at parse time is not fully inert under -n.

--trace annotates each recipe with the rule that triggered it and the reason, which is exactly the question “why is this being rebuilt.” It requires GNU Make 4.0 or newer.

--debug=b is the portable equivalent and is available on older versions including the 3.81 that macOS ships. The b is “basic”; v (verbose), i (implicit rules), and m (makefile remaking) add detail, and bare -d turns on everything at a volume that is rarely useful.

-p (--print-data-base) dumps the entire internal state: every variable with its origin, every rule including built-ins, and the files Make considered. It runs to hundreds of lines, so pipe it:

make -p | grep -A2 '^CFLAGS'
make -p -f /dev/null | less     # built-in rules with no makefile at all

A Worked Session: The Target That Always Rebuilds

This is the most common real complaint about a makefile, and it has a small number of causes. Here is a build that relinks on every invocation despite nothing changing:

CC := gcc

.PHONY: all version
all: app

app: main.o version
    $(CC) -o $@ main.o

main.o: main.c
    $(CC) -c $< -o $@

version:
    @echo "stamping version"

The symptom, on a tree where everything is already built:

$ make
stamping version
gcc -o app main.o
$ make
stamping version
gcc -o app main.o

Nothing changed, and app relinks anyway. Ask Make why:

$ make --debug=b
Updating goal targets....
 File `all' does not exist.
     File `version' does not exist.
    Must remake target `version'.
stamping version
    Successfully remade target file `version'.
   Prerequisite `version' of target `app' does not exist.
  Must remake target `app'.
gcc -o app main.o

The diagnosis is in one line: Prerequisite 'version' of target 'app' does not exist. A phony target never corresponds to a file, so it is never up to date, and anything depending on it is therefore always stale. The .PHONY declaration is correct; using that target as a prerequisite of a real file is the mistake.

The fix depends on intent. If the version stamp is genuinely an input, it must produce a real file so Make can compare timestamps:

app: main.o version.txt
    $(CC) -o $@ main.o

version.txt: $(shell git rev-parse HEAD > /dev/null && echo .git/HEAD)
    git describe --always > $@

If it is just a message, it does not belong in the graph at all; move it into the recipe:

app: main.o
    @echo "stamping version"
    $(CC) -o $@ main.o

The Other Causes

When --debug=b reports something else, the phrasing points at the cause:

File 'x' does not exist for a target you believe exists usually means a path mismatch: the rule writes build/app and something depends on app, or a VPATH search found a different file than you assumed.

A prerequisite is newer for no reason is typically a directory used as a normal prerequisite rather than an order-only one, since a directory’s mtime changes whenever a file is written into it.

Everything rebuilds after a branch switch is version control not preserving mtimes, covered in When Timestamps Lie.

A rule fires that you did not write is a built-in rule. Confirm with make -p -f /dev/null and disable them.

Debugging Phase 1

Everything above inspects the build. When the problem is a variable that is empty, wrong, or mysteriously overridden, you need the read phase instead, and the tools are the diagnostic functions:

$(info CFLAGS = "$(CFLAGS)")
$(info OBJS   = $(OBJS))
$(info origin = $(origin CC))
$(info flavor = $(flavor CFLAGS))

The quotes matter. $(info CFLAGS = $(CFLAGS)) cannot distinguish an empty variable from one holding a space, and trailing whitespace in a Make variable is both invisible and load-bearing.

$(origin) is the tool for “why is this value not what my makefile says.” It returns undefined, default, environment, file, command line, override, or automatic, which maps onto the precedence table in Where Values Come From. If $(origin CC) says environment, someone’s shell profile is in your build.

Two flags complete the set. --warn-undefined-variables catches the typo that expands to nothing:

$ make --warn-undefined-variables
Makefile:8: warning: undefined variable 'CFLGAS'

And -B (--always-make) rebuilds everything unconditionally, which is useful for separating “the graph is wrong” from “the recipe is wrong.” If make -B produces a correct result and plain make does not, the recipes are fine and the dependency graph is lying.

TipA fast triage order
  1. make -n: is it running what you expect?
  2. make --debug=b (or --trace): why is that target considered stale?
  3. $(info ...) on the suspect variable: is the value what you think?
  4. $(origin VAR): if not, where did it come from?
  5. make -p | grep VAR: the exhaustive answer, when the first four fail.

Common Pitfalls

Nine failures, and the two ideas behind all of them

Everything that goes wrong in a makefile is collected here, stated as symptom, cause, and fix. What makes the list worth reading straight through is that these are not nine unrelated quirks. Almost every one is a boundary error between the three languages or a phase confusion, and the last column of the table below says which:

Symptom Root cause
missing separator Three languages: spaces where a tab marks shell
Shell variable is empty Three languages: $ consumed by Make
cd does not persist Three languages: one shell per recipe line
Comparison fails on equal-looking text Three languages: invisible trailing whitespace
Variable references itself Phases: deferred expansion loops
$(wildcard) finds nothing Phases: parse time precedes recipes
Stale target after a failure Timestamps: mtime updated on partial output
Works serially, fails under -j Graph: a missing edge
make clean says up to date Graph: a target that is also a filename

missing separator

Symptom. Makefile:5: *** missing separator. Stop.

Cause. A recipe line indented with spaces instead of a tab. Make uses the leading tab to know a line is shell rather than rule or macro, so without it, your gcc command is parsed as a makefile construct. Finding neither = nor :, Make reports the missing separator. The message names the symptom of a failed parse, not the cause.

Fix. Use a tab. Configure the editor so it cannot happen: [{Makefile,*.mk}] with indent_style = tab in .editorconfig. Full treatment in Tabs, and Why.

WarningThe same error from an indented conditional

A tab in front of ifeq makes it a recipe line, and the shell has no ifeq. That one produces ifeq: command not found rather than missing separator, but the cause is identical: leading whitespace decided which language the line was in. Conditional bodies indent with spaces.

$ Crossing the Boundary

Symptom. A shell loop does nothing, or a command receives an empty string where a variable should be.

# BROKEN: prints "found " repeatedly
list:
    for f in *.c; do echo "found $f"; done

Cause. Make expands the recipe before handing it to the shell. $f is read by Make, which finds no variable f and substitutes nothing. The shell never sees it.

Fix. $$ escapes a dollar sign so it survives into the shell:

list:
    for f in *.c; do echo "found $$f"; done

The rule is mechanical: inside a recipe, $(...) belongs to Make and $$ belongs to the shell. This applies equally to shell command substitution, $$(date), and to awk scripts needing $$1.

cd Does Not Persist

Symptom. A recipe changes directory and the next line runs somewhere else.

Cause. Each recipe line gets its own shell process. The cd affects only the shell that ran it, which exits immediately.

Fix. Join the lines into one command, or enable .ONESHELL:

install:
    cd build && cp app /usr/local/bin/

Covered in Multi-Line Recipes; the .ONESHELL tradeoffs are in Special Targets.

Trailing Whitespace

Symptom. A conditional fails against a value that looks correct.

MODE := debug
ifeq ($(MODE),debug)      # does not match if MODE has a trailing space

Cause. Trailing whitespace is part of a Make variable’s value and is invisible in an editor. It commonly arrives from a $(shell) call or a hand-edited configuration block, and $(info MODE = $(MODE)) will not reveal it.

Fix. Quote when printing, $(info "$(MODE)"), and $(strip ...) anything whose provenance you do not control. Note also that VAR := value # comment includes the space before # in the value, which is a frequent source of this.

Recursive Variable Self-Reference

Symptom. *** Recursive variable 'A' references itself (eventually). Stop.

Cause. A = $(A) more with = stores the right side unexpanded, so every reference re-expands it forever. Make detects the loop and refuses.

Fix. Use :=, which expands the old value once and reassigns:

A := $(A) more

Or +=, which does the right thing for appending. See The Two Flavors.

$(wildcard) Sees Nothing

Symptom. A build fails on a clean tree and succeeds on the second run.

OBJS := $(wildcard build/*.o)     # empty until something has been built

Cause. $(wildcard) runs in phase 1, before any recipe. It cannot see files a recipe is about to create. Globbing an output directory is therefore always wrong.

Fix. Derive outputs from inputs, which do exist at parse time:

SRCS := $(wildcard src/*.c)
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))

The same reasoning applies to $(shell) inspecting build products, and to conditionals testing them. See What Runs When.

A Failed Recipe Leaves a Stale Target

Symptom. A build fails, you run make again, and it reports the broken target is up to date.

Cause. The shell creates the output file before the command runs. A command that fails partway leaves a truncated file with a fresh timestamp, which Make reads as current.

Fix. One line, near the top of every makefile:

.DELETE_ON_ERROR:

This is the most consequential single line in this chapter, because the failure is silent and produces wrong output rather than an error. Full discussion in .DELETE_ON_ERROR.

Works Serially, Fails Under -j

Symptom. make succeeds, make -j8 fails intermittently and passes on retry.

Cause. A missing prerequisite. The graph does not connect two targets that must be ordered, and serial execution happened to visit them in a workable order. Parallelism removes that accident.

Fix. Find the true dependency and declare it. This is not a Make bug and .NOTPARALLEL is not the answer; it hides the defect while surrendering the speedup. See Parallelism Is a Correctness Test.

make clean Says Up To Date

Symptom. make: 'clean' is up to date.

Cause. A file or directory named clean exists. Make compared the target against it, found no newer prerequisites, and concluded there was nothing to do.

Fix. Declare action targets phony:

.PHONY: all clean test install docs

A docs/ directory silently disabling make docs is the version of this you are most likely to meet. See Phony Targets.

TipThe two questions

When a makefile misbehaves, almost every cause above is reached by asking two questions in order. Which language is this line? resolves tabs, $ versus $$, the per-line shell, and stray whitespace. Which phase does this run in? resolves wildcards, shell calls, conditionals, and variable flavors. What remains after both is a graph problem: a missing edge, or a target that is secretly a filename.

Make and CMake

What generates the makefiles you were never meant to read

If you have worked in a modern C++ project, you have probably met a tree with a CMakeLists.txt in nearly every directory and wondered what collects them. That question has a clean answer, but it starts with a correction.

This section answers it from Make’s side: what generates the makefiles you find in a build/ directory, and how CMake’s structure differs from recursive make. For CMake as a language in its own right, its target model, its syntax, and how to write it, see The CMake Language.

ImportantCMakeLists.txt is not a makefile

CMake is a separate language with its own syntax and semantics. It shares nothing with Make beyond a problem domain. If you read CMakeLists.txt expecting makefile constructs, nothing will parse: there are no tab-indented recipes, no $(VAR) expansions with Make’s meaning, and no target: prerequisites rules.

More importantly, CMake is not a build tool at all. It is a generator. It reads your CMakeLists.txt tree once, at configure time, and writes out real build files for some other tool to execute. By default on Unix that other tool is Make, so the thing that actually builds your project is a set of generated makefiles that no human wrote and no human should edit.

cmake -S . -B build      # configure: read CMakeLists.txt, generate build/
cmake --build build      # build: run the generated makefiles

That two-step split is the whole architecture. Everything else follows from it.

How the Tree Is Collected

The mechanism is add_subdirectory(). The top-level CMakeLists.txt names its children, each child is read in turn, and each may name children of its own:

# CMakeLists.txt (top level)
cmake_minimum_required(VERSION 3.16)
project(demo C)

add_subdirectory(lib)
add_subdirectory(src)
# lib/CMakeLists.txt
add_library(util util.c)
target_include_directories(util PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
# src/CMakeLists.txt
add_executable(app main.c)
target_link_libraries(app PRIVATE util)

Reading is recursive, but the result is not. Every directory contributes its targets to one global picture, and CMake emits a single flat build graph covering the entire project.

This distinction is the one that matters, because the directory layout looks exactly like recursive make and behaves like its opposite:

Recursive Make CMake
Per-directory file A real makefile, executed Input read at configure time
Resulting graph One fragment per directory One graph for the whole project
Cross-directory dependencies Invisible to each sub-make Fully known
Parallelism Limited by the recursion structure Across the entire project

Recursive make suffers because each sub-make sees only its own fragment. CMake reads a tree and produces a whole, which is precisely the fix Peter Miller argued for.

NoteThe generated makefiles are not recursive either

CMake does write a Makefile into each mirrored build directory, which makes it look recursive. Those are thin conveniences: each one immediately cds to the build root and delegates to a single CMakeFiles/Makefile2 holding the real graph. Running make from a subdirectory still builds against complete dependency information.

The Concept Map

Most Make concepts have a CMake counterpart, with one genuine conceptual leap at the end.

Make CMake
A rule producing a binary add_executable(app main.c)
A rule producing a library add_library(util util.c)
CFLAGS target_compile_options(), target_compile_definitions()
-I include paths target_include_directories()
LDFLAGS, -l target_link_libraries()
VAR = value set(VAR value), scoped to the directory and below
Cross-compile variable block A toolchain file, -DCMAKE_TOOLCHAIN_FILE=...
Hand-written -MMD dependency generation Automatic

The leap is that a CMake target is an object with properties, not just a name in a graph. Those properties propagate along the link graph according to a keyword you choose:

  • PRIVATE: needed to build this target, not exposed to its consumers.
  • PUBLIC: needed to build this target and by anything that links it.
  • INTERFACE: not needed by this target, only by its consumers (typical for header-only libraries).

In the example above, lib/CMakeLists.txt declares its include directory PUBLIC. So when src/CMakeLists.txt says target_link_libraries(app PRIVATE util), the compile line for main.c picks up -I/path/to/lib automatically. Nothing in src/CMakeLists.txt mentions that path. The dependency carried its own build requirements along with it.

This has no equivalent in Make, where include paths are a global CFLAGS string that every rule shares and every developer edits by hand. It is the main reason large projects moved to CMake, and the main thing to internalize when reading one.

Reading a CMake Project

A few things make a generated build tractable when you need to debug it.

See the real compiler command. The default output shows progress, not invocations:

make -C build VERBOSE=1        # or: cmake --build build --verbose

Generate a compile database. Configuring with -DCMAKE_EXPORT_COMPILE_COMMANDS=ON writes build/compile_commands.json, containing the exact command for every source file. Language servers such as clangd consume this, and it is the fastest way to answer “what flags is this file actually being compiled with.”

Know where the real rules live. In a Makefiles build, the per-target rules are in build/<dir>/CMakeFiles/<target>.dir/build.make, and the flags are split out into flags.make next to it. Worth reading once, to see that the generated output is ordinary Make using the same -MD dependency mechanism described in Auto-Generated Dependencies.

You do not re-run cmake by hand. The generated makefiles depend on the CMakeLists.txt files, so editing one causes the next make to re-run CMake automatically. This is the include restart mechanism applied at project scale.

Never edit anything in build/. It is output. The next configure overwrites it, and deleting the directory entirely is a normal, safe operation.

Make or Ninja

CMake’s default generator on Unix is Unix Makefiles, but Ninja is the better choice for anything large:

cmake -S . -B build -G Ninja

Ninja was designed for exactly this role: a build language nobody writes by hand, optimized for a generator to emit and for a machine to execute quickly. It parallelizes by default, and its no-op builds are dramatically faster than Make’s on large projects, which matters because a no-op build is the one you run most. The CMakeLists.txt files do not change; only the generated output does.

Where Make Sits Today

What it still wins at, and what it has lost

Make is fifty years old, and the honest assessment is neither that it is obsolete nor that the newer tools are hype. It occupies a narrower niche than it once did, and inside that niche nothing has displaced it.

What Make Still Wins At

It is already there. No installation, no version pin, no lockfile, no daemon. A makefile in a repository works on a stranger’s machine, in a container, over SSH on a box you cannot install software on. For a small project this is worth more than any feature, because the alternative starts with a paragraph of setup instructions.

Zero configuration for small builds. Ten lines gets you a correct incremental build of a C program. The equivalent CMake project is comparable in length but requires CMake, a generator, and a build directory; the ceremony does not pay off until the project is large enough to need it.

Gluing heterogeneous tools. This is where Make is genuinely unmatched, and it follows directly from The Shell Is the Recipe Language. A pipeline that renders LaTeX, converts images with ImageMagick, generates code from a schema, builds a container, and publishes the result is not a C build, and no language-native toolchain covers it. Make does, because it never assumed anything about the work. This notebook is built that way.

Task running. The command menu described in Make as a Task Runner is a legitimate modern use, and its advantage is again ubiquity rather than quality.

One person can read the whole thing. A 60-line makefile is fully comprehensible in an afternoon, including its failure modes. That is not true of a generated Ninja file or a large CMake project, and for a small team it matters.

What Make Has Lost

Large C/C++ projects, to CMake and Ninja. Not because Make cannot express them, but because target-based CMake carries build requirements along the dependency graph and Make has only a global CFLAGS string. Add cross-platform configuration and toolchain detection, which Make has no answer for at all, and the case is decided. Ninja then beats Make on raw execution speed for the generated output.

Correctness under change, to content hashing. Every failure in When Timestamps Lie is structural. Ninja, Bazel, and Cargo hash inputs, so a restored backup, a branch switch, or a regenerated-but-identical file behaves correctly. They also track flags as inputs, which is why Make needs the separate-directory trick for debug and release builds and they do not.

Hermetic and distributed builds, to Bazel. Make’s recipes can read anything on the machine, so a build is reproducible only by convention. Bazel sandboxes each action, which is what makes remote execution and shared caching possible. At a thousand engineers that is transformative; at one it is overhead.

Language-native builds, to Cargo and Go. When a language ships a build tool that understands its module system, that tool wins by default. Nobody writes a makefile to build a Rust crate, and Cargo needs no dependency graph from you because it derives one from the source.

The Idea That Outlived the Tool

The closing observation is the one from the Overview: the reason Make’s successors all look somewhat like Make is that they inherited its model rather than replaced it.

Ninja is a dependency graph with faster execution. Bazel is a dependency graph with hermetic actions and content hashing. Cargo is a dependency graph specialized to one language’s module system. CMake is a generator of dependency graphs. Every one of them is targets, prerequisites, and staleness, with the trades adjusted.

That is why learning Make pays off beyond Make. The model transfers: once you know why a build is incremental, why an incomplete graph fails under parallelism, and why timestamps are a proxy rather than an answer, you can read any of the successors and know what questions to ask. Feldman’s afternoon in 1976 produced a tool that is now a poor choice for the job it was written for, and a model that every replacement still implements.
