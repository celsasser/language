Rust: Cargo and Crates

Published

October 13, 2026

Cargo

The Build System

Cargo is Rust’s build tool, package manager, and test runner. You’ll use it for everything. For a complete list of all subcommands that are installed in an environment, use cargo --list. Follows are the subcommands that are installed on my machine at 9:18 PM on 10/13/2026:

To get help on commands in your installation, use cargo help <command>. The handful of commands that I use regularly are:

cargo build             # debug build
cargo build --release   # optimized build
cargo check             # fast type-check without building
cargo clippy            # linter
cargo fmt               # formatter
cargo install --path .  # install current application to `~/.cargo/bin`
cargo new my_project    # create new project
cargo run               # build and run
cargo test              # run all tests

Commands in Detail

What each command is for, and when to reach for it

The commands below are the ones that deserve more than their one-line summary. Two conventions apply to nearly all of them:

  • Aliases. Single-letter commands such as b, c, r, and t are built-in aliases. You can define your own under [alias] in .cargo/config.toml, for example lint = "clippy --all-targets -- -D warnings".
  • The -- separator. A bare -- ends Cargo’s own options. Everything after it goes to the program Cargo launches: your binary for run, the test harness for test and bench, and the lint driver for clippy.

cargo add

cargo add edits Cargo.toml for you. It looks up the newest version on the registry, writes the entry into the right table, and updates Cargo.lock. It preserves the manifest’s existing formatting and comments, so it is safe to use on a hand-maintained file. Its counterpart, cargo remove (alias rm), deletes an entry.

cargo add serde --features derive   # [dependencies], with a feature enabled
cargo add serde_json@1.0            # an explicit version requirement
cargo add --dev pretty_assertions   # [dev-dependencies]
cargo add --build cc                # [build-dependencies]
cargo add rand --optional           # optional, gated behind a feature
cargo add my_lib --path ../my_lib   # a local crate on disk
cargo remove serde_json

Running cargo add serde --features derive, cargo add serde_json, and cargo add --dev pretty_assertions in a fresh project produces:

[dependencies]
serde = { version = "1.0.229", features = ["derive"] }
serde_json = "1.0.154"

[dev-dependencies]
pretty_assertions = "1.4.1"

Notice that it writes the full current version, "1.0.229", rather than "1". Under the caret rule that means >=1.0.229, <2.0.0: Cargo can still move forward within 1.x, but it will never resolve to anything older than what you tested against when you added it. As it runs, cargo add also prints the crate’s feature list, marking enabled features with + and available ones with -.

cargo bench

cargo bench compiles with the bench profile (which inherits from release) and runs the benchmarks in benches/. Rust’s built-in #[bench] attribute still requires nightly, so on stable the convention is Criterion, a statistics-driven harness that warms up, samples many iterations, and reports confidence intervals along with the change since the previous run. Setting harness = false tells Cargo not to wrap the file in the default test harness, so Criterion’s main takes over.

[dev-dependencies]
criterion = "0.5"

[[bench]]
name    = "fir"      # benches/fir.rs
harness = false
// benches/fir.rs
use criterion::{criterion_group, criterion_main, Criterion};
use my_dsp::fir_filter;
use std::hint::black_box;

fn bench_fir(criterion: &mut Criterion) {
    let samples = vec![0.5_f32; 4096];
    let taps = vec![0.1_f32; 64];
    criterion.bench_function("fir 4096x64", |bencher| {
        bencher.iter(|| fir_filter(black_box(&samples), black_box(&taps)))
    });
}

criterion_group!(benches, bench_fir);
criterion_main!(benches);
cargo bench          # run every benchmark
cargo bench fir      # only benchmarks whose names contain "fir"

Two details matter. A benchmark is compiled as a separate crate, like an integration test, so it can only reach your library’s pub items; code that lives only in main.rs has to move into lib.rs before it can be benchmarked. And black_box hides values from the optimizer. Without it, the compiler can notice that the result is never used and delete the work you meant to time, which is the same trap as timing a C loop at -O2 whose result is never read.

cargo build

cargo build compiles the package and all of its dependencies. Output lands in target/debug/ or target/release/, according to the profile.

cargo build                                  # dev profile, target/debug/
cargo build --release                        # release profile, target/release/
cargo build --target thumbv7em-none-eabihf   # cross-compile, target/<triple>/
cargo build --bin server                     # one binary in a multi-binary package
cargo build --timings                        # HTML report of where build time went

Cross-compiling needs the target’s standard library first: rustup target add thumbv7em-none-eabihf. Unlike a C toolchain, there is no separate cross compiler to install, because rustc is built on LLVM and ships with the code generators for every target it supports.

cargo check

cargo check runs the compiler through parsing, type checking, and borrow checking, then stops before generating code. Since code generation and optimization are where most of the compile time goes, check is several times faster than build, and it is the right command for the edit-compile loop. rust-analyzer runs it in the background every time you save.

The catch is that anything which only fails during code generation or linking (a missing native library, an undefined symbol from a build.rs link directive) will not show up. Run a real build before trusting a clean check.

cargo clippy

Clippy is Rust’s official linter, with several hundred lints that go beyond the compiler’s own warnings. It installs with the default rustup profile and runs exactly like check, with extra analysis on top. Given this loop, written the way a C programmer naturally would:

let samples = [0.25_f32, 0.5, 0.75];
let mut total = 0.0;
for i in 0..samples.len() {
    total += samples[i];
}

Clippy responds:

warning: the loop variable `i` is only used to index `samples`
 --> src/main.rs:4:14
  |
4 |     for i in 0..samples.len() {
  |              ^^^^^^^^^^^^^^^^
  |
  = note: `#[warn(clippy::needless_range_loop)]` on by default
help: consider using an iterator
  |
4 -     for i in 0..samples.len() {
4 +     for <item> in &samples {

The iterator form is not just style: it cannot go out of bounds, so there is no per-element bounds check for the optimizer to prove away and no off-by-one to make. Lints are organized into groups:

Group Default Catches
correctness deny Code that is outright wrong
suspicious warn Code that is very likely wrong
style warn Unidiomatic code
complexity warn Simple things done in a complicated way
perf warn Code that could easily be faster
pedantic allow Stricter lints with occasional false positives
nursery allow New lints still under development
restriction allow Lints that forbid language features; enable them individually
cargo allow Problems in Cargo.toml

Lint levels can be set per project in Cargo.toml. A group needs priority = -1 so that the individual lints listed after it override it:

[lints.clippy]
pedantic = { level = "warn", priority = -1 }
cast_precision_loss = "allow"
cargo clippy                                               # lint the package
cargo clippy --all-targets --all-features -- -D warnings   # CI: lint tests too, fail on any warning
cargo clippy --fix                                         # apply the suggestions that are safe to automate

--fix applies only machine-applicable suggestions. The loop above does not qualify, because the suggestion contains a placeholder (<item>) that a human has to name.

cargo doc

cargo doc runs rustdoc over your crate and every dependency, producing the same HTML you see on docs.rs.

cargo doc --open                     # build and open in a browser
cargo doc --no-deps                  # only your own crate
cargo doc --document-private-items   # include non-pub items (useful for binaries)

The underrated benefit is precision: the generated docs describe exactly the versions pinned in your Cargo.lock, and they work offline. docs.rs defaults to the latest release, which may not be the version you are using.

cargo fix

cargo fix applies the compiler’s machine-applicable suggestions to your source. Given let mut count = samples.len(); where count is never mutated, rustc warns “variable does not need to be mutable”, and cargo fix makes the change:

-    let mut count = samples.len();
+    let count = samples.len();
cargo fix                 # apply compiler suggestions
cargo fix --edition       # migrate code to the next edition
cargo fix --allow-dirty   # run even with uncommitted changes

Because it rewrites files in place, cargo fix refuses to run on a working tree with uncommitted changes unless you pass --allow-dirty. That way the fixes always appear as a reviewable diff. Its most important use is the edition migration. cargo clippy --fix is the same mechanism applied to Clippy’s lints.

cargo fmt

cargo fmt runs rustfmt over every file in the package. The stable configuration surface is deliberately small, and most of rustfmt’s options are nightly-only. That is by design: the goal is for all Rust code to look the same, which settles the brace-and-indent debate that C codebases fight one project at a time.

cargo fmt           # format in place
cargo fmt --check   # CI: exit non-zero if anything would change
# rustfmt.toml, at the package root
max_width = 120     # default is 100

cargo info

cargo info (added in Cargo 1.82) shows a crate’s registry metadata without leaving the terminal: description, license, minimum Rust version, links, and its feature table.

$ cargo info serde
serde #serde #serialization #no_std
A generic serialization/deserialization framework
version: 1.0.229
license: MIT OR Apache-2.0
rust-version: 1.56
documentation: https://docs.rs/serde
homepage: https://serde.rs
repository: https://github.com/serde-rs/serde
crates.io: https://crates.io/crates/serde/1.0.229
features:
 +default      = [std]
  std          = [serde_core/std]
  alloc        = [serde_core/alloc]
  derive       = [serde_derive]
  rc           = [serde_core/rc]
  serde_derive = [dep:serde_derive]
  unstable     = [serde_core/unstable]

The feature table is the main reason to use it: it tells you the feature names to pass to cargo add --features, and + marks what is on by default. Append a version (cargo info serde@1.0.200) to inspect an older release. Run inside a project that already depends on the crate, it describes the version in your lockfile.

cargo install

cargo install builds a binary crate from source, in release mode, and puts the executable in ~/.cargo/bin.

cargo install ripgrep            # build rg from crates.io
cargo install --locked ripgrep   # use the crate's own Cargo.lock
cargo install --path .           # install the current project
cargo install --list             # what is installed
cargo uninstall ripgrep

Use --locked by habit. Without it, install ignores the published lockfile and resolves dependencies fresh, so a new release of some transitive dependency can break the build of a tool that compiled fine yesterday.

WarningNot a library installer

Coming from pip install or npm install -g, it is natural to try cargo install serde. That fails, because serde has no binary. Rust has no global library directory: libraries are per-project dependencies, added with cargo add and compiled into each project that uses them.

install is also how Cargo grows. Any executable on your PATH named cargo-<name> runs as cargo <name>. That is why bundle and miri appear in the command list above without descriptions: they are not part of Cargo. cargo install cargo-bundle provided the first, and rustup component add miri the second.

cargo metadata

cargo metadata prints the package’s manifest data and its fully resolved dependency graph as JSON. It is the stable, machine-readable interface for tools: editor plugins, build scripts, and anything that needs to know about a project without parsing Cargo.toml and reimplementing Cargo’s resolver. Always pass --format-version 1; Cargo warns if you omit it, since the output format is versioned so that tools do not break.

cargo metadata --format-version 1 --no-deps | jq -r '.target_directory'
# /Users/me/demo/target

cargo metadata --format-version 1 | jq -r '.packages[] | "\(.name) \(.version)"'
# every package in the resolved graph, with its exact version

cargo tree answers the same questions for a person; cargo metadata answers them for a program. Rust tools usually consume it through the cargo_metadata crate rather than parsing the JSON by hand.

cargo new

cargo new creates a package in a new directory, and cargo init does the same in the current one.

cargo new demo         # binary package: src/main.rs
cargo new --lib dsp    # library package: src/lib.rs
cargo init             # turn the current directory into a package
demo/
├── .gitignore
├── Cargo.toml
└── src/
    └── main.rs

It also initializes a git repository, unless the directory is already inside one (pass --vcs none to skip it). The edition field defaults to the newest edition your toolchain supports.

cargo package

cargo package builds the .crate file that publish would upload: a gzipped tarball written to target/package/<name>-<version>.crate. You will rarely run it for its own sake, but --list is the best way to see exactly what you are about to ship:

$ cargo package --list
.cargo_vcs_info.json
.gitignore
Cargo.lock
Cargo.toml
Cargo.toml.orig
src/main.rs

Cargo.toml.orig is your manifest as written. Cargo.toml is a normalized rewrite, with path dependencies replaced by registry versions and workspace inheritance flattened, so the crate builds on its own. .cargo_vcs_info.json records the git commit it came from.

The valuable step is verification. After assembling the tarball, Cargo unpacks it and builds it in isolation. That catches the classic “works on my machine” failure, where a file the build depends on (a build.rs input, a file read by include_str!) exists in your checkout but was left out of the package. Control what goes in with include or exclude under [package].

cargo publish

cargo publish packages, verifies, and uploads to crates.io. The one-time setup is a crates.io account (sign-in is through GitHub) and an API token.

cargo login               # paste a token from crates.io's account settings
cargo publish --dry-run   # package and verify, upload nothing
cargo publish

crates.io rejects a crate without a description and a license (or license-file). Every dependency must also be resolvable from the registry: a path dependency needs a version alongside it (the path is used locally, the version once published), and git dependencies are not allowed.

WarningPublishing is permanent

A published version cannot be overwritten, and its version number can never be reused. The source remains downloadable indefinitely; yanking does not remove it. If a secret ends up in a published crate, rotate the secret. Crate names are also global and first-come, first-served, since crates.io has no namespaces.

cargo report

Cargo normally suppresses warnings from dependencies, since you cannot fix them anyway. That creates a blind spot: a dependency may rely on behavior the compiler has announced it will reject in a future release, and you would only find out when your build breaks. When that happens, Cargo prints a short notice at the end of the build, and cargo report shows the details. On stable Cargo it offers exactly one report:

cargo report future-incompatibilities          # the most recent report
cargo report future-incompatibilities --id 1   # a specific report, by the id in the notice

The usual fix is a cargo update of the named crate, since the maintainers have often already released a fix.

cargo run

cargo run builds if needed, then runs the binary.

cargo run                            # the package's only binary
cargo run -- --input data.csv -v     # arguments after -- go to your program
cargo run --release
cargo run --bin server               # choose among several binaries
cargo run --example plot             # run examples/plot.rs

cargo search

cargo search queries the registry by name and description:

$ cargo search serde --limit 3
serde = "1.0.229"         # A generic serialization/deserialization framework
serde-saphyr = "2.0.0"    # YAML (de)serializer for Serde, emphasizing panic-free parsing, fast builds and good error reporting. …
clickhouse = "0.15.3"     # Official Rust client for ClickHouse DB
... and 23351 crates more (use --limit N to see more)

Each line is formatted as a ready-to-paste Cargo.toml entry. The results include no download counts or maintenance signals, so for choosing between crates, crates.io or lib.rs are better. Once you have a candidate, cargo info shows the details.

cargo test

cargo test builds and runs three kinds of tests:

  • Unit tests live in a #[cfg(test)] module beside the code they test, so they can reach private items.
  • Integration tests live in tests/. Each file is compiled as a separate crate that sees only your public API.
  • Doctests are code examples inside /// doc comments, compiled and run so the documentation cannot drift out of date.
pub fn mean(samples: &[f32]) -> f32 {
    samples.iter().sum::<f32>() / samples.len() as f32
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn mean_of_constant_signal() {
        assert_eq!(mean(&[0.5, 0.5, 0.5]), 0.5);
    }
}
cargo test                       # everything
cargo test mean                  # only tests whose names contain "mean"
cargo test --test parsing        # only tests/parsing.rs
cargo test --doc                 # only doctests
cargo test -- --nocapture        # show println! output from passing tests
cargo test -- --test-threads=1   # run tests one at a time

The last flag exists because tests run in parallel threads by default. Tests that share a file, an environment variable, or a global will interfere with each other, and the failures will be intermittent.

cargo tree

cargo tree prints the resolved dependency graph:

$ cargo tree
demo v0.1.0 (/Users/me/demo)
├── serde v1.0.229
│   ├── serde_core v1.0.229
│   └── serde_derive v1.0.229 (proc-macro)
│       ├── proc-macro2 v1.0.107
│       │   └── unicode-ident v1.0.27
│       ├── quote v1.0.47
│       │   └── proc-macro2 v1.0.107 (*)
│       └── syn v3.0.9
│           ├── proc-macro2 v1.0.107 (*)
│           ├── quote v1.0.47 (*)
│           └── unicode-ident v1.0.27
└── serde_json v1.0.154
    ├── itoa v1.0.18
    ├── memchr v2.8.3
    ├── serde_core v1.0.229
    └── zmij v1.0.23
[dev-dependencies]
└── pretty_assertions v1.4.1
    ├── diff v0.1.13

(*) marks a subtree that has already been printed. The flags are what make it a diagnostic tool:

cargo tree --invert itoa    # who pulls this crate in?
cargo tree --duplicates     # crates present in more than one version
cargo tree -e features      # which features are enabled, and by whom
cargo tree --depth 1        # direct dependencies only
$ cargo tree --invert itoa
itoa v1.0.18
└── serde_json v1.0.154
    └── demo v0.1.0 (/Users/me/demo)

--duplicates deserves an explanation. Unlike a C linker, which would reject two copies of the same library as duplicate symbols, Cargo happily links semver-incompatible versions of one crate into a single binary, because each version’s symbols are mangled with a distinct hash. The costs are compile time, binary size, and a confusing class of type error: a Value from version 1 of a crate is a different type from a Value in version 2, even though the compiler prints them with the same name.

cargo update

cargo update moves Cargo.lock forward to the newest versions that Cargo.toml allows.

cargo update                           # every dependency
cargo update serde                     # just one
cargo update serde --precise 1.0.200   # an exact version (also works for going back)
cargo update --dry-run                 # show what would change

It rewrites only the lockfile. It never edits Cargo.toml, so it never crosses a major version: if the requirement is "1.0", version 2.0 is out of reach. A breaking upgrade means changing the requirement yourself, by hand or with cargo add serde@2, and then fixing whatever breaks.

cargo yank

cargo yank marks a published version as one that should not be chosen for new dependency resolutions.

cargo yank my_crate --version 1.0.1          # yank
cargo yank my_crate --version 1.0.1 --undo   # restore

A yank does not delete anything. Projects whose Cargo.lock already pins the yanked version keep building, which is the point: you can withdraw a broken release without breaking everyone downstream who depends on it. Since the code stays downloadable, a yank does nothing for a leaked secret.

See the Cargo commands reference in The Cargo Book for every command and flag.

Cargo.toml in Full

A complete manifest with all common fields looks like this:

[package]
name        = "my_project"
version     = "0.1.0"
edition     = "2021"
rust-version = "1.70"           # minimum Rust version required to compile this crate
authors     = ["Alice <alice@example.com>"]
description = "A short description"
license     = "MIT OR Apache-2.0"
repository  = "https://github.com/alice/my_project"

[dependencies]
serde  = { version = "1.0", features = ["derive"] }
regex  = "1.10"
rand   = { version = "0.8", optional = true }       # only included if the feature is enabled
my_lib = { path = "../my_lib" }                     # local crate on disk
some_fork = { git = "https://github.com/...", branch = "fix/thing" }

[dev-dependencies]
pretty_assertions = "1.4"   # only compiled for tests and benchmarks

[build-dependencies]
cc = "1.0"                  # only compiled for build.rs

[features]
default  = []               # features enabled by default (none here)
graphics = ["rand"]         # enable this feature to pull in rand

[profile.release]
opt-level = 3               # maximum optimization
lto       = true            # link-time optimization
strip     = true            # strip debug symbols from the binary

Editions

Opt-in language evolution without breaking the ecosystem

Yes, editions are named by year: 2015, 2018, 2021, and 2024. Each edition allows the Rust team to make changes to the language’s syntax and semantics that would otherwise be backward-incompatible, without forcing anyone to upgrade immediately.

The key insight is that editions are per-crate, and all editions can link together. A crate compiled with edition 2015 and a crate compiled with edition 2021 produce compatible object code. The edition setting lives in Cargo.toml and affects only the crate it belongs to. This means the ecosystem never splits the way Python 2 vs Python 3 did.

What changes between editions is language syntax and a small number of semantic rules, not the standard library. The standard library API is versioned by the Rust release channel separately. An example: in edition 2015 you had to write extern crate serde; at the top of main.rs to bring an external crate into scope. In 2018 that was removed entirely. Both editions call the same serde functions at runtime.

Edition Notable changes
2015 Original Rust. extern crate required. Old module path rules.
2018 extern crate no longer needed. Clearer use paths (crate::, super::). async/await syntax. ? usable in main. Non-lexical lifetimes.
2021 More precise closure captures (captures only what it uses, not the whole struct). IntoIterator implemented for arrays. Cargo feature resolver v2.
2024 gen blocks and coroutines. impl Trait lifetime improvements. Stricter unsafe requirements.

Migrating is low-friction. Running cargo fix --edition rewrites the parts of your code that need updating automatically, then you change the edition field in Cargo.toml. Most migrations take a few minutes.

NoteWhich edition to use?

Start new projects with the latest edition (2021 at minimum, 2024 if your toolchain supports it). There is no reason to start on an older edition. When reading existing code, the edition tells you which syntax rules apply, which matters when looking up path resolution or closure capture behavior.

Dependency Version Constraints

Cargo uses semantic versioning. The version string in Cargo.toml is a requirement, not an exact pin. Cargo selects the newest version that satisfies all constraints in the dependency graph:

Requirement Meaning Resolves to (e.g.)
"1.0" or "^1.0" >=1.0.0, <2.0.0 (default) 1.9.4
"1.2.3" or "^1.2.3" >=1.2.3, <2.0.0 1.9.4
"~1.2.3" >=1.2.3, <1.3.0 (patch only) 1.2.9
"=1.2.3" Exactly 1.2.3 1.2.3
"*" Any version latest

The caret rule (^) is the default and the most common. It reflects semver’s promise: a library increment its major version when it makes breaking changes, so >=1.0, <2.0 is safe to let Cargo update freely within.

Cargo.lock records the exact resolved versions. Commit it, for binaries and libraries alike.

That has been Cargo’s official guidance since August 2023. Before then, the advice was to commit the lockfile for binaries but not for libraries, and you will still see that rule repeated. The key fact behind both versions of the advice is that a library’s Cargo.lock never reaches its users: when your crate is a dependency, Cargo resolves the whole graph using only the top-level project’s lockfile. So committing a library’s lockfile cannot hold anyone downstream back. The old worry was the reverse: a committed lockfile means the library’s own CI keeps testing against old dependency versions, while a new user who adds the crate gets the latest ones and may hit a break the maintainer never saw.

The current guidance values a reproducible checkout over that concern, since a git bisect or a contributor’s first build is only meaningful if everyone resolves the same versions. The staleness problem is handled separately: let a bot such as Dependabot or Renovate keep the lockfile current, or add a CI job that runs cargo update before testing so it always tests what a new user would get.

Dependency Scopes

Not every dependency is needed in every context:

[dependencies]       # always compiled, included in the final binary
serde = "1.0"

[dev-dependencies]   # compiled only for `cargo test` and `cargo bench`
mockall = "0.12"
criterion = "0.5"

[build-dependencies] # compiled only for build.rs (runs before the main build)
cc = "1.0"

dev-dependencies are the right place for test helpers, assertion libraries, and benchmarking frameworks. They are absent from release builds entirely.

build-dependencies are for build.rs, a special script Cargo runs before compiling your crate. Common uses: compiling C code, generating Rust source from a schema, or probing the build environment.

Feature Flags

Features let you make parts of your crate optional, activated at compile time:

[features]
default  = ["logging"]          # enabled unless the user opts out
logging  = ["dep:log"]          # enables the `log` dependency
tls      = ["dep:rustls"]
full     = ["logging", "tls"]   # convenience: enables everything

A user of your crate enables features in their own Cargo.toml:

my_lib = { version = "1.0", features = ["tls"] }
my_lib = { version = "1.0", default-features = false }   # strip defaults

In your code, gate feature-specific code with #[cfg(feature = "tls")]:

#[cfg(feature = "tls")]
pub mod tls_support { ... }

Features are additive: enabling a feature can only add code, never remove it. This is a deliberate constraint that keeps the dependency resolver simple.

Build Profiles

Cargo compiles in two profiles by default. You can tune both:

[profile.dev]
opt-level = 0      # no optimization — fast to compile, slow to run
debug     = true   # include debug symbols

[profile.release]
opt-level = 3      # maximum optimization — slow to compile, fast to run
lto       = true   # link-time optimization: slower link, smaller/faster binary
strip     = true   # remove debug symbols from the output binary
panic     = "abort" # smaller binary: no stack unwinding on panic

cargo build uses dev. cargo build --release uses release. You can define custom profiles for benchmarks or special builds:

[profile.bench]
inherits  = "release"
debug     = true    # keep symbols for profiling

Environment Variables

Cargo manages a well-known list of environment variables. They fall into to major categories:

  1. Variables Cargo sets: these are variables that Cargo prepares for our consumption during compilation.
  2. Variables Cargo reads: these are variables that Cargo consumes during compilation.
env the Function

Rust includes the env module as part of the standard library. It includes functions to read and write environment variables.

Examples
use std::env;

let key = "HOME";
match env::var(key) {
    Ok(val) => println!("{key}: {val:?}"),
    Err(e) => println!("couldn't interpret {key}: {e}"),
}
use std::env;

let key = "KEY";
unsafe {
    env::set_var(key, "VALUE");
}
assert_eq!(env::var(key), Ok("VALUE".to_string()));

But the super-cool way of reading an environment variable is the env! macro.

env! the Macro

env! inspects an environment variable at compile time. This macro will expand to the value of the named environment variable at compile time, yielding an expression of type &'static str. If the environment variable is not defined, then a compilation error will be emitted. To not emit a compile error, use the option_env! macro instead.

Examples
let path: &'static str = env!("PATH");
println!("the $PATH variable at the time of compiling was: {path}");

You can customize the error message by passing a string as the second parameter:

let doc: &'static str = env!("documentation", "what's that?!");

build.rs

build.rs is one of those Cargo conventions that feels like magic until you know the rule behind it.

What is it?

Is it like a preprocessor?

It is sort of like a preprocessor, but it’s a useful distinction to draw. A C preprocessor does textual substitution inside your source before compilation. build.rs doesn’t touch or rewrite your .rs files at all. It’s better thought of as a pre-build hook: an arbitrary Rust program that runs first and influences the build from the outside via three main channels:

  • Environment variables for env!() (your version hash).
  • Generated code files written into OUT_DIR, which your crate then pulls in with include!(concat!(env!("OUT_DIR"), "/generated.rs")). This part is the closest thing to preprocessing/codegen.
  • Linker/compiler directives printed to Cargo (link a native library, add a search path, set a cfg flag).
Run by Magic?

How does Rust know to run it?

It’s pure convention over configuration. Cargo automatically looks for a file named exactly build.rs in the package root (next to Cargo.toml). If it exists, Cargo treats it as the package’s build script, compiles it as a standalone binary, and runs it before compiling your actual crate. That’s the whole rule: right name, right location. Nothing in Cargo.toml needs to point at it. If you want to opt out of the convention or use a different path, that’s when you configure it explicitly:

[package]
build = "my_build_script.rs"   # custom path
# or
build = false                   # disable auto-detection entirely

So the absence of configuration in your other project isn’t Rust doing something implicit and hidden; it’s you relying on the default that build = "build.rs" is assumed.

The Execution Model

This is the key mental model:

  1. Cargo compiles build.rs into its own executable (it can use dependencies you list under [build-dependencies] in Cargo.toml).
  2. Cargo runs that executable before building your crate.
  3. The build script communicates back to Cargo by printing specially-formatted lines to stdout, like cargo:rustc-env=... or cargo:rerun-if-changed=....
  4. Then your crate compiles, with whatever the build script set up now in effect.

Your build-hash-in-the-version case is a textbook example. The script runs git, captures the hash, and prints something like:

// build.rs
fn main() {
    let hash = /* run `git rev-parse --short HEAD` */;
    println!("cargo:rustc-env=BUILD_HASH={hash}");
}

Then in your actual source you read it at compile time with env!("BUILD_HASH"). The value gets baked into the binary as a string literal.

Intended Use

How is it intended to be used?

  • Compiling native/C code and linking it (via the cc crate). This is the single most common use.
  • Code generation: protobuf (prost/tonic), FFI bindings (bindgen), parsers, big lookup tables computed at build time.
  • Baking in build metadata: git hash, build timestamp, compiler version, target triple (your case; the vergen crate automates exactly this).
  • Feature/environment detection: probing whether a system library exists and emitting cfg flags accordingly.
Caching

Put many a good man in the asylum

By default Cargo re-runs the build script when any file in the package changes, and caches otherwise. Build scripts control this explicitly with:

println!("cargo:rerun-if-changed=path/to/file");
println!("cargo:rerun-if-env-changed=SOME_VAR");

The moment you emit any rerun-if-* line, you override the default and Cargo will only re-run for the conditions you list. This bites people with git-hash scripts: the hash changes on every commit, but no tracked file Cargo watches necessarily changed, so the baked-in hash can go stale. The common workaround is to watch .git/HEAD and the relevant ref, or to force a re-run each time.

See Packages, Crates, and Modules in The Rust Programming Language for more information.

Crates

A few fellas that I have taken a liking to

A crate comes in two flavors: executables and libraries. Library crates don’t have a main function, and they don’t compile to an executable. Instead, they define functionality intended to be shared with multiple projects. And when you feel like sharing your brilliance with the world, you can version and publish your library crate to crates.io where it will be hosted for others to pull down.

This little section briefly covers some published crates that I can use help with. Starting with clap.

clap

Command-line argument parsing, the civilized way

clap (Command Line Argument Parser) turns a Rust struct into a fully-featured CLI: --help, --version, validation, subcommands, and shell completions all come for free. You describe what your program accepts; clap handles the rest.

Add it to Cargo.toml with the derive feature, which enables the attribute-based API used throughout this section:

[dependencies]
clap = { version = "4", features = ["derive"] }

The Derive API

The derive API lets you describe your CLI as a struct. Clap reads the struct and its attributes at compile time and generates the parser automatically. This is the approach you will use in almost all real projects.

use clap::Parser;

#[derive(Parser)]
#[command(name = "greet", version = "1.0", about = "Greet someone")]
struct Cli {
    /// The name to greet
    name: String,

    /// How many times to repeat the greeting
    #[arg(short, long, default_value_t = 1)]
    count: u32,
}

fn main() {
    let cli = Cli::parse();

    for _ in 0..cli.count {
        println!("Hello, {}!", cli.name);
    }
}

Running ./greet --help produces:

Greet someone

Usage: greet [OPTIONS] <NAME>

Arguments:
  <NAME>  The name to greet

Options:
  -c, --count <COUNT>  How many times to repeat the greeting [default: 1]
  -h, --help           Print help
  -V, --version        Print version

Cli::parse() reads std::env::args(), validates the input, and returns a populated Cli. If parsing fails, it prints an error and exits — no Result to unwrap.

#[derive(Parser)]

Parser is the trait that drives everything. Applying #[derive(Parser)] to a struct generates an implementation of that trait, including the parse() and try_parse() associated functions. Without it, none of the other clap attributes do anything.

#[derive(Parser)]          // generates Cli::parse(), Cli::try_parse(), etc.
struct Cli { ... }

try_parse() is available when you want to handle errors yourself instead of letting clap exit:

let cli = Cli::try_parse()?;   // returns Result<Cli, clap::Error>

#[command(...)] Attributes

#[command(...)] applies to the struct as a whole and controls top-level metadata about your program.

#[derive(Parser)]
#[command(
    name    = "pexs24",
    version = env!("CARGO_PKG_VERSION"),
    author  = "Curtis",
    about   = "Process expression files for the 2024 dataset",
)]
struct Cli { ... }
Attribute Effect
name = "pexs24" Sets the program name shown in usage and help text
version = "1.2.3" Sets the version shown by --version
version = env!("CARGO_PKG_VERSION") Reads the version from Cargo.toml at compile time
author = "..." Sets the author shown in --help
about = "..." One-line description shown at the top of --help
long_about = "..." Longer description shown in --help (multiline)

name = "pexs24" matters because clap uses the binary file name by default. If your binary is named target/debug/pexs24_dev, that ugly name shows up in every usage example. Setting name pins it to a clean, version-independent string.

version = env!("CARGO_PKG_VERSION") is worth pausing on. env! is a built-in Rust macro that reads an environment variable at compile time. Cargo sets CARGO_PKG_VERSION to the version field in your Cargo.toml before invoking the compiler. The result is that your --version output always matches your Cargo.toml with zero manual synchronization.

# Cargo.toml
[package]
version = "0.3.1"
$ pexs24 --version
pexs24 0.3.1

Change the version in one place; the binary reflects it automatically.

#[arg(...)] Attributes

#[arg(...)] applies to individual fields and controls how each argument is parsed.

Positional Arguments

A field with no short or long attribute is positional — the user supplies it by position, not by name.

#[derive(Parser)]
struct Cli {
    #[arg(name = "FILE", num_args = 1)]
    input: String,
}
Usage: prog <FILE>
What does name = "FILE" mean?

The name attribute in #[arg(...)] sets the argument’s internal ID and, for positional arguments, its metavar — the placeholder text shown in usage and help output. The uppercase FILE in <FILE> is a Unix convention: metavars are written in ALL_CAPS to visually distinguish the placeholder from the flags around it, and to make the type of input obvious at a glance.

Usage: prog [OPTIONS] <FILE>              # FILE is the metavar
            ^^^^^^^^  ^^^^^^
            flags      positional argument

“FILE” is not arbitrary. It communicates meaning to the user: this argument expects a file path. By convention:

Metavar Communicates
<FILE> Expects a file path
<DIR> Expects a directory path
<HOST> Expects a hostname or IP address
<N> Expects a number
<PATTERN> Expects a regular expression
<KEY> Expects a key string

Clap will use the field name (uppercased) as the metavar if you omit name. So a field named input would display as <INPUT>. Setting name = "FILE" gives you a more informative, idiomatic label without renaming the Rust field.

If you want to control the metavar display independently of the ID, use value_name instead:

#[arg(value_name = "FILE")]
input: String,

value_name only affects the display; it does not change the ID. This is the preferred approach in clap 4.

num_args = 1 tells clap how many values this argument consumes. For a single value it is the default, so you typically omit it. More useful forms:

num_args Meaning
1 Exactly one value (the default)
0..=1 Zero or one value (use Option<T> for the field)
1.. One or more values (use Vec<T> for the field)
0.. Zero or more values
3 Exactly three values
Flags and Options

Adding short and/or long turns a field into a named argument rather than a positional one.

#[derive(Parser)]
struct Cli {
    /// Enable verbose output
    #[arg(short, long)]
    verbose: bool,          // --verbose / -v

    /// Output file path
    #[arg(short, long, value_name = "FILE")]
    output: Option<String>, // --output <FILE> / -o <FILE>, optional

    /// Number of threads
    #[arg(short = 'j', long = "jobs", default_value_t = 4)]
    jobs: u32,              // --jobs <JOBS> / -j <JOBS>
}

short and long without values derive from the field name: verbose becomes -v and --verbose. Assign explicit characters or strings when the default conflicts or is not what you want.

bool fields paired with short/long become flags — they are false by default and become true when passed. No value is consumed.

Option<T> fields are optional arguments — omitting them produces None; passing them produces Some(value).

Common #[arg(...)] Attributes
Attribute Effect
short Add a short flag derived from the field name (-v)
short = 'x' Add a specific short flag (-x)
long Add a long flag derived from the field name (--verbose)
long = "my-flag" Add a specific long flag
value_name = "FILE" Set the metavar shown in help text
name = "FILE" Set the argument’s internal ID (and metavar for positionals)
default_value = "8080" String default, parsed into the field’s type
default_value_t = 8080 Typed default — no parsing, must match the field type
required = true Force the argument to be provided (overrides Option<T>)
num_args = 1.. Accept multiple values into a Vec<T>
env = "MY_VAR" Fall back to an environment variable if the flag is absent
hide = true Omit the argument from help output

Doc comments (/// ...) above a field become the help text for that argument. Clap reads them directly — no separate help = "..." attribute needed.

Multiple Values

When a flag should accept a list of values, use Vec<T> and num_args:

#[derive(Parser)]
struct Cli {
    /// Input files to process
    #[arg(value_name = "FILE", num_args = 1..)]
    inputs: Vec<String>,

    /// Tags to apply
    #[arg(short, long, value_name = "TAG")]
    tags: Vec<String>,         // --tag foo --tag bar
}

Positional Vec<T> with num_args = 1.. collects all remaining positional arguments. Named Vec<T> fields (with short/long) allow the flag to be repeated: --tag foo --tag bar.

Subcommands

Subcommands model tools like git commit or cargo build where the first argument selects a mode of operation. Clap supports both, and both may have their own options:

<command> [command-options] <subcommand> [subcommand-options] [subcommand-args]

  • command: (defined on the top-level Cli struct)
  • command-options: (defined on the top-level Cli struct)
  • subcommand: (defined inside a specific enum variant)
  • subcommand-options: (defined inside a specific enum variant)

If a command option should work in either position, mark it global = true.

Define an enum with #[derive(Subcommand)] and embed it in your top-level Parser struct. By convention this struct is named Cli, but any name works — clap derives from the struct name you call .parse() on:

use clap::{Parser, Subcommand};

#[derive(Parser)]
#[command(name = "tool")]
struct Cli {
    /// Command-level option (applies to the root command)
    #[arg(long, value_name = "FILE", default_value = "tool.toml")]
    config: String,

    /// Global option: accepted before or after the subcommand
    #[arg(short, long, global = true)]
    verbose: bool,

    #[command(subcommand)]
    command: Commands,
}

#[derive(Subcommand)]
enum Commands {
    /// Compress a file
    Compress {
        #[arg(value_name = "FILE")]
        input: String,

        #[arg(short, long, value_name = "FILE")]
        output: Option<String>,
    },
    /// List available formats
    Formats,
}

fn main() {
    let cli = Cli::parse();

    if cli.verbose {
        eprintln!("Using config: {}", cli.config);
    }

    match cli.command {
        Commands::Compress { input, output } => {
            let dest = output.unwrap_or_else(|| format!("{}.gz", input));
            println!("Compressing {} -> {}", input, dest);
        }
        Commands::Formats => {
            println!("Supported: gz, zst, xz");
        }
    }
}
  • #[command(subcommand)] on the command field tells clap “when parsing, look for a subcommand name here”.
  • The enum Commands (tagged #[derive(Subcommand)]) is the dispatcher — it lists what subcommands are available and routes to the right one.
  • Compress and Formats are the actual subcommands — the things the user types on the command line
So the flow is
  1. clap sees a word on the command line.
  2. It hands it to the dispatcher enum (Command).
  3. The dispatcher enum matches it to a variant and populates that variant’s fields.
$ tool --help
Usage: tool [OPTIONS] <COMMAND>

Commands:
  compress  Compress a file
  formats   List available formats
  help      Print this message or the help of a subcommand

Options:
      --config <FILE>  [default: tool.toml]
  -v, --verbose
  -h, --help           Print help

$ tool compress --help
Compress a file

Usage: tool compress [OPTIONS] <FILE>

Arguments:
  <FILE>

Options:
  -o, --output <FILE>
  -v, --verbose
  -h, --help           Print help

Each subcommand gets its own --help page automatically.

Optional Subcommands

If the tool should run without a subcommand (falling back to some default behavior), make the field Option<Commands>:

#[derive(Parser)]
struct Cli {
    #[command(subcommand)]
    command: Option<Commands>,
}

fn main() {
    let cli = Cli::parse();

    match cli.command {
        Some(Commands::Compress { input, output }) => { /* ... */ }
        Some(Commands::Formats)                    => { /* ... */ }
        None                                       => println!("No subcommand given; try --help"),
    }
}

A Complete Example

Sans subcommands

Putting it all together: a realistic flat CLI (no subcommands) for a file processing tool, combining positional arguments, optional flags, typed defaults, and version output.

use clap::Parser;

#[derive(Parser)]
#[command(
    name    = "pexs24",
    version = env!("CARGO_PKG_VERSION"),
    about   = "Process expression files for the 2024 dataset",
)]
struct Cli {
    /// Input file to process
    #[arg(value_name = "FILE", num_args = 1)]
    input: String,

    /// Write output to FILE instead of stdout
    #[arg(short, long, value_name = "FILE")]
    output: Option<String>,

    /// Number of worker threads
    #[arg(short = 'j', long = "jobs", default_value_t = 4, value_name = "N")]
    jobs: u32,

    /// Enable verbose logging
    #[arg(short, long)]
    verbose: bool,
}

fn main() {
    let cli = Cli::parse();

    if cli.verbose {
        eprintln!("Processing {} with {} threads", cli.input, cli.jobs);
    }

    match cli.output {
        Some(path) => println!("Writing to {}", path),
        None       => println!("Writing to stdout"),
    }
}
$ pexs24 --help
Process expression files for the 2024 dataset

Usage: pexs24 [OPTIONS] <FILE>

serde

The serialization framework that the whole ecosystem agrees on

serde (a contraction of serialize/deserialize) is the crate Rust uses to convert data structures to and from external formats: JSON, TOML, YAML, MessagePack, CBOR, and dozens more. It is, by download count, the most-used crate in the ecosystem, and for good reason: nearly every library that touches a config file, an HTTP body, or a .json on disk speaks serde. Learn it once and the knowledge transfers everywhere.

The problem it solves is the one C/C++ programmers know painfully well. In C, turning a struct into JSON means hand-writing a function that walks each field and prints it, and parsing means hand-writing the inverse with all the error checking that implies. Every struct needs its own pair of functions, every format needs its own variant, and a single renamed field silently breaks the round-trip. serde generates all of that for you at compile time, and does it once for every format simultaneously.

The Big Idea

A Two-Sided Framework

The insight that makes serde different from a typical JSON library is that it splits the work in half and standardizes the seam between the halves.

  • Your type implements Serialize / Deserialize. These traits describe the shape of your data (“I am a struct with three fields named x, y, z”) without knowing or caring what format it will become.
  • A format crate (serde_json, toml, serde_yaml, …) implements a Serializer / Deserializer. These know how to write and read one specific format, without knowing anything about your particular struct.

serde defines the interface in the middle. Your type talks to that interface; the format crate talks to that interface; the two never talk to each other directly. This is why one #[derive(Serialize, Deserialize)] on your struct gives you every format at once. Add the toml crate and your existing structs serialize to TOML with no further changes.

It is the same separation-of-concerns move as a virtual interface in C++: the data model is the abstract base class both sides depend on, so neither side depends on the other.

Adding It to a Project

serde itself is the framework; you almost always pair it with at least one format crate. The derive feature enables the #[derive(...)] macros and is the part you will use constantly.

[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"          # the JSON format crate

For other formats, add the corresponding crate alongside it:

toml = "0.8"              # TOML, e.g. for config files
serde_yaml = "0.9"        # YAML
rmp-serde = "1"           # MessagePack (a compact binary format)

Deriving Serialize and Deserialize

The entire workflow starts by tagging your type. #[derive(Serialize, Deserialize)] reads the struct at compile time and generates both implementations.

use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
struct Config {
    host: String,
    port: u16,
    retries: u32,
}

That derive is the whole investment. From here, any format crate can read and write a Config. Here it is with JSON:

use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
struct Config {
    host: String,
    port: u16,
    retries: u32,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config {
        host: "localhost".to_string(),
        port: 8080,
        retries: 3,
    };

    // Serialize: struct -> JSON string
    let json = serde_json::to_string_pretty(&config)?;
    println!("{json}");

    // Deserialize: JSON string -> struct
    let parsed: Config = serde_json::from_str(&json)?;
    println!("{parsed:?}");

    Ok(())
}
{
  "host": "localhost",
  "port": 8080,
  "retries": 3
}
Config { host: "localhost", port: 8080, retries: 3 }

Two things worth noticing. First, deserialization is type-directed: serde_json::from_str knows to produce a Config because the binding is annotated let parsed: Config. serde reads the JSON to fill that specific shape, so a missing or mistyped field becomes a real Err, not a silent default. Second, the field names in the output come straight from the Rust field names. That mapping is the default, and it is adjustable, which the next section covers.

It Really Is Format-Agnostic

The same Config struct, with no changes, round-trips through any format crate. The only thing that changes is which crate’s to_string / from_str you call.

// JSON
let text = serde_json::to_string(&config)?;
let back: Config = serde_json::from_str(&text)?;

// TOML
let text = toml::to_string(&config)?;
let back: Config = toml::from_str(&text)?;

// YAML
let text = serde_yaml::to_string(&config)?;
let back: Config = serde_yaml::from_str(&text)?;

The same struct rendered in each format:

# TOML
host = "localhost"
port = 8080
retries = 3
# YAML
host: localhost
port: 8080
retries: 3

This is the payoff of the two-sided design: you describe your data once and gain every format the ecosystem supports. A config file in TOML, an API response in JSON, and a cache in MessagePack can all share the exact same struct definitions.

Customizing the Mapping with Attributes

Real-world data rarely matches Rust naming conventions exactly. JSON tends toward camelCase, your structs use snake_case, fields are sometimes optional, and external names do not always make valid Rust identifiers. serde’s #[serde(...)] attributes bridge the gap, much as clap’s #[arg(...)] attributes tune argument parsing.

use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
#[serde(rename_all = "camelCase")]      // userId in JSON, user_id in Rust
struct User {
    user_id: u64,

    #[serde(rename = "emailAddress")]   // override a single field's name
    email: String,

    #[serde(default)]                   // missing -> Default::default()
    active: bool,

    #[serde(skip_serializing_if = "Option::is_none")]
    nickname: Option<String>,           // omitted from output when None
}

The most common attributes, container-level (on the type) and field-level (on a field):

Attribute Level Effect
rename_all = "camelCase" Container Convert every field name to a naming style (camelCase, kebab-case, PascalCase, …)
deny_unknown_fields Container Error if the input contains a field the struct does not declare
rename = "name" Field Map this one field to a different external name
default Field Use the type’s Default value when the field is absent in the input
default = "path::to::fn" Field Call a function to produce the default
skip Field Never serialize or deserialize this field (must be Default-able)
skip_serializing_if = "Option::is_none" Field Omit the field from output when the predicate is true
flatten Field Inline a nested struct’s fields into the parent (handy for shared/extra fields)
with = "module" Field Use custom serialize/deserialize logic (e.g. a date format)

#[serde(default)] deserves a callout for anyone coming from C: it is how serde models optional input without making the field itself Option<T>. A field marked default may be absent from the JSON; serde fills it with Default::default() rather than erroring. Combine this with Option<T> only when “absent” and “present but null” need to be distinguished.

Nested and Collection Types

serde composes. Any type whose components all implement the traits gets them too, so structs of structs, Vec<T>, HashMap<K, V>, and Option<T> all work with no extra effort. Enums serialize as a tagged object by default.

use serde::{Serialize, Deserialize};
use std::collections::HashMap;

#[derive(Serialize, Deserialize, Debug)]
struct Server {
    name: String,
    endpoints: Vec<Endpoint>,
    metadata: HashMap<String, String>,
}

#[derive(Serialize, Deserialize, Debug)]
struct Endpoint {
    path: String,
    method: Method,
}

#[derive(Serialize, Deserialize, Debug)]
#[serde(rename_all = "UPPERCASE")]
enum Method {
    Get,
    Post,
    Delete,
}
{
  "name": "api",
  "endpoints": [
    { "path": "/users", "method": "GET" },
    { "path": "/users", "method": "POST" }
  ],
  "metadata": { "region": "us-east-1" }
}

When You Don’t Have a Struct

serde_json::Value

Sometimes the shape is unknown or genuinely dynamic, an arbitrary JSON blob you want to inspect at runtime. For that, serde_json::Value is an enum that can hold any JSON value, and the json! macro builds one inline.

use serde_json::{json, Value};

let data: Value = serde_json::from_str(r#"{ "name": "ada", "age": 36 }"#)?;

// Index into it like a tree; missing keys yield Value::Null
let name = data["name"].as_str().unwrap_or("unknown");
let age  = data["age"].as_u64().unwrap_or(0);

// Build a Value directly
let payload = json!({
    "status": "ok",
    "items": [1, 2, 3],
});

This is the escape hatch. Prefer a typed struct whenever the schema is known: you get validation, autocompletion, and compile-time guarantees that Value cannot offer. Reach for Value only when the data truly has no fixed shape.

A Practical Pattern

Loading a Config File

Tying it back to something you do already, here is the idiom for reading a typed config from a TOML file. It is the natural companion to a clap --config <FILE> flag.

use serde::Deserialize;
use std::fs;

#[derive(Deserialize, Debug)]
#[serde(deny_unknown_fields)]       // typo in the config -> loud error, not silent ignore
struct AppConfig {
    host: String,
    #[serde(default = "default_port")]
    port: u16,
    log_level: String,
}

fn default_port() -> u16 {
    8080
}

fn load_config(path: &str) -> Result<AppConfig, Box<dyn std::error::Error>> {
    let text = fs::read_to_string(path)?;
    let config: AppConfig = toml::from_str(&text)?;
    Ok(config)
}

deny_unknown_fields turns a misspelled key in the config file into an immediate, descriptive error instead of a silently-ignored setting, which is exactly the failure mode you want surfaced early.
