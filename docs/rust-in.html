Rust: Introduction

A practical bridge to Rust’s fundamentals

Published

June 18, 2026

Why Rust Exists

Rust was created at Mozilla Research around 2010 and reached 1.0 in 2015. The motivation was straightforward and familiar to anyone who has debugged a segfault at 2am: systems programming is unsafe by default, and the traditional tools (C, C++) leave memory safety entirely to the programmer.

The designers asked a pointed question: can we have the performance of C with memory safety guaranteed at compile time, without a garbage collector?

The answer is Rust.

The Core Design Decisions

1. Ownership replaces manual memory management

Rather than malloc/free or smart pointers bolted on after the fact, Rust builds ownership into the type system. The compiler tracks who owns what, and memory is freed automatically when the owner goes out of scope. No GC, no runtime overhead.

2. Borrowing replaces raw pointers

Instead of passing pointers around freely, Rust has a formal concept of borrowing — you can lend a reference to data without transferring ownership. The compiler (the borrow checker) enforces that references are always valid. No dangling pointers, no use-after-free.

3. Fearless concurrency

Data races are a compile error. The same ownership rules that prevent memory bugs also make entire classes of concurrency bugs impossible.

4. Zero-cost abstractions

Rust’s high-level features (iterators, generics, traits) compile down to the same machine code you’d write by hand. You don’t pay for what you don’t use — the same guarantee C++ makes, but delivered more consistently.

5. Explicit over implicit

Rust rarely does things behind your back. Integer overflow is checked in debug builds and wraps in release (with explicit opt-in). Type coercions are almost never automatic. Mutability must be declared. This is intentionally more verbose than C++ in places, in exchange for fewer surprises.

Five Questions Answered

When the Tangerine and Passion Fruit Kombucha Genie popped out of my bottle, he said to me: “Five Questions from ye, I shall answer truthfully. But on Rust, from ye, they must be.”

1. Does Rust support Inheritance? If not, then why?

No. Rust deliberately omits implementation inheritance, and the omission is a design choice, not an oversight.

Inheritance bundles two distinct things: code reuse (sharing implementation) and subtype polymorphism (treating a derived type as its base). Object-oriented languages couple them; you inherit the implementation to get the polymorphism. Decades of experience showed that this coupling causes problems: fragile base class syndrome, deep hierarchies that are hard to reason about, and the pressure to contort a design to fit a tree when the real relationships form a graph.

Rust separates the two concerns cleanly. For code reuse, you use traits with default methods — a trait can provide a default implementation of any method, and any type that implements the trait gets that implementation for free (or overrides it). For subtype polymorphism, you use trait objects (dyn Trait), which let you write code that works over any type implementing a given trait. You can also compose behavior by having one struct hold another as a field and delegating to it, which is explicit and therefore more honest about what is actually happening.

The payoff is that Rust’s type system is simpler to reason about. There is no implicit behavior coming from somewhere up the hierarchy, and the borrow checker doesn’t have to contend with inherited mutable state. If you miss inheritance, you usually find that a trait with default methods plus composition covers the real need without the baggage.

2. Is Rust as efficient and fast as C?

Yes, with one honest qualification.

On the machine-code level, Rust and C compile to essentially identical output. Both use LLVM (Clang also uses LLVM), both have no runtime or garbage collector, and Rust’s abstractions — iterators, generics, closures — are zero-cost: they disappear at compile time. Benchmarks between idiomatic Rust and idiomatic C are routinely within a percent or two of each other, and Rust sometimes wins because the compiler can apply optimizations that would be illegal in C due to aliasing rules (restrict in C is opt-in; Rust’s ownership model gives the compiler that guarantee automatically).

The qualification: Rust has bounds-checked array indexing in debug builds. In optimized builds, those checks are often eliminated when the compiler can prove an access is in range, and idiomatic safe Rust often uses iterators or slice methods that compile down without per-access bounds checks. In tight inner loops over arrays this can still matter in some cases, and C has no such checks by default. If you truly need manual unchecked indexing, Rust gives you the escape hatch via unsafe, but you have to ask for it deliberately. In practice, for most systems code, the difference does not appear outside of microbenchmarks.

3. Is it possible for a Rust app to experience a segfault?

Yes, but it requires deliberate effort.

In safe Rust, a segfault is essentially impossible by construction. The borrow checker prevents dangling pointers, use-after-free, and out-of-bounds memory access at compile time. What you get instead of a segfault is a compile error. The few things that could cause memory problems at runtime (like out-of-bounds slice indexing) are caught and turned into a controlled panic rather than undefined behavior.

However, Rust has unsafe blocks, and unsafe suspends those guarantees. Code inside an unsafe block can dereference raw pointers, call C functions via FFI, and do other things the compiler cannot verify. Any of those can produce a segfault if you get them wrong. The critical design point is that unsafe is explicit and lexically scoped, so when something does go wrong you know exactly where to look: somewhere inside an unsafe block, not anywhere in the program.

So: pure safe Rust, no segfaults. Unsafe Rust, yes — but you opted in, and the surface area is small and visible.

4. What makes Rust good for systems development?

Systems code has two requirements that historically have been in tension: it must be fast and it must be correct. C and C++ solved the first problem and left the second largely to the programmer. Garbage-collected languages solved much of the second problem and compromised on the first. Rust’s central achievement is that it solves both at the same time, and it does it through the type system rather than through a runtime.

More concretely, the properties that matter for systems work:

  • No garbage collector. Rust is suitable for real-time systems, embedded targets, kernels, and anywhere else where GC pauses are unacceptable. Memory is freed deterministically when owners go out of scope.
  • Predictable performance. Zero-cost abstractions mean you can write high-level code without paying a runtime penalty. The performance model is transparent in the same way C’s is.
  • Memory safety without overhead. The borrow checker eliminates entire classes of bugs (use-after-free, buffer overflow, data races) at compile time. These are the bugs that dominate CVE lists for systems software.
  • Fearless concurrency. The ownership rules make data races a compile error. Writing multithreaded systems code in Rust is substantially less dangerous than in C.
  • unsafe as a controlled escape hatch. When you genuinely need to do something the type system cannot verify (MMIO, inline assembly, platform intrinsics), you can. The unsafe boundary is explicit, auditable, and doesn’t corrupt the surrounding safe code.
  • First-class C interoperability. Rust can call C functions and expose a C ABI, which means it can be dropped into existing systems incrementally rather than requiring a full rewrite.

The result is a language that can do everything C can do, on the same hardware, with the same performance characteristics, while ruling out at compile time the bugs that make systems code notoriously hard to ship safely.

5. Could you please compare Rust to Go, listing the pros and cons of each?

Rust and Go are both modern systems-adjacent languages that improve on C in terms of tooling and safety, but they aim at different targets and make very different tradeoffs.

Rust Go
Memory model Ownership; no GC Garbage collected
Performance C-level; fully predictable Very fast; occasional GC pauses
Concurrency Ownership enforces data-race freedom at compile time CSP-style goroutines; runtime scheduler
Compilation Slower (borrow checking, monomorphization) Extremely fast
Learning curve Steep; borrow checker requires a new mental model Shallow; designed to be learnable in a day
Abstraction cost Zero-cost (generics, iterators compile away) Small runtime overhead (interfaces use dynamic dispatch)
Error handling Result<T, E>; explicit, composable Multiple return values; convention-based
Target use cases Systems programming, embedded, WebAssembly, security-critical code Network services, DevOps tooling, CLIs, cloud infrastructure

Rust pros: maximum performance, no GC, memory and thread safety by construction, rich type system (enums, traits, generics), excellent for safety-critical or resource-constrained environments.

Rust cons: steep learning curve, slower compile times, more boilerplate for simple tasks, the borrow checker fights you until the mental model clicks.

Go pros: fast to learn, extremely fast to compile, simple and readable, goroutines make concurrency approachable, excellent standard library for network and I/O work, easy to deploy (single static binary).

Go cons: garbage collector rules out hard real-time and most embedded targets, GC pauses are real (though small in modern Go), generics arrived late and are still maturing, less expressive type system, no way to enforce data-race freedom at compile time.

The practical heuristic: if you are writing a web service, a CLI tool, or infrastructure software where developer velocity matters more than squeezing every nanosecond, Go is faster to ship. If you are writing a database engine, an OS component, a codec, an embedded runtime, or anything where performance predictability or memory safety guarantees are non-negotiable, Rust is the better tool.

Crates

Before we define what a crate is, it’s important to understand what a fundamental unit of compilation is in Rust.

A compilation unit isn’t the smallest unit the compiler considers when compiling source. That is a syntactic unit. Rather it is the most granular unit the compiler creates when compiling code. For example, in C, a compilation unit is the object file (.o or .obj). But Rust is different.

The Rust compiler (rustc) does not compile individual files. Instead, it takes a single root file (like main.rs or lib.rs), automatically finds all the other files connected to it, and compiles that entire tree of files together in one single pass. And its output is either an executable (it has a main() function) or a library (it doesn’t have a main() function)

A crate is the fundamental unit of compilation, meaning it is the smallest unit of code that Rust will compile. The Rust compiler takes a crate and produces either an executable or a library. Think of it as the equivalent of a compiled C library (.a, .so) or a Python package on PyPI — the distributable unit that other projects depend on.

Two kinds of crates:

  • Binary crate — has a main() entry point, produces an executable. Root file is src/main.rs.
  • Library crate — no main(), produces a library for other code to use. Root file is src/lib.rs.

Packages

A package is what Cargo manages: a directory with a Cargo.toml manifest. A package contains at least one crate. Most projects you will work on are a single package with a single binary crate:

my_project/
├── Cargo.toml      # manifest: name, version, dependencies
├── Cargo.lock      # exact resolved dependency versions (commit this to git)
└── src/
    └── main.rs     # root of the binary crate

A library package has the same structure, but the crate root is src/lib.rs instead of src/main.rs. A package can contain both a main.rs and a lib.rs, producing a binary and a library from the same source tree.

Notelib.rs vs mod.rs?

They are the same in that they are both “roots” that define how code is organized, but they differ in scope:

  • lib.rs (Crate Root): The entry point for the entire library. It defines the top-level API exposed to external users and integration tests.
  • mod.rs (Module Root): The entry point for a sub-module located in a directory. It tells Rust that a folder (like src/commands/) is a module and manages the visibility of the files within that folder.

In modern Rust (since 2018), mod.rs is often replaced by a file with the same name as the folder (e.g., src/commands.rs instead of src/commands/mod.rs) to keep the file tree flatter, but their purpose remains identical.

Modules

A module is a namespace within a crate — the closest equivalent to a Python module. Modules organize code into logical units and control what is visible outside (pub) versus private. Items are private by default — you opt into visibility explicitly. Before we dive deep on our own, we are to share The Rust Programming Language’s “Modules Cheat Sheet”. It was just what I was looking for when learning about modules; so, here it is word for word:

Before we get to the details of modules and paths, here we provide a quick reference on how modules, paths, the use keyword, and the pub keyword work in the compiler, and how most developers organize their code. We’ll be going through examples of each of these rules throughout this chapter, but this is a great place to refer to as a reminder of how modules work.

Start from the crate root: When compiling a crate, the compiler first looks in the crate root file (usually src/lib.rs for a library crate or src/main.rs for a binary crate) for code to compile.

Declaring modules: In the crate root file, you can declare new modules; say you declare a “garden” module with mod garden;. The compiler will look for the module’s code in these places:

  • Inline, within curly brackets that replace the semicolon following mod garden
  • In the file src/garden.rs
  • In the file src/garden/mod.rs

Declaring submodules: In any file other than the crate root, you can declare submodules. For example, you might declare mod vegetables; in src/garden.rs. The compiler will look for the submodule’s code within the directory named for the parent module in these places:

  • Inline, directly following mod vegetables, within curly brackets instead of the semicolon
  • In the file src/garden/vegetables.rs
  • In the file src/garden/vegetables/mod.rs

Paths to code in modules: Once a module is part of your crate, you can refer to code in that module from anywhere else in that same crate, as long as the privacy rules allow, using the path to the code. For example, an Asparagus type in the garden vegetables module would be found at crate::garden::vegetables::Asparagus.

Private vs. public: Code within a module is private from its parent modules by default. To make a module public, declare it with pub mod instead of mod. To make items within a public module public as well, use pub before their declarations.

The use keyword Within a scope, the use keyword creates shortcuts to items to reduce repetition of long paths. In any scope that can refer to crate::garden:: vegetables::Asparagus, you can create a shortcut with use crate::garden:: vegetables::Asparagus; and from then on you only need to write Asparagus to make use of that type in the scope.

Here, we create a binary crate named backyard that illustrates these rules. The crate’s directory, also named backyard, contains these files and directories:

backyard
├── Cargo.lock
├── Cargo.toml
└── src
   ├── garden
   │ └── vegetables.rs
   ├── garden.rs
   └── main.rs

The crate root file in this case is src/main.rs, and it contains:

use crate::garden::vegetables::Asparagus;
pub mod garden;

fn main() {
    let plant = Asparagus {};
    println!("I'm growing {:?}!", plant);
}

The pub mod garden; line tells the compiler to include the code it finds in src/garden.rs, which is:

pub mod vegetables;

Here, pub mod vegetables means the code in src/garden/vegetables.rs is included too. That code is:

 #[derive(Debug)]
pub struct Asparagus {}

Now let’s get into the details of these rules and demonstrate them in action!

1. Inline

You can declare a module inline:

mod math {
    pub fn add(a: i32, b: i32) -> i32 { a + b }

    fn internal_helper() { }   // private: not accessible outside this module
}

// call it
math::add(1, 2);
2. File Based

Rust looks for src/math.rs

For larger code, modules live in their own files. Writing mod math; in main.rs tells Rust to look for the module’s code in src/math.rs:

src/
├── main.rs     ← contains: mod math;
└── math.rs     ← the math module
3. Directory Based

Rust looks for src/math/mod.rs

A module that has its own submodules gets a directory instead:

src/
├── main.rs
└── math/
    ├── mod.rs      # the math module root
    └── geometry.rs # submodule, accessed as math::geometry
WarningRauchen ist verboten

For cases 2 and 3, Rust decides which to use based on which file exists. You cannot have both src/math.rs and src/math/mod.rs.

Visibility

Four levels, from narrowest to widest:

Keyword Visible to
(none) Only code within the same module
pub(super) The parent module only
pub(crate) Anywhere within this crate, but not external users
pub Everyone — including external users of the crate 
// src/geometry/shapes.rs
pub struct Circle {
    pub radius: f64,        // visible to all
    center: Point,          // private — only code in this module can touch it
}

pub fn area(c: &Circle) -> f64 {
    std::f64::consts::PI * c.radius * c.radius
}

pub(crate) fn internal_check() { }  // crate-internal only

Submodules

A module can contain other modules. You declare them in the parent’s mod.rs the same way you declare top-level modules in main.rs:

// src/geometry/mod.rs
pub mod shapes;      // public submodule — accessible as geometry::shapes
pub mod transforms;  // public submodule — accessible as geometry::transforms
mod utils;           // private submodule — internal to geometry, invisible outside

You reference them with :::

use geometry::shapes::Circle;
use geometry::transforms::rotate;

Or fully qualified without use:

let c = geometry::shapes::Circle { radius: 5.0 };
This Hole is Deep

The nesting is arbitrarily deep. The directory layout mirrors the module tree at each level:

src/
├── main.rs
└── geometry/
    ├── mod.rs              # pub mod shapes; pub mod transforms;
    ├── shapes/
    │   ├── mod.rs          # pub mod circle; pub mod rectangle;
    │   ├── circle.rs       # geometry::shapes::circle
    │   └── rectangle.rs    # geometry::shapes::rectangle
    └── transforms.rs       # geometry::transforms

Each level follows the same rule: a mod.rs declares what is inside it, and child files or directories implement those submodules.

Spreading a Module’s API Across Files

The internal file structure does not have to match the public API. pub use re-exports items from submodules into the parent’s namespace, so callers see a flat surface regardless of how the code is organized internally:

// src/geometry/mod.rs
mod shapes;      // private — callers cannot reach geometry::shapes directly
mod transforms;  // private

// re-export selected items into geometry:: directly
pub use shapes::Circle;
pub use shapes::Rectangle;
pub use transforms::rotate;

Now from the outside:

use geometry::Circle;   // works — even though Circle lives in shapes.rs
use geometry::rotate;   // works — even though rotate lives in transforms.rs

The internal structure is hidden. The public surface of geometry looks like one flat module. This is how most published Rust libraries are organized: files and submodules for the authors’ benefit, pub use for a clean external interface.

mod.rs itself can also define things directly in the module’s namespace alongside its declarations:

// src/geometry/mod.rs
pub mod shapes;

// these live in geometry:: directly, not in any submodule
pub struct Point { pub x: f64, pub y: f64 }
pub fn origin() -> Point { Point { x: 0.0, y: 0.0 } }

Bringing Items Into Scope

use is your friend. Love him.

use is an extremely useful and flexible keyword that was described to me to an “alias injector”. The Rust Reference has the following to say about use:

A use declaration creates one or more local name bindings synonymous with some other path. Usually a use declaration is used to shorten the path required to refer to a module item. These declarations may appear in modules and blocks, usually at the top. A use declaration is also sometimes called an import, or, if it is public, a re-export.

It’s as if you are defining a root to which relative paths will resolve. Meanwhile the use of absolute paths are always an option. For example:

use geometry::shapes::Circle;

Circle::new(...);

Rust would be completely fine with the following:

geometry::shapes::Circle::new(...);

The thing I find the most cool about use is it’s flexibility. You may specify any portion of a full path and Rust will do the rest. use is essentially an alias injector: it binds a name at the current scope, and you can stop the path at any depth you like. Assuming that A:B:C:something exists, the following are all valid:

use A::B::C::something;

something();
use A::B;

C::something();
use A;

B::C::something();

I just went my pants. Very exciting indeed. And the architects did something that speaks on behalf of their thoroughness. It’s easier to demonstrate than it is to describe with words and hand puppets (🕺). Let’s assume that we have a module with the following hierarchy:

crate
└── network
    └── http
        ├── (functions/types defined directly in http)
        └── client  (a submodule)
Without self:
use network::http::client;

client::connect(...);       // ✅
http::get(...);             // ❌
network::http::get(...);    // ✅

You have: client, but you don’t have: http. You must write network::http:: to reach anything in it.

With self:
use network::http::{self, client};

client::connect(...};       // ✅
http::get(...);             // ✅

You have: http because self bound http itself. The self inside the braces refers to the module named at the end of the path before the ::{...}. So network::http::{self, client} is exactly equivalent to writing two separate use statements:

use network::http;
use network::http::client;
Superpowers and Conveniences

Finally, follows are some of the superpowers and conveniences built into use:

  • You can rename with as:

    use A::B::C::something as do_the_thing;
do_the_thing()

  • You can pull in multiple items from the same path with braces:

    use A::B::C::{something, another_thing};

  • You can combine both of the above:

    use A::B::C::{something, another_thing as other};

  • You can use self inside braces to bring in the module itself alongside its children:

    use A::B::{self, C};  // binds both B and B::C

  • You can glob-import everything public from a path:

    use A::B::C::*;  // everything public in C lands in the current scope

  • Simultaneously binding a list of paths with a common prefix, using the brace syntax:

    use a::b::{c, d, e::f, g::h::i};

  • Rebinding the target name as a new local name, using the syntax

    use p::q::r as x;

    This can also be used with the last two features:

    use a::b::{self as ab, c as abc}

See Use declarations in The Rust Reference for more information.

External Dependencies

Dependencies from crates.io (Rust’s public registry, the equivalent of PyPI) go in Cargo.toml:

[dependencies]
serde = { version = "1.0", features = ["derive"] }
regex = "1.10"

Run cargo add regex from the command line and Cargo writes the entry for you. Then use it in code:

use regex::Regex;

This is the pip install + import of Rust, collapsed into one tool that also handles building, testing, and formatting.

Operator Overloading

Many operators can be overloaded by implementing traits from std::ops. For example:

use std::ops::Add;

struct Point { x: i32, y: i32 }

impl Add for Point {
    type Output = Point;

    fn add(self, other: Point) -> Point {
        Point {
            x: self.x + other.x,
            y: self.y + other.y,
        }
    }
}

let p1 = Point { x: 1, y: 2 };
let p2 = Point { x: 3, y: 4 };
let p3 = p1 + p2;  // uses our Add implementation

In the following table we include some of A listers and indicate the operator, the trait (in std::ops) and the method signature. For a complete list, see std::ops.

Operator Trait Method
+ Add add(self, rhs: Rhs) -> Self
- Sub sub(self, rhs: Rhs) -> Self
* Mul mul(self, rhs: Rhs) -> Self
/ Div div(self, rhs: Rhs) -> Self
% Rem rem(self, rhs: Rhs) -> Self
==, != PartialEq eq(&self, other: &Rhs) -> bool, ne(&self, other: &Rhs) -> bool
<, >, <=, >= PartialOrd partial_cmp(&self, rhs: &Rhs) -> Option<Ordering>
[] Index index(&self, index: Idx) -> &Self::Output
[] (mut) IndexMut index_mut(&mut self, index: Idx) -> &mut Self::Output
NoteWhy are some by Reference and others by Value?

The reason comes down to Copy semantics. For PartialEq, the signature is:

fn eq(&self, other: &Self) -> bool;

Both sides take references because equality is a read-only inspection — you just need to look at both values, and you’re done. Neither side is consumed. Taking references here is the obvious choice regardless of whether the type is Copy or not.

For Add, the signature is:

fn add(self, rhs: Self) -> Self::Output;

The operands are taken by value because addition is modeled as consumption and transformation — you take the inputs and produce a new output. For types where this makes sense (like integers), the values are Copy, so “moving” them is a no-op anyway. The compiler just copies the bits and you never notice.

The reason Rust doesn’t default to references for Add is that it would be unnecessarily restrictive for non-Copy types. Consider a hypothetical big integer or a matrix type — you might genuinely want to consume both operands and reuse their memory in constructing the result, avoiding an extra allocation. If the trait required &Self, you’d lose that option.

So the general principle is:

  • If the operation is inspection (equality, ordering, hashing) → references make sense, nothing is consumed
  • If the operation is transformation (arithmetic) → by value, because the inputs are conceptually spent producing the output

Copy is opt-in, and non-Copy is the default. To make a type Copy, you have to explicitly opt in:

#[derive(Copy, Clone)]
struct Point {
    x: f32,
    y: f32,
}

Any type that doesn’t explicitly derive or implement Copy is automatically move semantics. So you get non-Copy behavior for free just by not doing anything.

And there are rules about when you’re even allowed to do that — the compiler will reject it if your type contains any non-Copy fields (like a String or a Vec). The idea being that Copy is a promise that “bitwise copying this value is always safe and correct,” and the compiler enforces that the whole type tree is consistent with that promise.

See Appendix B: Operators in The Rust Programming Language for the complete reference.

Variables

and Mutability

In C you declare a variable and it’s mutable by default. In Rust, variables are immutable by default. You opt into mutability with mut.

let x = 5;          // immutable
let mut y = 5;      // mutable
y += 1;             // fine
// x += 1;          // compile error

This isn’t just style — the compiler uses immutability information to reason about your program. It’s a habit worth building early.

Types

A scalar type represents a single value.

Scalar Types

Rust is statically typed. Types are usually inferred, but you can annotate explicitly. Rust has four primary scalar types: integers, floating-point numbers, Booleans, and characters:

let a: i32  = -42;       // signed 32-bit integer
let b: u64  = 1_000_000; // unsigned 64-bit (underscores ok in literals)
let c: f64  = 3.14;      // 64-bit float
let d: bool = true;
let e: char = 'z';       // Unicode scalar, 4 bytes (not u8!)

Integer types: i8, i16, i32, i64, i128, isize and their u counterparts. isize/usize are pointer-sized, like ptrdiff_t/size_t in C.

No implicit numeric conversions. You cast explicitly with as:

let x: i32 = 42;
let y: f64 = x as f64;

Tuples

A tuple groups a fixed number of values of different types into a single compound value. Unlike arrays, the elements do not have to share a type.

let point: (f64, f64) = (1.0, 2.5);
let record: (i32, &str, bool) = (42, "alice", true);

Accessing elements uses dot notation with a zero-based index. The index must be a literal — you cannot index a tuple with a variable.

let t = (10, "hello", 3.14);

let n = t.0;    // 10   — i32
let s = t.1;    // "hello" — &str
let f = t.2;    // 3.14 — f64

Destructuring is the idiomatic way to unpack a tuple, especially when returning multiple values from a function:

fn min_max(v: &[i32]) -> (i32, i32) {
    let mut lo = v[0];
    let mut hi = v[0];
    for &x in v {
        if x < lo { lo = x; }
        if x > hi { hi = x; }
    }
    (lo, hi)
}

let (low, high) = min_max(&[3, 1, 4, 1, 5, 9]);
println!("{} {}", low, high);   // 1 9

Use _ to ignore fields you don’t need:

let (_, second, _) = (1, 2, 3);

The unit type () is the zero-element tuple. It is Rust’s equivalent of void — the implicit return type of functions that return nothing, and the success payload in Result<(), E> when a function either succeeds with no data or fails.

fn greet(name: &str) -> () {    // () is implicit, rarely written explicitly
    println!("Hello, {}!", name);
}

Tuples are stack-allocated and implement Copy when all their elements do. They are most useful for returning multiple values from a function and for temporary groupings where defining a named struct would be overkill. For anything you’ll pass around extensively, prefer a named struct — it documents intent and the fields have names.

Fixed-Length Arrays

Arrays in Rust are fixed-size collections of elements of the same type, allocated on the stack. The syntax is [T; N] where T is the element type and N is the length, which must be known at compile time.

// Array of 5 integers
let arr: [i32; 5] = [1, 2, 3, 4, 5];

// Initialize all elements to the same value
let zeros = [0; 100];        // 100 zeros
let buffer = [0u8; 1024];    // 1024-byte buffer

// Access elements (zero-indexed, bounds-checked at runtime)
let first = arr[0];          // 1
let last = arr[4];           // 5

// Length is part of the type
println!("Length: {}", arr.len());  // 5
Key characteristics
  • Stack-allocated — arrays live on the stack, not the heap
  • Fixed size — length cannot change after creation
  • Type includes length — [i32; 3] and [i32; 5] are different, incompatible types
  • Bounds-checked — indexing out of bounds causes a runtime panic

Arrays are useful when you know the exact size at compile time (RGB colors, matrix dimensions, fixed buffers). For dynamic sizing, use Vec<T> instead (covered later).

// Iterating over arrays
let colors = [[255, 0, 0], [0, 255, 0], [0, 0, 255]];

for color in &colors {
    println!("RGB: {:?}", color);
}

// Arrays can be passed to functions by reference
fn sum(arr: &[i32; 5]) -> i32 {
    arr.iter().sum()
}

String Types

String and &str

Rust has two string types. The distinction maps directly onto owned vs. borrowed:

Type Owned? Mutable? Lives on Analogy
String Yes Yes Heap std::string in C++
&str No No Anywhere std::string_view in C++
Representation

Fat pointer: also known as a wide pointer, is a data structure that stores a memory address along with additional metadata. For example, an &str is a fat pointer that stores a pointer into a UTF-8 buffer and a length.

Skinny pointer: actually known as a thin pointer, is a plain old pointer: a single memory address.

Some common uses of fat pointers are:

  • Slices (Dynamic Arrays): a fat pointer for a slice stores the base memory address of the first element plus the length of the slice. This allows for safe bounds checking at runtime.
  • Trait Objects / Interfaces: in languages like Rust or Go, when you use dynamic dispatch, the fat pointer contains the data address and a vtable pointer (virtual method table). The vtable tells the program which specific methods to call for that object.
  • Memory Safety: Some research implementations use fat pointers to store bounds (base and end address) to prevent buffer overflows or keys/locks for temporal memory safety.

String stores three things: a pointer to heap memory, a length (bytes used), and a capacity (bytes allocated). It is not null-terminated. The length field is what tells Rust where the string ends.

&str is a fat pointer: a pointer into some UTF-8 buffer plus a length. It borrows that buffer — it owns nothing and cannot outlive the data it points into.

Both types are guaranteed to contain valid UTF-8. Rust will not let you construct an invalid string.

Creating a String
let a = String::from("hello");       // from a literal
let b = "hello".to_string();         // same, alternate spelling
let c = format!("{} {}", a, b);      // build from parts — like sprintf
let d = String::new();               // empty, build up with push/push_str
let mut e = String::new();
e.push('!');                         // append a char
e.push_str(" world");                // append a &str
String literals are &str
let s: &str = "hello";               // stored in the binary, 'static lifetime
let t: &str = &a[0..3];             // slice of an existing String

When to use which

Use &str for function parameters whenever you only need to read the text. It accepts both String and literals without any conversion:

fn greet(name: &str) {
    println!("Hello, {}!", name);
}

greet("world");                      // literal — works
greet(&String::from("Alice"));       // String — works, coerces automatically

Use String when you need to own or mutate the text.

Values

Data Types

Every value in Rust is of a certain data type, which tells Rust what kind of data is being specified so that it knows how to work with that data. We already went over the various scalars. Later we shall see some data structures. Here we are going to have a look at type wrapping (I don’t know what it’s really called) and Rust’s equivalent of void.

Option<T>

The “Null Problem”

Sometimes you have a value that might be missing. In C, you would use a pointer and set it to NULL when there is no value. In Java, you would just set the variable to null. In Rust, there is no such thing as null. Instead, Rust has a built-in type called Option<T> that explicitly represents the possibility of absence.

NoteWhy No Null?

Because null references are a billion-dollar mistake. They lead to runtime errors when you try to access something that isn’t there. By making the possibility of “no value” explicit in the type system, Rust forces you to handle it safely at compile time, eliminating an entire class of bugs.

Let’s meet our little buddy:

enum Option<T> {
    Some(T), // The value is present
    None,    // The "null" equivalent
}

We will learn more about Option<T> and how to use it in the chapter on Enums. For now, know that Option<T> is how Rust represents a value that can either be something (Some) or nothing (None).

Why this is better?
  1. The Compiler Forces You to Handle It: If you have an Option<String>, you cannot call methods like .len() on it directly. You must use a match statement or an if let to “unwrap” the value first.
  2. Type Safety: You can never accidentally treat a “null” value as a real one. If a variable is just a String, it is guaranteed to be a valid string. If it’s an Option<String>, you know it might be empty.
  3. Efficiency: Rust uses a “null-pointer optimization.” For types like references or Box, an Option<T> takes up the same amount of memory as a regular T. The None case is represented by a literal null pointer under the hood, but the language makes it impossible for you to interact with that pointer unsafely.

Unit Type

In Rust, () is called the unit type (and also the unit value). It is essentially Rust’s version of void from languages like C, C++, or Java, but with a key difference: it is an actual value that occupies zero bytes of memory. You will frequently see it used in Ok(...) statements: Ok(()). Looks a little weird doesn’t it? It looks like we are calling a function without specifying the function name. Here is the breakdown of Ok(()):

  1. The inner (): This is the “unit value.” It represents “nothing” or “empty success.”
  2. The outer Ok(...): This is the success variant of the Result enum.

Why do we use it? Most of our command functions (like execute) return a Result<(), Box<dyn Error>>. Since the Result type must contain something in the Ok case, we use () to say: “The operation finished successfully, but there isn’t a specific piece of data (like an integer or a string) to return to the caller.” Gemini told me to think of it like this:

  • Ok(42) -> “I succeeded, and here is the answer: 42.”
  • Ok(()) -> “I succeeded. That’s all you need to know.”

In short, () is Rust’s way to say “no meaningful value,” whether as a function’s return type or as the success payload in types like Result<(), E>.

Slices

A view into a sequence, without copying

A slice is a reference to a contiguous subsequence of an array or string. It is a fat pointer: two (machine) words wide, carrying both a pointer to the first element and a length. No heap allocation, no copy. Follows is a table of slice syntax and what it means:

Syntax Meaning
[..] Entire sequence
[a..b] From index a up to (not including) b
[a..=b] From index a through b (inclusive)
[a..] From index a to the end
[..b] From the start up to (not including) b 
let a = [10, 20, 30, 40, 50];

let all   = &a[..];      // [10, 20, 30, 40, 50] — the whole array
let first = &a[..3];     // [10, 20, 30]           — open on the right
let last  = &a[2..];     // [30, 40, 50]           — open on the left
let mid   = &a[1..4];    // [20, 30, 40]           — half-open (end excluded)
let incl  = &a[1..=3];   // [20, 30, 40]           — inclusive end with ..=

No negative indices

Unlike Python, Rust slices do not accept negative indices. To index relative to the end, use len():

let a = [10, 20, 30, 40, 50];

let last_one = &a[a.len() - 1..];   // [50]       — Python's [-1:]
let last_two = &a[a.len() - 2..];   // [40, 50]   — Python's [-2:]
let all_but_last = &a[..a.len()-1]; // [10,20,30,40] — Python's [:-1]

Type Meaning
&[T] Shared slice of any array or Vec<T>
&str String slice (a view into UTF-8 text)

These are the idiomatic types for function parameters that only need to read a sequence. A function accepting &[i32] works with arrays, Vec<i32>, and slices of either. A function accepting &str works with String, string literals, and string slices.

Conversions

Look at the target type, not the source

Rust’s conversions are deliberate and explicit. The key mental shift from languages like Python: think about what type you want to end up with, then find the method or trait that produces it.

Numeric casts with as

as performs primitive numeric casts. It is explicit and never implicit:

let i: i32 = 42;
let f: f64 = i as f64;
let b: u8  = 255i32 as u8;    // truncates if out of range — be careful

From and Into

In the following you will see syntax that looks a little like inheritance in other languages: A: From<B>. But we know it’s not inheritance, `cuz Rust doesn’t support inheritance. It is called a trait bound. It means “A implements the From trait for B.” In other words, you can convert from B to A using the From trait’s method. The following example is in The Rust Reference (there is a wicked looking syntax diagram on that page):

trait Shape {
    fn draw(&self, surface: Surface);
    fn name() -> &'static str;
}

fn draw_twice<T: Shape>(surface: Surface, sh: T) {
    sh.draw(surface);           // Can call method because T: Shape
    sh.draw(surface);
}

fn copy_and_draw_twice<T: Copy>(surface: Surface, sh: T) where T: Shape {
    let shape_copy = sh;        // doesn't move sh because T: Copy
    draw_twice(surface, sh);    // Can use generic function because T: Shape
}

struct Figure<S: Shape>(S, S);

fn name_figure<U: Shape>(
    figure: Figure<U>,          // Type Figure<U> is well-formed because U: Shape
) {
    println!(
        "Figure of two {}",
        U::name(),              // Can use associated function
    );
}

We will learn more about traits in the Structs, Enums and Traits section. And we will learn more about trait bounds in the Generics and Trait Bounds section.

For non-primitive conversions, Rust uses the From and Into traits. If A: From<B>, then you can write A::from(b) or, equivalently, b.into() (the compiler figures out the target from context):

let s: String = String::from("hello");   // &str → String via From
let s: String = "hello".into();          // same, using Into
let n: i64    = i64::from(42i32);        // i32 → i64

From/Into conversions are infallible by definition. If the conversion can fail, use TryFrom/TryInto instead, which return Result.

Parsing strings with .parse()

.parse() converts a &str to any type that implements FromStr. The target type is inferred from context:

let n: i32  = "42".parse().unwrap();
let f: f64  = "3.14".parse().unwrap();
let b: bool = "true".parse().unwrap();

Because .parse() returns Result, you handle failure explicitly. In real code use ? or match rather than .unwrap().

String and &str

From To How
&str String String::from(s) or s.to_string() or s.into()

String &str &s[..] — explicit slice

The String → &str direction is free: it is just taking a reference to the existing buffer.

ImportantWonder-Twin Power Activate in the form of Turbofish

The following example is taken out of our exs24 parser:

let seconds: f32 = seconds_text
    .parse::<f32>()
    .map_err(|error| format!("Invalid seconds value '{}': {}", seconds_text, error))?;

Notice the ::<f32> attached to parse. That fella is called a turbofish. In the example above, I found that I could remove it and it would still compile. So I asked Claude, and this is what he said:

It is not a cast. It is called the turbofish syntax, and it is a way to supply a generic type parameter directly to a method call. parse() is defined as:

fn parse<F: FromStr>(&self) -> Result<F, F::Err>

The F is a generic parameter. Rust needs to know what type F is before it can do anything. There are two ways to tell it:

  1. Turbofish on the method: rust "3.14".parse::<f32>()

  2. Type annotation on the binding: rust let seconds: f32 = seconds_text.parse()...

In your code, both are present at the same time, which is why removing the turbofish is fine. The : f32 annotation on seconds gives the compiler enough information to infer F = f32 without being told explicitly on the .parse() call. The turbofish becomes necessary when there is no annotation for the compiler to infer from, or when the inference is ambiguous. For example:

// compiler has no idea what type to parse into — turbofish required
let n = "42".parse::<i32>().unwrap();

// annotation does the same job — turbofish optional
let n: i32 = "42".parse().unwrap();

The ::<> spelling looks strange but follows the same pattern as other generic syntax. The extra :: is there because < alone would be ambiguous with a less-than operator at the call site.

Functions

Functions are beautiful, reusable blocks of logic. Wikipedia describes a function as “a callable unit of software logic that has a well-formed interface and behavior and can be invoked multiple times… Their primary purpose is to allow for the decomposition of a large and/or complicated problem into chunks that have relatively low cognitive load and to assign the chunks meaningful names (unless they are anonymous). Judicious application can reduce the cost of developing and maintaining software, while increasing its quality and reliability.” Where would any language be without them?

Common Type

The most commonly used function type in rust is declared with fn:

fn add(a: i32, b: i32) -> i32 {
    a + b       // no semicolon = expression = return value
}

println!("2 + 3 = {}", add(2, 3));

If your function doesn’t have a return type then you simply drop the -> <type> in the declaration. But if it does (have a return type), then the last expression in a block is its value. return exists but is idiomatic only for early returns. The reason this works is because the return value of a function is synonymous with the value of the final expression in the block of the body of a function. You can return early from a function by using the return keyword and specifying a value, but most functions return the last expression implicitly. I’m not crazy about dropping return. Including it makes it painlessly clear what is being returned. But then people won’t think your cool and they won’t come to your birthday party. Let the force guide you.

Anonymous Type

Another form of functions supported by Rust is closures. They are nameless, but may be assigned to variables and/or passed as arguments. There are a few differences between a closure and a fn function:

  1. They are nameless.
  2. They usually can infer parameter and return types and in such cases do not need to be specified.
  3. By default, they capture the state of variables in their surrounding scope.

The equivalent of the add function up above is any of the following:

let add = |a, b|                      a + b
let add = |a, b|                    { a + b }
let add = |a: i32, b: i32| -> i32   { a + b}

We cover closures in more detail later.

Control Flow

Conditional

An if expression allows you to branch your code depending on conditions. We think we know him well, and no doubt we do, but he’s got his own nuances in rust. The two that come to mind are:

  1. Rust’s Python like ternary which isn’t called a “ternary”.
  2. if with Some is a little strange, unique and super handy.

The “ternary” is a lot like Python’s ternary: it’s an if else squeezed that is typically squeezed into one line.

// if is an expression
let max = if a > b { a } else { b };

And if Some(var)... is a magical beast. I’m sure it does a lot more than I’m recalling, but right now the only use case I can think is how in one fell swoop it allows you to test an optional (Option<>) variable and if it has a value, then do something with it.

let cat: Option<String> = Some(String::from("George"));
if let Some(name) = &cat {
    println!("{}: fuzzy wuz he", name);
}

We go deeper in the Option<T> (next section).

Looping

As with most languages there are a number of ways to loop. I think the coolest one is via iteration of an object. I’m going to copy what Claude said about it. I was asking him about the following:

let body_lines: Vec<String> = [...];
for line in &body_lines {
    // do stuff with `line`
}

A for loop calls .into_iter() on whatever you give it. If you write for line in body_lines (no &), the vector is moved into the loop and consumed. After the loop, body_lines is gone. Writing for line in &body_lines passes a reference to the loop instead. The compiler calls .into_iter() on &Vec<String>, which yields &String references. The vector stays alive and usable after the loop. line is &String, not String.

What trait makes this work?

Two traits are at play:

  1. IntoIterator
    • IntoIterator is the trait that for loops depend on. A for loop is syntactic sugar for calling .into_iter() and then repeatedly calling .next() on the result. Any type that implements IntoIterator can appear in a for loop.
    • Vec<T> implements IntoIterator three ways:
      • for x in vec (consumes the vector, yields T)
      • for x in &vec (borrows the vector, yields &T)
      • for x in &mut vec (mutably borrows the vector, yields &mut T)
  2. Iterator
    • This trait defines the actual sequence and the logic for traversing the items. It requires defining an Item type and implementing the .next() method, which returns Some(item) until the iteration is complete, at which point it returns None.

The &Vec<T> case works because the standard library implements IntoIterator for &Vec<T>, which delegates to Vec::iter() under the hood and produces an iterator over &T values. So for line in &body_lines is exactly equivalent to for line in body_lines.iter(). The & form is just more concise and is what you will see in idiomatic Rust.

// loop
loop {
    break;   // only way to exit a bare loop
}

// while
while x > 0 {
    x -= 1;
}

// for over a range
for i in 0..10 {        // 0 to 9
    println!("{}", i);
}

// for over a collection
let nums = vec![1, 2, 3];
for n in &nums {
    println!("{}", n);
}

See Common Programming Concepts in The Rust Programming Language for more information.
