The Shell

A language whose type is text and whose composer is the pipe

Published

August 29, 2026

Why the Shell Exists

The shell is the oldest interactive programming language most of us use daily, and it is easy to mistake it for something less than a language. It looks like a place to type commands. It is, but that framing hides the design that makes it powerful. The shell is a language, and once you see it as one, the pieces that otherwise feel like disconnected trivia (quoting, globs, pipes, grep, find) snap into a single coherent picture.

The thesis of this notebook is one sentence:

The shell is a programming language whose only data type is text, and whose function-composition operator is the pipe.

Everything else follows from that. Hold onto it; we will return to it constantly.

The Core Design Decisions

1. The universal data type is a stream of bytes, interpreted as text

In C you have int, double, struct, pointers. The shell has one type that matters: a stream of characters. A filename is text. A number is text. The contents of a file are text. The output of a program is text. Because everything is the same type, any program’s output can feed any other program’s input. This is the Unix bet, made in 1973 and still paying off: standardize on the lowest-common-denominator format and you get composability for free.

2. The pipe is function composition

In a real language you write f(g(x)). In the shell you write g x | f. The pipe (|) connects the standard output of one program to the standard input of the next, and the connection is a live stream, not a temporary file. g and f run at the same time, with the kernel passing bytes between them. This is the shell’s single most important operator, and it is why small single-purpose programs (grep, sort, wc, cut) are worth more than their size suggests: they are composable functions.

3. Programs are the standard library

Python has import; C has #include. The shell’s library is /usr/bin. Every executable on your PATH is a callable function. grep is not built into the shell any more than printf is built into C; it is a separate program the shell invokes. This is why the toolkit feels open-ended: adding a function to the language is as simple as dropping an executable on the PATH.

4. The shell expands your text before any program sees it

This is the decision that surprises people coming from C. Before the shell runs a command, it rewrites the command line: it substitutes variables, expands * into filenames, runs $(...) sub-commands, and splits the result into words. The program you call receives the finished product and has no idea what the original text looked like. Quoting (the next section) is entirely about controlling this rewriting step. If you understand expansion, you understand 80% of the shell’s “gotchas.”

5. Exit codes are the boolean type

Every program returns an integer when it finishes: 0 for success, non-zero for failure. The shell treats 0 as true (note: the opposite of C). This is what makes &&, ||, and if work without a separate boolean type. grep returning “found nothing” is just grep returning 1, and that integer is enough to drive control flow.

This guide is general, but it focuses on zsh (the Z shell), the default on macOS and many Linux distros. If you use bash or another shell, almost all of this applies; differences are noted where they bite.

Variables and the Environment

We all know what a variable is: a value container with a name. Do we all know what an environment is? Sure - it’s a little harder to define, so we shall look in our dictionary: an environment is an overall structure within which a user, computer, or program operates. And we all know what a shell is thanks to the definition above. I searched for a graphic depicting a shell in relation to its environment, but didn’t find one, which sent me back to first principles. Let’s sketch it out. The dictionary definition is the misleading one here. The shell does live in an environment (a terminal, for example), but that is not the environment we mean. The environment in our sense is a container inside the shell: a labeled box holding some of the shell’s variables. The variables in the box are environment variables; the variables outside it are shell variables. That is the accurate picture, and it is the one to hold onto.

There is a second way to describe the same box, by its behavior rather than its location: the environment is precisely the set of variables the shell hands to every program it launches. These are two views of one fact: in the box and inherited by children are the same property, and we will see exactly why in Exported vs. Non-Exported below. For now, the one-sentence version: a shell variable is a named piece of text, and an environment variable is one that has been placed in the box and so travels to child processes. The whole distinction comes down to a single keyword, and getting it straight clears up most of the confusion around configuration, PATH, and “why does my variable disappear?”

Setting and Reading a Variable

Assignment has no let or var keyword and, critically, no spaces around the =. This trips up everyone at least once:

name="curtis"        # correct
name = "curtis"      # WRONG: the shell reads this as running the command `name`
                     #        with arguments `=` and `curtis`

The no-spaces rule is a direct consequence of decision #4 (the shell splits on whitespace): name = "curtis" is three words, so the shell treats name as a command. With no spaces, name="curtis" is a single word the shell recognizes as an assignment.

You read a variable back by prefixing it with $, which is just another expansion the shell performs before running the command:

echo "$name"         # curtis
echo "${name}"       # same; braces let you disambiguate, e.g. "${name}_backup"

The braces matter when the variable name butts up against other text. "$name_backup" looks for a variable called name_backup (and finds nothing); "${name}_backup" reads name and appends the literal _backup.

Exported vs. Non-Exported

A plain assignment creates a variable that lives only in the current shell. Child processes never see it. export promotes a variable into the environment, the bundle of name/value pairs that every child process inherits.

greeting="hello"            # shell variable: this shell only
export visible="seen"       # environment variable: this shell AND its children

The cleanest way to feel the difference is to launch a child shell and look:

Command Executed
sh_var="ding"
export env_var="dong"
echo "local: sh_var=[$sh_var] env_var=[$env_var]"
bash -c 'echo "child: sh_var=[$sh_var] env_var=[$env_var]"'
Output
local: sh_var=[ding] env_var=[dong]
child: sh_var=[] env_var=[dong]

The child shell inherited env_var but not sh_var. The non-exported variable was real and usable in the parent, but it stopped at the process boundary. This is the whole model:

Plain assignment Exported
Visible in current shell yes yes
Inherited by child processes no yes
Lives in the environment no yes
Typical use scratch values, loop counters, script-local state config the programs you launch need to read (PATH, EDITOR, LANG)

A few mechanical notes that follow from the model:

export greeting             # export an already-set variable
export PATH="$PATH:/opt/bin"   # the common idiom: append, then re-export

FOO=bar mycommand           # set FOO for ONE command's environment only,
                            # without touching the current shell at all

That last form is worth keeping in your pocket. FOO=bar mycommand puts FOO in the environment of mycommand and nothing else, which is the tidy way to pass a one-off setting (DEBUG=1 ./run.sh) without leaving it lying around.

CautionInheritance is one-way and by-copy

A child receives a copy of the parent’s environment. Nothing a child does to its own variables, not even exported ones, propagates back up to the parent. This is why you cannot write a normal script that changes your current shell’s directory or variables: it runs in a child, and its changes die with it. (The escape hatch is source script.sh, which runs the script in the current shell instead of a child. More on that below.)

source vs. Executing

Running a script the usual way (./script.sh) launches a child shell, so per the note above, any variables or cds it performs vanish when it exits. source script.sh (or its POSIX spelling . script.sh) instead runs the file’s commands in your current shell:

./setup.sh        # runs in a child; its exports do NOT survive
source setup.sh   # runs here; its exports and cd DO survive

This is exactly why you source ~/.zshrc to reload your config rather than executing it, and why Python’s venv activation is source venv/bin/activate: it needs to modify your current shell’s PATH.

The Standard Environment Variables

A handful of environment variables are conventional across Unix systems. Programs read them to discover where things live and how you like to work. These are the $x names you will see constantly:

Variable Holds
$PATH colon-separated list of directories searched for commands.
$HOME your home directory (~ expands to this).
$USER your login name.
$SHELL path to your login shell (e.g. /bin/zsh).
$PWD the current working directory.
$OLDPWD the previous directory (what cd - returns to).
$LANG / $LC_* locale: language, character encoding, formatting.
$EDITOR your preferred editor, used by git, crontab, etc.
$TERM terminal type, used for colors and capabilities.
$TMPDIR directory for temporary files.
$PROMPT / $PS1 prompt specification expanded by the shell. The same expansion is available using the -P option to the print builtin.

Let’s take a closer look at a couple of these fellas.

$PATH

$PATH is the one to understand deeply, because it is how the shell turns a command name into a program (decision #3, programs are the standard library). When you type grep, the shell walks $PATH left to right and runs the first grep it finds:

Command Executed
echo "$PATH"
Output
/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin

Order matters: a directory earlier in $PATH shadows the same-named command later. This is why /usr/local/bin usually comes first, so your installed tools win over the system defaults.

$PROMPT

A prompt sequence is a combination of literal text and escape sequences. An escape sequence is two or more characters that start with %. At the moment the shell draws the prompt, it expands each escape sequence into the data it represents, so the prompt is recomputed fresh every time it appears. zsh.sourceforge.io includes a Prompt Expansion reference.

My $PROMPT is defined as: %{(language) %n@%m %1~ %# %}. Using the prompt expansion reference, we shall break it down.

Literal/Sequence Data
%{ Opens a zero-width span. Everything up to the matching %} is sent to the terminal verbatim but counted as occupying no columns. Its normal job is to wrap color/escape codes so the shell’s idea of the cursor position stays correct. See the note below; an empty-looking pair around the whole prompt is unusual.
(language) Not a zsh escape sequence at all, just literal text the shell prints as-is. It is the active Python virtual environment’s name, inserted by a different mechanism than prompt expansion. We break this down under Pulling the virtual environment into the prompt below.
%n The username ($USERNAME).
@ Literal @.
%m The hostname up to the first .
%1~ The current working directory, with ~ substituted for $HOME where it applies. The integer limits how many trailing path components to show: %1~ shows just the last one, %~ (or %0~) shows the whole path. A negative integer counts leading components instead, so %-1~ shows the first.
%# A # if the shell is running with privileges (root), a % if not.
%} Closes the zero-width span opened by %{.
NoteThat outer %{ ... %} is doing nothing useful here

Read literally, your prompt wraps everything in a single zero-width span: %{ … %} with no escape codes inside. That tells zsh “none of this text occupies any columns,” which is wrong, the text plainly takes up space. If zsh were actually rendering this prompt, the cursor math would be off and line editing would smear. The reason you don’t see that breakage is that Warp does not use $PROMPT to draw the prompt. Warp renders its own prompt UI and only inspects $PROMPT to scrape a few facts out of it (the venv name, the directory). The stray %{ %} is almost certainly Warp’s own wrapper, not something you would write by hand. On a terminal that honors $PROMPT literally (Ghostty, iTerm2, Terminal.app, a plain tty), drop the outer %{ %} and you would write the prompt as (language) %n@%m %1~ %#.

Pulling the virtual environment into the prompt

The (language) in front of the prompt is the single most common piece of “prompt magic,” and it is worth seeing clearly because it is not magic at all. It is two ordinary mechanisms from earlier in this chapter working together.

When you run source venv/bin/activate, the activate script does two things (recall from source vs. Executing that source runs in your current shell, which is the only reason this can stick):

  1. It exports an environment variable, VIRTUAL_ENV, holding the path to the venv. This is the source of truth; any tool can read it to learn which environment is active.
  2. It edits your $PROMPT, prepending ($VIRTUAL_ENV's basename) so you get a visual reminder.

You can see the source of truth with no magic involved:

Command Executed
echo "$VIRTUAL_ENV"          # the env var the activate script exported
echo "$VIRTUAL_ENV_PROMPT"   # the label to show, if one was set
Output
/Users/curtis/Develop/school/language/venv
(language)

Note the directory is named venv but the prompt reads (language). By default activate would show (venv), the directory’s basename. The friendlier (language) comes from creating the environment with an explicit label, python -m venv --prompt language venv, which records that name in pyvenv.cfg; on activation it is exported as $VIRTUAL_ENV_PROMPT and that is what gets prepended. So the tag is ( + (the --prompt label, falling back to the basename of $VIRTUAL_ENV) + ), baked into $PROMPT at activation time. If you wanted to build it yourself rather than let activate do it, the idiomatic zsh way is a prompt function that runs each time the prompt draws, so it tracks the environment as you activate and deactivate:

# In ~/.zshrc. setopt prompt_subst lets $PROMPT run ${...} substitutions live.
setopt prompt_subst

venv_prompt() {
  [[ -z "$VIRTUAL_ENV" ]] && return
  echo "${VIRTUAL_ENV_PROMPT:-(${VIRTUAL_ENV:t}) }"   # :t = "tail", the basename
}

PROMPT='$(venv_prompt)%n@%m %1~ %# '

The single quotes are the crux: they keep $(venv_prompt) unexpanded when PROMPT is assigned, so the literal text $(venv_prompt) is stored in the variable. Then, because prompt_subst is set, zsh re-expands that stored string on every redraw, running the function fresh each time. The (language) tag therefore appears and disappears as you activate and deactivate. Use double quotes instead and the substitution would fire once at assignment, freezing whatever the venv was at that moment.

TipLet a prompt framework do this

Hand-rolling venv, git branch, exit status, and timing into $PROMPT gets tedious fast. The common move is to install a prompt engine that does it for you: Starship (a single binary, config in TOML, works across shells) is the popular modern choice; powerlevel10k and oh-my-posh are alternatives. They read the same VIRTUAL_ENV and run git under the hood; they just spare you the escape-sequence bookkeeping. This is also the clean way to get a rich prompt on a terminal like Ghostty that, unlike Warp, draws the prompt straight from $PROMPT and does no scraping of its own.

The Special Shell Parameters

Distinct from the environment variables above, the shell maintains a set of special parameters: read-only $x values it sets for you, mostly about the running script and the last command. You met $? back in Flow Control; here is the rest of the family:

Parameter Holds
$? exit code of the last command (0 = success)
$$ process ID of the current shell
$! process ID of the last backgrounded command
$0 name of the script (or shell) itself
$1, $2, … positional arguments passed to the script
$# number of positional arguments
$@ all arguments, as separate quoted words (use "$@")
$* all arguments, as one word

The argument parameters are what make a script callable. A minimal example ties them to things you have already seen:

#!/usr/bin/env bash
echo "script: $0"
echo "got $# arguments"

for arg in "$@"; do        # "$@" expands to each argument as its own word
    echo "  - $arg"
done
Warning"$@" vs $@ vs $*

Always quote it: "$@" is the only form that preserves arguments exactly, each as a separate word even when it contains spaces. Bare $@ and $* word-split, and unquoted $* collapses everything into one string. This is the same quoting hazard from the Quoting section, now applied to a script’s own inputs.

Arrays

A shell variable holds text. An array holds an ordered list of values, which matters because the alternative, jamming a list into one string and splitting it later, is exactly the practice the quoting section warns against. A path with a space in it survives an array intact and does not survive a space-separated string.

Assignment looks the same in both shells. Reading the values back does not, so the expansions below are written twice:

files=(report.txt "my notes.md" data.csv)     # zsh and bash both

# zsh
echo "$files[2]"        # my notes.md      (1-based, braces optional)
echo "${#files}"        # 3                (element count)
echo "$files[@]"        # all elements

# bash
echo "${files[1]}"      # my notes.md      (0-based, braces required)
echo "${#files[@]}"     # 3                (element count)
echo "${files[@]}"      # all elements

The braced forms ("${files[1]}", "${files[@]}") also work in zsh, so when in doubt, write those.

WarningArrays are where zsh and bash genuinely differ

Most of this guide applies to both shells. Arrays are the exception, and the differences bite immediately.

zsh bash
First index 1 0
All elements "$arr[@]" or "${arr[@]}" "${arr[@]}"
Element count ${#arr} ${#arr[@]}
Braces around subscript optional required
Associative arrays typeset -A declare -A, bash 4+ only

The 1-based indexing is the one that catches people, and it is deliberate: zsh follows the tradition of awk and the positional parameters ($1 is the first argument, not $0). Note also that ${#arr} means different things in the two shells: element count in zsh, but in bash it is the string length of the first element, which is a silent wrong answer rather than an error.

For portable scripts, write bash syntax with braces everywhere and 0-based indices. For your own .zshrc, use zsh’s.

Building and Iterating

files=()                          # empty
files+=(newfile.txt)              # append
files=("${files[@]}" prepended)   # prepend, the clumsy way

for file in "${files[@]}"; do     # quoted: each element stays one word
    echo "processing: $file"
done

Quoting the expansion matters for the same reason it always does. "${files[@]}" yields one word per element regardless of spaces; unquoted, each element is re-split on whitespace and my notes.md becomes two arguments.

A common source of arrays is a command’s output, and here the shells diverge again:

lines=("${(@f)$(ls)}")            # zsh: split on newlines only
mapfile -t lines < <(ls)          # bash 4+: read lines into an array

The zsh (@f) is a parameter expansion flag, splitting on newlines rather than all whitespace, which is what you want for filenames. Splitting command output on spaces is the classic way to break on a file named my notes.md.

Associative Arrays

An associative array maps string keys to values, a dictionary rather than a list. It must be declared before use:

typeset -A config                 # zsh   (declare -A in bash 4+)
config[host]="localhost"
config[port]="8080"

echo "$config[host]"              # localhost
echo "${(k)config}"               # keys:   host port
echo "${(v)config}"               # values: localhost 8080

(k) and (v) are two more zsh expansion flags, yielding keys and values respectively. In bash the equivalents are "${!config[@]}" for keys and "${config[@]}" for values.

Testing Whether a Key Exists

the $+ You Found

Now to the thing that sent you looking. Your search turned up $+aliases[run-help], and the + is the piece worth understanding, because it answers a question ordinary expansion cannot.

${+name} is zsh’s set test. It expands to 1 if the parameter is set and 0 if it is not, and it never expands the value itself:

name="curtis"
echo ${+name}          # 1
echo ${+nonexistent}   # 0

The reason this exists as its own operator is that unset and empty are different states, and plain expansion cannot tell them apart:

empty=""
echo "[${empty}]"      # []     <- looks identical to unset
echo "[${nope}]"       # []     <- but this one was never set
echo ${+empty}         # 1      <- set, holding an empty string
echo ${+nope}          # 0      <- genuinely not set

For an ordinary variable that distinction is often academic. For an associative array it is the whole question: is there an entry under this key? An empty result could mean “no such key” or “a key whose value is empty,” and $+ separates them.

Which brings us to what you were actually testing. zsh exposes several of its internal tables as associative arrays you can read like any other:

Array Contains
$aliases all defined aliases, keyed by name
$functions all defined shell functions, keyed by name
$parameters all parameters, keyed by name
$commands external commands found on $PATH, keyed by name
$options shell options and their on/off state
$builtins built-in commands

So the recipe you found reads directly:

if (( ${+aliases[run-help]} )); then
    echo "run-help is aliased to: $aliases[run-help]"
fi

${+aliases[run-help]} is 1 if an alias named run-help exists, 0 otherwise. The (( ... )) is arithmetic evaluation, which treats nonzero as true, so the whole thing reads as “if the alias exists.” And because $aliases is an ordinary associative array, you can read the definition out of it, list every alias with ${(k)aliases}, or even assign to it to create an alias.

NoteThe portable alternative

$+ and the $aliases table are zsh-specific. In bash, ${var+set} is the POSIX cousin, expanding to the word set when the parameter exists and to nothing when it does not:

[[ -n "${config[host]+x}" ]] && echo "key exists"   # bash 4+, works in zsh too

For aliases specifically, the portable test is to ask the shell rather than inspect a table:

alias run-help >/dev/null 2>&1 && echo "defined"

That works everywhere. The zsh table is nicer when you are already in zsh and want the value, not just its existence.

Why $PATH Is Both

One array in particular you have already been using without noticing. zsh ties $PATH (the colon-separated string) to $path (an array), keeping them synchronized:

echo "$PATH"           # /usr/local/bin:/usr/bin:/bin
echo "$path[1]"        # /usr/local/bin   (the same data, indexable)
echo "${#path}"        # 3                (how many entries, without counting colons)

path+=(/opt/homebrew/bin)      # append via the array; $PATH updates to match

Changing either one updates the other, which is what “tied” means.

This is much pleasanter than the export PATH="$PATH:/opt/bin" string surgery from earlier, and it is why zsh users often manipulate $path instead. The pairing is called a tied parameter, created with typeset -T, and you can make your own. $PATH stays a colon-separated string because that is what the environment must contain for child processes to read it; $path is the same data in a form the shell can index.

Parameter Expansion

${...} is a tiny string-editing language built into the shell.

You already use the plain form, $VAR or ${VAR}, to read a value. The braces, though, are not just there to disambiguate where a name ends (${VAR}_suffix). Inside them lives a small sublanguage for transforming the value on the way out: trimming a prefix or suffix, substituting a default, slicing a substring, changing case. It is the shell’s answer to the string operations you would reach for str.removeprefix or substr to do elsewhere, and it runs entirely in the shell with no external process. That last point matters: ${1#--profile=} does its work without forking sed or cut, which is why parameter expansion is the idiomatic tool for the small, hot string edits that CLI parsing is full of.

The whole family shares one shape: ${ parameter operator word }. The parameter is the variable (1, PROFILE, PATH); the operator is a punctuation glyph that names the transformation; the word is the argument to it. What follows are the operators you will actually meet in the wild.

Trimming Prefixes and Suffixes

# bites off the front, % bites off the back.

These four are the workhorses. Each takes a glob pattern (the same wildcards as globbing, not a regex) and removes the matched piece from one end of the value:

Expansion Removes Mnemonic
${var#pat} shortest match of pat from the front # is left of $ on the keyboard
${var##pat} longest match of pat from the front doubled = greedy
${var%pat} shortest match of pat from the back % is right of $
${var%%pat} longest match of pat from the back doubled = greedy

The single/double distinction is about greed, and it only bites when the pattern contains a *:

path=/usr/local/bin/python3

echo "${path##*/}"   # python3      longest front match of */  → strips every dir
echo "${path#*/}"    # usr/local/bin/python3   shortest → strips just the leading /
echo "${path%/*}"    # /usr/local/bin          shortest back match of /* → the dirname
echo "${path%.*}"    # (unchanged; no dot)     strips a file extension when present

${path##*/} and ${path%/*} are the shell’s built-in basename and dirname, running without a subprocess. That is the single most common use you will see.

Back to your parser, ${1#--profile=} reads exactly this way: take $1, strip the shortest front match of the literal --profile=, and hand back what remains. When $1 is --profile=release, the pattern --profile= matches the head and expansion yields release. There is no * in the pattern, so single vs. double # makes no difference here; # is just the conventional choice for “strip a known literal prefix.”

Defaults and Presence

Substitute a fallback, or assign one, when a variable is empty or unset.

The :-, :=, :+, and :? operators branch on whether a variable has a value. They are the shell’s ternary, and they retire whole if [ -z "$x" ] blocks:

echo "${EDITOR:-vim}"        # use $EDITOR, or "vim" if it is empty/unset
: "${CONFIG:=/etc/app.conf}" # as above, but ALSO assign the default back into $CONFIG
echo "${DEBUG:+--verbose}"   # if DEBUG is set, expand to "--verbose"; else to nothing
echo "${1:?missing argument}"  # if $1 is empty/unset, print the message and abort

The colon is the difference between “unset or empty” (with :) and merely “unset” (without). ${x-default} fires only when x is entirely unset; ${x:-default} also fires when x is set but empty. You almost always want the colon form.

${1:?message} is a particularly clean guard for a script’s own arguments: one line that either yields the argument or exits with your error, replacing a three-line if at the top of the script.

Slicing, Length, and Substitution

The rest of the toolkit: substrings, length, search-and-replace, case.

The remaining operators round out the string library. These are bash/zsh features (not in strict POSIX sh), so reserve them for scripts with a bash shebang:

name="deploy-prod-2024"

echo "${#name}"          # 16          length, like strlen
echo "${name:0:6}"       # deploy      substring: offset 0, length 6
echo "${name:7}"         # prod-2024   substring from offset 7 to the end
echo "${name/prod/stage}"   # deploy-stage-2024   replace FIRST match
echo "${name//-/_}"      # deploy_prod_2024        replace ALL matches (doubled /)
echo "${name^^}"         # DEPLOY-PROD-2024        upper-case (bash 4+; zsh: ${name:u})
echo "${name,,}"         # deploy-prod-2024        lower-case (bash 4+; zsh: ${name:l})

Substitution (${var/from/to}) is the in-shell sed s/// for the common case, and like the trimming operators it takes a glob pattern for from, not a regex.

Argument Parsing

The Real-World Loop: where parameter expansion, case, and shift come together.

Nearly every hand-written CLI parser is the same shape: a while loop over the positional arguments, a case that dispatches on the current one, and shift to advance. Here is the pattern in full, the kind of loop you will find at the top of countless real scripts:

PROFILE=debug
AUTO_RUN=false
SD_ROOT=

while [ "$#" -gt 0 ]; do
    case "$1" in
        --profile=*)
            PROFILE="${1#--profile=}"   # strip the flag, keep the value
            shift
            ;;
        -r|--run)
            AUTO_RUN=true
            shift
            if [ "$#" -gt 0 ]; then     # consume the NEXT arg as this flag's value
                SD_ROOT="$1"
                shift
            fi
            ;;
        -h|--help)
            usage
            exit 0
            ;;
        *)
            echo "Unknown argument $1" >&2
            usage
            exit 1
            ;;
    esac
done

The three moving parts: while [ "$#" -gt 0 ] runs until the arguments are exhausted; case "$1" inspects the front argument; shift drops $1 and slides $2 down into its place, decrementing $#. Each branch is responsible for consuming exactly the arguments it owns, one shift per argument eaten. Miss a shift and the loop spins forever on the same argument; add one too many and you skip an argument unparsed.

Notice the two different ways a flag takes a value. --profile=release carries its value attached, and ${1#--profile=} peels it off in place. -r release carries its value in the next argument, so the branch does a second shift to consume it. This split is exactly what the next callout is about.

WarningThis loop has a real bug

The -r|--run branch unconditionally swallows the following argument as SD_ROOT. But -r is a boolean flag, “should we auto-run?”, and its value here is true, set on the line above. Consuming the next argument as well means myscript --run --profile=release silently eats --profile=release into SD_ROOT and never parses the profile. Either -r is a boolean (take no argument) or it expects a path (document it, and reject a following flag), but it cannot quietly be both. When a flag conditionally consumes the next token, that next token is invisible to the rest of the parser, and mixing that with a boolean reading of the same flag is how parsers grow silent, order-dependent surprises.

NoteHow should an option take its argument? Prefer --option=value.

There are three conventions in circulation, and they are not equally safe:

Style Example Cost
Attached, = --profile=release One token, unambiguous. ${1#--profile=} extracts it locally.
Separate token --profile release Two tokens; the parser must look ahead and shift twice.
Glued short form -prelease Terse, but ambiguous with bundling (-p -r), and unreadable.

The attached --option=value form is the most bullet-proof, and your instinct is right. Its value travels with the flag as a single argument, so there is no “is the next token my value or the next flag?” lookahead, no risk of consuming a flag by accident (the bug above), and no ambiguity if the value itself starts with a dash (--pattern=-foo is unmistakable, whereas --pattern -foo looks like two flags). The parser branch stays entirely local: match --option=*, then ${1#--option=}. The separate-token form is what most GNU tools also accept, and it is fine when you handle the lookahead deliberately, but the = form removes the entire class of “who owns the next argument” mistakes. Reserve the glued short form for genuine single-letter boolean flags, where bundling (-rf) is a feature, not a hazard.

For anything beyond a handful of flags, reach for a real parser instead of hand-rolling: bash’s built-in getopts (POSIX short options), the GNU getopt program (long options too), or, honestly, a different language once the flag matrix gets wide.

Optional Values Need Two Patterns

When a flag’s =value is optional, bare --flag and --flag=value are different tokens.

Once you commit to the = convention, a subtlety surfaces the moment a flag’s value becomes optional. Suppose --run should enable auto-run on its own, but also accept an optional --run=<path> to override a default. The trap: the glob --run=* requires the literal = to be present, so a bare --run does not match it. You need two branches, one per spelling:

--run)                           # bare: enable, keep the default path
    AUTO_RUN=true
    shift
    ;;
--run=*)                         # with a value: enable, and maybe override
    AUTO_RUN=true
    value="${1#--run=}"          # everything after '='; may be the empty string
    if [ -n "$value" ]; then     # only override when a real path was given
        SD_ROOT="$value"
    fi
    shift
    ;;

This also settles a tempting shortcut: “can’t I just assign ${1#--run=} to a variable and test whether it’s empty?” You can, but only to answer one of three separate questions, and it is easy to conflate them:

What you want to know How you actually test it
Was --run passed at all? The case pattern. Entering either branch means yes; do not inspect a variable for this.
Did they use --run=value or bare --run? Which branch fired. Matching --run=* means a value was supplied (possibly empty).
Was the supplied value non-empty? [ -n "$value" ] (or [ -z "$value" ]), always quoted.

Emptiness alone cannot distinguish the first two rows, because SD_ROOT ends up empty both when the user passes nothing (--run) and when they pass an empty value (--run=). That ambiguity is exactly why a separate boolean like AUTO_RUN earns its place: it records “did they ask to run?” unambiguously, set the instant either branch fires, independent of whether a path came with it. Reserve the emptiness test for the narrow question it answers well, “is there a usable value here?”, and let the case structure answer the rest.

The Built-in Parser getopts

The POSIX shell’s own option parser, for when the hand-rolled loop gets tedious

The hand-rolled while/case/shift loop is portable, but it grows repetitive: every flag needs its own branch, its own shift bookkeeping, and its own error handling. getopts is a POSIX built-in that absorbs that boilerplate for short options (-v, -o file, and bundled forms like -vo). It is not a separate program; it is a shell keyword you call once per iteration of a while loop, and it walks the arguments for you.

The mental model: you hand getopts an option string describing which flags exist, and it hands you back, one call at a time, the next flag it found:

verbose=false
output=

while getopts "vo:h" opt; do
    case "$opt" in
        v) verbose=true ;;
        o) output="$OPTARG" ;;      # $OPTARG holds the value for a flag with ':'
        h) usage; exit 0 ;;
        ?) usage; exit 1 ;;         # getopts sets opt to '?' on an unknown flag
    esac
done

shift "$((OPTIND - 1))"            # drop the parsed options; leave the positionals
echo "remaining arguments: $@"

Three pieces do the work:

  • The option string "vo:h". Each letter is a valid flag. A colon after a letter means that flag takes an argument: o: is -o value. So v and h are boolean, o expects a value. A leading colon (":vo:h") switches getopts into silent error mode, where you handle bad input yourself instead of letting it print to stderr.
  • $OPTARG. When a flag takes an argument, getopts puts that argument here. In the loop above, -o report.txt leaves opt=o and OPTARG=report.txt.
  • $OPTIND. The index of the next argument getopts will look at. After the loop, OPTIND - 1 is the count of tokens consumed by options, so shift "$((OPTIND - 1))" slides the leftover positional arguments (the filenames, the paths) down to $1, $2, ready for a for arg in "$@" afterward. This is the step people forget, and without it your positionals still have the flags in front of them.

What you get for free is exactly the tedium the manual loop makes you write by hand: bundling (-vo file is understood as -v -o file), the = and separate-token forms of an argument (-ofile and -o file both work), and a clean stop at the first non-option argument or at the -- sentinel.

Warninggetopts does short options only

This is the catch, and it is why the hand-rolled loop never fully goes away. POSIX getopts understands -v, not --verbose; there is no long-option support, and --profile=release will not parse. If you need long options you have three choices: accept short-only, hand-roll the case loop from the previous section (which handles --profile=* naturally), or step outside the shell to the separate GNU getopt program (note: no s), which does support long options but has its own quoting sharp edges. For anything with a serious flag matrix, that last signal, “I am now fighting the parser”, is usually the moment to reach for Python’s argparse or Rust’s clap instead.

Notegetopts (built-in) vs. getopt (program)

The near-identical names hide a real difference. getopts (with the s) is the shell built-in shown above: POSIX, portable, short options only, no subprocess. getopt (no s) is an external program, GNU’s version parses long options and can re-order arguments, but its classic form mishandles values with spaces and its “enhanced” mode needs careful eval set -- "$@" wrapping. When someone says “use getopts,” they almost always mean the safe built-in. Reach for the external getopt only when you specifically need long options and cannot move to a real language.

Running Commands and Capturing Output

Every command hands back two separate things, and confusing them is the root of most “why didn’t that work?” moments.

When a command finishes, it gives you two distinct things: a stream of text (its output) and a single integer (its exit status). These travel on different channels and serve different jobs. The text is the data the command produced; the integer is a verdict on whether it succeeded. The whole secret to this section is keeping them apart in your head.

If you come from C, you already know this shape. A function like int fputs(const char *s, FILE *stream) does two things at once: it writes characters to a stream (a side effect on stdout) and it returns an int (a status). A shell command is the same: it writes text to stdout and returns an integer status. The text is not “the return value” in the C sense; it is the side effect on the stream. The return value is the integer. Tangling those two is exactly what trips people up.

The Three Standard Streams

Every command is born with three streams already wired up. The rest of this section, and later all of pipes and redirection, is about what you connect them to.

Stream Number Default Purpose
stdin 0 keyboard where the program reads input
stdout 1 terminal where the program writes normal output
stderr 2 terminal where the program writes errors and diagnostics

The separation of stdout from stderr is deliberate and important: it lets you capture a program’s results while still seeing its errors on screen (or route them somewhere else entirely). A program that mixes errors into stdout is considered poorly behaved precisely because it pollutes the data stream that the next program in the pipe is trying to read.

The two channels a command hands back map onto this picture cleanly: the text you can capture is stdout (stream 1), and the integer verdict is the exit status (not a stream at all, a separate value we get to below).

Capturing stdout

Command Substitution

This is the answer to the question that started this section: yes, you can take what a command sends to stdout and assign it to a variable. The mechanism is command substitution, written $(...). The shell runs the command inside the parentheses, captures everything it wrote to stdout, and substitutes that text in place.

Yes, indeed. There are two methods of specifying command substitution: $(...) and `...`.

result=$(date)     # modern form, preferred
result=`date`      # legacy backtick form, same effect

But they did battle at Thunderdome. Two syntaxes entered, one syntax left. Guess which one left. Yes, the super-syntax flying the dollar-sign cape. They do the same thing, but $(...) is better in every case that matters. The decisive difference is nesting. With $(...) you simply nest:

newest=$(basename $(ls -t | head -1))

With backticks you cannot nest directly; the inner ones must be escaped, and it gets ugly fast:

newest=`basename \`ls -t | head -1\``

Backticks also collide visually with single quotes and are easy to misread. They survive only in old scripts and quick one-liners. Reach for $(...) and never look back.

A one-line reminder on assignment first (the full story is in Variables and the Environment): you assign with name=value and no spaces around the =. With that in hand:

result=$(date)          # run date, capture its stdout into result
echo "$result"          # Mon Jun  9 11:04:21 PDT 2026
export today=$(date +%F)   # same idea, but placed into the environment

$(...) is not limited to assignment. Because the shell replaces it with text before running the outer command, you can drop a command’s output anywhere a word is expected:

echo "Today is $(date +%A)"   # Today is Monday
kill $(pgrep firefox)         # pgrep prints PIDs; kill receives them as arguments
mkdir "backup-$(date +%F)"    # backup-2026-06-09

That captured text is exactly what people mean by “the returned result.” There is no separate text-return channel hiding behind the command; it is stdout, grabbed and pasted in.

One small surprise for C programmers expecting raw bytes: command substitution strips trailing newlines. date prints a line ending in \n, but result=$(date) holds the text without it. This is almost always what you want (it keeps "backup-$(date +%F)" from breaking across a line), but it means $(...) is not a byte-exact copy of the stream.

Warningstderr is not captured

$(cmd) captures stdout only. Anything cmd writes to stderr sails straight past the capture and onto your terminal. So out=$(grep foo missing.txt) leaves out empty and still prints grep: missing.txt: No such file or directory to the screen. To fold stderr into the captured text, redirect it into stdout first:

out=$(grep foo missing.txt 2>&1)

That 2>&1 idiom is covered under Redirection.

Exit Status

the Other Return Value

The second thing a command hands back is its exit status: an integer from 0 to 255, where 0 means success and any non-zero value means some kind of failure. This is the shell’s boolean type (decision #5), and it is what if, &&, and || actually test. The special variable $? holds the exit status of the most recent command:

grep -q "thesis" shell.qmd
echo $?        # 0 if the word was found, 1 if not

Here is the crux of the confusion. You cannot capture the exit status with $(...). Command substitution captures text from stdout; the exit status is a separate integer that lives in $?. They answer different questions:

You want… Use…
the command’s output (text) var=$(cmd)
whether it succeeded (yes/no) test cmd directly, or read $?

A useful detail ties them together: assigning a command substitution does not clobber $? with the assignment’s own status, so $? afterward still reflects the inner command. That lets you grab both in two lines:

output=$(some-command)   # capture the text
status=$?                # capture the verdict, before any other command runs

The “before any other command runs” matters: $? is overwritten by the next command, so read it immediately.

A Look-alike

Arithmetic Substitution $(( ))

One construct looks almost identical to command substitution but does something entirely different. $(( ... )), with doubled parentheses, is arithmetic substitution: it evaluates a math expression and substitutes the numeric result. It does not run a command.

count=$(( count + 1 ))    # increment count
area=$(( width * height ))
echo "$(( 7 % 3 ))"       # 1

It is worth pointing out only because $(cmd) and $(( expr )) are one keystroke apart on the page and easy to confuse. The single-paren form runs a command and captures its stdout; the double-paren form does arithmetic. Different jobs, similar costume.

Quick Reference

Goal Syntax
Capture a command’s stdout var=$(command)
Same, legacy form (avoid) var=`command`
Capture stdout and stderr var=$(command 2>&1)
Read the last command’s exit status $?
Capture output and status together out=$(cmd); st=$?
Evaluate arithmetic $(( expression ))

Quoting and Expansion

Quoting is not decoration. It is how you control the shell’s rewriting of your command line (decision #4 above). Get quoting wrong and the shell hands your program a mangled set of arguments; get it right and you have exact control over what every program receives.

The Processing Order

Before any command runs, the shell walks your line through a fixed pipeline:

  1. Parse quotes to decide which characters are literal and which are special.
  2. Expand variables ($VAR), command substitutions ($(...)), and globs (*, ?, []).
  3. Split the unquoted result into words on whitespace.
  4. Remove the quote characters so the program never sees them.
  5. Run the command with the finished argument list.

The single most useful debugging habit in the shell is to ask: what does this look like after step 4, when the program actually receives it?

Three Quote Types

The three quoting styles are three different settings for “how much expansion do I want?”

Single Quotes 'text'

literal everything

  • No expansions at all. Every character is taken verbatim.
  • You cannot put a single quote inside single quotes, not even escaped.
Command Executed
echo 'Hello $USER * $(date)'
Output
Hello $USER * $(date)

Use single quotes whenever you want the program, not the shell, to interpret the text. Regular expressions are the classic case: the regex metacharacters $, *, [ mean something to grep, and you almost never want the shell touching them first.

Double Quotes "text"

expand variables, but nothing else

  • Variable and command expansion happens: $VAR, ${VAR}, $(command).
  • Globs stay literal: *, ?, [] are passed through untouched.
  • A few escapes work: \", \$, \\.
Command Executed
echo "Hello $USER, files: *.txt"
Output
Hello curtis, files: *.txt

Double quotes are the safe default for strings that contain variables. Crucially, they also suppress word splitting, so "$file" survives intact even if the filename contains spaces. This one habit prevents a large fraction of real-world shell bugs.

No Quotes

bare: everything expands

  • Everything expands: variables, globs, command substitution.
  • Word splitting happens on whitespace, so one bare variable can become many arguments.
Command Executed
echo Hello $USER, files: *.qmd | head -c 50
Output
Hello curtis, files: index.qmd la-decomposition.qm%

Bare words are what you want when you intend the expansion, for example ls *.txt, where letting the shell turn *.txt into a list of filenames is the whole point.

Quote Removal in Action

The quote characters are removed before the program runs. The program receives the content, never the quotes:

When the following is run over our DATA 605 notebook.

grep "matrix" la-eigenspace.qmd | head -1

We receive:

- **Matrix operations**: See [Matrix multiplication](la-matrices.qmd#multiplication) and ...

grep receives matrix as its first argument, with no quotes attached. The quotes existed only to tell the shell how to build that argument.

Word Splitting

Unquoted text splits on whitespace into separate arguments. This is the difference between passing one argument and passing several:

# These are NOT the same:
echo "one two three"     # 1 argument:  "one two three"
echo one two three       # 3 arguments: "one", "two", "three"

For echo the visible result is the same, but for a program that cares how many arguments it received, the distinction is everything. This is also why unquoted variables are dangerous: rm $file where $file is my report.txt tries to remove two files, my and report.txt. rm "$file" does the right thing.

Mixing Quotes

Adjacent quoted and unquoted pieces concatenate into a single word, so you can mix styles within one argument to control expansion piece by piece:

Command Executed
echo 'User: '$USER' at '$(date +%H:%M)
Output
User: curtis at 13:40

The literal labels are single-quoted (no surprises), while $USER and $(date ...) are left bare so they expand.

Common Patterns

# Regex with special chars → single quotes keep them away from the shell
grep '\$[0-9]+' file.txt

# Variable inside a regex → double quotes so $USER expands but * does not
grep "^$USER:" /etc/passwd

# Remote command with spaces → quote so the whole thing arrives intact
ssh server "cd /path/with spaces && ls -la"

# Preserve a literal asterisk for the program
find . -name "*.txt"    # good: find receives *.txt and matches itself
find . -name *.txt      # bad:  the shell expands * before find runs

That last pair is worth staring at. find’s -name wants the pattern *.txt, but if you leave it bare the shell expands it first against the current directory, and find receives a list of filenames instead of a pattern. Quoting hands find the pattern it asked for.

Quick Reference

Need Use Example
Literal everything 'text' grep '\$[0-9]+'
Variables but no globs "text" echo "Hello $USER"
Everything expands text (bare) ls *.txt
Whitespace preserved "text" rm "$file"

The one insight to keep: the shell processes quotes and expansions before your command ever sees its arguments.

Globbing

A glob is a filename pattern the shell expands into a list of matching paths. It is one of the expansions from step 2 above, and it deserves its own section because people routinely confuse it with regular expressions. They are not the same language, and conflating them is a common source of frustration.

Globs Are Not Regexes

A glob is a small pattern language for matching filenames, expanded by the shell. A regex is a richer pattern language for matching text inside lines, used by programs like grep. The same character means different things in each:

Pattern As a glob (filenames) As a regex (text)
* any run of characters zero or more of the previous item
? exactly one character zero or one of the previous item
. a literal dot any single character

So *.txt as a glob means “any filename ending in .txt,” but *.txt as a regex would be a syntax error (there is nothing before the * to repeat). Keep the two languages mentally separate and a lot of confusion evaporates.

The Glob Operators

Glob Matches
* any number of characters (including none), except a leading .
? exactly one character
[abc] one character from the set
[a-z] one character from the range
[!abc] one character not in the set
** any depth of directories (recursive; on by default in zsh) 
ls *.qmd            # every .qmd file in this directory
ls la-*.qmd         # every .qmd file starting with "la-"
ls chapter?.md      # chapter1.md, chapter7.md, but not chapter12.md
ls [abc]*.txt       # .txt files starting with a, b, or c
ls **/*.png         # every .png at any depth (zsh)

What Happens When Nothing Matches

This is a genuine bash vs. zsh difference, and it surprises people who switch:

  • bash: if a glob matches nothing, it is left unexpanded and passed through literally. ls *.xyz with no .xyz files actually runs ls *.xyz, and ls complains it cannot find a file literally named *.xyz.
  • zsh: if a glob matches nothing, it is an error and the command does not run at all: zsh: no matches found: *.xyz.

zsh’s behavior is safer (it refuses to run a command built from a broken assumption) but trips up scripts written for bash. When you need the literal pattern regardless of matches, quote it.

Pipes and Redirection

Here is decision #2 made concrete. Every program starts life with three open streams, and the shell lets you rewire them.

Rewiring the Three Streams

Recall the three standard streams every command is born with: stdin (0), stdout (1), and stderr (2). The pipe and redirection are the two tools for rewiring them, the first connecting a program to another program, the second connecting a program to a file.

The Pipe |

The pipe connects one program’s stdout to the next program’s stdin:

grep "matrix" *.qmd | wc -l        # how many matching lines, total
ls -l | grep "\.qmd$" | sort -k5 -n   # qmd files, sorted by size

Read a pipeline left to right as data flowing through a series of transforms. ls -l produces lines, grep keeps the ones ending in .qmd, sort orders them by the 5th column numerically. Each stage is a function; the pipe is the composition. This is the same shape as sort(grep(ls())), written in the order the data actually travels.

Redirection

Where the pipe connects programs to each other, redirection connects a program to a file:

command > file       # send stdout to file (overwrite)
command >> file      # send stdout to file (append)
command < file       # take stdin from file
command 2> file      # send stderr to file
command > out 2>&1   # stdout to out, then stderr to wherever stdout now goes
command 2>&1 | less  # merge stderr into stdout, then pipe both into less

The 2>&1 idiom reads as “make stream 2 (stderr) point to wherever stream 1 (stdout) currently points.” Order matters: > out 2>&1 redirects stdout to the file first, then aliases stderr onto it, so both land in out. Reverse the order and stderr would still be going to the terminal.

TipThe redirect-then-pipe trick

A pipe only carries stdout. If a program writes the interesting part to stderr (compilers love to do this), cmd | grep error will miss it. Merge first with cmd 2>&1 | grep error.

Heredocs: A File That Isn’t There

<< redirects stdin from text written inline.

The redirections above all connect a stream to a file. The heredoc connects stdin to text you write directly in the script, no file required:

cat <<EOF
Hello, world.
This is line two.
EOF

Three things are happening, and it helps to name them separately because none of them is obvious from the syntax.

  1. << is stdin redirection. It belongs to the same family as <. Where command < file says “read stdin from this file,” command <<EOF says “read stdin from the lines that follow, up to the line EOF.” Mechanically the shell collects the body, hands it to the kernel as an anonymous stream, and wires that stream to the command’s file descriptor 0. From the command’s point of view there is no difference between the two; it is reading stdin, and it neither knows nor cares that the bytes came from your script instead of the disk.
  2. EOF is not a keyword. It is a word you choose as the terminator, and the shell simply reads until it finds a line containing exactly that word. <<END, <<MARKER, and <<CHEESE all work identically. EOF is convention, borrowed from the acronym for end-of-file, and nothing more. The terminator must be alone on its line with no leading whitespace and no trailing spaces, which is the single most common way a heredoc breaks.
  3. cat has no argument here. This is the part that reads wrong at first glance. cat file.txt prints a file, so you expect cat <<EOF to be operating on something named to its right. It is not. cat was given no filename at all, so it falls back to the same behavior grep has: with no file to open, read stdin. The heredoc body is not an argument to cat; it arrives on stream 0. cat’s entire job is “copy stdin to stdout,” which makes it the natural vehicle for a heredoc.

Reading the Real-World Form

The idiom you will actually meet in the wild combines a heredoc with an output redirection:

cat > "$TMPHDR" <<EOF
#define APP_VERSION "$APP_VERSION"
#define BUILD_NUMBER "$BUILD_NUMBER"
EOF

There are two independent redirections on one command, which is why it looks dense. Untangled:

Piece Stream Effect
<<EOF stdin (0) the body below becomes cat’s input
> "$TMPHDR" stdout (1) cat’s output overwrites that file

So the data path is: body → cat’s stdin → cat copies it → cat’s stdout → the file. cat is a pure pass-through in the middle; the heredoc supplies the content and > decides where it lands. The order of the two redirections does not matter, since they touch different descriptors: cat > "$TMPHDR" <<EOF and cat <<EOF > "$TMPHDR" are the same command. And because > truncates, the file’s previous contents are replaced, which is exactly what a generated header wants.

NoteWhy cat and not echo?

For a single line, echo "text" > file is simpler and you should use it. Heredocs earn their keep the moment the content is multi-line, contains quotes, or is meant to be read as a block in the source. A heredoc lets the generated file appear in the script in its final shape, which is worth a lot when the thing you are generating is itself source code.

Quoted vs. Unquoted: Expansion

By default the body of a heredoc is treated like a double-quoted string: $variables, $(command substitution), and backticks are all expanded. That is the whole point in the example above, since $APP_VERSION has to become a real version number.

The consequence is that any $, backtick, or backslash you want to survive literally must be escaped:

cat > version.h <<EOF
// Generated by build/version.sh. Overridden by a bare \`cmake ../sources\`.
#define APP_VERSION "$APP_VERSION"
#define COST "\$5"
EOF

The backticks around cmake ../sources are escaped because unescaped backticks are command substitution; the shell would try to run cmake ../sources and paste its output into the file. \$5 reaches the file as $5, since bare $5 would expand to the script’s fifth argument (almost always empty).

Quoting the delimiter turns expansion off entirely:

cat > script.sh <<'EOF'
echo "Home is $HOME"        # written literally; $HOME is NOT expanded here
EOF

Quoting the delimiter (<<'EOF', <<"EOF", and <<\EOF are equivalent) makes the body behave like a single-quoted string: no expansion, no escaping needed. This is the right choice whenever you are generating a script, an awk program, or anything else full of dollar signs that belong to another language.

Form Expansion in body Use when
<<EOF $var, $(...), backticks live you want to inject shell values
<<'EOF' none, fully literal the body belongs to another language
<<-EOF as <<EOF, plus strips leading tabs the heredoc sits inside an indented block

The <<- variant deserves a note because indentation inside a function or if block is otherwise awkward. Normally the body and the terminator must start at column zero, which breaks the visual flow of an indented script. <<- strips leading tab characters (only tabs, not spaces, a genuine wart) from every body line and from the terminator, letting the block indent naturally.

The Herestring <<<

A close relative, worth knowing because it appears constantly in bash and zsh: <<< feeds a single string to stdin without the ceremony of a delimiter.

grep "foo" <<< "$text"                # search a variable's contents
read -r first second <<< "one two"    # split a string into variables
wc -c <<< "hello"                     # 6, the trailing newline counts

<<< "$text" replaces the older echo "$text" | grep foo, saving a process and a subshell. It is the same idea as a heredoc scaled down to one line: an anonymous stream built from text you already have, wired to stdin.

Warning<<< is not POSIX

The heredoc (<<) is POSIX and works in every shell. The herestring (<<<) is a ksh extension adopted by bash and zsh, and it is absent from POSIX. A minimal /bin/sh such as dash or BusyBox ash rejects it outright with Syntax error: redirection unexpected. In a script declaring #!/bin/sh, use printf '%s\n' "$text" | cmd instead. See shebangs and portability.

grep Reads stdin Too

Worth stating early because it changes how you use it: grep searches files when given filenames, but with no filename it reads stdin. That is what makes it a pipeline citizen.

grep "pattern" file.txt        # search a file
ps aux | grep "python"         # search another program's output
cat file.txt | grep "pattern"  # works, but the file form above is simpler

That last line is the famous “useless use of cat”: since grep "pattern" file.txt already reads the file directly, piping cat into it adds a process for nothing. It is harmless and occasionally convenient, but knowing that grep reads files natively is the cleaner habit.

Flow Control

Everything so far has been about a single command line. Flow control is how you assemble those lines into programs: run something only if a condition holds, run it repeatedly, or branch on a value. The shell has if, while, for, and case, and they look roughly like their C cousins, but one design decision makes them feel different at first.

Conditions Are Exit Codes, Not Booleans

Recall decision #5 from the intro: every program returns an integer when it finishes, 0 for success and non-zero for failure, and the shell treats 0 as true (the opposite of C). The shell has no boolean type, so this exit code is the condition. When you write if grep -q foo file, the shell does not evaluate an expression; it runs grep, and branches on whether grep succeeded.

if grep -q "matrix" la-eigenspace.qmd; then
    echo "found it"
fi

grep -q searches silently and exits 0 if it matched, 1 if it did not. There is no comparison operator here at all; the exit code is the condition. This is worth internalizing, because it means any command can be a condition. if ping -c1 host, if make, if curl -sf url are all valid and idiomatic.

The last command’s exit code is always available in $?, which is occasionally useful for inspecting or branching on a specific failure code:

grep -q "matrix" file.qmd
echo $?        # 0 if matched, 1 if not

The test Command, a.k.a. [ ]

So if if runs a command, how do you test a plain fact like “does this file exist?” The answer is a program named test, which evaluates a condition and exits 0 or 1 accordingly. It has an alias that makes the syntax look like other languages: [. Yes, the open bracket is literally a command (which is why it needs spaces around it, and why it needs a closing ] as its final argument).

# These two lines are identical:
if test -f config.toml; then echo "exists"; fi
if [ -f config.toml ]; then echo "exists"; fi

That equivalence is the thing to remember when the syntax feels fussy: [ -f config.toml ] is just calling the program [ with the arguments -f, config.toml, and ]. The spaces are mandatory because they are argument separators, not decoration. [-f config.toml] would be the shell looking for a command named [-f.

File Tests

These are the options you are always looking up. They each ask one yes/no question about a path:

Test True when
-e path path exists (any type)
-f path exists and is a regular file
-d path exists and is a directory
-r path exists and is readable
-w path exists and is writable
-x path exists and is executable
-s path exists and is non-empty (size > 0)
-L path exists and is a symbolic Link 
[ -f "$file" ]          # is it a regular file?
[ -d "$dir" ]           # is it a directory?
[ -e "$path" ]          # does it exist at all?
[ -s "$logfile" ]       # does it exist and have content?
[ ! -e "$path" ]        # ! negates: true when path does NOT exist

String and Number Tests

Strings and numbers use different operators, and mixing them up is a classic bug. Strings compare with = and !=; numbers compare with the lettered operators -eq, -lt, and friends.

Strings Numbers
-z str empty (zero length) n -eq m equal
-n str non-empty n -ne m not equal
s1 = s2 equal n -lt m less than
s1 != s2 not equal n -le m less or equal
n -gt m greater than
n -ge m greater or equal 
[ "$name" = "curtis" ]      # string equality uses =, not ==
[ -z "$input" ]             # true if $input is empty
[ "$count" -gt 10 ]         # numeric: greater than
WarningAlways quote variables inside [ ]

If $file is empty, [ -f $file ] expands to [ -f ], which test misreads, and [ "$a" = "$b" ] with an empty unquoted $a becomes [ = "$b" ], a syntax error. Quoting ([ -f "$file" ]) keeps each value a single argument no matter what it contains. This is the same word-splitting hazard from the quoting section, and [ ] is where it bites hardest.

Combining Tests

[[ ]]

zsh and bash also provide [[ ]], a shell keyword rather than a program. Because the shell parses it specially (it is not subject to word splitting), it is safer and supports &&, ||, and pattern matching directly:

[[ -f "$file" && -r "$file" ]]     # exists AND readable
[[ "$name" == cur* ]]              # == does glob-style pattern matching here
[[ "$n" -gt 0 && "$n" -lt 100 ]]   # combine numeric tests

Prefer [[ ]] for new code in bash/zsh: it does what you mean with fewer footguns. Reach for the older [ ] only when you need POSIX portability (e.g. scripts that must run under sh/dash).

Arithmetic: (( ))

Where numbers behave like numbers

There is a third bracket, and it exists because the two above are fundamentally text tools. [ ] and [[ ]] compare strings, and their numeric operators (-gt, -lt) are a lettered workaround bolted on for the cases where you need arithmetic.] (( )) inverts that: inside it, everything is a number and C’s operators mean what they mean in C.

n=5

if (( n > 0 )); then           # reads exactly like C
    echo "positive"
fi

(( count = 10 * 3 ))           # assignment, no $ and no spaces problem
(( count += 5 ))               # compound assignment
(( i++ ))                      # increment

Three things are immediately different from the bracket forms, and each is a reason Google kept suggesting it:

  1. The operators are C’s. >, <, >=, ==, !=, &&, ||, %, *, + all work directly. No -gt, no -a, no remembering which family a given test belongs to.
  2. No $ is needed on variable names. Inside (( )) a bare word is read as a parameter, so (( n > 0 )) works. $n also works and is harmless.
  3. No quoting hazard. Word splitting does not happen inside (( )), so the “always quote your variables” rule that dominates [ ] simply does not apply.

Why Prefer It Over [ ] for Numbers

The strongest argument is not convenience, it is a correctness bug that [[ ]] will hand you silently:

[[ 10 > 9 ]]  && echo true || echo false     # false  <- !!
(( 10 > 9 ))  && echo true || echo false     # true

Inside [[ ]], > is a string comparison, so it compares "10" and "9" lexicographically, and "1" sorts before "9". The test is not an error and produces no warning; it just quietly gives you the wrong answer. Every number that crosses a digit-count boundary is affected, which means the bug tends to appear only once your counter passes 9 or your version number reaches 10.

Inside [[ ]] you must write [[ 10 -gt 9 ]] to get numeric comparison. Inside (( )), > is arithmetic and there is nothing to get wrong. Hence the rule:

Testing Use
Numbers (( ))
Strings, files, patterns [[ ]]
POSIX portability required [ ]

The Exit Status Inversion

(( )) is a command like any other, so it produces an exit status, and here it does something that looks backwards until you see why:

(( 1 )); echo $?        # 0   (success)
(( 0 )); echo $?        # 1   (failure)

The rule is that (( expr )) succeeds when the expression evaluates to nonzero. This is C’s notion of truth (nonzero is true) being translated into the shell’s notion of success (zero is success), so the two conventions get bridged at exactly this boundary. It is why (( ${+aliases[run-help]} )) from the arrays section reads naturally: $+ yields 1 for “exists,” (( )) treats 1 as true, and the if sees success.

A useful consequence is that a bare variable is a truth test:

if (( count )); then           # true when count is nonzero
    echo "we have $count items"
fi
Warning(( i++ )) can kill a script under set -e

This one is genuinely nasty and worth knowing before it bites. Post-increment evaluates to the variable’s old value, so when i is 0, (( i++ )) evaluates to 0, which is a failed exit status. Under set -e, which exits on any failure, the script dies on a line that looks incapable of failing:

set -e
i=0
(( i++ ))         # evaluates to 0 -> exit status 1 -> script exits here
echo "never reached"

Three fixes, in rough order of preference:

(( ++i ))         # pre-increment: evaluates to the NEW value, 1, so it succeeds
(( i++ )) || true # explicitly discard the status
i=$(( i + 1 ))    # use the expansion form, which has no exit status at all

The same hazard applies to any arithmetic that legitimately evaluates to zero, such as (( total = a - b )) when the two are equal.

$(( )): the Expansion Form

You have already seen its sibling, back in the while loop: $(( )) with a leading $ is arithmetic expansion, which computes a value and substitutes it into the command line rather than producing an exit status.

n=$(( 3 + 4 * 2 ))         # 11   (normal precedence)
echo "$(( n / 2 ))"        # 5    (integer division)
echo "$(( n % 3 ))"        # 2    (modulo)

The distinction is worth stating plainly, since the two forms look nearly identical:

Form Purpose Yields
(( expr )) evaluate for a condition or side effect an exit status
$(( expr )) evaluate for a value the computed number, as text

So (( i++ )) is a statement, while i=$(( i + 1 )) is an assignment. Use the first in conditions, the second when you need the number itself.

The C-Style for Loop

This is the construct you remembered seeing, and now it should read plainly. The for (( )) form uses arithmetic evaluation for all three clauses, giving the shell a genuine counting loop:

for (( i = 0; i < 5; i++ )); do
    echo "$i"
done

Note it is for (( with the double parens, not for (. This is the exception to the “the shell’s for is a for-each” rule from the for section: when you genuinely need to count, this is the readable way. Reach for it sparingly, though, since iterating over a glob or a list is more idiomatic shell, and a loop counting to a fixed number is often a sign that a list would serve better.

NoteLimits: integers only (mostly)

Shell arithmetic is integer arithmetic. $(( 7 / 2 )) is 3, not 3.5, and the fractional part is discarded rather than rounded.

zsh is the partial exception: it supports floating point in (( )), so (( 3.5 > 2 )) works there. bash does not, and the same line is a syntax error. Since this is one of the wider zsh/bash gaps, portable scripts needing real numbers hand the job to a tool that has them:

echo "scale=2; 7 / 2" | bc      # 3.50   (bc: an arbitrary-precision calculator)
awk 'BEGIN { print 7 / 2 }'     # 3.5    (awk does floating point natively)

Since you have already met awk, it is usually the more convenient of the two, and it is already in your toolkit.

if / elif / else

With conditions understood, the branching itself is unremarkable:

if [ "$count" -eq 0 ]; then
    echo "nothing found"
elif [ "$count" -lt 10 ]; then
    echo "a few"
else
    echo "lots"
fi

The then can share a line with if if you separate them with a semicolon (if ...; then), which is the conventional style. fi closes the block (if spelled backwards, a 1970s flourish that also gives us esac for case).

while and until

while loops as long as a command keeps succeeding; until is its mirror, looping until a command succeeds:

# Count down
n=5
while [ "$n" -gt 0 ]; do
    echo "$n"
    n=$((n - 1))        # $(( )) is arithmetic expansion; see (( )) below
done

# Wait for a service to come up
until curl -sf http://localhost:8080/health; do
    sleep 1
done

The most idiomatic while in the shell reads a stream line by line. This is the canonical way to process input that may contain spaces, and it leans on every concept so far:

while IFS= read -r line; do
    echo "got: $line"
done < input.txt

read pulls one line into line and exits non-zero at end of file, ending the loop. IFS= prevents leading/trailing whitespace from being trimmed, and -r stops backslashes from being interpreted, so the line arrives exactly as written.

for

The shell’s for is a for-each over a list of words, not a C-style counter. This is a direct consequence of the thesis: the shell deals in lists of text, so iterating over a glob or a command’s output is the natural shape.

# Iterate over files (the glob expands to the list)
for file in *.qmd; do
    echo "processing $file"
done

# Iterate over the words of a command's output
for branch in $(git branch --format='%(refname:short)'); do
    echo "$branch"
done

# C-style counter, when you genuinely need numbers (bash/zsh)
for ((i = 0; i < 5; i++)); do        # see Arithmetic: (( ))
    echo "$i"
done

The first form is the one you will write most. for file in *.qmd reads as “for each file matching *.qmd,” and because the glob produces a proper list, filenames with spaces survive (unlike iterating over unquoted command output, which word-splits).

case

the Shell’s switch

case matches a value against a series of glob patterns (not regexes, and not C’s exact-value switch), running the first branch that matches. It is the cleanest way to dispatch on a string, and it shows up constantly in argument parsing.

case "$1" in
    start)
        echo "starting"
        ;;
    stop|halt)              # | separates alternative patterns
        echo "stopping"
        ;;
    *.txt)                  # patterns are globs, so this matches any .txt arg
        echo "a text file"
        ;;
    *)                      # the default case: * matches anything
        echo "unknown: $1"
        ;;
esac

The anatomy: each branch is pattern) commands ;;. The ;; terminates a branch (there is no fall-through by default, unlike C, so no break is needed). | offers alternative patterns, and * as the final pattern is the catch-all default, exactly like default: in a switch. Because the patterns are globs, case is genuinely more expressive than C’s switch: *.txt, [0-9]*, and cur* are all valid patterns.

TipWhy case for argument parsing

The case "$1" in start) ... stop) ... shape is the backbone of nearly every init script and CLI dispatcher you will read. When you see a script handling subcommands, it is almost always a case on $1. Recognizing the pattern makes a lot of “real world” shell instantly legible.

Searching

grep

grep is the shell’s text search function. The name is an artifact of its lineage: in the old ed line editor, the command g/re/p meant “globally search for a regular expression and print” the matching lines. That expansion also tells you exactly what grep is built around: it is line-oriented and regex-driven. It reads input one line at a time, tests each line against a pattern, and prints the lines that match. Almost every option is a variation on that one loop.

Once you see grep as “filter lines by regex,” the design coheres. It is not a general text tool; it is one tightly-focused function, which is exactly why it composes so well in pipelines.

grep [options] "pattern" file(s)
grep [options] "pattern" directory/*

Choosing Which Files to Search

There are two distinct ways to tell grep which files to look in, and they operate at different stages. Knowing which is which removes a lot of confusion.

1. Shell Glob

*.qmd

The shell expands the glob before grep runs (this is just globbing from the previous section). grep never sees *.qmd; it receives the actual filenames the shell substituted in.

grep "pattern" *.qmd        # current directory only
grep "pattern" *.txt *.md   # multiple types, current dir

Because the shell does the expansion, this only reaches files in the current directory. It cannot recurse, because the glob is resolved before grep ever starts.

2. grep’s Own --include

With recursive search (-r), grep walks the directory tree itself and decides which files to open. --include is a filter grep applies during that walk, so it works at any depth:

grep -r "pattern" . --include="*.qmd" | wc -l

The distinction in one line: the glob is the shell choosing files for grep; --include is grep choosing files for itself. Use the glob for a quick search of one directory; use -r --include to sweep a whole tree.

3. Via find

You can also let find locate the files and hand them to grep. Here grep is used as a filter rather than for its output: find asks grep -l “does this file contain the pattern?” and keeps the files for which the answer is yes.

find . -name "*.qmd" -exec grep -l "matrix" {} \;
Output
./la-determinants.qmd
./la-eigenspace.qmd
./la-vspaces.qmd
./pb-combinatorics.qmd
./la-theorems.qmd
./la-matrices.qmd
./la-transformations.qmd
...

The {} is a placeholder for each file find discovers, and \; ends the -exec command (escaped so the shell does not eat the semicolon). We will dig into find next.

Regular Expressions, Briefly

The “regular expression” in grep’s name is the pattern language it tests each line against. A full treatment is its own subject, but the operators you reach for daily are few:

Pattern Matches
. any single character
* zero or more of the previous item
^ start of line
$ end of line
[abc] one character from the set
\b a word boundary
word1\|word2 either alternative (with -E) 
grep -i "matrix" la-eigenspace.qmd | head -3      # case-insensitive
grep -E "\bmatrix\b" la-eigenspace.qmd | head -3  # whole word only
NoteBasic vs. Extended regex (-E)

grep has two regex dialects. In basic regex (the default), +, ?, |, and () are literal characters, and you must backslash-escape them to get their special meaning. Extended regex (grep -E, historically egrep) makes them special without escaping. When a pattern is fighting you with backslashes, reach for -E; it is almost always what you actually want.

The Cheat Sheet

The flags below are the ones worth memorizing. Notice how each is a small variation on the core “filter lines by regex” loop, changing either what gets matched or what gets printed.

# What to match
grep "text" file.txt        # lines containing "text"
grep -i "text" file.txt     # case-insensitive
grep -w "text" file.txt     # whole word only
grep -E "a|b" file.txt      # extended regex: a OR b
grep -v "text" file.txt     # invert: lines that DON'T match

# What to print
grep -n "text" file.txt     # prefix each match with its line number
grep -H "text" *.txt        # prefix each match with its filename
grep -l "text" *.txt        # just the names of files that match
grep -c "text" file.txt     # just the count of matching lines
grep -o "text" file.txt     # print only the matched part, not the whole line

# Where to look
grep -r "text" .            # recurse through subdirectories
grep -r "text" . --include="*.qmd"   # recurse, but only certain files

A useful mental split: the first group changes the predicate (which lines count as matches), the second changes the projection (what you see for each match), and the third changes the scope (which files are searched). Most real commands pick one from each group.

Finding

find

If grep filters lines by content, find filters files by metadata: name, type, size, modification time, permissions. It is the shell’s other great search function, and the two are complementary. grep answers “which lines say X?”; find answers “which files are X?”

find walks a directory tree and, for every entry it encounters, tests it against the conditions you give and runs an action on the ones that pass. Its syntax looks alien at first because it is really a tiny expression language, but the shape is always the same:

find <where> <tests> <action>
find . -name "*.qmd"                  # by name, anywhere below here
find . -type f -name "*.png"          # regular files only (not directories)
find . -type d -name "images"         # directories named "images"
find . -size +1M                      # larger than 1 megabyte
find . -mtime -7                      # modified in the last 7 days
find . -name "*.tmp" -delete          # find and delete, in one pass

The Two Ways to Run a Command on Each File

find’s superpower is handing every matching file to another program. There are two idioms, and the difference is performance.

# One grep process PER file. The {} is the current file; \; ends the command.
find . -name "*.qmd" -exec grep -l "matrix" {} \;

# One grep process for MANY files. The + batches them into few invocations.
find . -name "*.qmd" -exec grep -l "matrix" {} +

With \;, find runs the command once per file, which is simple but slow across thousands of files. With +, find collects many filenames and passes them to a single command invocation, the same way you would type grep -l "matrix" a.qmd b.qmd c.qmd by hand. Prefer + when the command accepts multiple files.

Warningfind vs. glob: who recurses?

A shell glob like *.qmd only sees the current directory (and **/*.qmd in zsh for recursion). find recurses by default and works identically in every shell. When you need to reach into subdirectories portably, find is the dependable choice.

Editing a Stream

sed

grep selects lines; sed transforms them. The name is short for stream editor, and that is exactly what it is: it reads input one line at a time, applies an editing command to each, and writes the result out. Same line-at-a-time loop as grep, but instead of deciding whether to print a line, sed decides how to rewrite it. It edits a stream, not a file in place (unless you ask), which is what makes it a natural pipeline citizen.

You will use sed for one thing far more than any other: search and replace. The substitute command, s/old/new/, is the 90% case.

sed 's/old/new/'           # replace FIRST match on each line
sed 's/old/new/g'          # replace ALL matches on each line (g = global)
sed 's/old/new/gI'         # global, case-Insensitive

The s/// syntax is s, a delimiter, the pattern, the same delimiter, the replacement, the delimiter again, then optional flags. The delimiter is usually /, but it can be any character, which is the trick for editing paths without a thicket of backslashes:

# Replacing a path: / as delimiter forces escaping every slash
sed 's/\/usr\/local/\/opt/g'
# Use | as the delimiter instead and it reads cleanly
sed 's|/usr/local|/opt|g'

sed in a Pipe vs. In Place

By default sed writes to stdout, so it drops straight into a pipeline and never touches your files:

grep -r "TODO" . | sed 's/TODO/DONE/'    # transform the search output
cat config.txt | sed 's/debug/release/g'

To edit files in place, use -i. This is where a real portability wrinkle bites, and it is worth calling out because it catches everyone on macOS:

sed -i 's/old/new/g' file.txt        # GNU/Linux: edits file.txt in place
sed -i '' 's/old/new/g' file.txt     # BSD/macOS: -i REQUIRES an argument
                                     #            ('' = no backup suffix)
sed -i.bak 's/old/new/g' file.txt    # both: edit in place, keep file.txt.bak
Warningsed -i is not the same on macOS and Linux

GNU sed (Linux) treats -i as a standalone flag. BSD sed (macOS) requires an argument right after -i: the backup suffix, or '' for none. A script written on Linux with bare -i will fail cryptically on a Mac, and vice versa. When in doubt, sed -i.bak works on both and leaves you a backup.

A Few Other sed Tricks

Substitution is the bulk of it, but three more commands round out the daily kit:

sed -n '5p'             file.txt   # print ONLY line 5 (-n silences default printing)
sed -n '10,20p'         file.txt   # print lines 10 through 20
sed '/^#/d'             file.txt   # delete comment lines (those starting with #)
sed '/^$/d'             file.txt   # delete blank lines

The pattern is consistent: an optional address (a line number, a range, or a /regex/) followed by a command (p print, d delete, s substitute). sed applies the command to every line the address matches. That is the whole mental model.

Columns and Computation

awk

Where sed edits lines as text, awk understands them as records made of fields. By default it splits each line on whitespace into $1, $2, $3, and so on, with $0 being the whole line. The instant your data has columns, awk is the right tool, and it is shockingly capable: it is a complete little programming language with variables, arithmetic, and conditionals, not just a one-trick filter.

The grain of awk is pattern { action }: for each line, if the pattern matches, run the action. Omit the pattern and the action runs on every line; omit the action and matching lines are printed (so awk '/foo/' is a slower grep foo).

# Print the first column of each line (e.g. the PID from `ps`)
ps aux | awk '{print $1}'

# Print columns 1 and 5, in a different order
ls -l | awk '{print $5, $1}'

# Only rows where column 5 (file size) exceeds 1000
ls -l | awk '$5 > 1000 {print $9}'

That third example is the one that shows why awk earns its keep: $5 > 1000 is a real numeric comparison used as the pattern, and {print $9} is the action. You are filtering and projecting columns in a single expression, which would take a clumsier grep/cut combination otherwise.

Field Separators and Built-in Variables

The default split is on whitespace, but -F sets any delimiter, which is how awk reads /etc/passwd, CSVs, and other delimited data:

awk -F: '{print $1}' /etc/passwd     # usernames: split on : and take field 1
awk -F, '{print $2}' data.csv        # second column of a CSV

A handful of built-in variables make awk feel like a language rather than a filter:

Variable Holds
$0 the entire current line
$1, $2, … individual fields
NF Number of Fields on this line
NR Number of the Record (the line number so far)
FS the input Field Separator (what -F sets) 
awk '{print NF}'        file.txt   # how many fields on each line
awk 'NR==1 {print}'     file.txt   # print just the first line (a header)
awk '{print NR, $0}'    file.txt   # number every line, like `grep -n`
awk '{print $NF}'       file.txt   # $NF is the LAST field, however many there are

$NF deserves a moment: NF is a number, so $NF is “the field whose index is NF,” i.e. the last field. It is the idiomatic way to grab the last column when you do not know how many there are.

awk Can Accumulate

Because awk has variables that persist across lines, it can compute running totals, and the BEGIN/END blocks let you run setup and teardown. This is the feature that lifts it above the line-at-a-time tools:

# Sum the file sizes reported by `ls -l`
ls -l | awk '{total += $5} END {print total}'

# Average of the numbers in column 3
awk '{sum += $3; count++} END {print sum / count}' data.txt

total += $5 runs on every line, quietly accumulating; the END { } block runs once, after the last line, and prints the result. (BEGIN { }, its mirror, runs once before the first line, handy for printing a header or setting FS.) At this point awk has stopped being a filter and become a tiny report generator, which is exactly when to reach for it instead of stitching together five smaller tools.

Tipgrep, sed, awk: which one?

The three text tools divide cleanly along what they do to a line. grep decides whether to keep a line (select). sed rewrites a line (transform). awk treats a line as columns and can compute across them (analyze). When a task feels awkward in one, it is often because it belongs to another: filtering by a numeric column is awk, not grep; bulk find-and-replace is sed, not awk.

Composition Idioms

This is where the thesis pays off. None of the tools above is impressive alone. Their power is that they compose, and a handful of pipelines show up constantly once you start thinking in functions and streams. Read each one left to right as data flowing through transforms.

Count matches across a project

grep -r "TODO" . --include="*.qmd" | wc -l

grep emits one line per match; wc -l counts lines. Composition turns “search” into “count” with no new tool.

Find the most common values

grep -rho "la-[a-z]*\.qmd" . | sort | uniq -c | sort -rn | head

A classic four-stage idiom. grep -o extracts just the matched filenames, sort groups identical lines together, uniq -c collapses runs into counts, and the final sort -rn orders by count descending. This “sort | uniq -c | sort -rn” sequence is the shell’s GROUP BY ... ORDER BY COUNT.

Search inside a program’s output, not a file

ps aux | grep "[p]ython"

grep filtering ps is the canonical “is this running?” check. The [p] trick is a small joke that works: the regex [p]ython matches the text python, but the grep process’s own command line contains [p]ython, so grep does not match itself.

Edit a set of files chosen by content

grep -rl "old_name" . --include="*.qmd" | xargs sed -i '' 's/old_name/new_name/g'

grep -rl lists the files that contain the old name, and xargs feeds that list as arguments to sed, which does the replacement. xargs is the bridge that turns a stream of filenames (stdout) back into command arguments, the inverse of how a pipe normally works.

TipThe shape to internalize

Almost every shell task decomposes the same way: produce a stream (ls, find, grep, a program’s output), transform it through filters (grep, sort, uniq, cut, sed), and consume the result (wc, less, a redirect to a file, or xargs into another command). When a task feels hard, you are usually missing one of those three stages, not a fancier tool.

Gnarly Breakdowns

find in a Loop

The bulletproof way to iterate over files found by find, including files whose names contain spaces, tabs, newlines, or anything else.

find '<path>' -name "<filter>" -print0 | while IFS= read -r -d '' f
do
    # f is a row in the results of the `find` expression
    echo "$f"
done

This one earns its place in “Gnarly Breakdowns” because every piece of it exists to defend against a single enemy: filenames can contain almost any character. On a Unix filesystem the only two bytes forbidden in a filename are / (the path separator) and the null byte \0. Everything else is fair game: spaces, tabs, newlines, quotes, glob characters. A robust loop over filenames has to treat the filename as opaque bytes, and that constraint is what shapes every flag below.

The naive version, and why it breaks

The obvious thing to write is:

for f in $(find '<path>' -name "<filter>")   # don't do this
do
    echo "$f"
done

It reads beautifully and it is wrong. The problem is what $(...) does with the text find produces. Command substitution drops the output into the command line as unquoted text, and the shell then performs word splitting and glob expansion on it before for ever sees it.

Word splitting chops that text apart on every character in IFS, which by default is space, tab, and newline. So consider a single file named my report.txt. find prints it as the eight-character string my report.txt, but the shell splits it on the space into two words, and the loop runs twice: once with my and once with report.txt. Neither names a real file.

WarningTwo failures, not one

The $(find ...) approach has a second, sneakier bug. After word splitting, the shell runs filename expansion (globbing) on each word. If find turns up a file literally named *.c, that word gets expanded against the current directory and silently becomes the list of .c files there. Word splitting mangles names with whitespace; globbing mangles names containing *, ?, or [. The for ... in $(...) form is exposed to both.

You can partially rescue the naive loop by setting IFS=$'\n' so it splits only on newlines instead of spaces. That fixes filenames with spaces, but it still falls apart on the legal-but-evil filename that contains a newline, and it does nothing about globbing. There is no value of IFS that makes for f in $(...) fully safe, because newline is itself a legal filename character. We need a separator that is not a legal filename character. There is exactly one: the null byte.

Enter -print0

-print0 is a find action, the sibling of the default -print. Where -print writes each result followed by a newline, -print0 writes each result followed by a null byte (\0, an actual zero byte).

That single choice solves the unsolvable. Newline can appear inside a filename, so it cannot reliably mark the end of one. The null byte cannot appear inside a filename (it is one of the two forbidden bytes), so it is the one perfectly unambiguous delimiter. find ... -print0 produces a stream like:

./a.txt\0./my report.txt\0./weird\nname.txt\0

where each \0 is a real zero byte. The list is now parseable with zero ambiguity, no matter what the names contain. The convention is widespread: xargs -0, grep -z, sort -z, and cut -z all speak this same null-delimited dialect, which is why find -print0 | xargs -0 ... is such a common pairing.

Reading the stream back

while ... read

Now we need a consumer that respects null delimiters, and that rules out for. We pipe the stream into a while read loop instead. You have already seen read as the canonical line reader; here it is the same tool with two extra flags. Let’s take the loop header apart left to right:

while IFS= read -r -d '' f
Piece What it does Why it’s here
IFS= Empties the field separator for this command only Stops read from trimming leading/trailing whitespace, so spaced .txt survives intact
read Reads one record from stdin into a variable The loop body runs once per record; read returns non-zero at end of stream, ending the loop
-r “Raw” mode: do not treat backslash as an escape A literal \ in a filename stays a \, not an escape sequence
-d '' Set the record delimiter to the null byte This is the keystone: it tells read to stop at \0 instead of at newline, matching -print0
f The variable each record lands in Inside the loop, "$f" is one complete, untouched filename

The -d '' flag is the half that pairs with -print0. read normally splits its input on newlines; -d overrides that delimiter. Bash strings can’t hold an actual null byte, so -d '' (an empty string) is the idiom the shell interprets as “delimit on \0.” Producer emits null-terminated records, consumer splits on null-terminated records: the two halves are matched, and a newline buried inside a filename now sails through as ordinary data.

The IFS= and -r here do exactly the job described earlier for plain line reading; read is doing the same work, just with a different delimiter. The only genuinely new ingredient compared to the everyday while IFS= read -r line loop is -d ''.

NoteQuote $f in the body

The breakdown’s example uses echo $f, but in real scripts write echo "$f" (and rm "$f", mv "$f" ..., and so on). An unquoted $f re-introduces the very word splitting and globbing this whole construction exists to avoid: the careful null-delimited reading is undone the moment you expand the variable bare. The quotes are the last link in the chain.

A subtlety

the pipe creates a subshell

One trap worth naming. Because the loop is on the right side of a |, it runs in a subshell. Any variable you set inside the loop (a counter, an accumulator) is lost when the loop ends, since the subshell’s environment doesn’t propagate back to the parent. If you need to keep state, use process substitution instead of a pipe, which keeps the loop in the current shell:

count=0
while IFS= read -r -d '' f
do
    count=$((count + 1))
done < <(find '<path>' -name "<filter>" -print0)
echo "$count files"   # the count survives

Note the redirect < <(...): the loop reads from a file descriptor fed by find, rather than being piped into. Same null-delimited contract, no subshell.

TipThe shape to internalize

find ... -print0 | while IFS= read -r -d '' f; do ...; done. Producer null-terminates with -print0; consumer splits on null with -d ''. It is verbose, but it is the only loop that is correct for every legal filename. When you need state to survive, swap the pipe for done < <(find ... -print0).

Writing Safe Shell

Shell rarely crashes; it obeys. That is precisely what makes it dangerous, and why a handful of defensive habits matter more than cleverness.

The breakdown above is a special case of a general truth: the shell’s failure modes are quiet. A C bug segfaults, a Rust bug refuses to compile, but a shell bug runs perfectly on your test directory and then silently does the wrong thing weeks later on an input you didn’t anticipate. The language won’t warn you; it just follows a word-splitting or globbing rule you forgot was in play. That is unnerving, and the right response is not to avoid shell but to aim your caution at the few places the sharp edges actually live. They are surprisingly few.

Quote every expansion

The single highest-leverage habit. An unquoted $var is subjected to word splitting and globbing; a quoted "$var" is passed through verbatim. This is the same mechanism that broke for f in $(find ...), and it bites everywhere variables appear.

rm $file        # splits on spaces, expands globs: a loaded gun
rm "$file"      # one argument, exactly as stored: safe

cp "$src" "$dst"            # quote both sides, always
echo "${args[@]}"          # quote array expansions too: "${arr[@]}"

If you do one thing differently after this notebook, make it this.

The shebang, and the promise it makes

The first line chooses your language.

A script is just a text file; something has to decide which interpreter runs it. That decision is made by the first two bytes. If a file begins with #!, the kernel reads the rest of that line as the path to an interpreter and executes it, handing your script’s path as an argument. ./build.sh with #!/bin/sh on top becomes /bin/sh ./build.sh. The name is a contraction of hash (#) and bang (!).

Two properties fall out of this that explain most shebang confusion:

  • The kernel needs an absolute path. It does not search $PATH. #!bash will not work; the line must name a real file such as /bin/bash.
  • It only applies when the script is executed directly. ./script.sh honors the shebang. bash script.sh ignores it completely, because you already named the interpreter. This is why a script with a wrong shebang can appear to work: everyone has been invoking it via bash script.sh.

The shebang is a promise about which dialect the file is written in. The two you will actually write:

Shebang Means Use when
#!/usr/bin/env bash “this file is bash; give me bash” scripts for machines you control (the common case)
#!/bin/sh “this file is portable POSIX shell” installers, CI, containers, anything widely deployed

#!/usr/bin/env bash is preferred over #!/bin/bash because it searches $PATH rather than hard-coding a location. On macOS, /bin/bash is bash 3.2 from 2007 (Apple froze it over a GPLv3 licensing objection), while a Homebrew bash 5 lives in /opt/homebrew/bin. env finds the modern one; the hard-coded path is stuck with the antique.

Warning#!/bin/sh is a promise, and nothing enforces it

#!/bin/sh declares POSIX, but which shell you actually get depends on the system, and none of them will hold you to the promise:

  • Debian and Ubuntu: /bin/sh is dash, a minimal POSIX shell. Bashisms fail here.
  • Alpine and most containers: BusyBox ash. Also minimal.
  • macOS: /bin/sh is bash 3.2 running in POSIX mode, and POSIX mode does not disable bash syntax. [[ ]], arrays, and <<< all still work.

The macOS case is the trap. Write #!/bin/sh, use [[ ]], and it runs perfectly on your laptop, then dies the moment it reaches a Debian CI runner or an Alpine image. Declaring sh gets you no local warning whatsoever. If you write #!/bin/sh, you must check the script with a tool (below); if you would rather not, declare bash honestly and use it freely.

Which to choose is a question about reach, not virtue. Personal scripts, repo tooling, and build helpers on known machines should say bash and use arrays, [[ ]], and <<< without guilt; POSIX costs real ergonomics and buys nothing if bash is always present. Reach for #!/bin/sh when the script must run somewhere you do not control: install scripts, container entrypoints, CI bootstrapping. The one genuinely bad option is claiming sh and writing bash anyway.

Checking POSIX compliance

Since no shell enforces the #!/bin/sh promise, two external tools do. They catch different things, so they complement rather than replace each other.

Run it under a strict shell. dash implements little beyond POSIX, so it rejects bashisms that bash-as-sh would wave through. This is a technique, not a feature: dash has no --posix or check flag, it simply fails on what it does not support.

dash ./script.sh        # bashisms surface as errors

Its limitation is that it is a runtime check. An unsupported command only fails if execution reaches it, so a [[ ]] inside an untaken branch goes unnoticed. Unsupported syntax like arr=(a b c) fails at parse time and is caught regardless.

Lint it statically. shellcheck -s sh reads the whole file without running it, so branch coverage is irrelevant, and it names each bashism with a rationale.

shellcheck -s sh ./script.sh    # -s sh forces POSIX rules regardless of shebang

Use ShellCheck as the primary check and dash as a confirming smoke test. Together they answer the question a container was the only obvious way to answer.

NoteWhat POSIX actually costs you

The features you give up under #!/bin/sh are the ones you reach for most: arrays, [[ ]] (use [ ]), <<< (use printf ... |), ${var,,} case conversion, $'...' escapes, and C-style for ((i=0;...)). Heredocs, $(...), parameter expansion, and functions are all POSIX and stay available. local is technically not POSIX but is implemented by every shell in practice, dash included, so it is a safe exception.

Fail loudly

set -euo pipefail

Put this at the top of every script. It converts the shell’s silent shrug into an immediate, visible stop, which is exactly the safety net your instinct is asking for.

#!/usr/bin/env bash
set -euo pipefail
Flag Effect Without it
set -e Exit the moment any command fails The script charges past a failed step and runs the next one on bad state
set -u Treat use of an unset variable as an error A typo’d $flie quietly expands to the empty string
set -o pipefail A pipeline fails if any stage fails, not just the last grep x file \| sort reports success even when grep couldn’t open the file
Noteset -e is a blunt instrument

It is a real improvement, but it has well-known blind spots: it ignores failures inside most conditionals and command substitutions, and a command whose non-zero exit you expect (like grep finding no match) will halt the script unless you handle it, e.g. grep x file || true. Treat set -e as a strong default, not a guarantee, and still check the exit codes that matter.

Note also that -e and -u are POSIX but pipefail is not. In a #!/bin/sh script write set -eu and check pipeline stages yourself.

Know the anti-patterns by name

Most shell disasters are a small, recognizable set. Learn to flinch at these:

  • Unquoted $(...) in a for loop. The construction this whole section grew out of. Reach for find -print0 | while read -d '' instead.
  • Parsing ls. ls is for humans; its output is ambiguous and locale-dependent. Use a glob (for f in *.txt) or find for machine consumption.
  • Building command lines by string concatenation. cmd="rm $args"; $cmd re-runs splitting and globbing on the whole string. Use an array instead: cmd=(rm -- "$file"); "${cmd[@]}".
  • Forgetting --. A filename beginning with - is read as an option. rm -- "$file" tells the command “no more flags follow,” so -rf.txt is treated as a name, not a switch.

Let a linter retrain your instinct

shellcheck is the static analyzer the shell never shipped with. It catches the quoting, splitting, and set -e mistakes above automatically, and it explains why each one is a bug with a linked rationale. Run it on every script:

shellcheck myscript.sh

It is the fastest way to convert vague unease into concrete, named knowledge. After a few weeks of heeding it, the rules stop being a checklist and become reflex.

Verifying what you download

What a checksum actually proves, and what it does not.

Shell scripts install things, and installing means fetching a binary and running it. The ritual advice is “check the SHA-256.” Worth understanding what that defends against, because the usual explanation (catching corruption in transit) is the least of it: HTTPS already integrity-checks the wire, and a flipped bit fails the TLS record MAC long before any checksum sees it.

The real threat is that the file was already wrong before you downloaded it. TLS protects the channel, not the contents. It guarantees you received exactly the bytes the server sent; it says nothing about whether those bytes are the ones the author built. What can go wrong upstream:

  • Compromised distribution infrastructure. Someone reaches the release host, a CDN, or a package mirror and swaps the artifact. TLS delivers the tampered file with a perfectly valid padlock. This is not hypothetical: the Linux Mint ISO replacement (2016), the PHP git server compromise (2021), and the xz/liblzma backdoor (2024) were all of this shape.
  • A stolen maintainer account. A leaked release token uploads a malicious build to the legitimate release page. Nothing about the transport looks wrong, because nothing about it is wrong.
  • Mirrors and redistribution. Fetching from anywhere but the origin adds a party to trust. A checksum from the origin is what lets you use an untrusted mirror safely.

This leads to the distinction that makes the whole practice make sense. A checksum does two different jobs, and only one of them is about security:

Job Defends against Requires
Integrity truncated or corrupt download, bad mirror a hash from anywhere
Authenticity tampered artifact, compromised host a hash or signature from an independent path
WarningA checksum from the same page proves less than it looks

If you fetch the tarball and its advertised SHA-256 from the same server over the same connection, an attacker who can change one can change the other. Verifying that hash confirms your download completed intact. It does not establish that the artifact is genuine. The check is only as independent as the channel the hash arrived on.

Signatures are categorically stronger for exactly this reason. A GPG signature or Sigstore attestation is verified against a key you obtained previously and separately, so the trust anchor is not the download server. Compromising the host no longer suffices; the attacker needs the private key as well. That is a genuinely independent path, which a same-page checksum is not.

# Integrity: did the bytes arrive whole? (hash from the release page)
shasum -a 256 tool.tar.xz          # macOS; sha256sum on Linux

# Authenticity: was this signed by the key I already trust?
gpg --verify tool.tar.xz.asc tool.tar.xz

In practice the strongest check available is usually agreement across independent sources: if a distro package, the upstream release, and a checksum you obtained by another route all match, an attacker would have had to compromise several unrelated systems at once. That is a far higher bar than any single hash.

NoteWhat a package manager is actually buying you

The security value of apt, brew, or nix is not convenience, it is that they maintain that independent trust path on your behalf. Homebrew keeps artifact hashes in a git-versioned formula repository separate from upstream’s release host, so a silent upstream swap shows up as a mismatch. Installing by hand with curl | tar is a perfectly reasonable choice, but it is precisely that second path you are giving up, and doing the verification yourself is how you get it back.

TipThe safe-shell starting block

Every script: #!/usr/bin/env bash then set -euo pipefail. Every variable: "$quoted". Every script before you trust it: shellcheck. That trio neutralizes the large majority of shell bugs, which frees you to be relaxed about the 90% of shell that is genuinely safe, and sharp only where it counts.
